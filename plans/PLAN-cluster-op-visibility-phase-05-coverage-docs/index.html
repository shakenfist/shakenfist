    Cluster op visibility phase 5: CI helpers, coverage and documentation¶

    This is a detailed phase plan under PLAN-cluster-op-visibility.md. Phase 4 put has_pending_operations on the instance, network and artifact views behind the object-pending-operations capability, and client-python#436 added await_no_pending_operations() and the per-object listing accessors. This phase moves the functional suite's await helpers onto that field, adds the one end-to-end check the earlier phases could not write as unit tests, and puts right what the documentation says about how long a finished operation is visible.

    Planning effort: medium (per the master plan). Review effort: medium. The code is test-only. The documentation step touches about twenty sites, and the risk there is saying one fact two ways, not saying it wrongly once.

    Scope¶

    In scope:

    • _await_object_operations_complete() in shakenfist/deploy/shakenfist_ci/base.py, rebuilt on the client's await_no_pending_operations(), with unit tests.
    • TestOutstandingOperationsBodyAll moved onto the client's new wrappers for the body-path reads.
    • One new merge-queue functional test, proving on a real cluster that the per-instance sweep's operations are stored as observational and never become last_cluster_operation.
    • Every statement of how long a finished cluster operation stays visible, in docs/, swagger and code comments, made consistent with the one-minute deleted-object sweep. This absorbs #4603.
    • A docs/developer_guide/ci.md section on waiting for an object's operations in the functional suite.
    • A walk of the master plan's success criteria, recorded in this file, so the push audit (phase 6) starts from a known position.

    Out of scope, deliberately:

    • A fallback for servers that do not advertise object-pending-operations (decision 3).
    • Anything that changes server behaviour. If a step finds a server bug, it files an issue and says so; it does not fix it here.
    • The deleted-object sweep's cadence or backlog. That is PLAN-deleted-object-sweep.md's work. This phase only describes it correctly.
    • The master plan's other Future work items (interfaces carrying a pointer, the four remaining runs_after sites, a fail-closed delete walk, the agent preflight not targeting its instance).

    What the survey found¶

    The survey ran on 2026-10-25 against develop at 9efbff1481. Phase 4 is complete. #4606 and its follow-up #4617 are on develop, and client-python#436 merged on 2026-10-23. Most of the master plan's phase 5 premises hold. Two findings change the phase: the deleted-object sweep now runs every minute, so phase 4's lifetime numbers were already stale when they merged, and the boolean field cannot carry the error check the helpers rely on today.

    1. The client side is ready. client-python develop (fdcfe6e) has get_instance_clusteroperations(), get_network_clusteroperations() and get_artifact_clusteroperations() (shakenfist_client/apiclient.py:887-945) and await_no_pending_operations(object_type, object_ref, namespace=None, timeout=None, interval=1) (apiclient.py:1897). The helper raises IncapableException when the capability is missing or a view lacks the field, TimeoutException on timeout, and ResourceNotFoundException if the object disappears while it waits. CI installs the client from a checkout of client-python at the matching revision, not from PyPI (shakenfist/actions .github/workflows/smoke-cluster.yml:7-32 and :414-430), so the suite can call these methods now.
    2. The helper today. _await_object_operations_complete() (base.py:1382-1425) polls list_cluster_operations_for_target() every 10 seconds for an instance and every 5 for a network, for up to 5 minutes. It fails the test on an op in error only if it saw that op outstanding earlier in the same wait. It reads neither op's observational flag, so a billing sweep that errors (#4585's family; #4608 stopped it erroring the instance, not the op) fails whatever test happened to be waiting. It has eight callers in five files: instance_hotplug.py:72, :109 and :218 (a mixin the smoke suites run on every PR), smoke_ci_tests/test_networking.py:491, cluster_ci_tests/test_coalescing.py:561, cluster_ci_tests/test_api.py:37, and the two thin wrappers in base.py. Its comment cites the master plan file, which the plan-history-in-source audit (#4630) discourages.
    3. The field cannot carry the error check. has_pending_operations is a boolean, and an op in error is not pending. A helper that only polled the field would return happily after the hot-plug it waited for had failed, and the test would fail later, on an assertion that says nothing about the op. The error check has to come from a listing (decision 2).
    4. Nothing runs this suite against an older server. The smoke workflow checks out shakenfist and client-python and deploys both (finding 1). functional-tests.yml and scheduled-tests.yml run the PR head or develop, and no job runs the suite against a released server. The master plan's "keep the by-target fallback for older servers" therefore describes a branch no CI job would ever take (decision 3).
    5. The deleted-object sweep runs every minute now. #4595 (deleted-object-sweep phase 2, merged 2026-10-22) moved per_deleted_object_checks() from every fifteen minutes to every minute (shakenfist/daemons/cluster/main.py:1080), within a DELETED_OBJECT_SWEEP_SECONDS budget (shakenfist/config.py:777, default 20). Operations become eligible thirty seconds after a final state (daemons/cluster/scheduled_tasks.py:913-916). Errored ops are still never hard deleted (#3922), so their target rows wait for the seven-day CLUSTER_OPERATION_TARGET_RETENTION prune. Three consequences:
    6. Phase 4 merged a day after #4595 and said "about fifteen minutes" in five places, all wrong on arrival: docs/developer_guide/api_reference/clusteroperations.md:41, the all parameter's swagger text at external_api/instance.py:2546, external_api/network.py:1073 and external_api/artifact.py:1065, and docs/release_notes/v07-v08.md:1454. The master plan repeated it three times.
    7. The sixteen "thirty seconds" lines that #4603 and this survey found (listed in step 5d) are now close on timing, but most say an op is removed thirty seconds after it finishes, when thirty seconds is when it becomes eligible. #4603's own proposed wording ("up to fifteen minutes") is now wrong as well.
    8. Running every minute is not the same as reaching an op within a minute. Once a pass has walked a type's final-state objects to the end, the sweep does not walk that type again for DELETED_OBJECT_WALK_RECHECK, five minutes (scheduled_tasks.py:76 and :1081-1084). So even on an idle cluster a finished op is removed between thirty seconds and about six minutes after it finishes. (Corrected during step 5c review: this bullet first said "within a minute or two".) On a cluster whose sweep has a backlog, sfcbr today (PLAN-deleted-object-sweep.md phase 4), removal waits longer, until the sweep reaches the op.
    9. The sweep coincidence cannot be provoked. The master plan asks for a test that hot-plugs while a billing sweep fires. per_instance_checks_and_usage() runs every five minutes (main.py:1068) and enqueues one node_inst_op per created instance, with collect_billing_statistics and health_check_kvm_process at user_facing priority (scheduled_tasks.py:552-602). No API enqueues those tasks, so a test cannot make one land inside a given await. The only on-demand observational enqueue is the blob checksum GET (external_api/blob.py:345), whose op targets a blob, and a blob carries neither the pointer nor the field.
    10. TestOutstandingOperationsBodyAll (cluster_ci_tests/test_api.py:17-70) makes three raw _request_url calls: two with all in the body, one with ?all=true. The client's get_network_clusteroperations() sends all in a JSON body (apiclient.py:920-925), which is exactly the path #3629 broke. So the wrapper is the body path, and the call that has to stay raw is the query-string one, because the client never sends that. The master plan's "it must keep one raw call, because the raw body path is what it tests" had that backwards, and is corrected at source. With the one-minute sweep, the completed ops the test looks for are visible for between thirty seconds and about six minutes (finding 5), not up to fifteen minutes. The test reads straight after _await_network_operations_complete(), so that is enough, and no open issue reports it flaking.
    11. Cluster CI tests only run in the merge queue (docs/developer_guide/coding_rules.md, "Cluster CI tests only run in the merge queue"). test_api.py and any new test under cluster_ci_tests/ get no CI signal on the PR.     Decisions¶

    1. The helpers wait through the client's await_no_pending_operations(). They do not poll the field by hand. The point of the phase is that the functional suite should depend on the same contract a user would, and the client helper is that contract. Every hot-plug test on every PR then exercises the capability, the field, the view and the client helper end to end. The helper is passed timeout=300, keeping today's five minutes, and interval=poll_interval, keeping today's 10 and 5 seconds. A client TimeoutException becomes today's self.fail() message. I have not claimed the switch is cheaper. A full view GET and a by-target listing that hydrates a handful of ops cost about the same, and cost is not the reason for it.

    2. The error check moves to two listings around the wait. Before waiting, the helper reads list_cluster_operations_for_target() once and records the UUIDs of ops already in error. After the wait it reads the listing again and fails the test, with today's message, on any op that is in error, is not observational, and was not in the first set. Observational ops are ignored, which is the master plan's phase 3 addition: a billing sweep that errors is recorded on the op and is not the test's business. This is stricter than today in one case and the same in the others. Today's check misses an op that goes from queued to error between two polls, because it never saw the op outstanding. The bracketing check catches it. An op that errors before the first listing is ignored, as it is today, because a helper that starts after the mutation returned cannot tell that op from history.

    3. No fallback for older servers. This is the decision a reviewer is most likely to dispute, because the master plan asks for the fallback. Finding 4 is the reason: no CI job runs this suite against a server older than itself, so a fallback branch would never run, and an untested wait loop is the kind of code this plan exists to remove. If the capability is missing, the helper fails the test, saying the suite expects a server at its own revision that advertises object-pending-operations. A suite run against the wrong server then fails at once and says why. A fallback would quietly measure something else instead. If an upgrade job that runs this suite against a released server is ever added, it can add the fallback, with a job to test it.

    4. The end-to-end test checks the classification, not the coincidence. The master plan's test needs a sweep to land inside one particular await, which a test cannot arrange (finding 6), so as written it would pass whether or not the fix worked. What the functional suite can prove, and the unit tests cannot, is that a real sweep op on a real cluster reaches the targets table as observational and is never named by last_cluster_operation. The new test creates an instance and waits for the sweep to reach it, bounded at eight minutes: the five-minute cadence, one fill and one processing pass, and margin. It then asserts that the sweep op is listed with observational: true, that the pointer never names it, and that has_pending_operations is false once nothing mutating is outstanding. The race itself is covered by the unit tests of phases 2 to 4, and by the hot-plug tests, which now wait on the field (decision 1). The test goes under cluster_ci_tests/, so the PR does not pay for the wait and the merge queue does, in parallel with the rest of that suite. A blob checksum variant was considered and declined: a blob carries neither pointer nor field, so it could only check the stored flag, and phase 3's classification test already pins that.

    5. TestOutstandingOperationsBodyAll reads the body path through the client. Its two body-path reads become get_network_clusteroperations(uuid, all=True) and get_network_clusteroperations(uuid). The query-string read stays a raw _request_url, because the client never sends a query string (finding 7). The docstring says why. The test also asserts that every listed op carries an observational key, which phase 4 made part of the response and which nothing in the functional suite checks yet.

    6. #4603 is absorbed and re-scoped for the one-minute sweep. The fact is stated in full in one place. docs/operator_guide/database.md already describes the deleted-object sweep (around line 968, inside "High-Churn Dedicated Tables"). That paragraph gets its own heading and becomes the canonical statement. A finished operation becomes eligible for hard delete thirty seconds after it reaches a final state, and the deleted-object sweep, which runs every minute, removes it and its target rows. Once the sweep has walked operations to the end it waits five minutes before walking them again, so removal normally comes within about six minutes of finishing, and later while the sweep is working through a backlog. Errored operations are never hard deleted, so their target rows stay until the CLUSTER_OPERATION_TARGET_RETENTION prune, seven days by default. Every other page gives the short form, "eligible thirty seconds after finishing and removed by the deleted-object sweep", and links to the canonical paragraph. Code comments and swagger text state eligibility only, and never the cadence, because the cadence belongs to another subsystem and has changed once already. Code comments are not allowed to drift with it. The PR says Fixes #4603.

    7. The functional-suite convention goes in ci.md; the top-level docs do not change. A new section in docs/developer_guide/ci.md, "Waiting for an object's cluster operations", says that tests wait with _await_instance_operations_complete() or _await_network_operations_complete(), never by polling last_cluster_operation. It says what the helpers wait for, that observational ops never hold or fail a wait, and what fails a test. It sits before "Creating instances in the functional suite", not after it, to stay clear of the section the 4407 worktree is adding there (finding 10). ARCHITECTURE.md, AGENTS.md and README.md are left alone, because none of them describes the affected storage or API (finding 10), so the master plan's success criterion about them is met without an edit. No convention for agents changes. No comment goes on #3278: the ci.md section is where a test author will look, and the tracking issue would only restate it.

    8. Phase 5 closes the plan's implementation. It records a walk of every master plan success criterion in this file's Execution notes, with the command or link that shows each is met. Phase 6, the push audit, then starts from evidence rather than from the table.

    Risks and mitigations¶

    • The rebuilt helper returns too early. If has_pending_operations were wrong, every hot-plug test would race again. Mitigation: phase 4's sqlite tests pin the field against the listing, and the smoke suites' three hot-plug tests (instance_hotplug.py) fail loudly if the attach has not landed when the helper returns. That is the exact failure this plan started from. The management session reads their results on the PR, not only the job's colour.
    • The helper now fails where it used to pass. Decision 2 catches an op that errors between polls, which today's loop missed, and decision 3 fails without the capability. A test that has been passing while one of its ops errored will start failing. Mitigation: that failure is real and is the point, but the management session checks any new smoke failure on the PR against the op it names before calling it a regression of this phase.
    • The sweep test is slow, or does not see a sweep. It holds one merge-queue worker for up to eight minutes. A loaded cluster whose per-instance pass runs out of its ten-second budget before reaching the instance would fail it. Mitigation: the wait is bounded and recorded with addDetail. Step 5f measures it on a cluster before merge. If it routinely runs past six minutes, or fails for lack of a sweep, the bound or the test's place in the suite is revisited before merge, not after.
    • TestOutstandingOperationsBodyAll's window is now short. Completed ops stay visible for as little as thirty seconds, rather than for up to fifteen minutes (finding 7). Mitigation: the test reads straight after the await, and step 5f runs it on a cluster. If it flakes, the fix is to create a fresh op immediately before the all=True read, not to widen the window.
    • A lifetime statement is missed or contradicts the canonical one. Mitigation: the Definition of done greps for both wordings, and the management session reads every site step 5d touched against the canonical paragraph.
    • ci.md and base.py conflict with the 4407 worktree. Mitigation: the new ci.md section sits before "Creating instances in the functional suite", and the 4407 change adds its section after it. In base.py the two changes touch different methods. Whichever merges second rebases, which should be mechanical.
    • The client helper's semantics change under the suite. CI installs client-python at the matching revision (finding 1), so a client change to await_no_pending_operations() reaches this helper with no review here. Mitigation: step 5a's unit tests pin the calls the helper makes, and the ci.md section names the client helper, so a client reviewer can see who depends on it.
