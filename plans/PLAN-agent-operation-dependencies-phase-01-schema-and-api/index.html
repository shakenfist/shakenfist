    Dependency-aware agent operations phase 1: schema, object and API¶

    Prompt¶

    This phase gives an agent operation somewhere to record its dependency edges, teaches the object the one new terminal state the cascade needs, and puts the edges on the three creating endpoints behind a capability token with submission-time validation. It writes no evaluator: nothing in this phase reads an edge and acts on it, and an operation created with edges in this phase executes exactly as it does today. Phase 2 is what makes the edges mean something.

    Ground every change in the tree rather than in the master plan's prose. The pattern this phase follows almost exactly is PLAN-agent-operation-deadlines phase 2, whose commit 02cfb79b48 ("Add agent operation deadline columns") added two static and two attribute columns to the same two tables with additive ADD COLUMN IF NOT EXISTS migrations, and whose phase 3 declared the REST parameters on the same three endpoints. Read that commit and its phase plan before starting: its decisions 2, 4, 7 and 8 are reused here by reference rather than re-argued.

    The files this phase touches are shakenfist/schema/agentoperation_data.py, shakenfist/schema/agentoperation_attributes.py, a new shakenfist/schema/agentoperation_dependency.py, shakenfist/mariadb.py, protos/database.proto, shakenfist/daemons/database/main.py, shakenfist/operations/agentoperation.py, shakenfist/external_api/base.py, shakenfist/external_api/instance.py, shakenfist/external_api/app.py, docs/developer_guide/state_machine.md, docs/operator_guide/database.md and docs/developer_guide/api_reference/.

    Planning effort: high. The master plan does not specify a review effort for this phase; review at high effort anyway, because the abort state and the submission-time namespace check are the two places where a wrong answer is expensive to detect.

    Scope¶

    In:

    • Two JSON static columns on agent_operations, depends_on and runs_after, and one JSON attribute column on agent_operation_attributes, dependency_failure. Both tables' versions bump and both migrations are additive.
    • A typed edge model with its own permitted-target set, per decision 5 of the master plan, and a per-edge settle delay, per decision 3 of its "Decisions already made".
    • abort in AgentOperation.TERMINAL_STATES and in state_targets, in one commit, per decision 3 of the master plan.
    • The three creating endpoints gaining the two parameters, their declarations, a capability token, and submission-time validation per decision 6.
    • depends_on and runs_after on external_view().
    • A live-MariaDB migration test, and documentation of the columns, the state and the parameters.

    Out:

    • All evaluation. No dispatcher change, no cascade, no settle-delay enforcement, no dependency-wait budget, no configuration option, and no database_load_budget.yaml amendment. Those are phase 2, and decisions 1, 2, 8, 9 and 10 of the master plan belong to it.
    • dependency_failure on external_view(). The column lands here because this is the schema phase; the only writer is the cascade, so the field appears on the wire in phase 2 (decision 1 below).
    • Any client change. client-python is phase 3.
    • The developer-guide model page and the example index. Phase 4.
    • Mixed-type edges with cluster operations, declined by the master plan's decision 4 and filed as #4824.

    What the survey found¶

    Phase 0 verified this plan's claims about the tree six weeks of commits ago. The survey re-checked the ones phase 1 depends on. The master plan's description of the work is substantially right; the corrections below are to its scope boundaries and to stale line references, and one of them moves work from phase 2 into this phase.

    1. The phase 1 prerequisite is met. client-python-k3s learned abort in PR #164 (539521411c, "Learn the aborted agent operation ending"), which is an ancestor of both v0.4.0 and v0.4.1. AGENT_OP_FAILED_STATES = ('error', 'expired', 'abort') is at shakenfist_client_k3s/cluster.py:138, and exceptions.py:1275 gives an aborted operation its own explanation ("the operation was aborted because something it depended on failed"). So this repository may emit abort.
    2. The attributes table is already at version 4, not 3. The deadlines plan's phase 2 took it to 3; expiry_reason took it to 4 afterwards. The bumps in this phase are therefore agent_operations 3 -> 4 (shakenfist/mariadb.py:493) and agent_operation_attributes 4 -> 5 (:494). A brief written from the master plan's prose would have got this wrong.
    3. BaseOperation.STATE_ABORT already exists (shakenfist/operations/baseoperation.py:53), and AgentOperation inherits it. No new constant is needed — only the state_targets edges and the TERMINAL_STATES membership, which is what makes decision 3 of the master plan a two-line change with a wedged-queue failure mode if it is split across two commits.
    4. The cluster-operation precedent gives no column precedent. cluster_operations is a hand-written table whose only variable-shape column is metadata_json (shakenfist/mariadb.py:2308-2343), so a cluster operation's depends_on rides inside that blob and never has a column of its own. agent_operations is generated from its pydantic model by pydantic_to_sqlalchemy_table (:19749), where a list annotation becomes a JSON column (schema/sqlalchemy.py:338-341, :382). The precedent to follow is therefore commands, which is list[dict] on the model and _json_dumps(data.commands) at the direct layer (:19944), not the cluster dependency model.
    5. VALID_CLUSTER_OPERATIONS still has exactly one consumer, the dependency.validate_op_type validator at shakenfist/schema/operations/baseclusteroperation.py:117, as phase 0 found. Nothing else reads it, so decision 5's "leave it alone and give the agent edge its own set" costs nothing.
    6. Several line references in the master plan and in the phase 0 plan have drifted. The three creating endpoints are now at shakenfist/external_api/instance.py:2383, :2450 and :2516 (phase 0 recorded :2334, :2401, :2467); the array-of-object type tokens are at shakenfist/external_api/base.py:1038-1039 (recorded as :821-829, which is now the middle of NETWORKSPEC_SCHEMA); Instance.agent_operation_next is at shakenfist/instance.py:3279 (recorded as :3164). The master plan's design-sketch reference is corrected at source by this commit; the phase 0 plan is a historical record and is left alone.
    7. Issue #4826 has been fixed since phase 0 filed it. The master plan's "Bugs found during this work" reads as though the always-empty agent_operations_queue view field is outstanding. It landed in PR #4832 (merge 29b9a16226): there is now an Instance.agent_operations_queued() accessor (shakenfist/instance.py:3261) which is the single reader of the queue key, and external_view() goes through it (:844-851). Corrected at source — the entry now records that it was fixed and where. This matters to phase 1 only as a warning: an instance's external view embeds each queued operation's full external_view(), so the two fields this phase adds to that view appear in the instance view too.
    8. A new structured parameter spec is not automatically covered by the documentation consistency test, and there is already one gap. shakenfist/tests/external_api/test_api_reference_specs.py checks the published key list of each structured spec against the API reference, but SPEC_SECTIONS (:60) is a hand-written three-entry dict — diskspec, networkspec, videospec. shapespec, added to ARGTYPES at shakenfist/external_api/base.py:1098 by PLAN-placeable-capacity phase 2, is in neither that dict nor the API reference: grep -rn shapespec docs/ --include=*.md finds only that plan. This phase adds its own spec to SPEC_SECTIONS and documents it (decision 7 below). The shapespec gap is not fixed here and no issue is filed: it belongs to PLAN-placeable-capacity, which is in flight and whose own documentation work is unfinished, so the durable record is a note against that plan rather than a duplicate issue.
    9. The Agent Operations state diagram currently matches state_targets exactly. Every edge in the mermaid block at docs/developer_guide/state_machine.md:48-84 has a counterpart in AgentOperation.state_targets (shakenfist/operations/agentoperation.py:65-86) and vice versa, checked edge by edge. Nothing enforces that — check-doc-anchors checks links, not diagrams — so the agreement is luck, and this phase is about to add a state. Decision 11 below closes it.
    10. agent_operation_timing() is the convention for a pre-creation refusal, at shakenfist/external_api/base.py:441. It returns (value, None) or (None, <400 response>) and its docstring states the convention explicitly; all three endpoints call it before creating any object or event. The submission-time validation of decision 6 gets the same shape, for the same reason.

    Nothing else in the master plan's phase 1 row was wrong.

    Decisions¶

    1. All three columns land in this phase; only two of them reach the external view. The master plan puts "the failed dependency on the wire in external_view()" in phase 2, which reads as though the column arrives then too. Splitting it that way would give phase 2 a second table migration and a second version bump on a table this phase has just migrated, for one nullable column. Instead dependency_failure is added here, with nothing writing it, exactly as the deadlines plan's phase 2 added last_progress and attempts and said "nothing reads any of these values yet". external_view() gains depends_on and runs_after here, because a client which cannot read back what it submitted has no way to confirm an edge was recorded; dependency_failure joins the view in phase 2, which is the first moment it can be anything but null, following the expiry_reason precedent (#4075). The master plan's phase 2 row is amended at source to say the column already exists.
    2. AgentOperation.current_version stays at 3. No object version bump, no _upgrade_step_3_to_4. This is decision 2 of the deadlines plan's phase 2, adopted by reference and for its reasons: a bump makes every not-yet-rolled node raise on any operation an already-rolled API node created, for the length of the rollout, and agent operations are the one object type whose writer and readers are reliably different processes on different machines. There is also nothing to migrate — an absent edge list is an empty list, not a gap. The fact a deployment needs is "does this database have the columns?", and that is the table version, which sf-database refuses to start behind.
    3. The stored shape is list[dict], and the typed model is a validator over it. depends_on and runs_after are list[dict] on AgentOperationData, mirroring commands, so the direct layer writes _json_dumps(...) and the gRPC layer carries a JSON string, both unchanged in kind from what they already do. Type safety comes from a pydantic field_validator on AgentOperationData which constructs the edge model from every entry and raises if it will not build, so a malformed or mixed-type edge cannot be stored or read back unnoticed. The alternative — Optional[list[agent_dependency]] on the frozen model — would be more idiomatic pydantic and would force a model_dump at the direct layer, a model_validate at the read, and a decision about what AgentOperationData means when it crosses gRPC as a string. The validator buys the same guarantee at the same boundary for less machinery.
    4. The edge model is agent_dependency in a new module, shakenfist/schema/agentoperation_dependency.py, with VALID_DEPENDENCY_OPERATIONS = frozenset([ObjectType.AGENTOPERATION]). The cluster dependency model and VALID_CLUSTER_OPERATIONS are not touched. This is decision 5 of the master plan, and the point of it is that the edge is admitted in one direction only: a cluster operation still cannot name an agent operation, so the mixed-type edges declined by decision 4 stay out by construction rather than by anyone remembering. A new module rather than a second model in baseclusteroperation.py, because that file is the cluster vocabulary and the name would then be a lie in the other direction. It sits in shakenfist/schema/ rather than in shakenfist/schema/operations/, which holds cluster-operation schema models exclusively, beside the agent operation's own two schema modules, because that is where a reader looks for one.
    5. op_type is on the model with a default and is not a published API field. The model carries op_type: ObjectType = ObjectType.AGENTOPERATION so the persisted edge dict has the same shape as a cluster dependency — an evaluator written later reads {'op_type': ..., 'op_uuid': ...} either way — and the validator refuses any other value. The API object a caller sends is {"op_uuid": ..., "settle_seconds": ...} and nothing else, with additionalProperties: False. Publishing a field with exactly one legal value would be API noise, and a caller who sent the wrong one would earn a 400 for a constant. This is the decision most likely to be argued with: the counter-argument is that omitting op_type makes widening to #4824 a published-shape change rather than a new enum value. That is true, and it is the right trade, because #4824 is declined rather than deferred to a known date, and a field nobody may vary is a worse cost paid now than a parameter change paid never.
    6. settle_seconds is declared minimum: 0, maximum: config.AGENT_OPERATION_MAX_DEADLINE, and no new configuration option is introduced. That ceiling already exists and already means "the longest a caller may park an instance's executor slot"; the declaration precedent is deadline_seconds at shakenfist/external_api/instance.py:2314-2316. The honest consequence, which phase 4 documents rather than designs around: once phase 2 lands its 300-second dependency-wait budget, a settle longer than the budget guarantees the dependent operation is aborted. Tying the declared maximum to the budget's config value instead would mean introducing a configuration option in the phase that cannot enforce it, which is the "documenting a lie" failure the deadlines plan's phase 2 step 2e named.
    7. Two type tokens, agentdependency and arrayofagentdependency, and the single form goes in SPEC_SECTIONS. Only the array form is used by an endpoint, as is true of diskspec; the single form exists because test_api_reference_specs.py resolves a documented section through ARGTYPES[token]['properties'] and so keys on the object schema, not the array. Adding both means the existing documentation consistency test covers the new spec with no edit to the test's own logic, which is the difference between a documented spec and survey finding 8's shapespec.
    8. Submission validation is one helper, and it does not disclose existence. api_base.agent_operation_dependencies(depends_on, runs_after, caller_namespace) lives beside agent_operation_timing() and returns ((depends_on, runs_after), None) or (None, <400>). For each named edge it reads the operation once and refuses if it does not exist, is not an agent operation, or is in a namespace the caller cannot read — request_namespace() not in (dep.namespace, 'system'), the test requires_instance_ownership performs at shakenfist/external_api/base.py:2000. Master plan decision 6 says 400 for all three, and that is kept, but the message is the same for all three, so a caller cannot use the refusal to learn that an operation they may not see exists. The repository's instinct elsewhere is a 404 for exactly this reason; a 400 is right here because the caller sent a bad parameter rather than addressed a missing resource, and the non-disclosure that the 404 was buying is bought by the shared message instead.
    9. Namespace is checked once, at submission, and never again. Master plan decision 6, restated here because it is the kind of thing a later reviewer tries to "fix": re-checking at evaluation would let a namespace change break a chain already in flight.
    10. abort gains edges from initial, preflight and queued, and abort -> deleted. Not from executing. Only queued -> abort is reachable by phase 2's evaluator, which runs on the head agent_operation_next() returned and so only ever sees a queued operation. The other two are declared for completeness, exactly as expired's initial edge was and for the reason its comment gives. executing -> abort is deliberately absent: aborting work already running is agent-side cancellation, which is a non-goal of this plan, and declaring the edge would invite a future site to take it. abort -> deleted is not optional — delete() removes the rows and then assigns deleted (shakenfist/operations/agentoperation.py:553-561), so without it a user deleting an aborted operation raises InvalidStateException.
    11. A unit test compares the Agent Operations mermaid block to state_targets. Survey finding 9 found the two agree today by luck. A test which parses the ## Agent Operations section's stateDiagram-v2 block and compares its edge set to AgentOperation.state_targets — mapping [*] --> x to the None key and x --> [*] to a None value — makes the documentation obligation falsifiable rather than a review item. It is in scope because this phase is the one adding a state, and it is the only new test in this phase that is not about the phase's own code.
    12. Dependency edges are not recorded as object references. external_view() already carries references_to and references_from from the object_references machinery, and an edge is arguably a reference. It is not registered as one: the reference tables exist for blob and artifact reference counting and drive hard-delete safety, and adding an edge there would make a dependency keep its dependent's row alive, which is precisely the opposite of the sweep behaviour decision 9 of the master plan relies on.

    Risks and mitigations¶

    • The abort state wedges an instance queue if the commit is split. agent_operation_next() breaks out of its loop on a state it has not been taught, leaving the entry at the head forever (shakenfist/instance.py:3406-3415). A commit which adds the state_targets edge without the TERMINAL_STATES membership is that bug. Mitigation: step 1d does both in one commit and the brief says so; the management session checks the diff of that commit specifically, before running anything.
    • A migration which adds a different column type from what a fresh create_all produces. schema/sqlalchemy.py maps a list field to mysql.LONGTEXT deliberately, so an ADD COLUMN ... JSON would leave a migrated cluster and a fresh cluster with different schemas and nothing in the unit suite could tell: it mocks MariaDB completely. Mitigation: step 1f asserts the migrated column type equals the freshly created one, and mutation-tests that assertion by deliberately introducing the divergence.
    • The validator in decision 3 runs on every read. Every _direct_get_agent_operation constructs an AgentOperationData, which now builds an agent_dependency per edge. For an operation with no edges that is two empty-list iterations, which is free; for one with edges it is a handful of pydantic constructions on a path the sidechannel dispatcher polls per ready instance every five seconds. Mitigation: the lists are expected to hold one or two entries, and the dispatcher reads an operation it was already reading. If a reviewer thinks this is material, the measurement to ask for is phase 2's, which is where the per-pass read cost is budgeted (shakenfist/data/database_load_budget.yaml); flag it rather than optimising blind.
    • A client sends an edge against a server which has the parameter but no evaluator. Between this phase and phase 2 landing, a declared dependency is accepted, stored, visible on the view, and silently ignored at dispatch — the operation runs in queue order as it does today. Mitigation: the capability token is the signal, and it is added in this phase, so a client which checks it will believe dependencies work. That is the real exposure, and the mitigation is that both phases land in the same release cycle and the token's own comment says what it promises. If the two phases look likely to be separated by a release, the token should move to phase 2 instead; that is a decision for the operator at the back brief, not for the implementer.
    • A namespace check written against the wrong direction. The idiom is request_namespace() not in (dep.namespace, 'system'), which admits a caller in the dependency's namespace and a caller in system. Inverting it would let any caller name any operation, or lock system out. Mitigation: step 1e's test list includes both a cross-namespace refusal and a system caller succeeding, which fail in opposite directions if the test is inverted.
