    Scheduler reservations phase 5b — the hard ceiling¶

    Prompt¶

    Phase 5a spent its calibration window, read it on 2026-11-13 against the decision rule D2 pre-registered, and the rule said Hold. The flip of CLAIM_ENFORCEMENT_HARD from advisory to binding, the cluster CI assertion inversion and the documentation did not run, and are this phase. The row that held it was the structural one — five namespaces admitted a single instance larger than the whole claim it was charged to — and the cause was in another repository: private-ci sized a combination claim for the largest pending job and then charged it to whichever job GitHub dispatched.

    That is fixed. private-ci's phase 3g bound sf-e2e, oVirt 4.5 on Rocky 8 and OpenStack via Kolla-Ansible master on Debian 13 to their own runners (kerbside#727, merged 2026-11-14 19:48 UTC), read the seven days that followed, and found the class gone: zero over-limit runs fleet-wide against five in the seven days before. It handed that over on shakenfist/private-ci#311 on 2026-11-25. Plan-blocker b21's two conditions — the binding phase landed and deployed, and a fresh seven-day window available — are therefore both met, and this phase may be planned and may read.

    Before executing any step, read phase 5a's Observations and Outcome in full: D2's table is this phase's rule unchanged, phase 4c's figures are the baseline, and 5a's step 4, 5 and 6 briefs are where this phase's work was specified. Then read the admission primitive (shakenfist/mariadb.py's _direct_admit_instance_placement), the capacity stage constants (shakenfist/constants.py), the create path's exhaustion branch (shakenfist/external_api/instance.py), the refusal contract's operator page (docs/operator_guide/capacity_refusals.md) and the cluster CI claim tests (shakenfist/deploy/shakenfist_ci/cluster_ci_tests/test_namespace_claims.py). Do not trust 5a's line numbers: every one has moved, most of them by more than a thousand lines.

    Planning effort¶

    High. The flip changes a published refusal contract — a new status code, a new stage name, two new body fields and a classification three components read — and it does so in a file another plan rewrote 1,900 lines of since the contract was last specified. The measurement that gates it has to be read against a rule fixed before the data is seen, which is a discipline rather than a procedure. Review effort: high, for the same reasons, and because an error in the 403's body shape reaches clients.

    Scope¶

    In scope:

    1. Read a fresh seven-day window against phase 5a's D2 rule, exactly as written, and record Flip, Hold or Unreadable.
    2. If, and only if, the rule says Flip: set CLAIM_ENFORCEMENT_HARD = True, introduce CAPACITY_CLAIM_STAGE, classify it in neither transient nor permanent, thread the claim uuid through CapacityAdmissionDenied and the placement-denied audit event, and publish HTTP 403 with the D16 body when every candidate was refused at the claim stage.
    3. Declare the 403 in the instance create endpoint's OpenAPI response list, with its own example body.
    4. Invert the cluster CI test that asserts an over-claim create succeeds, and fix every unit test and tool whose assertion or output text is conditioned on the constant being False.
    5. Rewrite the documentation that says the ceiling is advisory, specifying the 403 once on the refusal contract's own page.
    6. Close out this phase.

    Out of scope, and why:

    • Re-deriving or re-tuning D2. The rule was pre-registered in phase 5a and amended once, before any data was seen, with Michael's agreement. It is read as written. A phase that reaches its own measurement and adjusts the threshold has not measured anything.
    • Re-reading the window phase 5a spent (2026-11-05 to 2026-11-12). n24 forbids it and so does the point of the exercise.
    • Anything about how private-ci sizes or binds claims. 3g owns that, it has handed over, and its own remaining work (the Merged cell for private-ci#322) is private-ci's.
    • The anti-starvation policy (D18's 15-minute rule) and delegated claim creation (D15). Phase 4c deferred both; neither is touched by making a ceiling binding.
    • Splitting a hold stage out of TRANSIENT_CAPACITY_STAGES. PLAN-placeable-capacity.md phase 4 owns that, for the same frozenset and for the same reason. See R2.
    • Phase 9's push audit. It runs last, and it audits the documentation this phase rewrites.

    What the survey found¶

    Phase 5a said this phase "needs no fresh survey of the enforcement contract", and in one sense that was right: D5's discriminator and D6's classification are intact, and the three step briefs still describe the right work. In another sense it was wrong. Every file reference in them has moved, and the briefs' scope is short by two documentation surfaces and one OpenAPI declaration that nobody had looked for. The contract decisions survived; the map to the tree did not.

    F4 — place_on_candidates() walks the candidate list twice, and that cannot manufacture a mixed all-claim dict. The second pass (instance.py:1663) runs only when every refusal in the first pass was demand_only, and by F3 a claim denial never is. The implementer does not need to reason about the two passes; it needs to not break this.

    F5 — the denials dict carries three keys and no claim uuid. instance.py:1646-1650 builds {failing_stage, dimensions, demand_only} per candidate, and CapacityAdmissionDenied.__init__ (exceptions.py:217) still takes two arguments. demand_only is a derived property, not a constructor field, so threading the uuid means a third argument and one more key. 5a's step 4 addendum is correct as written.

    F6 — the advisory events already name the claim; the denial event does not. The instance placement denied event at :1498-1505 carries failing_stage, dimensions and enforce and no claim, and place_instance() drops the uuid at :1518. This is exactly the asymmetry 5a's review round (iii) asked this phase to close.

    F7 — the refusal contract has a dedicated operator page, and 5a's F6 never listed it. docs/operator_guide/capacity_refusals.md is 290 lines whose entire job is this contract: which refusals are transient, whether the refusal is queued, the response body, the stage field, the transient field, the refusal as recorded on the instance, and Retry-After. It currently states that a scheduling refusal "returns a JSON body with four fields", enumerates the stage values exhaustively (filter names, capacity_guard, unknown), and mentions claims nowhere at all — grep -i claim over it returns nothing. Every one of those statements becomes incomplete at the flip: a fifth stage, a second status code, and two body fields the page does not know about. This is the largest single gap between 5a's step 6 brief and the work.

    F8 — the 507 is a declared OpenAPI response, so the 403 must be declared too. The create endpoint's swag_from(...) block at external_api/instance.py:770-808 lists each status code with its description, an example body and, for the 507, {'headers': [api_base.TRANSIENT_RETRY_AFTER_HEADER]}. The example lives at :273-278 as instance_post_507_example, with a comment explaining that Retry-After cannot be expressed in the tuple format and is named in the description instead. A 403 that is not added here is absent from the published specification at openapi.shakenfist.com, and shakenfist/tests/external_api/test_openapi_spec.py validates that specification without being able to notice something missing. docs/developer_guide/api_reference/instances.md:93 also sends the reader to the capacity-refusals page for "that response's format, its stage and transient fields, and the Retry-After header", which after the flip describes only one of the two responses.

    F9 — v0.8 is not released, so the release notes are not history. 5a's step 6 brief said of docs/release_notes/v07-v08.md:1459: "check whether it describes the release or the present, and if the release, leave it and say so in the back brief rather than falsifying history." The file is the release notes for the release being prepared, so "Claim ceilings are advisory this release. It is rewritten, not preserved. The passage continues at :1677 with a status-code list for claim creation refusals (507 and others) which is a different subject and stays as it is.

    Risks and mitigations¶

    R1 — a 403 that names a claim which no longer exists. The uuid and the dimensions have different sources either side of a rollback (D4), so a delete-and-create in between produces a refusal naming a claim nobody can grow. Mitigation: D4 makes dimensions optional and uses its emptiness as the discriminator, and step 2's test list includes the empty-dimensions case explicitly. The management session checks that the 403's text in that case recommends nothing — a body that says "grow claim X by 4 vCPU" about a deleted claim is worse than one that says only which claim refused.

    R2 — collision with PLAN-placeable-capacity.md phases 4 and 5. That plan's phase 4 must split a hold stage out of TRANSIENT_CAPACITY_STAGES ("a refusal caused by another namespace's hold is not transient"), and its phase 5 is called The refusal contract.     R3 — merge CI breaks on every platform if step 3 misses a site. The cluster CI test runs in merge CI and is not locally runnable, so a missed assertion is found by the merge queue and not by tox. Mitigation: F14 enumerates the sites rather than describing them, and the Definition of done includes a grep that must come back empty. The five that held phase 5a were all one job landing on a peer's claim, and what fixed it was a per-job binding token in another repository, which nothing in this repository can keep working.
