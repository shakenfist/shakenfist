    PLAN: Cluster op visibility phase 6 -- push audit¶

    Planning effort: medium. Review effort: medium.

    Why this phase exists¶

    Phases 1 to 5 landed in six pull requests over three months. Each was reviewed on its own terms, and none was read beside the others. This phase runs PUSH-AUDIT.md over all six, plus the client-python pull request that carried phase 4's client half.

    The plan's idea is a single rule, applied in many places: an operation whose every task only measures is observational. It is recorded, but it never becomes last_cluster_operation, never counts as pending, never fails a CI wait, and failing it never errors its object. Phases 2 to 5 each wrote some of those places, and #4608 added another after phase 3. Whether every place agrees is the question no single phase's review could ask, so this audit adds it as its own heading (decision 6).

    Scope¶

    In scope.

    • The six merges in decision 1, under every PUSH-AUDIT.md heading: wave 1, the wave 2 mechanical sweep, the style judgment portion, and 2a to 2d.
    • Two headings of this plan's own: the coherence of the observational and pending rules (step 6h), and the client half of the contract, shakenfist/client-python #436 (step 6i).
    • The master plan's Future work entries, none of which has an issue (survey finding 8). Disposition decides which become issues.

    Out of scope.

    • 4608 (issue-fix-4585) and #4621 (issue-fix-4604). Both fix¶

      defects that predate this plan, in code the plan touched, and the Merged column does not claim them (survey finding 5). #4608 does add a consumer of this plan's observational_tasks declarations, so step 6h reads that consumer at $TIP without auditing the pull request.
    • The other later merges that touch audited files (survey finding 5). They matter only where they change whether a finding still holds, which decision 2 covers.
    • Fixing what the audit finds. Decision 7 says where each kind of finding goes.
    • Editing shakenfist/client-python. Findings there become client-python issues (decision 3).

    Risks and mitigations¶

    • The audit rubber-stamps merged code. Each phase had its own review, and a reviewer reading six reviewed diffs is inclined to agree with them. Mitigation: decision 10 makes every clean heading list what it read. 6d and 6h each ask what a change switches on, not only whether it is correct. 6j rejects a report that names no functions.
    • Findings against code that has since changed. Eleven later merges touch audited files, and phase 1 is three months old. Mitigation: decision 2's three classifications. 6j spot-checks one "still true" claim per report at $TIP.
    • The client range is audited as if it were this repository. client-python has its own conventions, and no runbook. Mitigation: decision 3 limits 6i to the contract and the five-item floor, and findings go to client-python as issues, never as edits.
    • Parallel agents interfere. Mitigation: decision 5. Only 6b, which runs alone first, and 6j write files or run the suite.
    • Predating defects are graded as this plan's. S1 and S2 each say they predate the plan, and a reviewer reading the Future work list could mistake them for findings. Mitigation: decision 7's predating grade, under which they become issues and not findings, so they cannot hold the plan open.
    • Wave 1 is slow or fails for reasons outside these ranges. Mitigation: decision 9, and the back-brief gate after 6b, so a broken develop is reported before wave 2 is spent.
