    Scheduler reservations phase 5a — the calibration re-run and the hard ceiling¶

    Prompt¶

    Phase 5 landed three of its four steps as PR #4800 (merge 660d4f65e7, 2026-11-05) and deliberately held the fourth: the advisory→hard flip of CLAIM_ENFORCEMENT_HARD, gated on plan-blocker b13, the re-run of phase 4c's observation measurement. Phase 5's branch merged and was deleted, so the "step 3 lands as a later commit on this branch" the Execution notes describe is no longer available. This phase carries the flip instead.

    Before executing any step, read phase 4c's Observations section and its "Does phase 5 flip CLAIM_ENFORCEMENT_HARD?" answer — that record is the baseline this phase's measurement is compared against, and its three "what is still missing" items are this phase's entry conditions. Read the admission primitive (shakenfist/mariadb.py's _direct_admit_instance_placement), the capacity stage constants (shakenfist/constants.py), the create path's exhaustion branch (shakenfist/external_api/instance.py) and the cluster CI claim tests (shakenfist/deploy/shakenfist_ci/cluster_ci_tests/test_namespace_claims.py). Ground every claim in what the code does today; this plan's own survey found seven of phase 5's step 3 premises wrong.

    Planning effort¶

    High. The flip changes a refusal contract that three components already publish and one consumes, it inverts a cluster CI test's assertion, and its gate is a measurement whose decision rule has to be fixed before the data is read rather than after. Phase 5's own step 3 brief, written at high effort three days ago, has seven stale or wrong premises — recorded in What the survey found — which is the measure of how much this area has moved.

    Scope¶

    In scope:

    1. Pin the measurement window's start from the conductor's own data, and open it.
    2. Pre-register the numeric decision rule for the flip, and read the window against it exactly as written.
    3. Populate claim_uuid on the admission-denial path, which D16's refusal body needs and which today is set only on the admitted path.
    4. If, and only if, the rule says flip: set CLAIM_ENFORCEMENT_HARD = True, publish a distinct claim refusal stage, classify it as not retry-worthy, and map a claim refusal to HTTP 403 with the D16 body.
    5. Invert the cluster CI test that today asserts an over-claim create succeeds.
    6. Update the documentation that says the ceiling is advisory.
    7. Close out phase 5 and this phase.

    Out of scope, and why:

    • Changing how the conductor sizes claims. If the rule says hold, the defect is in private-ci's sizing and the fix belongs to PLAN-claim-coverage-and-sizing.md, which owns that code. This phase stops and says so rather than widening.
    • Reconsidering CLAIM_EXACT_MIN_RUNS. Exact sizing is private-ci's decision (its phase 3d), shipped on at 5 runs. This phase measures its cost under enforcement and reports it; it does not change it.
    • The anti-starvation policy (D18's 15-minute rule). Phase 4c established the population and not the outcome, and said the policy keeps its own phase. Unchanged here.
    • Delegated claim creation (D15) and publishing private-ci. Phase 4c future work, untouched.
    • Phase 9's push audit. It runs after this phase and reads this phase's merges among the rest.
    • Claims for the remaining unclaimed namespaces. The survey found this already discharged; see F8.

    What the survey found¶

    Seven of phase 5 step 3's premises are wrong or stale, two of them load-bearing. Corrections were made at source in the master plan's phase 5 section, its Execution table and the index.md row as part of this phase's planning commit, and phase 5's own step 3 row is marked superseded by this plan rather than having its line numbers repaired — maintaining two copies of the same brief is how they diverge.

    F1 — every line number in step 3's brief has drifted, because step 1 of the same phase moved the code. CLAIM_ENFORCEMENT_HARD is at mariadb.py:27715, not 27461. The result['admitted'] and result['claim_over_limit'] branch is at instance.py:1232 with _event_claim_over_limit() at instance.py:1253, not ~1182. The claim guard inside admit_instance_placement is at mariadb.py:28889 (claim_guarded = enforce and CLAIM_ENFORCEMENT_HARD), not 28541-28640. Step 1's extraction of place_on_candidates() is what moved them, in the same pull request.

    F2 — the capacity stage sets have moved out of the API layer, so step 3(d) names the wrong file. TRANSIENT_CAPACITY_STAGES and PERMANENT_CAPACITY_STAGES now live in shakenfist/constants.py:241 and :268; external_api/base.py:141-142 only re-exports them. The comment in constants.py explains why: a preflight abort records the same classification on the instance (issue 4568) and instance.py cannot import the API layer. Editing external_api/base.py:135-148 as the brief says would change nothing.

    F3 — there is no claim stage to split out of the transient set; one has to be created. This is the first load-bearing finding. CAPACITY_GUARD_STAGE = 'capacity_guard' (constants.py:220) is the single stage every guard denial publishes — node, cluster and claim alike — and it is that one constant which sits in TRANSIENT_CAPACITY_STAGES (constants.py:257) with a comment saying claim denials "must be split out of this set at that point". So step 3(d) is not a frozenset edit: a distinct stage has to be introduced, published where the claim guard is the refusing one, and classified. The guard that makes this enforceable already exists: tests/external_api/test_capacity_error.py:229-241 walks scheduler.py for stage literals and asserts every published stage is in one of the two sets, so a new stage classified into neither fails a test — but note its second assertion, which pins classified - stages to exactly {CAPACITY_GUARD_STAGE} and will need the new name added.

    F4 — by the time the create path refuses, there is no single exception to map, and the claim guard's node-independence is what makes a 403 well defined. This is the second load-bearing finding, and it is the one step 3(c) is quietest about. external_api/instance.py:1261-1277 refuses after the walk has tried every candidate, holding a denials dict rather than one CapacityAdmissionDenied, and its comment says so: "There is no single stage here — denials may span 'cluster', 'claim' and 'node' across different candidates (D30)". What rescues the mapping is an invariant of the primitive rather than of the caller: the claim guard is statement (2) in _direct_admit_instance_placement, before either node guard, and mariadb.py:28880-28886 records why it is node-independent — "a claim's limits are namespace-denominated and node-independent, so a missing node capacity row says nothing about whether the namespace has exceeded what it claimed". A claim refusal therefore aborts the transaction on every candidate before any node guard runs, in both passes of the demand re-walk, so "every denial is at the claim stage" is the only shape a claim refusal can take. That is the discriminator, and it is provable rather than heuristic. See D5.

    F5 — claim_uuid is not populated on the denial path, and D16's body names the claim. AdmitPlacementResult.claim_uuid exists and is documented as "the claim this admission was charged against … so an event recorded on the namespace can name which claim it was", but it is assigned only at mariadb.py:29120, inside the advisory read-back on the admitted path. The _AdmissionDenied handler at mariadb.py:29170-29174 sets failing_stage and dimensions and returns, leaving claim_uuid at the '' default from mariadb.py:28205. A refusal body that must name the claim cannot, today. See D4.

    F6 — the advisory doc line list is 9 lines, not 10, and two of them are unrelated. Running phase 8's own item-12 grep (grep -rn -i 'advisory' docs ARCHITECTURE.md --include='*.md', less docs/plans/ and docs/components/) returns nine lines. Seven are claim-ceiling statements: docs/glossary.md:63, docs/operator_guide/scheduler.md:456, :460 and :522, docs/developer_guide/subsystem_internals.md:312, docs/operator_guide/database.md:932, docs/release_notes/v07-v08.md:1459, plus ARCHITECTURE.md:212. That is eight. The remaining two, docs/developer_guide/ci.md:15-16, use the word about CI lint lanes and must not be touched. subsystem_internals.md:337 also describes the flip without using the word and belongs on the list.

    F7 — phase 4c's three entry conditions are all met, and two were met by a different mechanism than it named. Phase 4c said the flip needed a sizing input tracking real use, a CI_SIZES floor covering a cluster job's first run, and a re-run.

    • Sizing input: done, and done well. private-ci conductor/db.py:4911's get_claim_sizes() now takes, per row, the larger of claim_peak_* — the cluster's own high-water mark on the claim, which is peak_used_* from phases 4 and 7a — and the conductor's reconstruction from instance lifetimes. That directly addresses the 2.12x–5x under-statement phase 4c measured, because the ledger mark cannot sit below the instances it marked.
    • The floor: addressed by a different mechanism. Rather than raising CI_SIZES, private-ci's phase 3a added s-cloud and s-cluster size tokens (conductor/provisioner.py:103-108) so a cloud or cluster job no longer shares a combination key — and therefore a claim size — with every small job, and db.py:4998 added an all-history MAX so a new job does not fall to the bare floor. The problem phase 4c named is solved; the solution is not the one it proposed.

    The cause is mis-assignment, not mis-measurement¶

    4c's two failure modes were both measurement defects -- an under-measured aggregate peak, and a peak smaller than one runner. Neither is what this window shows. The conductor's own cost row for all five namespaces records the peak correctly:

    runner size l (6 / 12288 / 300), peak_allocated 18 / 28672 / 520,
peak_concurrent_instances 2,
peak_shapes [{"cpus": 12, "ram_mb": 16384, "disk_gb": 160, "count": 1}]

    6 + 12 = 18 cpus, and claim_peak_* equals the reconstruction on every row. The measurement is right. What is wrong is which job the claim was sized for: in all five namespaces the job that ran was kerbside / sf-e2e, whose single nested 12-cpu VM is larger than the 10-cpu and 6-cpu claims made for the three other kerbside jobs named above. The claim was sized for a pending job and then charged for a different job's placements.

    Filed as shakenfist/private-ci#311, against PLAN-claim-coverage-and-sizing.md as D2 requires, with the window's evidence and the reproduction. That plan already holds the fix in design: phase 3b's per-job binding gives a job a runner GitHub can hand to nothing else, so "the claim is sized for the job that will run" -- its own words. What this reading adds is that 3b is a prerequisite for hard enforcement rather than an efficiency improvement, and that sf-e2e is the job to bind first. The issue also costs the cheaper alternative of giving sf-e2e its own size token, as phase 3a did for cloud jobs, which fixes this case without fixing the general one.

    The exposure is 5 in 37, not 5 in 3770. sf-e2e ran 37 times in the window: 32 landed on an 18-cpu claim, which is the combination maximum taken while sf-e2e was itself pending, and 5 landed on a 6- or 10-cpu claim. So the cost of flipping today is not a 0.71/day aggregate residue but a 13.5% chance per run that this one job is refused permanently, and the l pool it shares holds at least nine job names across kerbside and ryll. That is the number the flip decision should be read against.

    That mis-assignment is the norm rather than the exception, and mostly harmless: across the window the claim was sized for a different job than the one which ran in 2464 of the 3771 cost rows (65.3%), because combination_claim_size() claims for the largest pending job in the combination. It only bites when the job that actually arrives holds a single instance bigger than the claim the combination produced -- 5 of those 2464, every one sf-e2e landing on a claim sized for a smaller lane.

    Under hard enforcement those five creates are refused, not delayed: the 12-cpu VM cannot fit a 6-cpu claim however long it waits, and there is no operator remedy short of changing the declaration. That is exactly the condition D2's row 3 names structural and sets to 0.
