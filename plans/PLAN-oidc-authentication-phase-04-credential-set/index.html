    Phase 4: minting the entitled credential set at login¶

    Context¶

    Phase 4 of PLAN-oidc-authentication.md. Planning effort: high. Review effort: high — the master plan asks for it by name, on the grounds that this is the cluster's privilege boundary and the failure mode is silent.

    Phase 0 settled the two questions this phase's shape depends on. Human sessions use exchange rather than direct-bearer, so what a person ends up holding is an ordinary namespace key and the access tokens minted from it. And a credential stays one namespace deep, so the multiplicity of a person who works in several namespaces is held by the client as a set of single-namespace keys rather than by one credential naming several.

    Phase 3 built the half of a human login that happens before any of this: discovery, the client_id and oidc_scopes columns no discovery document can supply, and GET /auth/login, the unauthenticated endpoint that tells a client which providers this cluster will accept a person from.

    What is missing is the act in the middle. A person completes a flow at their provider — phase 7's work, in client-python — and comes back holding an identity token. Nothing in this repository turns that token into the set of credentials the person is entitled to. The targeted workload exchange, POST /auth/federated (shakenfist/external_api/auth.py:2419), requires the caller to name one namespace and one mapping rule, which a person has no way to know and which would in any case need one call per namespace.

    This phase builds the server half: one unauthenticated request carrying one identity token, matched against every mapping rule the cluster holds for that issuer, minting one namespace key per match.

    Scope¶

    In scope.

    • POST /auth/login: validate an identity token, find every mapping rule it satisfies, and mint one namespace key per rule.
    • A rule accessor that reads every rule's policy for one issuer in a bounded number of database round trips rather than two per rule.
    • An audience override on federation.validate_token(), because the audience an identity token carries is not the audience a workload token carries (survey finding 1).
    • Replay refusal, rate limiting and a cap on the size of the minted set, all on an endpoint anybody may call.
    • Audit events on each minted key, on each namespace minted into, and on each refusal that has an identifiable owner.
    • The documentation an operator and an API consumer need, and the capability token a client feature-detects this with.

    Out of scope.

    • Both OAuth flows, the credential cache, and choosing which member of the set to present per request. All of that is phase 7, in client-python. Nothing in this phase performs a token request, a device authorization request or a PKCE exchange.
    • Serving a namespace key's metadata back as a read — that is phase 6 and issue #3672. This phase returns each credential's expiry and scopes in the mint response, which is a different thing: it is what the caller was just given, not a read of what exists (decision D10).
    • Any change to server-side authorisation. request_namespace() stays a string split (shakenfist/util/access_tokens.py:83), and none of the fifty-seven sites that read it move. Phase 0 refused that change and gave three reasons; this phase does not reopen it.
    • Periodic re-discovery, provenance on jwks_uri, and the GET /auth/login TTL cache. All three are master-plan Future work entries written by phase 3.
    • Any change to what POST /auth/federated accepts or returns. The workload exchange is not refactored to share an implementation with the login path; what they share is federation.py, which is where the master plan's review checklist says shared validation lives.

    What the survey found¶

    The master plan's phase 4 section makes one falsifiable claim about the tree — that request_namespace() is still a string split at shakenfist/util/access_tokens.py:83 — and it is still true. The mechanism the section describes, "match the identity token's claims against the mapping rules of each namespace which has one", is buildable as described. Nothing in that section is wrong.

    Eight things it does not say, each of which changes what the phase has to build.

    1. A human identity token cannot validate against an issuer's configured audience¶

    This is the finding that most changes the phase, and it would have been found by the implementer only after writing a test against a real provider.

    federation.validate_token() (shakenfist/federation.py:294) reads configuration.audience and passes it to jwt.decode() with verify_aud on and require naming aud. The operator guide describes that column as "Tokens must be minted for this. Usually your cluster's API URL" (docs/operator_guide/authentication.md:163), and the worked GitHub Actions example has the workflow request a token with audience=https://sf.example.com (docs/operator_guide/authentication.md:470). For a workload that is exactly right: the workload asks its provider for a token stamped with whatever audience we tell it to ask for.

    A person cannot. OpenID Connect Core 1.0 §2 requires an ID token's aud to contain the client_id of the relying party, and that is what Keycloak and Authentik stamp. The client identifier is already a column, added by phase 3, and it is the field that decides whether an issuer is offered for login at all (shakenfist/external_api/auth.py:2778). So an operator who follows the operator guide — API URL in audience, client identifier in client_id — has configured a cluster where every human login fails aud verification, with a refusal deliberately terse enough to give them nothing to work from.

    Nothing in the master plan, phase 0 or phase 3 mentions this. Open question 4 settled that the audience is per-issuer rather than per-cluster and stopped there, because at the time the only tokens were workload tokens.

    2. /auth/federated is described in the code as the only unauthenticated route with a body¶

    limit_federated_body_size (shakenfist/external_api/app.py:232) refuses an oversized body before any reader parses it, and its comment opens "/auth/federated is the only unauthenticated route which takes a body". The check is a path equality test against that one string.

    That comment is true today — GET /auth/login takes no body — and this phase falsifies it. The hook has to cover the new route, or the endpoint's own size check is the only one, and the endpoint's own check is documented in the same comment as unable to protect anything: by the time a flask_restful method runs, log_request has already called get_json(force=True) and parsed the whole body.

    Credential redaction, by contrast, is already inherited. handles_credentials() (shakenfist/external_api/base.py:111) tests path == '/auth' or path.startswith('/auth/'), so a body and response on /auth/login are redacted in the request log without any change.

    3. A rule's issuer lives in its attributes row, so "every rule for this issuer" has no indexed path¶

    MappingRules (shakenfist/mapping_rule.py:606) can list every rule on the cluster — get_all_mapping_rules() (shakenfist/mariadb.py:16118) when no namespace is given — but what it yields is static rows: uuid, namespace, name, version. The issuer the rule accepts, the claims it binds, its scopes, its TTL and its key name prefix are all in the attributes row, reached through policy() (shakenfist/mapping_rule.py:474). Iterating MappingRules and calling policy() costs one attributes read per rule, and the state filter every caller needs (AuthNamespaceRulesEndpoint.get, shakenfist/external_api/auth.py:1703) costs a second read per rule.

    Two round trips per rule, on an endpoint an anonymous caller may reach sixty times a minute per source address, is the shape of amplification that enforce_rate_limit's own docstring (shakenfist/federation.py:462) warns about for issuer resolution. On a cluster with two hundred rules it is four hundred round trips per login attempt.

    The tree already contains both halves of the answer, each added for exactly this reason.

    • find_namespace_keys() (shakenfist/mariadb.py:14646, direct at 14082, gRPC at 14467) returns each static row joined with its attributes row, wrapped by keys_with_attributes() (shakenfist/namespace_key.py:425), whose docstring says the alternative "would cost two extra point reads per key on /auth".
    • reap_expired_namespace_keys() (shakenfist/daemons/cluster/scheduled_tasks.py:842) resolves "which of these objects is in an actionable state" with one get_objects_by_state() call (shakenfist/mariadb.py:5085) rather than reading .state per object, after the per-object version was measured at ~15,200 round trips per pass on sfcbr and filed as issue 3814.

    4. get_objects_by_state() returns None for failure, and the distinction is load bearing here¶

    Its docstring says so explicitly: "or None if the query failed (distinct from [] which means no matches)". A login that reads None as "no rule is in an actionable state" mints nothing, which is safe. A login that reads None as "do not filter by state" mints from soft-deleted rules, which is an authorisation bypass: delete() on a mapping rule is a soft delete (shakenfist/mapping_rule.py:601) and the row survives until the hard-delete reaper gets to it.

    5. The replay table's second key component is a mapping rule, and a login has no single rule¶

    _get_federation_replay_table() (shakenfist/mariadb.py:2433) has a composite primary key on (token_id, rule_uuid), and its docstring justifies the grain: "Refusal is per (token, rule) rather than per token because exchanging one identity against two rules to reach two namespaces is a legitimate pattern, while re-exchanging it against the same rule is not."

    A login is precisely that legitimate pattern, performed in one request. Claiming the pairs one at a time means a login that mints three of five and then fails can never be retried to completion: the retry finds three pairs taken and two free, and returns a set of two with no indication that it is short. rule_uuid is a plain UUID column with no foreign key, so what goes in it is a matter of meaning rather than of schema.

    6. Each mint is a bcrypt hash, and nothing bounds how many a login performs¶

    NamespaceKey.new() (shakenfist/namespace_key.py:202) hashes the secret with hash_secret() (shakenfist/namespace_key.py:49) — bcrypt at the library default cost — and then writes a static row, an attributes row, two state transitions and the audit events the caller adds. FEDERATION_RATE_LIMIT_PER_MINUTE defaults to 60 (shakenfist/config.py:612) and is counted per source address, so one address may make sixty login attempts a minute. Multiplied by the number of rules a single identity happens to match, with no cap, that is an unbounded amount of deliberately slow work reachable by anybody holding one valid identity token.

    7. The two existing predicates for "which issuers count" disagree¶

    GET /auth/login lists issuers in TrustedIssuer.ACTIVE_STATES, which is {STATE_INITIAL, STATE_CREATED} (shakenfist/trusted_issuer.py:62), and narrows further to issuers that are login capable: a client_id, plus at least one of authorization_endpoint and device_authorization_endpoint.

    issuer_claiming_url() (shakenfist/federation.py:247), which is what issuer_for_token() resolves through, accepts any issuer whose state is not STATE_DELETED.

    Corrected during execution of step 4c. This finding first said the two sets differ for an issuer in STATE_ERROR or STATE_DELETE_WAIT. Neither state exists for a trusted issuer: state_targets (shakenfist/trusted_issuer.py:67) admits only None -> initial, initial -> {created, deleted} and created -> deleted, because configuring an issuer is atomic and so its state machine has no error state and nothing between created and deleted. The two sets really differ in two places. An issuer whose static row was written but whose state write did not land reads as a state of None, which is not STATE_DELETED, so it resolves through the exchange's predicate while the listing's ACTIVE_STATES test excludes it. And they differ for every issuer configured for workloads only, which is every issuer in existence today.

    So a token from an issuer GET /auth/login does not advertise would otherwise resolve and validate on the login path. Changing issuer_claiming_url() would change the workload exchange, which is out of scope; the login endpoint has to apply the narrower predicate itself, and the two predicates then have to be expressed once rather than twice.

    8. Minted keys accumulate until two sweeps have run, and this cluster has been bitten by that before¶

    Expiry is enforced at use, so a lapsed key stops authenticating immediately. Removal is slower: reap_expired_namespace_keys() soft deletes a key only NAMESPACE_KEY_REAP_GRACE after it expired, and per_deleted_object_checks hard deletes it CLEANER_DELAY after that. A person who logs in repeatedly across five namespaces leaves five keys per login for the whole of that window, and issue 3814's history is what happens when namespace keys accumulate: the sweep's cost grew with the backlog rather than with the work.

    This is not a reason to make a re-login rotate rather than mint (decision D8 explains why it must not), but it is a number the operator documentation should give honestly.

    Decisions¶

    D1. The endpoint is POST /auth/login, beside the GET that advertises it. The two halves are one surface: a client reads the GET to learn which providers it may start a flow at, and posts the resulting token to the same path. The alternative — making namespace and rule optional on POST /auth/federated — would give one endpoint two authorisation shapes, targeted and set-wide, chosen by the absence of a field. That is the kind of distinction a later edit loses. Registering a second method on the existing resource also inherits handles_credentials() redaction (finding 2) and the /auth/ swagger family without further argument.

    D2. The login path verifies aud against the issuer's client_id, and federation.validate_token() grows an audience override to do it. Finding 1 is otherwise unanswerable: an operator cannot put both their cluster's API URL and their client identifier in one audience column, and OpenID Connect gives them no choice about what a provider stamps in an identity token.

    The override is a parameter on the existing function, not a second copy of validation. The master plan's review checklist forbids a second copy of JWT validation, JWKS fetching or caching, and it is right to: the algorithm allowlist (shakenfist/federation.py:47), the zero leeway (shakenfist/federation.py:68) and the require list are the security properties, and they must not come to exist twice.

    Consequence, stated so that a reviewer can check it and a test can assert it: a workload token stamped with the cluster's API URL is refused by POST /auth/login, and a human identity token stamped with the client identifier is refused by POST /auth/federated — unless an operator has deliberately set audience and client_id to the same string, which is their business. Two token shapes, two doors.

    The login path does not accept either audience. Accepting both would let a CI workload's token mint the whole entitled set rather than the one credential its rule names, which is a widening nobody asked for and which no test would notice.

    D3. Every rule the identity satisfies mints, including a rule owned by system, and nothing else does. The authorisation decision stays entirely in mapping rules. This phase adds no second policy beside them, no allow list of namespaces a login may mint into, and no special case keyed on a namespace's name.

    The master plan asks that this phase "must mint several single-namespace keys without ever minting one into system as a side effect". Requiring an explicit, claim-matched rule owned by system is what satisfies that: there is no path to a system key that does not go through a rule an administrator wrote in the system namespace, and the operator guide already describes such a rule as "a standing offer of administrative credentials to whoever satisfies its claims".

    This is the decision a reviewer is most likely to argue with, so here is the alternative and why it loses. The alternative is to exclude system from the set-minting login entirely, so that an administrator who wants a cluster-admin credential must call the targeted exchange naming system and its rule. It has a real argument: phase 0 refused multi-namespace credentials partly because a credential naming system alongside a tenant namespace would satisfy caller_is_admin on every request, and a set containing a system key puts an administrative credential in the client's cache for the whole of its TTL, where a client bug that picks the wrong member escalates.

    It loses on three counts. It would make the one endpoint humans use the one endpoint that silently ignores a rule the operator wrote, which is a worse failure than the one it prevents — the operator sees their rule listed, matching, and doing nothing. It does not actually remove the credential from the client's cache, because the targeted exchange is still there and phase 7 will use it. And it puts a namespace name in the authorisation path, which is exactly the coupling phase 0's answer to open question 5 was pleased to avoid.

    What the phase does instead is make the mint loud rather than forbidden: a system mint gets its own audit event wording, and the operator documentation says in terms that a mapping rule in system turns a group membership at the identity provider into cluster administration.

    D4. The token is claimed once for the whole login, keyed on the issuer rather than on a rule. Finding 5 is the reason: per-rule claiming makes a retry after a partial failure return a silently short set, which is the worst available outcome because the client cannot tell. One claim, taken before any key is minted, makes a retry a clean refusal the person can act on — ask the provider for another token.

    The claim goes in the existing table with the issuer's uuid in the rule_uuid column, and that column's docstring is extended to say that its second component is "what the token was spent on": a mapping rule for a targeted exchange, an issuer for a login. No migration, and no new table for one more meaning of the same claim.

    A consequence worth writing down: minting is not transactional, so a failure part way through leaves the person with a partial set and a spent token. That is the same trade POST /auth/federated already makes and documents — "the right way round to be wrong", because the alternative is a window in which one token mints twice — and the fix is the same: ask the provider for another token.

    D5. A login that matches no rule is refused with 401 and the same terse category as every other refusal. Not a 200 carrying an empty list. A client that received 200 [] would have to treat a successful login with no credentials as a distinct state, and the honest reading of it — "you are authenticated and entitled to nothing" — is not distinguishable by the client from "this cluster has not finished being configured".

    401 rather than 403 for consistency with the exchange, which answers 401 to every refusal including a claim mismatch, and because a different code for "token good, no entitlements" would turn the endpoint into an oracle for whether a given identity matches any rule at all.

    D6. The size of the minted set is capped by configuration, and exceeding the cap refuses the whole login. Finding 6 is the reason for a cap; the refusal rather than a truncation is because a truncated credential set is one the person cannot tell is incomplete, and they would discover it as a permission denied in whichever namespace fell off the end.

    FEDERATION_MAX_LOGIN_CREDENTIALS, defaulting to 16. The number is chosen against the only evidence there is: phase 0 step 0c found the CI conductor holding eight keys, in eight namespaces, which is the largest real credential set anybody has. Sixteen is twice that and still bounds the work a single valid token can command at sixteen bcrypt hashes.

    The refusal is 507. The request is well formed, the token is good, and the caller can do nothing about the answer; what is wrong is that the cluster's rules and its cap disagree. It is not transient, so 503 would be a lie, and it is not the caller's input, so the 400 family misdescribes it.

    This plan first chose 409 and the back brief asked about it. The answer came from this API's own documented taxonomy, which the planning survey had not read: the comment above CLAIM_REFUSAL_STATUS (shakenfist/external_api/auth.py:1937) reserves 409 for a request that "conflicts with the durable state of a resource", where "the caller has to change something ... before it can succeed", and gives 507 to capacity exhaustion, where "no change to the request will help until something is released". A person who matches more rules than the cap allows cannot change anything, which makes 409 a misdescription by this repository's own rule and 507 the code its neighbours already use for instance scheduling and address exhaustion. The refusal is logged with the counts and the setting name, and the response names neither.

    D7. The rule set is read in two queries, not two per rule. Add a joined accessor filtered by issuer in SQL, mirroring find_namespace_keys(), plus one get_objects_by_state() call to drop rules that are not in an actionable state, mirroring reap_expired_namespace_keys(). Both precedents exist because the per-object version was measured and found wanting (finding 3).

    None from get_objects_by_state() refuses the login. Finding 4 explains why the alternative is an authorisation bypass rather than a performance regression.

    D8. A key's name carries a random discriminator, exactly as the exchange's does, and never the person's identity. NamespaceKey.new() rotates an existing key of the same name — new hash, new nonce, same uuid — so a deterministic name derived from the subject would mean that logging in on a laptop invalidates the credential a session on a workstation is still using. The random discriminator is what makes a second login additive.

    The person is identified in provenance, where the exchange already puts sub, jti and the satisfied claims, and not in the key's name, which is visible to everyone who can list the namespace's keys. provenance['source'] is 'login' rather than 'federated', so an operator can tell a human's credential from a workload's without reading the rest of it.

    D9. The login budget is its own, keyed login-mint:<source>. Phase 3 separated the metadata endpoint's budget from the exchange's, and gave the reason: the two cost very different amounts and a shared counter means a burst of one throttles the other. A login mint is the most expensive of the three — a JWKS fetch and up to sixteen bcrypt hashes — so it gets the third budget rather than sharing the metadata endpoint's. The prefix is eleven characters, which leaves the 64 character column room for the longest IPv6 address.

    D10. The response carries each credential's expiry and scopes alongside its secret. Phase 7 cannot write a credential cache without knowing when each member expires, and the endpoint that serves a key's metadata as a read is phase 6, which is not built. Returning them here costs nothing and discloses nothing: the caller has just been handed the secret those two facts describe. The alternative — phase 7 inferring expiry from the rule's key_ttl, which it cannot see — is how a cache comes to outlive the credential it holds.

    D11. A refusal is evented where there is an owner to tell, and logged where there is not. The same rule _federated_refusal() (shakenfist/external_api/auth.py:2379) already applies, for the same reason: /auth/login is unauthenticated, and eventing an anonymous caller's refusals into a namespace's audit log would hand them a way to write unbounded rows there. A login has no single owning rule, so an untrusted issuer, a rejected token or a cap refusal is logged only. A per-rule claim mismatch is not evented either, because a login evaluates every rule and a person entitled to one namespace would otherwise write a near-miss event into every other namespace on the cluster on every login.

    That last one is a deliberate loss of signal and is worth being explicit about: the probing a namespace owner would want to see is visible on the targeted exchange, which is where a caller naming their rule is doing something a stranger would not.

    Risks and mitigations¶

    Risk Mitigation
    An operator configures human login, follows the operator guide for audience, and every login fails with a deliberately uninformative 401. D2 makes it impossible by validating against client_id. 4e's operator paragraph covers the operator who already has an issuer configured. The management session checks 4c's test that a token stamped with the issuer's audience is refused — that test is the one that proves which value is in force.
    A mapping rule in system quietly becomes a cluster-administration grant to anyone in a group. Not prevented, by decision: D3 argues the alternative is worse. Made legible instead — distinct audit wording on the key and the namespace, and an operator-guide paragraph that says it in terms. The management session checks both exist and that a cluster with no system rule never mints into system.
    A soft-deleted rule mints, because the state filter was dropped or because get_objects_by_state() failed and the failure was read as an empty answer. 4a's accessor docstring states that it does not filter state and that callers must. 4c tests both the filter and the None case. 4d mutates both and records which test kills each.
    One valid identity token commands an unbounded amount of bcrypt work. D6's cap, D9's own rate-limit budget, and a test that exceeding the cap mints nothing. The cap's default is argued from phase 0's measurement rather than chosen.
    A retried login returns a short set the client cannot tell is short. D4's single claim for the whole login, taken before any mint. 4d mutates the claim to after the first mint and requires a test to catch it.
    Keys accumulate and feed the sweep cost issue 3814 described. Not fixed here — D8 explains why a re-login must be additive. Documented honestly in 4e with both grace periods named, so an operator sizing a cluster can see it. Worth a Future work entry in the master plan if 4c's review finds the window longer than this plan assumes.

    Back brief¶

    Three things need Michael's answer before 4c runs, and one before 4a does. The first is the one that matters.

    1. D3: does a matching mapping rule in system mint at login? The plan says yes, on the argument that the alternative makes the one endpoint humans use the one that ignores a rule the operator wrote. The alternative — exclude system from the set and require a targeted exchange for an administrative credential — is a defensible reading of the master plan's "never minting one into system as a side effect", and it is cheap to build either way. Expensive to change afterwards, because it is a documented authorisation property by the time 4e has run.
    2. D6: is 409 the right refusal for exceeding the cap, and is 16 the right default? The code is a judgement call between a wrong family and a lie; the default is argued from a sample of one.
    3. D5: 401 for a token that matches no rule, or something a client can distinguish? The plan chooses consistency with the exchange and non-disclosure over a client's ability to tell "nothing for you" from "bad token". A person seeing "login refused" when their administrator has simply not written their rule yet is the cost.
    4. 4a's proto change touches generated stubs. Phase 3 hit a generated-descriptor conflict on develop and resolved it by regenerating. If another phase is adding a gRPC method right now, 4a should be sequenced against it rather than discovered in a rebase.
