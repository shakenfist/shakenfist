    Placeable capacity phase 1: extract the shared set-placement core¶

    Prompt¶

    Before responding to questions or discussion points in this document, explore the shakenfist codebase thoroughly and ground your answers in what the code actually does today. Do not speculate when you could read instead. Flag uncertainty explicitly.

    This is phase 1 of PLAN-placeable-capacity.md. Read that master plan's "Phase 1: extract the shared set-placement core" section first, and phase 0's D13 and D15 (PLAN-placeable-capacity-phase-00-decisions.md), which constrain what this phase may assume. This phase changes production code on the instance create path and the start-redirect path, and promises no behaviour change on either.

    Citations below are into develop at 90d164035d unless stated otherwise.

    Planning effort¶

    High, as the master plan specifies: this is a behaviour-preserving refactor of a correctness-critical path, and the generalisation it performs is the thing both later primitives are built on, so a wrong abstraction here is paid for twice. The review effort is high for the same reason.

    Scope¶

    In:

    • A shape value type, so placement can be evaluated for a requested shape rather than only for an Instance row.
    • Converting the scheduler's filter, affinity and ranking stages to read that shape.
    • One all-or-nothing multiset entry point that walks several shapes through those stages, each shape's tentative charge visible to the next.
    • Routing both existing production callers through it at one shape, with no behaviour change: same candidate ordering distribution, same exceptions, same audit events.
    • Unit tests for the multiset path, and mutation testing to prove they would catch its removal.

    Out:

    • Any API, capability string, client method or schema change. The dry run (C) is phase 2; holds (A) are phases 3 and 4.
    • Any production caller at more than one shape. There is none until phase 2.
    • Gang create (B). Out of scope for the whole plan.
    • Changing what any filter decides, what any stage is called, or what any event contains. This phase moves where the arithmetic lives, not what it concludes.
    • The claim guard. find_candidates() is claim-blind today — the claim is enforced in admit_instance_placement() — and stays claim-blind here.

    What the survey found¶

    The master plan's phase 1 section was written on 2026-11-04. Its central factual claim has since been falsified by another plan, and the correction materially changes what this phase is.

    F1. The duplicated placement walk is already gone. The master plan says POST /instances and preflight "run two placement walks that must change together". They did when it was written. They do not now: scheduler-reservations phase 5 extracted the walk as Instance.place_on_candidates() (shakenfist/instance.py:1549) in commit 036f255758 on 2026-11-05 — one day after this master plan was written — and routed both callers through it (shakenfist/external_api/ instance.py:1235, shakenfist/operations/ node_inst_netdesc_op.py:270). The comment the master plan quotes no longer exists in the tree; grep -rn 'must change together' shakenfist/ returns nothing. The sharing is documented, too: docs/operator_guide/scheduler.md:363-366 already states that "there is a single shared placement walk (Instance.place_on_candidates()) that both the create path and the start-redirect operation use". That commit deliberately left each caller its own candidate construction and its own after-handling (an HTTP response here, an operation redirect there), which is the right split and is not changed here.

    This phase is therefore not the de-duplication the master plan describes. What is left is the part that was always the point: the placement pipeline evaluates one Instance, and both C and A need it to evaluate a multiset of requested shapes. The master plan's phase 1 section has been corrected at source as part of this phase's planning commit, so a later reader does not plan against the stale sentence.

    F2. The pipeline is Instance-bound end to end. Scheduler.find_candidates(inst, candidates=None) (shakenfist/scheduler.py:914) reads exactly six things from the instance: inst.cpus, inst.memory, inst.disk_spec, inst.affinity, inst.namespace (inside _affinity_neighbour_skip(), :193) and inst.uuid (the same function's self-skip, and every audit event's subject). It also wraps the whole decision in inst.attribute_memo() (:930) so the nine attribute reads cost one row fetch, and reaches instance.placement_filter(node, inst) in the CPU and RAM filters (:729, :814) to avoid charging a reschedule twice. Nothing else about the instance is used. That is a short enough list to replace with a value type.

    F2a, found while executing step 1a. F2 enumerated what find_candidates() reads from the instance but not who else calls the predicates it reads them in. Five helpers in shakenfist/tests/test_scheduler.py call them directly with a real Instance: HasSufficientCPUPredicateTestCase._call (:2446), CpuCeilingAgreementTestCase._admits (:2607), HasSufficientRAMPredicateTestCase._call (:2699), HasSufficientDiskPredicateTestCase._call (:2834) and HasIdleDiskBandwidthPredicateTestCase._call (:2881). Twelve tests across three of them fail on the converted signature; the other two pass by accident rather than by design — _admits because its fixture sets used_cpus=0, which short-circuits the placed_on comparison, and the bandwidth helper because that predicate never reads its shape argument at all. D8 has been amended to say what this means.

    F3. The filters that would need to see a tentative charge read five different figures across two ledgers. For a multiset this matters more than it looks: charge only the committed ledger and ten shapes all pass the measured checks against one snapshot, which is issue 3636's failure mode one level up. The five, with the filter that reads each:

    Figure Source Read by
    used_cpus capacity row _has_sufficient_cpu (:684)
    cpu_total_instance_vcpus metrics same filter, max() of the two
    memory_available metrics _has_sufficient_ram live check (:753)
    memory_total_instance_actual metrics same filter, KSM ceiling
    used_memory_mb capacity row same filter, committed ledger
    disk_free_instances metrics, in bytes _has_sufficient_disk (:829)

    _has_reasonable_queue_state() (:602) and _has_idle_disk_bandwidth() (:857) are load shedding rather than capacity — they say a node is momentarily busy, not that it cannot host the shape — so there is nothing for a tentative charge to debit in either. The capacity rows arrive as a dict of row dicts from _capacity_by_node() (:288), read fresh on every decision, with a degraded flag that must keep its present meaning: an absent row means an unguarded node that must not be refused on a ledger which does not exist (P7).

    F4. There is no shape abstraction to reuse, and the house idiom for one is clear. grep for a placement shape type finds nothing. Value types in this codebase are NamedTuple (shakenfist/mariadb.py carries seven, including SchedulerNodeCapacityRead at :27859) or @dataclass(frozen=True) (shakenfist/resource_health.py:45). The import direction is also settled: scheduler.py imports instance (:13) and instance.py imports no scheduler, so a shape type in scheduler.py creates no cycle.

    F5. The candidate ordering ends in a weighted random shuffle, so "no behaviour change" cannot mean reproducible output. find_candidates() returns every surviving candidate ordered best bucket first, and within a bucket shuffled by Efraimidis–Spirakis A-Res weighted sampling (scheduler.py:1362-1368). Two calls with identical inputs legitimately differ. Behaviour preservation is therefore a claim about the candidate set, the bucket tiers, the exceptions and the events — not about list order.

    F6. The event stream is a documented diagnostic interface. find_candidates() emits ten add_event_multi() calls directly plus one or two per stage from _log_and_raise_on_error() (:876, called at nine stages), and docs/operator_guide/scheduler.md:1086-1092 tells an operator to pick the create-path pass by looking for the schedule inputs event whose forced_candidates is false, then read that pass's schedule have highest affinity. A refactor that reshapes or re-subjects those events breaks a written procedure.

    F7. Preflight already uses the pipeline as a fit test and throws the answer away. node_inst_netdesc_op.py:193 calls s.find_candidates(inst, candidates=[config.NODE_UUID]) purely for its exception, returning None on success. That is a dry run against one node by another name, and it is the one existing caller whose shape the new core most directly serves.

    F8. An in-flight sibling phase edits the same create-path hunks. scheduler-reservations phase 5a (In progress, planned in the shakenfist-wt-sched-p05a worktree, not yet implemented) will edit shakenfist/external_api/instance.py:1261-1277, the branch where the walk has exhausted its candidates, to publish 403 for an all-claim refusal. That is within a few lines of the create path this phase touches. Neither change needs the other; they conflict textually if both are open at once.

    Nothing else in the master plan's phase 1 section was wrong. The section's "all or nothing", "each shape's tentative charge visible to the next" and "existing single-instance callers routed through it" all describe work that still needs doing, and GET /admin/resources, API_CAPABILITIES and the client surface are correctly phase 2's.

    Decisions¶

    Numbered D1 onward; these are this phase's own numbers. Master plan and phase 0 decisions are cited as such.

    D1. The core is denominated in a shape, not in an in-memory Instance. Add a frozen value type — PlacementShape, a NamedTuple in shakenfist/scheduler.py per F4 — carrying cpus, memory_mb, disk_gb, affinity, namespace, instance_uuid (optional, for the affinity self-skip) and placed_on (optional, for the reschedule charge). One factory, from_instance(), is the only place that reads an Instance.

    The rejected alternative is tempting and cheap: baseobject.py supports in_memory_only=True objects, so each shape could be a throwaway Instance and find_candidates() would not change at all. It is rejected on three grounds. add_event_multi() suppresses in-memory-only objects, so a dry run built this way would silently emit no events while the create path emits twenty — two different code paths for the same decision, with F6's documented procedure true of only one. Minting an instance uuid per speculative evaluation is the shape of the leak the baseobject.py:195-201 comment records as issue 3532. And a hold in phase 3 is a row, not an instance, so the fake would have to be built out of a shape anyway; the shape is the real abstraction and the Instance is the special case.

    D2. Every figure a filter reads is charged tentatively, both ledgers and the measurements. All six rows of F3's table, in their own units — disk_free_instances is bytes, so its debit is disk_gb * GiB. The overlay is a copy taken for the duration of one multiset decision and discarded with it; neither the metrics snapshot nor the capacity rows are mutated in place, because the Scheduler instance outlives the call and other decisions read the same dicts. A node with no capacity row stays uncharged and unguarded on the ledger terms, exactly as P7 requires, and is still charged on the measured terms.

    D3. The core ranks with the existing ranker, unchanged, and does not pack. Each shape is placed on the head of its own freshly ranked candidate list, with the charges from earlier shapes applied. The ranker deliberately spreads allocation away from the most committed nodes (scheduler.py:1310, shakenfist

    3937), which phase 0's D15 records as correct and as the reason¶

    aggregate headroom fragments. A dry run that packed instead would answer "fits" for an assignment the real scheduler would never choose, which is the one thing a dry run must not do.

    D4. Shapes are walked largest-first, and a negative answer is a lower bound rather than a proof. Order by memory, then vCPUs, then disk, descending — first-fit-decreasing. Greedy assignment can fail where some other assignment would have succeeded; this phase states that rather than implying optimality. It costs nothing for C, which the master plan already makes advisory by construction, and phase 3 inherits the statement to reason about for A, where a false refusal refuses a claim the cluster could have met. Exact search is rejected: it is NP-hard in the general case, and more to the point the real scheduler is greedy too, so an exact answer would describe a placement that would never happen.

    This is the decision most likely to be argued with, and the argument against it is real: for A a wrong "no" is a refused claim, and "advisory by construction" is phase 2's licence, not phase 3's. The answer is that a greedy core which matches the scheduler is honest about the cluster, where an exact core would be accurate about a cluster we do not run; and that the remedy if phase 2's shadow counts show greedy refusing real-world sets is to reorder shapes, not to search, which this decision leaves open.

    D5. Events are addressed by an explicit target list, and a core given no targets emits none. The instance path passes exactly today's related_objects — the instance plus each forced candidate node — so every event in F6 keeps its subject, name, order and payload. Phase 2's dry run will pass no targets and write nothing, which is also what keeps a speculative query out of the event log and off the database-load budget that PLAN-database-load-reduction spent eight phases recovering.

    D6. Affinity does not see tentative set-mates in this phase. Capacity is charged across the set; affinity is not, because the hard filter (:623) and the scorer both read placed Instance objects through _placed_instances() (:666) and a shape has no row to be a neighbour of. The core's docstring says so. Synthesising neighbour records now is rejected: it would fork _affinity_neighbour_skip()'s predicate, which docs/developer_guide/coding_rules.md:7 ("Never restate a visibility predicate") exists to prevent, and no caller is known to need it yet. Phase 2's shadow scoring is where we find out whether one does — the eight-instance kerbside-patches topology is the candidate — and this is recorded in the master plan's Future work rather than left in a plan nobody re-reads.

    D7. find_candidates(inst, candidates=None) keeps its name and signature. The multiset entry point is added beside it, and find_candidates() becomes the one-shape wrapper: it builds the shape, enters inst.attribute_memo() (so the database-load win at :930 is not lost — the memo belongs to the instance, not to the core), and calls the core with today's event targets. Both production callers are unchanged at their call sites. The fake at shakenfist/tests/test_external_api.py:35 also keeps working.

    D8. Behaviour preservation is proved in two different ways, because F5 rules out the obvious one. At step 1a the entire existing test suite passes, and the only edit permitted to a test file is the construction of the argument passed to a converted predicate — one line per helper, as F2a names them. No assertion, no expected value, no test name and no fixture may change, and any other test edit in that step's diff is a behaviour change until argued otherwise. At step 1b, the new multiset tests assert candidate sets, bucket tiers, exception types and stages, and event sequences; never list order.

    Amended during execution. This decision first read that no test file may change at all, which F2a showed to be unachievable: converting a private predicate's parameter changes the type its direct callers must pass, and five of those callers are test helpers. The rule's purpose survives the amendment — a test edit still signals a behaviour change — because the amendment admits only argument construction, which carries no assertion. Reverting to the original rule would have meant leaving the predicates Instance-bound, which is the phase.

    D9. The multiset path carries production traffic from the first commit. Both callers route through it at one shape rather than the core sitting dormant behind a phase-2 caller. A generalisation that only ever runs at n=1 in production until phase 2 would have its interesting case first exercised by a new API; this way the walk, the overlay and the all-or-nothing unwind are on the create path from the day they land, at the arity where their behaviour is already known.

    Review round 3 (2026-11-07, AEDT) raised no fix and no document items — seven consider and three informational — which is the exit condition, and one of the seven was taken anyway. PlacementSnapshot.charge() applied no reschedule self-charge exemption, where both capacity filters do: a shape carrying placed_on == X assigned to X had its figures added on top of a row which already counted them, so every later shape in the set saw X as fuller than it was. Not reachable in production — one shape per call, and the last shape's charge is discarded with the snapshot — and pessimistic rather than over-placing when it becomes reachable, which is why it was not a fix. It was still a latent defect in this phase's own new code and a three-line fix, so it was taken rather than carried into phase 2.

    The fix is wider than the review suggested. The review proposed exempting the committed account, mirroring the filters. The exemption here covers both accounts: a reschedule which lands an instance back where it started changes nothing about that node at all, on the ledger because place_instance() early-outs on an unchanged placement, and on the measurement because it counted the instance before the decision and counts it after. The filters exempt only the committed account, and that asymmetry is theirs and predates the snapshot; a phase which promises behaviour preservation is the wrong place to change it. The narrower fix was run as a mutation to prove the tests tell the two apart.

    The invariant AGENTS.md and the developer guide gained in round 2 stated only its forward half — a figure a filter reads must be debited. Both now carry the mirror: an exemption a filter applies must be applied to the charge.

    The other six consider items were declined. Two were re-raises of items already handled in rounds 1 and 2 (the per-shape schedule inputs comment, which exists, and the event-payload construction, which is recorded in the master plan's phase 2 section). One was about the parameter this round's predecessor added, which is the point at which a review is reviewing its own earlier advice. The two test gaps — hard affinity and the degraded capacity read, neither exercised by a multiset test — are both exercised through the new core by the existing single-shape tests, because find_candidates() is now a caller of find_candidates_for_shapes(): every one of those tests runs the multiset path at n=1. And restating instance.placement_filter() as shape.placed_on == node is the conversion this phase exists to make, not duplication to remove.

    One repository-level flake, unrelated to this phase. The Test the internal_ca role pre-commit hook fails on the first --all-files run in a fresh worktree, reporting "files were modified by this hook" while its own output says all nine of its cases passed, and passes on every run after that. It left nothing dirty in the tree on any occasion. Seen twice, in this worktree and in phase 0's. It is not this plan's to fix and no issue has been filed yet.
