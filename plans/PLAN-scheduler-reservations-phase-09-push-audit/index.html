    PLAN: Atomic scheduling via reservations phase 9 -- push audit¶

    Why this phase exists¶

    PLAN-scheduler-reservations.md ends, as every master plan must, with a phase that runs the repository's PUSH-AUDIT.md over the whole plan's work. This plan is the largest the repository has run it on: eighteen phases across four months, thirty-one merge commits here and two more in client-python, and roughly 35,000 non-plan insertions.

    The master plan says why the per-phase audits are not enough, and the reason is concrete rather than theoretical. Phase 4 shipped the namespace claims API without adding auth: namespace-claims to the API's capability list, so no client could feature-detect claims. That was found by a passing question at phase 4's close-out, not by phase 4's own review, and nothing in a per-phase audit would have caught it: the gap was only visible from the whole, by asking what the plan had promised a client and whether the server had advertised it. That defect is the reason this phase exists, and finding its siblings is what the phase is for.

    Recommended planning effort: medium (done). The judgment lenses run at the efforts given in the step table. Two are at high: the security lens, because the range adds an admission path that refuses creates and an admin CRUD surface over it, and the cross-phase lens, because it is the lens this phase exists to run and the one no earlier audit could have.

    Scope¶

    In scope:

    • PUSH-AUDIT.md wave 1 and its wave 2 mechanical sweep over the twenty-one code-bearing ranges of D1.
    • The style-conformance judgment portion, and the four wave 2 judgment lenses -- 2a code quality, 2b test review, 2c documentation, 2d security -- over the groups D6 fixes.
    • The cross-phase lens: what the phases did to each other, and what is missing that is only visible from the whole. This is the phase's reason for existing and it is its own step.
    • The master plan's specific instruction to re-check every code identifier cited by the developer guide's Guarded counters for finite resources section against shakenfist/mariadb.py (D10).
    • client-python 135ab53042 (client-python#375), phase 4b's client half, audited from here (D5).
    • Closing out phase 5b's Merged cell and its outstanding definition-of -done item 17 (F2), as this phase's first commit.
    • Recording the findings, their grades and their disposition in this file, and closing out this phase and the plan.

    Out of scope:

    • Fixing anything the audit finds. The master plan says findings land as their own pull request, and that is what a blocking finding gets. This pull request carries the phase 5b close-out, this plan, and the audit record. D7 says how the two relate.
    • Re-running client-python d484fdc (client-python#442), phase 7b. It applied the floor checklist in its own pull request and that result is cited, per the plan-push-audit-phase shared block (F8).
    • Re-reviewing this plan's own phase plan files as documentation. The plan files are the audit's input, not its subject; the ten plan-file-only ranges of D2 get floor item 1 and nothing more.
    • Any work belonging to PLAN-placeable-capacity.md, which has landed 1,900 lines in shakenfist/mariadb.py across this plan's code since phase 3. Its ranges are not in D1 and a finding against them is filed, not fixed.
    • The deferred designs this plan declined: batch create (D8 in the master plan), and a server-side placement queue, which PLAN-transient-capacity-refusals.md owns.

    What the survey found¶

    Twelve findings. Four change what the audit does, and one is a premise of the master plan's phase 9 section that is now wrong.

    F1 -- the master plan's audit range is superseded, and by a rule written after it. The phase 9 section says to rewrite every develop...HEAD in PUSH-AUDIT.md to ea3c9bf63..develop, restricted to a pinned path list. That text was written on 2026-08-25 (9ddab70a05). On 2026-09-13 PUSH-AUDIT.md gained a What $RANGE means section (f445a9d31e, "Teach the audit runbook to read the Merged column") which rules the union approach out in terms: "Run the whole audit once per range and pool the findings; a plan with four merges gets four passes, not one pass over a union that git cannot express." The plan-push-audit-phase shared block agrees. D1 follows the runbook and this phase corrects the master plan at source. The path list the master plan asks for becomes unnecessary with it: each range is a pull request from this plan's own branches, so nothing in it is unrelated work and there is nothing to filter out. One confirmation that the two anchors at least agree: ea3c9bf63 and 87a58a81e^1 both resolve to ea3c9bf632bd18e6820ade80b3eef5eb1dd1327e, so the master plan's arithmetic was right even though its method is superseded.

    F2 -- phase 5b's Merged cell is blank, and PUSH-AUDIT.md says a blank cell stops the audit. The runbook's range rule ends: "If a plan's Merged column is missing or a cell is blank, stop and say so -- that is an unauditable plan." Phase 5b reads Complete with —, because a phase cannot record the merge commit of its own pull request; its own Future work says so and owes the cell to this phase. It is 31f3350c1c (#5087), merged 2026-11-26 19:53 UTC, and this phase's first commit fills it. The same commit can close something else 5b left open: its definition-of-done item 17 was recorded as not run because the cluster CI test runs only in the merge queue, and the merge queue has since run it.     F10 -- client-python still has no PUSH-AUDIT.md. Confirmed by ls.     F11 -- the capability string this phase exists for was fixed, which narrows the cross-phase lens rather than closing it. The API advertises auth: namespace-claims as of the phase 4a close-out, and phase 7a added three more tokens. So the specific defect is gone. The question the lens asks is the general one: what else did a phase promise that a later phase was supposed to publish, and did it?     F12 -- one range touches .github/workflows/functional-tests.yml, which is the only unattended thing the plan added. That is floor item 2's subject, and it matters for a reason F2 names: the functional_lanes job is excluded on pull_request and runs only on merge_group or workflow_dispatch, which is what made phase 5b's item 17 unsatisfiable from its own pull request. Whether a cluster test this plan added can fail without anyone seeing it is a real audit question, not a formality.

    Nothing else the master plan's phase 9 section claims was found wrong. The three orphan defect fixes it names (49e98a67c8 #3722, 45332ff810 #3918, a5c6216339 #3937) all resolve, are merge commits, and carry code; they are rows in D1.

    The disagreement, and how it was resolved¶

    Two lenses reached opposite verdicts on the same site, which is worth recording in full because the site still looks wrong to a careful reader.
