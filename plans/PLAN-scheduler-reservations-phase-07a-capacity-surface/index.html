    Scheduler reservations phase 7a: an operator-readable capacity surface¶

    Prompt¶

    This is a phase plan under PLAN-scheduler-reservations.md. The master plan's Prompt section applies unchanged. D-numbers are the phase 0 decisions in PLAN-scheduler-reservations-phase-00-decisions.md, P-numbers are phase 3's in PLAN-scheduler-reservations-phase-03-primitive.md, and G-numbers are phase 7's in PLAN-scheduler-reservations-phase-07-diagnostics.md. Phase 7b's plan lives in shakenfist/client-python as docs/plans/PLAN-scheduler-reservations-phase-07b-client-views.md and numbers its decisions D1..D8, which collide with phase 0's; where this plan cites one it says "7b's D4". This phase's own decisions are numbered H1..H9.

    Planning effort: high. The code is small, but it adds a gRPC RPC, changes a request message, touches the scheduler's metrics loader that find_candidates() also reads, and lands across two repositories in an order that matters. Review effort: medium. Every step is independently falsifiable, and only step 3 can change behaviour that is not new.

    Situation¶

    The master plan's survey table (under Phase scope stubs, "Phases 7a and 7b were added on 2026-10-20") lists what this plan publishes and where an operator can read it. Apart from the per-node ledger, which has a client verb and 7b is giving a command, the answers are "nowhere" or "curl only". 7a is the server half: it makes the cluster claims ledger, every claim in the cluster, and the reasons a hypervisor is missing from /admin/resources readable over REST, and then gives each of them an sf-client reader.

    Mission and problem statement¶

    An operator should be able to answer three questions without curl or a database shell:

    1. How much of the cluster is promised to claims, how much is used by unclaimed namespaces, and how much is left for either? This is the singleton both capacity guards refuse against.
    2. Which claims exist across the whole cluster, and which of them still cover placements?
    3. Why is this hypervisor missing from the capacity view?

    Each answer has to come from the counters the guards actually use, not from a second ledger derived beside them.

    Scope¶

    In scope:

    • A read of the cluster_capacity singleton, published in /admin/resources.
    • An admin-only, cross-namespace claim listing, with its coverage_state filter applied in SQL.
    • The reason each active node is missing from per_node, published beside it.
    • Capability tokens for all three, and a real admin_resources_get_example.
    • Unit, live-MariaDB and functional coverage.
    • The apiclient verb and sf-client readers in client-python (7b's D7).
    • API reference and operator guide documentation.

    Out of scope, each for a stated reason:

    • Rewriting /admin/resources as a read over the typed capacity columns. That is phase 5's D11 third call site. This phase adds keys to summarize_resources() and leaves its Scheduler() construction alone (H7).
    • Any change to admission or ranking. No guard, filter stage or ranking term moves. Step 3 touches the metrics loader that find_candidates() reads, and the Definition of done pins that its candidate behaviour is unchanged.
    • The N+1 in the per-namespace claims listing, beyond the shared render path. H5 fixes it for both listings, because they share one render function. A general audit of external_view() re-reads is not this phase's.
    • Teaching CI's sizing tooling to read the exclusion reasons. shakenfist_ci/sizing.py and retries.py would benefit. The benefit is real but optional, and it is recorded under Future work.
    • A release. Phase 8 cuts one covering phases 4b to 7b (4b's D7).

    What the survey found¶

    Surveyed against shakenfist 9efbff1481 and client-python fdcfe6e (both develop, 2026-10-25). The 7a stub was written on 2026-10-20 from shakenfist ebc0f9772b. The corrections below have been applied at source, in the master plan's 7a and phase 5 stubs and in phase 7's Future work, as part of this planning commit. A later step does not need to redo them.

    1. There is no "read the claim guard makes". The stub says the singleton should be "published from the same read the claim guard makes". Both guards on the singleton are guarded UPDATEs. Neither reads it:
    2. the unclaimed-placement guard at mariadb.py:27577-27586 is unclaimed_used + x <= total - claimed;
    3. the claim guard, _claim_capacity_guard() at mariadb.py:28440, is claimed + limit + GREATEST(0, unclaimed_used - migrated) <= total.

    The only reads of the row are post-rollback diagnostics: the cluster stage of _admission_denial_dimensions() at mariadb.py:27287-27300, and _cluster_capacity_dimensions() at :28633. The other reader is the reconciler's own reply, whose ClusterCapacity message is at database.proto:2775 and is decoded at mariadb.py:26300-26311. No RPC reads the singleton on demand, so this phase adds one.

    What the stub meant is still achievable, and it is simpler than it looked. Both guards test against the same quantity, total - claimed - unclaimed_used. The claim guard's migration term only ever adds to the headroom of the one namespace being migrated. So there is exactly one per-dimension headroom figure to publish, and it can be pinned against both guards (H2). 2. A hypervisor vanishes from per_node in five ways, not one. The stub names only the queue-length exclusion (scheduler.py:1088-1090). The full set: - The node is not active. get_active_node_metrics() iterates Nodes([], prefilter='active') (scheduler.py:51). - Its metrics row is stale (over 120s, :58). - It has no metrics row (:66-71). - Its metrics read raised ReadException (:80-84). The node is then left out of the metrics dict entirely. - Its queue is too long (:1088).

    The stale and empty cases are worse than "dropped without a trace". Both store metrics[node] = {}. summarize_resources() reads is_hypervisor from the metrics dict (:1085), so it skips such a hypervisor as a non-hypervisor. The server itself cannot tell a stale hypervisor from a network node today. Each of the three metrics cases already writes an audit event naming its cause, so the information exists at the point the decision is made. It is just not kept. 3. get_namespace_claims('') lists every claim, and the object layer already uses it as the admin view. NamespaceClaims(namespace=None) calls it with no restriction (namespace_claim.py:450-451). No REST endpoint reaches that path, and it has no coverage_state parameter: GetNamespaceClaimsRequest carries only namespace (database.proto:3107). The filter needs a proto field. In the table the column is state; coverage_state is the name it is published under (namespace_claim.py:375). 4. The claims listing makes N+1 reads. NamespaceClaims iterates rows it has already read. NamespaceClaim.external_view() then calls self._row(), which is mariadb.get_namespace_claim() (namespace_claim.py:251-252), once per claim. A cluster-wide listing is where that is worst. 5. The API reference documents none of /admin/resources. docs/developer_guide/api_reference/admin.md has sections for locks, VDI token public keys and the CA certificate, and nothing for resources. Meanwhile external_api/admin.py:1-6 claims "API reference docs exist: yes ... include examples: yes", and the example body at :103-105 is { ... }. The operator guide covers the fields (docs/operator_guide/scheduler.md:398, :893-904). 6. Phase 5's D11 rewrites the same endpoint. "admin.py's capacity view becomes a read over the typed capacity columns" (phase 0 decisions, D11). Whatever this phase adds to summarize_resources(), phase 5 has to carry through that rewrite. The phase 5 stub now says so, and the functional tests added here pin the keys. 7. 7b is planned, but not pushed. Its plan is on client-python branch scheduler-reservations-phase-07b-client-views at 3db3dab, in worktree client-python-wt-sr-p07b, with no pull request. Step 8 here adds to 7b's node capacity command, so it cannot start until 7b's step 4 has merged. Since that survey, client-python develop has moved from d789e0b to fdcfe6e, so 7b's line references need rechecking when it executes. That is 7b's concern, and it is noted here only because this phase depends on 7b. 8. Two stub line references had drifted. mariadb.py:28175 (the guard) and :29023 (the cluster-wide listing comment) are now :27577 / :28440 and :29296. scheduler.py:1053 and :1089 and admin.py:103 are still accurate. 9. Phase 7's Future work records an undone item that has been done. It says the census collector's LogQL filter in shakenfist/actions stops above the guard, and that "no issue has been filed yet".     Decisions¶

    H1. The singleton goes into /admin/resources as a top-level cluster_capacity key, not onto an endpoint of its own. The stub left this open. The reader that matters is 7b's node capacity, which already fetches /admin/resources, and one fetch means the per-node and cluster ledgers come from the same moment. That is not a transaction, but it is close enough that a reader is not comparing numbers taken minutes apart. The key is named for the table, so a reader can grep from the response to the schema. It is deliberately not folded into the existing total key. total.cpu_available is a sum of per-node headroom, bounded by measurement. cluster_capacity.total_cpus is a sum of node limits. Putting the two side by side under one key is exactly the confusion D2 of 7b refuses to create in a table.

    H2. Publish the singleton's own nine counters, plus one derived headroom per dimension, unallocated_<dim> = total - claimed - unclaimed_used. The stub forbids re-deriving the counters by summing claim rows, and nothing here does: the counters are the row. The headroom is derived, because every reader wants it. If each client computes it, the arithmetic exists in several places, and that is 7b's own first risk (the binding marker drifting from the server). It is computed in one Python function, beside the read, whose docstring names both guard expressions it mirrors. A live-MariaDB test pins it against both guards (DoD). unallocated_* can be negative. Admission cannot drive it below zero, but the reconciler rebuilds claimed_* from the sum of every active claim's limits, whether or not they fit. A negative figure is published as it is, the same as a negative cpu_available.

    H3. Absent and unreadable are two flags, and neither is a zero. cluster_capacity always carries row_present and degraded. If the row is absent (the reconciler has never run, the P7 normal state) or the read failed, all twelve figures are null. That follows cpu_committed_row_present and capacity_degraded, and it is what 7b's D5 (- for a server None) already renders. updated_at is published too. It is the row's last write by admission or by the reconciler, not the last reconcile, and the docs say so.

    H4. The read is bounded, and it swallows failures to degraded, like the per-node read in the same response. It is GetClusterCapacity, with a {} request and a reply carrying ClusterCapacity cluster, bool present, bool degraded and double updated_at, reusing the reconciler's message. The admin endpoint is not a hot path, so it could take the default budget. It does not, for two reasons. The CI headroom probe and the capacity wait poll this endpoint throughout every cluster job. And a response in which one read gives up after 10 seconds while another hangs for the full retry budget is harder to reason about than one in which both degrade the same way.

    H5. The cross-namespace listing is GET /admin/claims, with an optional coverage_state of active or expired, and it renders from the rows it already read. Three alternatives were considered:

    • /auth/namespaces/claims would shadow a namespace named claims.
    • /auth/claims sits in a family whose federation surface already says "claims" for JWT bound_claims. The OIDC plan will make that collision worse.
    • /admin is where cluster-wide, admin-only capacity views already live (/admin/resources), and the operator who reads one reads the other.

    Any other value of coverage_state gets a 400. Neither filter touches object state: a deleted-state claim still holding capacity is listed, for the reason NamespaceClaims.__iter__ gives (namespace_claim.py:459-480).

    NamespaceClaim.external_view() gains an optional row argument. Both this listing and the per-namespace one pass the row the iterator already holds, so listing N claims costs one claims read rather than N+1. The per-namespace endpoint is included because the two share the render path, and fixing one without the other would leave two shapes of the same function.

    H6. Exclusions are published as excluded: {node_uuid: {reason, ...}}, covering active nodes only. The reasons are queue too long (with node_queue_waiting and the threshold, reusing _has_reasonable_queue_state()'s dict at scheduler.py:208-219), stale metrics (with the row's age), no metrics and metrics unreadable.

    Non-active nodes are left out because a client already has their state from get_nodes(), and 7b's view joins against it anyway. Reporting them would cost a second, unfiltered Nodes walk on an endpoint CI polls continuously, to publish something already published.

    The three metrics reasons are reported for any active node, whatever its role. The server cannot know the role of a node whose metrics it could not read, and that is finding 2's point. The client filters on is_hypervisor from get_nodes(). A non-hypervisor with fresh metrics is not a candidate and is not "excluded", so it is not listed.

    The reasons are captured where the decision is already made: get_active_node_metrics() takes an optional dict to record them, and Scheduler.refresh_metrics() keeps it as self.metrics_unavailable. Its return value and the self.metrics shape do not change, so find_candidates()'s input is byte-for-byte what it was.

    H7. This phase extends summarize_resources() and leaves the endpoint's Scheduler() construction to phase 5. Migrating the admin view onto typed-column reads is D11's, and doing half of it here would leave phase 5 with a view half-migrated by someone else. The cost is that phase 5 inherits two more keys to carry. The phase 5 stub now says so, and step 6's functional tests fail if a rewrite drops them.

    H8. One capability token per new surface, in the admin family: cluster-capacity, cluster-resources-excluded and cluster-claims. Splitting them costs nothing, and it follows the comment on namespace-events / namespace-claim-events (app.py:418-425): separate reads are advertised separately. A client meeting a server without a token renders 7b's D5 n/a rather than guessing, which is what issue 4003 says happens otherwise. test_root.py's EXPECTED_CAPABILITIES snapshot is updated in the same commit.

    H9. The client lands as two pull requests, on either side of the server's. The verb get_cluster_claims() is tiny, and it can merge to client-python develop before the server does. It is gated on its token, so it simply raises IncapableException against an old server. It has to merge first. Cluster CI builds the client from develop (4b's survey correction), and test_namespace_claims.py routes every request through a client verb on purpose, so step 6's functional test cannot pass until the verb exists.

    The CLI readers merge last. They extend 7b's node capacity, which does not exist yet. They are also the best test of the response shapes, so writing them against a shape that might still change in review is the double-work 7b's D7 was written to avoid.

    So there are three pull requests: client-python (step 5), then shakenfist (steps 1 to 4, 6, 7 and 9), then client-python (step 8). Step 9's close-out goes in the shakenfist pull request, because the master plan lives there. Step 8 records its own outcome in its client pull request, and the 7a row's Merged cell names all three at the next phase's close-out.

    Risks and mitigations¶

    • Step 3 changes what find_candidates() reads. The metrics loader is shared, so a careless change moves placement. Mitigation: H6 confines the change to an optional out-parameter, and the step's constraint is that test_scheduler.py passes unmodified.     • /admin/resources gets slower, or fails more often. It gains one primary-key read. Mitigation: H4 bounds it and degrades it instead of raising. Step 6's functional test runs under the same polling as every other cluster test, so a regression shows up as CI timing.

    • Step 8 waits indefinitely on 7b. Mitigation: the server surface is useful without it (curl, --output json, the verb). The blocker is recorded with plan-blockers, so the wait is visible rather than forgotten.
