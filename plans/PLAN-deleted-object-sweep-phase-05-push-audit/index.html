    Phase 5: push audit of the deleted-object sweep¶

    Parent plan: PLAN-deleted-object-sweep.md.

    Planning effort: medium. Review effort: medium. The master plan says only "run PUSH-AUDIT.md over the merged ranges recorded in the table above", and the runbook supplies the headings, so the planning judgement is in three places: which ranges, what to do about the two 33fl landings the Execution table does not name, and which question is worth a heading of its own beyond the runbook's. All three are decided below.

    Decisions continue the plan's single sequence: phase 4 used D24-D29, so this phase starts at D30.

    Why this phase exists¶

    Four phases landed in nine days, 20 to 28 October, and every one of them changed shakenfist/daemons/cluster/scheduled_tasks.py and shakenfist/mariadb.py. Phase 1 instrumented the sweep, phase 2 replaced its single FIFO with per-type round-robin work and a paged read, phase 3 moved 25 of the 29 object types' hard deletes onto a batch RPC and changed the cadence, and phase 4 raised one configuration value and wrote the operator guide. Four pull request reviews each saw one of those; nothing has looked at them as one body of work.

    That matters more here than the shared block's general argument does, because of what phase 3 did. Moving a type's hard delete onto a batch means restating, in a declaration, the set of tables that type's hard_delete() used to delete from. A type whose table went missing in that restatement still hard deletes cleanly, still passes its own tests, still reports success to the sweep -- and leaks the rows it no longer removes, for every object of that type, on every cluster. That is exactly the class of defect a per-phase review is worst at and an audit of the accumulated diff is best at, and it is why this phase carries a heading of its own (D35).

    Scope¶

    In scope.

    • The four merges which put phases 1 to 4 on develop (D30), audited under every PUSH-AUDIT.md heading: wave 1, the wave 2 mechanical sweep, the style judgment portion, and 2a to 2d.
    • One heading of this plan's own: whether the batch declaration removes what each type's pre-batch hard_delete() removed (D35).
    • The two 33fl pull requests that landed phase 4's steps 4b and 4c, under the five-item floor from the plan-push-audit-phase shared block rather than a runbook, because 33fl has none (D31).
    • Three seeded findings the planning survey already has in hand (D36).

    Out of scope.

    • Fixing anything. Findings are graded and dispositioned; blocking ones get a fix branch of their own, as D37 says. The audit's own pull request changes only this plan and the master plan.
    • The 25 later commits on develop which touch the audited files (survey finding 4). They are other plans' work. Where one of them changed something this plan wrote, it is a reason to check a finding at $TIP rather than something to audit.
    • #4759, the functional-test flake the faster sweep exposed. It is a true consequence of this plan and the master plan's Future work now records it, but the fix is in a suite this plan never touched and the issue is already filed with three fix directions.
    • #3922 (errored objects are never hard deleted). The gate that held it -- phase 4's drain and soak -- has now opened, which the master plan's Future work says. It is the next piece of work, not part of auditing this one.
    • The live cluster. Phase 4's readings are complete and recorded; this phase reads code.

    Decisions¶

    D30 -- Four ranges, git diff only, greps per range and judgement pooled¶

    $RANGES means the four ranges in survey finding 1, each written git diff <sha>^1 <sha>. $TIP means develop at 08c26e343b, the commit this branch was cut from.

    git log is forbidden on these ranges. Each merge brought a phase branch with its own history, and git log <sha>^1..<sha> over phase 3's range lists commits that arrived under it alongside, with no way for the reader to tell which. The runbook's own range rule exists for this.

    The mechanical greps run once per range, with each range's literal output recorded under its own sub-heading, because that is the only form in which a reader can check that the audit read all four. The judgement headings (style, 2a to 2d, and D35's) read the four ranges together, because every defect worth finding here is one the phases did to each other and a per-range pass cannot see it.

    Generated files under shakenfist/protos/ are exempt from judgement review; the genprotos check in step 5b covers them.

    D31 -- The two 33fl landings are audited here, under the five-item floor¶

    33fl has no PUSH-AUDIT.md, so the shared block's floor applies: the five numbered items, plus the questions 33fl's blast radius raises. They are audited in this plan rather than in 33fl, for three reasons. They are steps of phase 4 and no Merged cell names them, so the block's "audited there, as part of the pull request that lands it" route is already closed. Their diffs are 258 and 6 lines. And the record belongs with the plan that caused the change, where the next reader of this plan will find it.

    The questions worth asking of those two beyond the floor, because 33fl runs unattended against production and this repository does not:

    • #1095 adds a nightly computation over four Prometheus queries. If a query returns nothing -- a leadership change inside the hour leaves the gauge absent -- does the fact report unavailable rather than zero, as D26 required and its tests pin? A guard that reads absence as zero turns "we cannot see the sweep" into "the sweep is perfect", which is the failure the whole regression guard exists to prevent.

    D34 -- Grading, and what a grade commits to¶

    Blocking -- a correctness or security defect reachable on a supported configuration, data left behind or removed wrongly, or a documented fact that is false in a way that would mislead an operator acting on it. Blocking findings are fixed before the plan is Complete.

    Advisory -- everything else: structure, naming, a test that could be stronger, a documentation gap that misleads nobody.

    Every finding gets a disposition: fixed in #NNNN, filed as #NNNN, recorded on an existing issue, or declined in writing with a reason. "Noted" is not a disposition.
