    Dependency-aware agent operations phase 0: research and decisions¶

    Prompt¶

    This phase resolves the seven open questions in PLAN-agent-operation-dependencies.md into recorded decisions, and re-cuts that plan's phase table against them, so that the implementation phases build on settled semantics. It produces no production code.

    Ground every answer in the tree rather than in the master plan's prose, which was written in 2026-08 before PLAN-agent-operation-deadlines executed: the cluster operation dependency machinery (BaseClusterOperation.depends_on / runs_after and the three _end_for_dependency() helpers in shakenfist/operations/baseoperation.py, the dependency model in shakenfist/schema/operations/baseclusteroperation.py, and the dequeue walks in shakenfist/daemons/queues/workitem.py:144-213 and shakenfist/daemons/network/workitem.py:563-630), the agent operation object and its queue (shakenfist/operations/agentoperation.py, Instance.agent_operation_next at shakenfist/instance.py:3164), the sidechannel dispatcher (_dispatch_loop at shakenfist/daemons/sidechannel/main.py:2008), and the API's declared-parameter machinery (shakenfist/external_api/base.py:803-840, shakenfist/external_api/validation.py:626). The client surface lives in the sibling client-python repository and the first example application in client-python-k3s.

    Planning effort: high (this is the decisions phase for a plan whose subtle parts are queue semantics, cascade failure handling and cross-namespace authorisation). Review effort for the recorded decisions: high.

    Scope¶

    In: answering the master plan's seven open questions, recording each as a numbered decision with rationale in the master plan (replacing its "Open questions (resolve in phase 0)" section), re-cutting the master plan's phase table against those decisions, and updating the design-sketch text the decisions change.

    Out: all implementation — no schema column, no API parameter, no evaluation code, no client change, no documentation beyond the plan files themselves. Issues are filed for work this phase decides to defer, but nothing is fixed here.

    What the survey found¶

    The survey checked every factual claim the master plan makes about the tree. Five were wrong or incomplete, two of them load-bearing on the plan's own rationale; the rest of the plan's reading of the code holds. Four corrections are applied at source in this planning commit, as marked; the two that are really decisions rather than facts are left for step 0c, because recording a decision is this phase's job and not the planner's.

    1. The cluster-operation dependency wait is already bounded, and the master plan's description of it is incomplete. Both dispatchers give up once the defer budget is spent — DEPENDENCY_DEFER_BUDGET = 30 at shakenfist/operations/baseoperation.py:44, roughly six minutes of exponential backoff, then abandon_dependency_wait() aborts the dependent operation (issue #3992). The master plan's Situation section says only that "an in-flight dependency defers it", which reads as an unbounded wait. Corrected at source.
    2. Dependency cycles are structurally impossible, so the master plan's decision 4 rests on a hazard that cannot occur. A depends_on edge can only name an operation that already exists — the API assigns the UUID (AgentOperation.new(str(uuid.uuid4()), ...) at shakenfist/external_api/instance.py:2334, :2401, :2467), a client cannot pre-declare one, and an edge is static at creation with no API to add one later. Every edge therefore points backwards in creation order and the graph is a DAG by construction. What actually needs bounding is a wait on a dependency that never goes terminal, which is the hazard #3992 found in the cluster-operation machinery and fixed with a budget rather than with a deadline. The gate on PLAN-agent-operation-deadlines still holds — queue-time expiry, the terminal-only lazy pop, the reaper and the capability-token precedent are all load-bearing below — but "deadlines are the cycle-breaker" is not the reason. Left for step 0c, since it is decision 4 that has to change and that is a decision.
    3. Widening VALID_CLUSTER_OPERATIONS is not the right mechanism, and is wider than the design sketch intends. That frozenset (shakenfist/schema/operations/baseclusteroperation.py:37) has exactly one consumer, the dependency.validate_op_type validator at :117 — so the sketch's "admit ObjectType.AGENTOPERATION to the dependency schema's permitted operation types" is mechanically cheap, but it admits the edge in both directions and so settles open question 2 (mixed-type edges) by accident, in favour of allowing them, with no evaluator on the cluster side that can read agent operation state. The name is also then a lie. Corrected at source as a note on the sketch; which mechanism replaces it is decision work for 0c.
    4. The API already has the shape this plan needs for an array-of-objects body parameter, and a worked precedent. shakenfist/external_api/base.py:821-829 carries arrayofdiskspec and arrayofnetworkspec, each nesting a structured schema (DISKSPEC_SCHEMA, NETWORKSPEC_SCHEMA), and validation.py:626 compiles an array of object into a fields.List of a nested schema, so a DEPENDENCYSPEC_SCHEMA plus an arrayofdependency token is a pattern the repository already runs. The master plan says only "API parameters". Corrected at source.
    5. Documentation is less of a greenfield than phase 5's row assumes. docs/operator_guide/agent_operations.md already exists (252 lines: one executor per instance, the two budgets, where they are enforced, expired versus error, retry and the reaper, what to tune) because PLAN-agent-operation-deadlines phase 7 wrote it, and docs/developer_guide/api_reference/agentoperations.md and instances.md carry the API surface. There is no developer-guide page for the agent operation model. Corrected at source.

    Premises the survey checked and found unchanged or true:

    • depends_on / runs_after are on BaseClusterOperation (baseoperation.py:392-402) and not on BaseOperation, so AgentOperation inherits neither. The three cascade helpers (abandon_dependency_wait, abort_for_unsuitable_dependency, cancel_for_missing_dependency) and _end_for_dependency() are likewise cluster-only, and they reach for defer(), current_defer_count and the schema model's target_fields, none of which an agent operation has. Sharing the evaluation with the cluster dispatchers is therefore a bigger refactor than the master plan's "evaluation semantics mirror workitem.py" implies, and there are two copies of that walk to mirror, not one.
    • depends_on semantics as the plan states them: missing dependency errors (cancel_for_missing_dependency → BaseClusterOperation.STATE_ERROR), a dependency in error/deleted/abort aborts (abort_for_unsuitable_dependency → STATE_ABORT), an in-flight one defers — with correction 1 above. runs_after is ordering only and a missing dependency is a logged warning (workitem.py:174-213).
    • The sidechannel has no defer machinery, and a blocked operation staying queued costs nothing to express: agent_operation_next() leaves a dispatchable head on the queue and the dispatcher skips an instance that already has an executor.
    • node_aop_op wraps an agent operation's preflight in a cluster operation and already carries depends_on / runs_after (shakenfist/schema/operations/node_aop_op.py:55-56), so the type systems are adjacent as the plan says.
    • _dispatch_loop is throttled per instance at DISPATCH_CHECK_INTERVAL = 5 (daemons/sidechannel/main.py:94), and that constant is not just a comment: shakenfist/data/database_load_budget.yaml:311-323 derives the (GetInstanceAttributes, sidechannel) per-instance term from it, tools/derive-database-load-budget.py restates it, and a unit test fails if they drift (issue #4039). Any per-pass read this plan adds has a budget entry to amend — the master plan's open question 6 names the cost but not the file that holds it.
    • client-python-k3s is a de-facto example application as claimed: shakenfist_client_k3s/cluster.py:2593 has execute_and_await(instance_uuids, cmds), which submits one operation per instance and then awaits each in turn — exactly the fan-out a declared chain would replace — and it stores cluster state in namespace metadata (primitives.py:293, :569).
    • The prerequisite plan has genuinely landed, not merely been marked Complete: AgentOperation.STATE_EXPIRED, TERMINAL_STATES and the executing -> queued retry edge are in operations/agentoperation.py:35-123, reap_instance_executors() and expire_unpromoted_head() are in the sidechannel daemon (main.py:1727, :710), the per-command handler classes declare reports_progress and retryable (main.py:456-591), and the four merge commits spot-checked from its phase table (45debf843, 9bca46412, 4a122bcd3, 185de6b32) are all ancestors of develop.

    Decisions this plan already takes¶

    The survey settles enough that deferring every question to the research steps would be a pretence. These are taken now, with the reasoning; steps 0a and 0b test the two that rest on something other than reading the code, and 0c records the set in the master plan after the back brief.

    1. The cascade state is abort, and the capability token is what makes it safe. A dependent operation whose depends_on failed moves to abort — a state AgentOperation.state_targets does not currently reach — rather than to error or to expired. It is the vocabulary the cluster-operation cascade already uses, it is already in constants.FINAL_OBJECT_STATES so an aborted operation is hard-delete swept (an errored one is not: #3922), and it does not claim either that the operation failed or that a timing budget ran out, neither of which is true of a cascade. The cost is that client-python pins the terminal set by hand (TERMINAL_AGENT_OPERATION_STATES at apiclient.py:234, commented as "exactly AgentOperation.TERMINAL_STATES"), so a released client would poll an aborted operation to its full timeout — the #363 bug the deadlines plan's phase 6 just fixed. That cost is avoidable rather than accepted: the new parameters are gated behind an API_CAPABILITIES token the way deadline_seconds was (#4005), so an operation can only reach abort if it was created by a client that declared a dependency, which is a client that knows the state.

    Step 0b found that argument to be half true, and it is corrected here rather than in the step's own section. It holds for a client which polls the operations it created itself — _await_agentop in client-python — and fails for a client which polls an instance's whole operation list. client-python-k3s's await_idle() (shakenfist_client_k3s/cluster.py:2321) reads every operation on an instance, including other callers' and historical ones, deliberately treats a state it does not recognise as still running, and has no timeout of its own; its comment justifies that with "the server moves every operation out of whatever state it is in within its deadline", which a terminal state falsifies. So one aborted operation created by a new client stalls a released k3s plugin polling the same instance until the hard-delete sweep removes the operation — CLEANER_DELAY, an hour by default — after which the listing stops reporting it and the wait proceeds. Bounded, diagnosable (it notes the unrecognised state once), and still an hour of silence inside a cluster install. The plan's answer is that client-python-k3s is a repository we own and is already phase 5's business, so it learns the state there; whether it should learn it before the server can emit one is a question for the back brief. 2. Strict FIFO is preserved: a dependency-blocked head blocks the operations behind it (open question 1), and declaring a dependency does not opt an operation out of queue ordering. agent_operation_next()'s durability argument is that the head of the queue is the unit of recovery, and its crash-safety argument is that there is one executor per instance; scanning past a blocked head replaces the head pointer with per-operation claims, which the deadlines plan named as the reason concurrency is its own master plan (PLAN-agent-operation-deadlines.md, "Why concurrency stays out of scope"). Two semantics for queue order, depending on whether an operation declared an edge, is also the kind of subtlety decision 5 of the master plan says the documentation exists to avoid. 3. The stall that decision 2 accepts is bounded by a dedicated dependency-wait budget, not by the caller's deadline. A blocked head whose wait exceeds the budget is aborted, mirroring abandon_dependency_wait(). The deadline cannot be the bound: AGENT_OPERATION_DEFAULT_DEADLINE is 600 seconds but a caller may ask for up to AGENT_OPERATION_MAX_DEADLINE, 86400 (shakenfist/config.py:378, :460), so with deadlines as the only bound one caller could stall an instance's queue for a day by asking for a day. The budget is wall-clock from the first blocked evaluation rather than a defer count, because the dispatcher's pass rate is throttled and variable where the cluster dispatchers' backoff is not, and a wall-clock budget needs one attribute write on first block rather than one per pass. Proposed value: 300 seconds, in the same ballpark as the cluster-operation budget's effective six minutes; the operator confirms it at the back brief. 4. Edges are validated at submission, which is also the cycle answer (open questions 3 and 5). The API handler reads each named dependency once and refuses with a 400 if it does not exist, is not an agent operation, or belongs to a namespace the caller could not read; it does not walk the graph, because survey finding 2 shows there is no cycle to find. Namespace is checked at submission only and never re-checked at evaluation: the edge was authorised when it was declared, and re-checking would let a later namespace change break a chain already in flight. 5. Evaluation happens in the dispatcher, between agent_operation_next() and start_instance_executor() (open question 6), not inside agent_operation_next(). The deadline check lives inside that method, which is the tempting precedent, but it runs under the agent_operations attribute lock and a multi-edge walk under that lock would hold it across several database reads. In the dispatcher the blocked operation simply stays queued — which is what the master plan's design sketch says and what the sidechannel's lack of defer machinery makes free — and a cascade abort is a state write that the next pass's lazy pop retires. Cost control: nothing is read for an operation that declares no edges (the overwhelming majority), reads happen at most once per DISPATCH_CHECK_INTERVAL per instance because they hang off the existing throttled check, and a dependency observed in a terminal state is cached in process for the life of the dispatcher generation, since terminal is absorbing. The database_load_budget.yaml entry is amended in the same phase as the code, as a code-derived term. 6. Cross-instance edges cost nothing extra at evaluation, so they land with same-instance edges rather than in a phase of their own. The evaluator reads the dependency's state by UUID and never looks at which instance it belongs to; the only instance-aware work is the namespace check decision 4 puts in the API handler. The master plan's separate phase 3 therefore collapses into its phase 2, which is part of what 0c re-cuts. 7. Mixed-type edges are out of scope (open question 2), and the mechanism chosen for decision 1 keeps them out by construction: a new VALID_DEPENDENCY_OPERATIONS set and an agent-operation-only edge model, rather than widening VALID_CLUSTER_OPERATIONS, so a cluster operation still cannot name an agent operation and the two cluster dispatchers need no change at all. The use case ("run this script after the artifact fetch") is real and is expressible today by awaiting the fetch client-side; admitting it would mean a third and fourth evaluation site, in processes whose cascade helpers write STATE_ABORT through machinery agent operations do not have. Filed as an issue and recorded under Future work rather than silently dropped. 8. Settle delay is a field on the agent edge model, not on the shared one. Decision 3 of the master plan is kept as an edge attribute, but it goes on the agent-operation edge model, because a settle_seconds on the shared dependency model would appear on every cluster-operation edge with no evaluator honouring it. 9. The documentation deliverable is a developer-guide page plus an example index (open question 7). The model treatment — ordering, independence, deadlines, dependencies, retry, with worked examples — goes to a new docs/developer_guide/agent_operations.md, because the existing docs/operator_guide/agent_operations.md is a tuning and enforcement page for operators and the dependency vocabulary is an API contract. The example suite is an index section naming sibling repositories, with client-python-k3s as its first entry and its rolling-update chain as the worked example; no new CI is built to exercise examples, because each example repository already has its own. The second example is left to be chosen when there is a second feature to exercise, recorded as an issue rather than invented in a planning document.

    The decision most likely to be argued with is decision 2, strict FIFO. The case against it is real: one caller's blocked chain stalls every other caller's operations on that instance for up to the dependency-wait budget, and a cross-instance chain makes that easy to cause by accident — instance X's operation waiting on instance Y's slow transfer blocks X's queue for callers who have nothing to do with either. The case for it is that the alternative is not "better utilisation" but a second queue contract: an operation that declared an edge would be dispatchable out of order, which makes "put a file, then execute it" true only for operations that declared nothing, and which asks agent_operation_next() to hold a dispatchable candidate that is not the head — the exact head-pointer-to-claims change the deadlines plan refused. Step 0a measures how often an instance's queue actually holds operations from more than one submitter, because if the queue is nearly always shallow and single-caller then the objection is theoretical and decision 2 is free; if it is not, the operator should hear that before 0c records it.

So 300 s is about twice the worst single-hop latency this cluster has produced, which is a margin rather than an indulgence -- and it is now a number with evidence behind it instead of an analogy to the cluster-operation defer budget. A chain more than two hops deep on a busy instance could legitimately exceed it, which is a thing to document rather than to design around: the budget aborts, it does not corrupt.

    Reading for decision 2. The data does not say the objection is theoretical, and does not say it is real. Queues do get deep on sfcbr (50.6% of operations arrive behind another), but the depth comes from bursts of different commands on one instance within seconds, and nothing distinguishes that from a single caller. If the operator treats "one caller at a time per instance" as an acceptable operating assumption, strict FIFO costs nothing measurable beyond what the dispatch interval already imposes. If cross-caller isolation on one instance matters, this step provides no evidence either way, and decision 2 should be taken on the structural argument already in the plan, recorded as not measured.

    State audit (step 0b)¶

    Audited against the tree as it stands on 2026-11-07, after the deadlines plan landed. Two changes are assessed: (i) a new terminal state abort on AgentOperation, and (ii) a queued operation at the head of its instance's queue that is deliberately not dispatchable for minutes because a declared dependency has not finished.

    Two facts frame the table. First, abort is not new vocabulary: BaseOperation.STATE_ABORT = 'abort' already exists (shakenfist/operations/baseoperation.py:53) and is inherited by AgentOperation, which simply has no state_targets edge to it.     Phase numbers were written against the master plan's table as it stood before step 0c re-cut it, and the re-cut moved two of them.     Queue-order assumptions: does anything assume the queue drains promptly?

    Each item states what would misbehave if a healthy instance's queue head sat undispatched for minutes, and where the obligation lands.

    1. The deadline fires, and it is the only enforcement point that does. A blocked head is queued; agent_operation_next() (instance.py:3228-3246) expires and pops it when deadline_passed(), with the reason "the operation deadline passed while queued" and expiry_reason = deadline. The reaper ignores queued heads (main.py:1870) and _preflight has already run. Time spent blocked accrues against the deadline because it is absolute from request receipt. Consequences: (a) the dependency evaluation must run after agent_operation_next() in the dispatcher or an expired head could be cascaded rather than expired; (b) a dedicated wait budget is genuinely needed, because the default deadline is 600 s but a caller may ask for 86400 s, and deadline_seconds=0 with a live progress timeout is unbounded up to the 86400 s backstop (obligation: evaluation phase); (c) only the head is deadline-checked, so a blocked operation behind another blocked operation is not expired until it becomes head.
    2. The dispatcher only looks at ready agents. _dispatch_loop (main.py:2008-2110) skips an instance whose agent is not ready or ready-degraded (:2060-2064) before ever calling agent_operation_next(). A blocked head on an instance whose agent went away is neither evaluated nor deadline-expired for as long as the agent is away. Pre-existing for any queued head, but a dependency wait makes it likelier to be observed.
    3. Per-instance throttle and database cost. DISPATCH_CHECK_INTERVAL = 5 (main.py:94) is claimed before the read, so a blocked head is re-examined every five seconds. Today a dispatchable head is read once and handed to an executor; a blocked head costs an attributes read, an operation read and a state read every five seconds for the whole wait, plus the dependency's own state read(s), per blocked instance. The budget term at shakenfist/data/database_load_budget.yaml:311-323 must be amended, and a terminal dependency should be cached in process.
    4. Dispatcher pass duration and the supervisor. The dispatcher evaluates instances serially in one thread and records dispatcher_last_pass once per pass (main.py:2096); supervise_dispatcher() replaces it after 120 s of no pass (:2122-2142). The loop's own docstring records that a wedged gRPC read can consume about 90 s. Extra dependency reads inside the pass enlarge the window in which one wedged call starves every other instance on the node; the 300 s heartbeat log is unaffected. A dependency read that blocks must not be allowed to approach 120 s.
    5. reap_instance_executors does not disturb a blocked head (see the table), but it also does not help one: if a blocked head is somehow left blocked forever there is no reaper for it. The dedicated budget is the only bound, which is why it must be enforced somewhere that runs without a live executor (the dispatcher pass is the candidate).
    6. Strict FIFO, and the stall it accepts. Everything behind a blocked head waits, including a second operation that the same caller submitted without a dependency and operations from other callers. agent_operation_next() has no notion of a claim: it returns the head or nothing, and an initial/preflight head also returns nothing (:3248-3269).
    7. Cascade is lazy and ordered by queue position. The dispatcher can only observe a dependency failure for an operation that has reached the head. A dependent that sits behind a long-running head remains queued in the API (not abort) for as long as the head runs, even though its dependency failed minutes earlier, and a chain (C depends on B depends on A) propagates one hop per head-arrival. Clients awaiting the tail see queued for the duration. The dedicated wait budget bounds the stall once the dependent is head but does not make a failure visible earlier.
    8. Hard-delete of a dependency looks like a missing one. A dependency that completed, expired, aborted or was deleted is swept from the database after CLEANER_DELAY (3600 s, FINAL_OBJECT_STATES); an errored dependency is never swept (issue #3922). A dependent that reaches the head more than an hour after its dependency finished (possible because a caller may set a deadline of up to 86400 s) will find the dependency absent, and absence is ambiguous between "completed successfully" and "failed". Separately, delete() (agentoperation.py:553-561) removes the operation's static and attribute rows before setting deleted, so AgentOperation.from_db() returns nothing for a user-deleted dependency while its state row still reads deleted: the evaluator must read the dependency's state by UUID, not hydrate the object, or it will misclassify a deleted dependency as missing.
    9. A deleted blocked operation pops, but a deleted dependency cascades. A user DELETE of the blocked head removes its static rows, so agent_operation_next() finds from_db() empty and pops it (instance.py:3215-3220): no change needed. The dependent of a deleted operation is the case in item 8.
    10. Retry interaction. A retried operation is re-queued at the head it already holds (main.py:677), and attempts counts dispatches, so a blocked operation does not consume attempts. A dependency that is in a terminal state stays there, so re-evaluation after a retry is cheap and need not be repeated if cached.
    11. No metric or health check exists to be misled. Nothing exports queue length or oldest-queued age, so a multi-minute head wait is invisible to operators except through the instance audit events and the INFO "Dispatching agent operation" log. Not an incompatibility, but the evaluation phase should log (and probably event) the first blocked evaluation and the cascade, or a stalled instance is hard to diagnose. The existing inst.add_event('dispatching agent operation') (main.py:2082) is emitted only on dispatch.
    12. CI awaits. _await_command allows 900 s and _await_agentop_complete takes a per-call timeout, so a bounded wait fits. Any test that submits a dependent and a follower on one instance, expecting the follower to run, will be held for the budget; tests of the cascade should assert on abort using _await_agentop_state once abort is classified (see CI table).
    13. Instance externally visible queue is empty. See the agent_operations_queue row: the key bug means the one surface designed to show "what is queued behind what" does not work.
    14. Other callers: client-python-k3s. await_idle waits for an instance's entire operation list to settle, so a dependent waiting in the queue is simply waited for, which is correct; the hazard is the terminal-state one in the table.

    BREAKS verdicts

    Two things break, and neither is in the dispatcher. The first is client-python-k3s await_idle (cluster.py:2321-2443): it classifies an unknown state as still running, has no timeout of its own, and justifies that with a premise (every state leaves within its deadline) that abort falsifies. This matters beyond the k3s plugin because the capability gate protects only the creating client: await_idle and the CLI both read an instance's whole operation list (all=True), so a single aborted operation created by a newer client stalls every released client that polls the same instance -- for up to CLEANER_DELAY, an hour by default, after which the hard-delete sweep removes the operation and the listing stops reporting it. The claim that no released client can be hung by a state it cannot cause holds for the clients which poll their own operations (_await_agentop) and fails for list-polling clients. Whether to treat that as acceptable, or to add the state to client-python-k3s and ship it before the server change, was left to the plan rather than settled here; the operator chose the second at the back brief, so it is now a prerequisite of phase 1. The second break is the conditional BREAK in agent_operation_next()'s unknown-state branch (instance.py:3288-3301): adding abort to state_targets without adding it to TERMINAL_STATES wedges the queue permanently; this is a single-commit obligation rather than a design question. The unguarded error writes that the 2026-08 audit worried about no longer exist (all go through fail()), so nothing in the sidechannel daemon breaks on abort. Two further hazards are design obligations rather than breakage: the ambiguity between a hard-deleted and a failed dependency (queue list item 8) and the unbounded dedicated budget interaction with deadline_seconds=0 (item 1).
