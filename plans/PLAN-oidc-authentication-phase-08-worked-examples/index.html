    OIDC authentication phase 8: worked operator examples¶

    Prompt¶

    This phase was planned by /next-phase oidc-authentication on 2026-11-21, immediately after phase 7 merged as client-python#456. The master plan is PLAN-oidc-authentication.md; read its phase 8 paragraph and open question 12 before this file.

    The master plan sets the bar for this phase and it is the reason most of the step table is agentic rather than editorial:

    the examples must be produced by actually configuring the two providers, not written from memory of how they work. A plausible-looking walkthrough that does not run is worse than no walkthrough.

    Planning effort¶

    Medium, reviewed at high, as the master plan specifies. The planning itself was mostly verification: the operator documentation this phase extends is already extensive, and the work was finding out what of it is true. One survey finding changed the phase's shape and was referred to Michael (D1).

    Scope¶

    In scope:

    • An end-to-end worked example of configuring Keycloak for human login, produced against a real Keycloak.
    • The same for Authentik, produced against a real Authentik.
    • Making a group claim able to grant a namespace at all, which it cannot today (see finding 1 and D1).
    • The tools/ lab that stands both providers up, so the walkthroughs are reproducible and phase 9 inherits a starting point rather than a blank page.
    • Closing open question 12: the operator half is this phase, and the users' half became a real gap the moment phase 7 shipped a login verb this repository's user guide does not mention.

    Out of scope:

    • Driving a login end to end against a live cluster with a live provider. That is phase 9, and it needs CI topology this phase does not build. This phase proves the provider half against real providers and the cluster half against what they actually emit, captured as fixtures.
    • sf-client verbs for issuers and mapping rules (client-python#451, still open). The walkthroughs call the REST API with curl, exactly as the existing GitHub Actions example does and for the same stated reason.
    • Any change to what a rule's matcher may contain. The matchers stay exact strings or lists of exact strings; only what a token's claim value may be is widened.
    • Globbing, prefix matching or regular expressions in claim matching, which the developer guide declines on the record and this phase does not reopen.

    What the survey found¶

    The master plan's phase 8 paragraph was written in 2026-06 and every file reference in it has since moved. More importantly, two of its factual claims are now false and one of its deliverables is impossible against the tree as it stands.

    1. A group claim cannot grant a namespace today¶

    This is the finding that reshaped the phase. federation.claim_matches() refuses any token claim value that is not a str (shakenfist/federation.py:413-429):

        if not isinstance(value, str):
        return False

    A groups claim in an OpenID Connect identity token is an array of strings. Keycloak's group-membership mapper writes one (it implements the multivalued group list, optionally as full paths); Authentik's default OpenID profile mapping does the same. So bound_claims of {"groups": "sf-admins"} can never match either provider's token, and the phase's central deliverable -- "including how a group claim reaches a namespace grant" -- cannot be written truthfully.

    The behaviour is pinned by a test, which is why it cannot be read as an oversight (shakenfist/tests/test_federation.py:658):

        def test_non_string_claim_values_never_match(self):
        # A claim of 1 must not satisfy a matcher of "1": a federation
        # that coerces is one that eventually accepts the wrong thing.
        self.assertFalse(federation.claim_matches(1, '1'))
        self.assertFalse(federation.claim_matches(True, 'true'))
        self.assertFalse(federation.claim_matches(None, 'None'))
        self.assertFalse(federation.claim_matches(['a'], 'a'))

    The comment argues coercion, and coercion is a good argument for the first three assertions. It is not an argument for the fourth: comparing a matcher against each element of a list of strings coerces nothing. The list case was swept in with the scalar cases and never had a rationale of its own.

    Worse, the operator guide already advises the binding that cannot work (docs/operator_guide/authentication.md:539): "bind the narrowest claim that expresses the entitlement, usually a group, rather than an address". An operator following the guide today writes a rule that silently never fires, and the login is refused with the deliberately uninformative 401 that POST /auth/login gives every refusal.

    This was referred to Michael, who chose to fix the matching in this phase. See D1.

    3. "Nothing in the tree exercises Keycloak" is no longer true¶

    Phase 3 added Keycloak- and Authentik-shaped fixtures to the discovery tests, precisely because their issuer URLs differ in the way that breaks discovery (shakenfist/tests/test_oidc_discovery.py:27-30, and test_a_keycloak_issuer_keeps_its_realm_path at :146). The trailing-slash asymmetry the walkthroughs have to explain is already settled in code and documented at docs/operator_guide/authentication.md:275-283.

    4. The generic human-login documentation is already written¶

    The phase 8 paragraph implies an operator guide with an issuer section and little else. Phases 3 and 4 wrote 160 lines of human-login operator documentation that is accurate and detailed: ### Discovery (240), #### When discovery must succeed (314), #### Re-running discovery (338), ### Updating an issuer (358), ### Human login metadata (395) and ### Human login mints credentials (431). The client_id-is-not-audience trap phase 4's survey found is already a prominent warning box (465-490).

    So this phase owes less than the paragraph suggests on mechanics and all of what it suggests on provider specifics: nothing anywhere tells an operator which buttons to press at Keycloak or Authentik, and that is the whole of the gap -- plus the group-claim hole in finding 1.

    5. Authentik advertises a device endpoint it may not honour¶

    Authentik's discovery document carries device_authorization_endpoint, pointing at the global /application/o/device/ path, and its discovery document is per-application at /application/o/<slug>/.well-known/openid-configuration. But the device code flow only works when the active brand has a device-code flow configured, which is not the default and which Authentik's own documentation says must be created by hand.

    Shaken Fist decides login capability from the discovery document's endpoints (docs/operator_guide/authentication.md:401), so an Authentik issuer will be advertised as device-capable while every device login against it fails. sf-client prefers the device flow wherever it is advertised, so the default experience on a stock Authentik is a login that cannot complete. The walkthrough has to say so; whether the cluster should do anything about it is noted under future work rather than decided here.

    6. The user guide never mentions logging in¶

    docs/user_guide/authentication.md has six sections, none about human login, and its single reference to a login (:138) is about provenance.     Decisions¶

    D1. A list-valued claim matches by exact membership¶

    claim_matches() gains one case: when the token's claim value is a list, it matches if any element is a string equal to the matcher, or equal to one of the matcher's alternatives.

    Everything the existing tests pin stays pinned. No globbing, no prefix matching, no regular expressions, no coercion: 1 still does not match "1", a non-string element is skipped rather than stringified, and a nested list does not recurse. An empty list matches nothing, as an empty matcher list already does.

    This is what every other OpenID Connect relying party does with a group claim, and the alternative is worse than it looks. Authentik can emit a scalar entitlement claim through a custom scope mapping, so a documentation-only phase is possible there; Keycloak has no group-driven way to emit a scalar. Its group-membership and role mappers are multivalued by construction, so the Keycloak walkthrough would have to tell an operator to set a per-user attribute on every person -- which is not group-driven entitlement at all, and contradicts the operator guide's own advice.

    Michael chose this option over a documentation-only phase and over splitting the matching change into its own phase.

    D2. The widening lives in claim_matches() and nowhere else¶

    match_claims() is not touched beyond what D3 requires, and no comparison is written a second time. This is the property matching_rules()'s docstring already names: exact string equality "stays in one function so that it cannot be loosened in one place and not the other". A list case added in the wrong place would be the loosening that docstring is guarding against.

    D3. Provenance records the elements that matched, not the whole claim¶

    match_claims() records the claims that satisfied a rule into the minted key's provenance, as the token's values rather than the rule's matchers. For a scalar that is unchanged. For a list, provenance records only the elements which matched.

    This is the decision most likely to be argued with, so here is the argument on both sides. Recording the whole array is the literal reading of "the token's value", and an auditor might reasonably want to see everything the token claimed. Against that: a person's complete group membership is not what the grant was made on, it is unbounded in a way a scalar claim is not, and it would be written onto every key of every login and kept for the life of the key. The matched subset is the grant as it was actually made, which is what the docstring says provenance is for, and it is the narrower thing to store about a person.

    Mechanically, claim_matches() stays a predicate and gains a sibling that returns the matching values; the predicate is bool() of the sibling, so D2 still holds -- there is one comparison, used two ways.

    D4. Both providers get a full walkthrough, Keycloak first¶

    Not one walkthrough with a list of Authentik deltas. The two differ in the three things most likely to go wrong -- the trailing slash on the issuer URL, where the group claim comes from, and whether the device flow works at all -- so a reader configuring Authentik from a Keycloak-shaped walkthrough is reading around the parts that matter. Keycloak goes first because its issuer URL is the unsurprising one.

    D5. The providers are configured for real; the cluster half is proved against fixtures¶

    Steps 8a and 8b stand up each provider in Docker, configure it, complete a login by hand, and capture two artefacts per provider: the discovery document, and the decoded claim set of a real identity token. Those captures are committed as test fixtures and the cluster-side tests in 8c assert against them.

    What this phase does not do is drive sf-client login against a live cluster trusting a live provider. That needs a cluster whose sf-api can reach the provider over TLS it trusts, which is CI topology, which is phase 9. The split is deliberate: the expensive, rot-prone knowledge in a walkthrough is the provider configuration, and that is what is being verified against the real thing here.

    D6. The lab lands in the repository, under tools/¶

    tools/idp-lab/ carries a compose file with pinned image tags, a setup script that configures both providers through their admin APIs, and a README. Three reasons: a walkthrough nobody can reproduce is a walkthrough that rots silently; phase 9 needs a containerised provider and should start from something that already works; and the captures in D5 have to be regenerable or they become unfalsifiable. tools/ is where this repository keeps scripts of this kind, and the scripts are files rather than inline YAML because CI steps must not carry large scripts.

    D7. The user guide gets a pointer, not a second walkthrough¶

    A short section in docs/user_guide/authentication.md saying that a person logs in with sf-client login, that the cluster mints one key per namespace they are entitled to, and linking client-python's docs/human-login.md by absolute URL. The client's documentation is the client's to maintain, and a copy here is a copy to drift. This closes the users' half of open question 12.

    D8. The device-flow caveat is documented in two places and fixed in neither¶

    Finding 5 means a stock Authentik advertises a device flow that does not work, and step 8b established that in a stronger form than the finding claimed: the discovery document taken before a brand device-code flow exists and the one taken after are identical byte for byte. Nothing a relying party can read distinguishes a working Authentik from a broken one. There are also two switches rather than one -- the brand's device-code flow, and the provider's own grant_types, whose API default is empty -- and the document advertises the endpoint, and lists the device grant in grant_types_supported, in both broken states.

    This phase documents it: in the Authentik walkthrough as two steps the operator must not skip, and in the discovery section as a caveat about what the endpoint list proves. It does not add a probe, a health check or a configuration flag, because the cluster cannot distinguish "advertised and unconfigured" from "advertised and working" without starting a flow, and a cluster that starts flows at an identity provider to test it is the thing the discovery section already refuses to do on a timer. Future work records the alternative.

    The administrative steps, in order¶

    Every step was done through the admin REST API so that it is reproducible; the admin console path is given beside each one, because that is what the walkthrough will describe. The token below is a master realm admin-cli password grant:

    curl -sS -k -X POST https://localhost:8443/realms/master/protocol/openid-connect/token \
  --data-urlencode 'client_id=admin-cli' \
  --data-urlencode 'grant_type=password' \
  --data-urlencode "username=${KC_ADMIN_USER}" \
  --data-urlencode "password=${KC_ADMIN_PASS}"

    1. Create the realm shakenfist. Console: Manage realms -> Create realm. POST /admin/realms with {"realm": "shakenfist", "enabled": true} -> 201. The realm name is the last path element of the issuer URL, which is https://<host>/realms/shakenfist.

    2. Create the group sf-admins. Console: Groups -> Create group. POST /admin/realms/shakenfist/groups with {"name": "sf-admins"} -> 201.

    3. Create the client shakenfist, public. Console: Clients -> Create client, then Client authentication off. POST /admin/realms/shakenfist/clients -> 201 with:

    {
  "clientId": "shakenfist",
  "name": "Shaken Fist command line client",
  "enabled": true,
  "publicClient": true,
  "standardFlowEnabled": true,
  "directAccessGrantsEnabled": false,
  "serviceAccountsEnabled": false,
  "redirectUris": ["http://127.0.0.1:*"],
  "webOrigins": [],
  "attributes": {"oauth2.device.authorization.grant.enabled": "true"}
}

    Public, not confidential, because the thing registering is a command line program on a person's laptop. A confidential client's secret would have to be distributed to every person who logs in, at which point it is not a secret; the public client plus PKCE is what the loopback-redirect shape is for, and the device grant requires a public client anyway. There is also nothing for a secret to protect here: POST /auth/login verifies the token's signature and client_id, not a client secret.

    redirectUris is http://127.0.0.1:*. The command line client binds an ephemeral loopback port (_RedirectServer((address, 0), ...) in client-python's shakenfist_client/commandline/auth.py), so the redirect URI it sends is http://127.0.0.1:<random>/ and cannot be registered exactly. Keycloak's trailing * matched http://127.0.0.1:45678/ in the real flow below. Plaintext http on a loopback literal is correct here and is what the device grant exists to avoid needing at all.

    oauth2.device.authorization.grant.enabled is the OAuth 2.0 Device Authorization Grant. Console: the OAuth 2.0 Device Authorization Grant checkbox under Authentication flow.

    1. Add the group membership mapper, which is the step this whole exercise turns on; see the subsection below.

    2. Create the person and give them a password. Console: Users -> Add user, then Credentials -> Set password with Temporary off. POST /admin/realms/shakenfist/users -> 201 with username, enabled, emailVerified, email, firstName, lastName and a "temporary": false password credential. emailVerified and the non-temporary password are both deliberate: each of the alternatives puts a required action on the account, and the login then stops on an extra screen before any token is issued. That consequence was not exercised here -- the lab user was created this way from the start -- so if the walkthrough states it, state it as a reason to set the two fields rather than as an observation.

    3. Put the person in the group. Console: Users -> the user -> Groups -> Join Group. PUT /admin/realms/shakenfist/users/<user uuid>/groups/<group uuid> -> 204. The two uuids come from GET .../users?username=<name>&exact=true and GET .../groups?search=<name>.

    Getting a groups claim into the ID token¶

    This is the most valuable note in this section, because three separate things can each leave the claim out of the identity token while it is present in the access token or at /userinfo, and Shaken Fist only ever sees the identity token.

    The mapper. Keycloak ships no groups client scope and no group claim by default. What is needed is a protocol mapper of type oidc-group-membership-mapper ("Group Membership" in the console). The least surprising home for it is the client's own dedicated scope -- console: Clients -> shakenfist -> Client scopes -> shakenfist-dedicated -> Add mapper -> By configuration -> Group Membership:

    curl -sS -k -X POST \
  "https://localhost:8443/admin/realms/shakenfist/clients/<client uuid>/protocol-mappers/models" \
  -H "Authorization: Bearer ${TOKEN}" -H 'Content-Type: application/json' \
  -d '{"name": "groups",
       "protocol": "openid-connect",
       "protocolMapper": "oidc-group-membership-mapper",
       "config": {"claim.name": "groups",
                  "full.path": "true",
                  "id.token.claim": "true",
                  "access.token.claim": "true",
                  "userinfo.token.claim": "true",
                  "introspection.token.claim": "true"}}'

    "id.token.claim": "true" is the member that puts it in the identity token, and it is the one to check when the claim is visible at /userinfo but a login is still refused. Console: the Add to ID token switch.

    full.path decides whether the value is /sf-admins or sf-admins, and the two paths disagree about its default. Both were observed:

    How the mapper was created groups in the ID token
    config with "full.path": "true" ["/sf-admins"]
    config with "full.path" absent ["sf-admins"]

    So a mapper POSTed without the key behaves as if it were false. But the key's declared default is true, which is what the admin console renders and submits -- GET /admin/serverinfo reports, for oidc-group-membership-mapper:

    full.path             type= boolean default= 'true'
id.token.claim        type= boolean default= 'true'
access.token.claim    type= boolean default= 'true'
userinfo.token.claim  type= boolean default= 'true'

    An operator clicking through the console therefore gets the full path, with a leading slash. The captured fixture is the full-path form and the string to bind is /sf-admins, with the slash. A walkthrough that says "bind sf-admins" is wrong for the console path, and one that says the opposite is wrong for anybody scripting the API without the key. Both forms are plain list elements, so either works once it is bound to the string the token actually carries. Note also that the leading slash is a path: a group nested under another is /parent/child, which is the real reason to keep full paths on.

    groups is not a scope Keycloak knows. Asking for it is a hard refusal from the device endpoint:

    {"error": "invalid_scope", "error_description": "Invalid scopes: openid profile groups"}

    (HTTP 400.) scopes_supported in a stock realm's discovery document is openid, organization, roles, email, offline_access, microprofile-jwt, address, acr, web-origins, kc-admin-api, service_account, profile, phone, basic -- no groups. So the issuer's oidc_scopes for this configuration must be openid profile, not openid profile groups. The claim arrives anyway, because a dedicated-scope mapper is always in scope.

    The alternative was tried and works, and is worth a sentence in the walkthrough but not the main path: create a realm client scope literally named groups (POST /admin/realms/shakenfist/client-scopes, attributes {"include.in.token.scope": "true"}), put the same mapper in it, and assign it to the client. Then groups appears in scopes_supported and openid profile groups is accepted. Assigned as an optional client scope it is a trap:

    Requested scope Granted scope in the token response groups claim
    openid profile groups openid groups email profile ["/sf-admins"]
    openid profile openid email profile absent

    An operator who sets up the optional scope and then leaves oidc_scopes at its openid default gets no claim, no rule match, and the deliberately uninformative 401. Assigning it as a default client scope avoids that, at the cost of the claim being in every token whether asked for or not.

    Enabling the device grant¶

    oauth2.device.authorization.grant.enabled on the client is the whole of it. For Keycloak, unlike the other provider, there is nothing at a brand or flow level to configure.

    But that setting is not what puts the endpoint in the discovery document. Checked on a second, empty realm whose only clients were Keycloak's six built-ins, none of which has the grant enabled -- the document still carried:

    "device_authorization_endpoint": "https://localhost:8443/realms/emptyrealm/protocol/openid-connect/auth/device"

    So the endpoint is advertised per realm while the grant is enabled per client, and Shaken Fist's login metadata reads the former. A Keycloak issuer is therefore advertised as device-capable whether or not the registered client can use the grant: the same shape as survey finding 5 describes for the other provider, reached by a different route. The symptom when the attribute is missing was observed too -- a public client in that realm without it answered the device endpoint with a 400:

    {"error": "unauthorized_client", "error_description": "Client is not allowed to initiate OAuth 2.0 Device Authorization Grant. The flow is disabled for the client."}

    That is a one-line check an operator can run before blaming the cluster, and it is clearer than anything the cluster says.

    One client setting breaks the device grant and nothing else. Setting Proof Key for Code Exchange Code Challenge Method to S256 on the client (pkce.code.challenge.method) makes Keycloak require a challenge on every request, including the device authorization request, which has nowhere to put one:

    POST .../protocol/openid-connect/auth/device   -> 400
{"error": "invalid_request", "error_description": "Missing parameter: code_challenge_method"}

    Confirmed by setting the attribute, observing the 400, and clearing it; with the attribute set, the authorization endpoint answered 200 for the same client, so the breakage is specific to the device grant. The command line client sends S256 on the authorization code flow of its own accord (PKCE_CHALLENGE_METHOD = 'S256'), so leaving the client's PKCE method unset gives PKCE on the browser flow and a working device flow. The walkthrough should say to leave it empty and say why, because "require PKCE" is exactly the box a careful operator ticks.

    Three things the containers needed that are easy to get wrong¶

    1. TLS is already there, and it is the wrong certificate. Unlike the other provider, Authentik needs no certificate supplied to serve https: it generates one on first boot and listens on 9443 with it.

    subject=O=authentik, CN=authentik default certificate
issuer=O=authentik, CN=authentik default certificate

    That is enough for a capture made with curl -k. It is not enough for a cluster, and the failure is worth stating because it is not the one an operator expects. The certificate carries no subjectAltName, so Python's TLS refuses it by hostname even when it is itself the trust anchor. Pointing FEDERATION_JWKS_CA_BUNDLE at that very certificate and calling oidc_discovery.fetch() gave:

    OIDCDiscoveryFailed: could not fetch
https://localhost:9443/application/o/sf/.well-known/openid-configuration:
SSLError: ... [SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed:
Hostname mismatch, certificate is not valid for 'localhost'.

    "Trusting the certificate" does not fix this; only replacing it does. A certificate with a SAN was generated, uploaded as a keypair (POST /api/v3/crypto/certificatekeypairs/ with certificate_data and key_data), and set as the brand's Web certificate (PATCH /api/v3/core/brands/<uuid>/ with web_certificate). The running server picked it up within seconds with no restart. With that done, oidc_discovery.fetch() on the live provider succeeded:

    ACCEPTED. members: 5
  issuer = https://localhost:9443/application/o/sf/
  authorization_endpoint = https://localhost:9443/application/o/authorize/
  token_endpoint = https://localhost:9443/application/o/token/
  device_authorization_endpoint = https://localhost:9443/application/o/device/
  jwks_uri = https://localhost:9443/application/o/sf/jwks/

    So the discovery half of this phase is proved against the live provider and not only against the fixture. The lab's certificate was made the same way step 8a's was, with -addext 'subjectAltName=DNS:localhost,IP:127.0.0.1'.

    2. The bootstrap variables create an API token as well as a password. AUTHENTIK_BOOTSTRAP_PASSWORD, AUTHENTIK_BOOTSTRAP_TOKEN and AUTHENTIK_BOOTSTRAP_EMAIL are read on first boot. The token is what makes the whole configuration scriptable -- it is a bearer token for /api/v3/ from the first second, with no initial-setup flow to click through. This is the single biggest difference from the other provider's setup, where an admin password grant has to be exchanged for a token first.

    3. The issuer URL is decided by the request's Host header, not by a configuration setting. There is no KC_HOSTNAME equivalent here: the document fetched through localhost:9443 names https://localhost:9443/... as its issuer. An operator behind a reverse proxy therefore gets the issuer their proxy presents, which is right, but it also means a capture taken through the wrong name is silently wrong.

    Getting a groups claim into the ID token¶

    The default OpenID profile mapping carries it. No custom scope mapping was needed. This is the opposite of the other provider, which ships no group claim at all.

    GET /api/v3/propertymappings/provider/scope/<profile uuid>/ returns, verbatim, the shipped expression:

    avatar = request.user.avatar
return delete_none_values({
    "name": request.user.name,
    "given_name": ak_obj_attr(request.user, "given_name", "name"),
    "family_name": ak_obj_attr(request.user, "family_name"),
    "preferred_username": request.user.username,
    "nickname": request.user.username,
    "groups": [group.name for group in request.user.groups.all()],
    # Only expose URL-based avatars: generated avatars are inline base64
    # SVG data URIs, which would bloat the ID/access token for every
    # user without a real avatar URL (OIDC expects a URL here).
    "picture": avatar if avatar and not avatar.startswith("data:") else None,
})

    [group.name for group in request.user.groups.all()] is the whole of it: group names, as a JSON array, with no path and no uuid. A real identity token carried "groups": ["sf-admins"].

    Two conditions have to hold as well as the mapping being assigned, and both were checked by driving real logins:

    The provider's Include claims in id_token must be on. It is on by default. When it is off, the scope mappings' claims are served from /userinfo and from the access token but not from the identity token, which is the only token Shaken Fist ever sees.

    The profile scope must actually be granted, which decides what the issuer's oidc_scopes has to be. Four requests, same provider, same person:

    Requested scope Granted scope groups claim
    openid profile email profile email openid ["sf-admins"]
    openid profile profile openid ["sf-admins"]
    openid openid absent
    (no scope parameter at all) profile email openid ["sf-admins"]

    So oidc_scopes must be at least openid profile. The last row is Authentik's documented behaviour -- a request naming no scopes is treated as requesting every scope the provider has configured -- and it is a trap of its own, because it makes a hand-rolled test pass while the real client, which always names its scopes, fails.

    Unlike the other provider, groups is not a scope here and asking for one would be wrong: the claim rides on profile.

    The device flow, and what survey finding 5 got right¶

    Finding 5 held, and the evidence is stronger than the finding claims. It said Authentik advertises device_authorization_endpoint whether or not a brand device-code flow exists. Both states were captured.

    Before any brand flow was configured (flow_device_code is null on a stock default brand, confirmed by reading GET /api/v3/core/brands/), the discovery document carried:

    "device_authorization_endpoint": "https://localhost:9443/application/o/device/"
"grant_types_supported": [..., "urn:ietf:params:oauth:grant-type:device_code"]

    A device login was then driven by hand, and it fails in the worst possible way -- not at the first step, but at the person's browser, after they have already typed their password:

    1. POST /application/o/device/ answers 200 with a real device_code, user_code, verification_uri and verification_uri_complete. Nothing here hints at a problem.
    2. The person opens verification_uri_complete. Unauthenticated, it 302s to the brand's authentication flow, so they log in normally.
    3. Back at /device?code=<user_code>, authenticated, it answers a bare 404 with an empty body. No message, no error page content. The server log says what the browser does not:
    "event": "Brand has no device code flow configured",
"logger": "authentik.providers.oauth2.views.device_init",
"status": 404
    1. The client's token poll keeps answering authorization_pending until the code expires. The default expires_in is 60 seconds, so the whole thing is over in a minute with nothing said.

    After configuring the brand flow, the same login completed. Two API calls:

    # a flow with the stage configuration designation, and no stages at all
POST /api/v3/flows/instances/
  {"name": "default-device-code-flow", "title": "Device code flow",
   "slug": "default-device-code-flow", "designation": "stage_configuration",
   "authentication": "require_authenticated"}

# point the default brand at it
PATCH /api/v3/core/brands/<uuid>/ {"flow_device_code": "<flow uuid>"}

    Interface: Flows and Stages -> Flows -> Create, then System -> Brands -> edit the default brand -> Default code flow. The flow was created with no stages bound to it and that is enough; nothing had to be added to it.

    And here is the part that makes the caveat worth documenting: the discovery document did not change by one byte. The capture taken before the brand flow existed and the capture taken after are identical -- same 2188 bytes, same members, compared as parsed JSON and found equal. Nothing a relying party can read distinguishes a working Authentik from a broken one. That is a stronger statement than "the endpoint is advertised anyway", and it is what the operator guide should say.

    A third state was captured for the same reason. A provider created with the API's default grant_types of [] -- no device grant at all -- still produced a discovery document advertising device_authorization_endpoint and listing the device grant in grant_types_supported. So that member is static per provider too, and cannot be used as a second opinion. The device endpoint's refusal for such a provider is actively misleading:

    {"error": "invalid_client", "error_description": "Client authentication failed (e.g., unknown client, no client authentication included, or unsupported authentication method)"}

    (HTTP 400.) Nothing in that says "the device grant is not enabled on this provider", and it arrives at the client, not the person. The equivalent message at the other provider names the actual cause.

    So there are two independent switches, either of which breaks a device login while discovery looks perfect: the provider's grant_types, and the brand's flow_device_code. The walkthrough has to name both.

    Both logins, completed¶

    Both flows were driven end to end against the real server, through Authentik's flow executor API (/api/v3/flows/executor/<slug>/), which is what the browser interface itself posts to.

    Device code. Worked, once the brand flow existed. From a browser with no session, which is the real case:

    POST /application/o/device/                       -> 200, user_code + URIs
GET  /device?code=<user_code>                     -> 302 /flows/-/default/authentication/?next=...
     (the person logs in: identification, then password)
GET  /device?code=<user_code>                     -> 302 /if/flow/<authorization flow>/?code=<user_code>
     stage: ak-provider-oauth2-device-code-finish  (one button)
POST /application/o/token/ grant_type=...device_code -> 200 with an id_token

    Two things to tell a person. The code is pre-filled when they use verification_uri_complete, so the code-entry stage never appears -- but the brand flow is still what makes the route exist, which is why it cannot be skipped. And there is a confirmation stage they must press, ak-provider-oauth2-device-code-finish, even though the provider's authorization flow was the implicit consent one. It is the device grant's own step, not the consent setting, which is exactly the same shape the other provider has.

    Authorization code with PKCE. Worked, with an S256 challenge, no client secret, and a loopback redirect on an ephemeral port:

    GET /application/o/authorize/?response_type=code&client_id=shakenfist
    &redirect_uri=http://127.0.0.1:45678/&state=...
    &code_challenge=...&code_challenge_method=S256&scope=openid+profile+email
# -> 302 http://127.0.0.1:45678/?code=...&state=...
POST /application/o/token/ grant_type=authorization_code
    client_id=shakenfist code=... redirect_uri=http://127.0.0.1:45678/
    code_verifier=...
# -> 200 with an id_token

    No consent page on this flow. The redirect carries code and state and no iss parameter, which the other provider does send.

    What Authentik accepts for a wildcard port. This is a real walkthrough question and the answer is not the obvious one. redirect_uris is a list of objects, not of strings:

    [{"matching_mode": "regex",
  "url": "http://127\\.0\\.0\\.1:[0-9]+/",
  "redirect_uri_type": "authorization"}]

    matching_mode is strict or regex. A regex entry is what matches an ephemeral port; it was proved against two different ports, 45678 and 51237, both of which completed.

    The trap is that the other provider's form, http://127.0.0.1:*/, is accepted by the API as a strict entry and then matches nothing. With it configured, the authorization request answers 400 with an HTML error page -- correctly not a redirect, since the redirect URI is the thing in doubt -- and the log says:

    "cause": "redirect_uri_no_match",
"event": "The request fails due to a missing, invalid, or mismatching redirection URI (redirect_uri)."

    Note also that the regex is a regex: the literal dots have to be escaped or they match any character. Authentik's own documentation says so and it is easy to copy a Keycloak-shaped value straight past it.

    The two flows produce the same claim set. Compared member by member: identical keys, and identical values for everything except auth_time, exp, iat, jti and sid, which are per-token by construction. aud, acr, amr, iss and groups are the same. So one fixture is enough, and it was taken from the device flow, as step 8a's was.

    Left uncommitted in the worktree:

    • shakenfist/tests/files/idp/authentik-id-token-claims.json

    • grep -c device_authorization_endpoint on this file is 1. There is no mtls_endpoint_aliases member, so the count differs from the other provider's fixture, which is 2. Neither count is a safe test; read the top-level key with json.
    • token_endpoint_auth_methods_supported is ["client_secret_post", "client_secret_basic"] and does not include none, even though this provider is a public client and its token requests carry no secret and succeed. The member is static; do not read anything into it.
    • scopes_supported is ["openid", "email", "profile"], which is derived from the provider's assigned mappings -- the probe provider with no mappings published ["openid"] alone.
    • claims_supported lists groups, which is the one place in the document where the group claim is visible at all.

    Things the plan's row said that did not hold¶

    • "It needs TLS for the same reason step 8a did." True in the end but not in the way the row means: Authentik serves https out of the box, so curl -k captures work immediately and no certificate has to be supplied for this step. What the certificate is needed for is a cluster, because the built-in one has no subjectAltName and FEDERATION_JWKS_CA_BUNDLE cannot rescue a hostname mismatch. That distinction is worth the walkthrough's time; the row's version is not.
    • "the default OpenID profile mapping, or a custom scope mapping if that is what it takes -- record which". The default mapping, with no change. The thing that actually needs recording is not the mapping but the scope: oidc_scopes must include profile or the claim is absent, and that is the Authentik analogue of the other provider's optional-scope trap.
    • "Configure a device-code flow at the brand, which is not the default". Correct, and it is only half the configuration -- the provider's grant_types must list the device grant too, and its API default is the empty list. The row names one switch where there are two.
    • The row implies a groups claim might need work. It needs none. The work on this provider is in the three fields whose API defaults are empty, and in the redirect URI's matching mode.

    Step 8d — mutation testing¶

    Every property D1, D2 and D3 claim was broken on purpose, one at a time, against the matching change of step 8c (3a36d68549). 14 mutations: 12 behaviour-changing ones, all killed, and 2 proven semantic no-ops which survive by construction. Two of the twelve survived on the first round and are the two most informative rows below: each was a real gap in the tests, and each is now closed.

    The harness is run-mutants.sh in this session's scratchpad, beside mutants.yaml (the twelve), mutants-noops.yaml (the two), and pristine/ holding the three files step 8c touched. It drives ~/bin/mutation-check, which applies one mutant at a time, gives the file an mtime it has never had so no stale .pyc is trusted, runs the command in its own process group under a 300s timeout, and always puts the file back. ./run-mutants.sh --all re-runs the whole set in about three minutes. The test command is both modules in full, not just the matching tests:

    python -B -m testtools.run shakenfist.tests.test_federation        (96 tests)
python -B -m testtools.run shakenfist.tests.test_oidc_discovery    (34 tests)

    so a mutant that breaks MatchingRulesTestCase, the token exchange or the captured discovery documents is seen rather than missed. All ClaimMatchingTestCase names below are in shakenfist/tests/ test_federation.py.

    M7b: a missing test, found by re-aiming a no-op¶

    The mutant the row did not ask for and should have: drop the isinstance check from the matcher-side filter (alternatives = list(matcher)). It survived, and no test could have killed it, because it is a semantic no-op -- a candidate is always a str, in on a list compares with ==, and a str never equals an int, a bool, None or a list. The filter on that side is defence in depth against a damaged row, not a behaviour.

    Re-aimed one-sidedly as M7b -- coerce with str() rather than skip -- it was a real behaviour change: a claim of '1' would satisfy a matcher of [1]. That survived too, which is a missing test and not a note: the module's "no coercion" promise was pinned on the claim side and not on the matcher side, which step 8c rewrote. Closed with test_a_non_string_alternative_is_skipped_not_stringified. Rule creation refuses to write such a matcher (mapping_rule.validate_bound_claims()), so this is the damaged-row path, which is exactly where a coercion would be unobserved.

    M8a: the order assertion could not see sorting¶

    test_the_matched_values_are_the_ones_that_matched asserted ['b', 'c'] from matched_claim_values(['a', 'b', 'c'], ['c', 'b']). That distinguishes the claim's order from the matcher's, which is what it was written for, but its expected value is also the sorted one, so sorted() survived while reversed() was killed. The fix is in the test, not the code: a second assertion whose expected order is neither sorted nor the matcher's, matched_claim_values(['c', 'b'], ['a', 'b', 'c']) == ['c', 'b']. D3's "in the order the token listed them" is now actually tested.

    The two no-ops, and why they stay in the tree¶

    # What was changed Verdict
    M7 the matcher-side isinstance filter dropped (alternatives = list(matcher)) SURVIVED, semantic no-op
    M11 else: return [] → else: candidates = [value] for a value which is neither string nor list SURVIVED, semantic no-op

    Both survive for the same reason, and neither is a missing test: the final equality filter already excludes a non-str, so neither guard can change an outcome. They are kept because they keep the declared list[str] return honest and say what the function means; the behaviour each is standing in for is mutated one-sidedly by M7b and M11b, and both of those are killed. They live in mutants-noops.yaml rather than mutants.yaml so that the killing set exits 0, and so a later round can confirm they are still no-ops rather than rediscovering it.

    This is the one place the definition of done needs reading rather than applying: "a surviving mutation is a failed definition of done, not a note" is right about a mutation which changes behaviour and wrong about one which cannot. Read it as every behaviour-changing mutation is killed by a named test, which is what the twelve above are. The two no-ops are recorded rather than excused: each was re-aimed until it did change behaviour, and the re-aimed form is in the killed set.
