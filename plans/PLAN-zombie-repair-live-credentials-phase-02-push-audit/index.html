    PLAN: Zombie repair live credentials phase 2 -- push audit¶

    Why this phase exists¶

    The master plan PLAN-zombie-repair-live-credentials.md ends, as every master plan must, with a phase that runs PUSH-AUDIT.md over the whole plan's work. This plan has one code phase, so the audit range is that one pull request.

    Phase 1 landed on 2026-10-03 as #4419 and closed #3836. Its status was never closed out: both the master plan's Execution table and the docs/plans/index.md row still read Not started for work which has been on develop for seven weeks. The first commit of this phase records it, because the Merged cell is what makes the range auditable at all.

    Recommended planning effort: medium (done). The audit's own judgment lenses run at the efforts given in the step table; the security lens is the one at high, because the range is credential and authentication code.

    Scope¶

    In scope:

    • PUSH-AUDIT.md wave 1 and its wave 2 mechanical sweep over the range, run in this worktree.
    • The four wave 2 judgment lenses: 2a code quality, 2b test review, 2c documentation, 2d security.
    • Mutation testing, extended past what phase 1's definition of done required -- see survey finding 7 and decision 5.
    • Filing the two issues the master plan's Future work defers to this phase, and linking them from Future work (survey finding 9).
    • Recording the audit's findings and disposition in this file, and closing the phase and the plan out.

    Out of scope:

    • Fixing anything the audit finds. The master plan says findings land as their own pull request, and that is what a blocking finding gets. This pull request carries the phase 1 close-out, this plan, and the audit record.
    • Re-reviewing the master plan file itself as documentation (decision 7).
    • The two deferred designs the plan already declined: atomic creation of the three object types, and a namespace-has-no-usable-key health signal. This phase files the issue for the second; it does not build either.

    What the survey found¶

    Ten findings. Five of them change what the audit should do, and one is a real coverage gap in phase 1.

    1. The range is a single merge. f79a23cd5c^1..f79a23cd5c (#4419), recorded in the master plan's Merged cell by this phase's first commit. It is a two-parent merge, so reading it against its first parent is the whole of what landed. One range means one pass, not a pooled union.

    2. The master plan said this phase gets no plan file, and that is now false. Its Execution preamble read "This is a single pull request. It has no separate phase files". That was written about phase 1, whose steps are inline, but as written it covers phase 2 as well, and this phase does get a file -- as every other push-audit phase in this repository does (PLAN-kerbside-deployer-phase-07-push-audit.md, PLAN-transient-capacity-refusals-phase-07-push-audit.md). Corrected at source in the planning commit, so the sentence now scopes itself to phase 1.

    3. tox -e genprotos does not apply. No .proto file is in range (git diff --name-only <range> | grep -c '\.proto$' is 0). Step 2b says so rather than running it.

    4. tools/mermaid-lint.sh has nothing in range. The runbook says to render diagrams when the diff touches markdown, and this diff does touch six markdown files -- but none of the four guide pages it changed carries a ``mermaid fence (verified: all four grep to0`). The render is a docker build for no diagram, so step 2b states the check and skips it.

    5. Wave 1's four style greps are already clean on this range. Run at planning time per this repository's habit of executing a definition-of-done item rather than asserting it: no added line over 120 characters, no stray print(, no new etcd reference, no new mariadb.get_all_* pushdown violation. All four returned nothing.

    6. Wave 2's mechanical sweep is already clean too. No added TODO/FIXME/HACK/XXX, no new # noqa, # type: ignore or pragma: no cover, and no new subprocess/os.system/shell=True. 25 new test functions. Separately, and not part of the runbook's sweep, no dependency manifest changed either -- the sweep has no command for that, so this one is an addition of this plan's own.

    The range is 20 files and 1,879 insertions, but that number flatters it: 1,034 insertions are the master plan file itself and about 553 are tests, leaving roughly 294 lines of production code across seven modules (baseobject.py, daemons/cluster/scheduled_tasks.py, mariadb.py, namespace.py, namespace_key.py, trusted_issuer.py, mapping_rule.py). The audit should be scaled to 294 lines, not to 1,879 (decision 2).

    1. Phase 1's mutation checks were genuinely run, and they leave two of the three overrides untested. #4419's body records counts, not assertions: deleting the NamespaceKey override fails 10 tests, restoring None-on-error in the direct key reader fails 4, removing the rotation heal fails 2. That is the definition of done met. But the briefs only ever asked for the key path, so nothing has ever mutated the TrustedIssuer or MappingRule overrides, and the pinned structural test in test_mariadb_orphans.py would keep passing if either returned the wrong state, because it only checks that an override exists. This is the survey's one substantive gap, and decision 5 puts it in scope.

    2. The implementation deliberately diverges from brief 1b, and the divergence is undocumented outside the code. Brief 1b said a raised DatabaseUnavailable is "caught by the existing ignore_exception" and the zombie "is not removed from _ZOMBIE_CANDIDATES, so it is retried next pass". _repair_zombies() (shakenfist/daemons/cluster/scheduled_tasks.py:1643-1703) instead returns False on DatabaseUnavailable and ends the pass for that object type, catching only other exceptions per object. Its docstring gives the reason -- a tier-wide failure must not spend another _grpc_call retry budget per remaining object inside a job whose watchdog is petted only between jobs -- and three tests pin the distinction (test_unreadable_liveness_writes_nothing_and_retries, test_other_liveness_failures_cost_only_that_object, test_unavailable_database_stops_zombie_repair_after_one_budget). This reads as the better design rather than a slip, but no phase outcome records that the plan was overridden, so the 2a lens is told to reach its own verdict rather than inherit mine.

    3. Neither issue this phase must file exists. Searched gh issue list --state all for the open-question-3 health signal (a namespace with no usable key) and for the legacy namespace_attributes.keys column, by several wordings each; both come back empty. Both are real outstanding work, so the index row now names them.

    4. #3836 is closed, on 2026-10-03T08:33:17Z, by #4419. Nothing to do; recorded so the audit does not re-check it.

    Nothing else in the master plan's Phase 2 section is wrong. Its range rule, its "findings land as their own pull request", and its instruction to file the open-question-3 issue first all hold as written.

    Decisions¶

    1. One range, one pass. f79a23cd5c^1..f79a23cd5c. Every diff command substitutes f79a23cd5c^1 f79a23cd5c for $RANGE. develop...HEAD is forbidden here: the phase has merged, that diff is empty, and a clean report over an empty diff is the exact failure PUSH-AUDIT.md's range rule exists to prevent.

    2. Scale the audit to the range. Four judgment lenses and a mechanical step, not the ten-step shape the kerbside-deployer audit needed. That audit read eleven ranges across three repositories; this one reads 294 lines of production code in one repository, with no ansible, no shell, no protos and no cross-repository seam. Inflating it would buy findings about the audit rather than about the code.

    3. Skip genprotos and mermaid-lint.sh, and say so in the report. Justified by survey findings 3 and 4. A skipped check that is not reported reads later as a check that passed.

    4. Re-run wave 1 and the mechanical sweep even though planning ran the greps clean. Survey findings 5 and 6 are evidence for this plan -- they say the audit will not trip over trivia, so it is worth spending on the lenses. They are not the audit record. pre-commit run --all-files and tox have not been run in this worktree at all, and the greps need to appear in the audit's own output with their commands beside them.

    5. Mutation testing is in scope, and extends to the two overrides phase 1 never mutated. Survey finding 7. The step re-runs the three mutations #4419 recorded, to confirm the counts independently, and then adds four: make TrustedIssuer and MappingRule's overrides return STATE_DELETED unconditionally, and make each return STATE_CREATED unconditionally. A test must fail for each. If making an override always return created fails nothing, then no test proves that a genuinely dead issuer or rule is still collected, and the plan's own mission -- that a zombie its read path would not honour is "still marked deleted and collected, exactly as today" -- is unevidenced for two of its three types.

    This is more than phase 1's definition of done asked for, and that is the point: the audit's job is to find what the phase's own checks did not cover.

    1. The security lens runs at high effort. The range decides whether a credential authenticates. A fail-open in the liveness predicate deletes live keys; a fail-closed one in the attribute readers turns a tier blip into a 503. Both are in the diff, and the second is new behaviour reaching the REST layer.

    2. The documentation lens reads the four guide pages, not the plan file. docs/operator_guide/database.md, docs/operator_guide/authentication.md, docs/developer_guide/database_internals.md and docs/developer_guide/subsystem_internals.md are the user-visible surface and carry the facts that can disagree between pages. The 1,034-line plan file in the same diff is the instrument being executed, is reviewed by the planning and review cycle, and would otherwise dominate the lens by sheer line count. It is context for the lens, not a target.

    3. Findings land as their own pull request. The master plan says so. This pull request carries three things and no fixes: the phase 1 close-out, this plan, and the audit record with its disposition table.

    4. Correct the master plan at source in the planning commit (survey finding 2), rather than leaving a sentence which tells the next reader this file should not exist.

    Security (2d)¶

    • S1, medium. _heal_missing_state() (shakenfist/namespace_key.py:273-285, called from :230 and :265) branches on self.state.value is not None, and get_state() returns None both for an absent state row and for a failed read. mariadb.get_state_checked() exists for exactly this distinction and its own docstring warns that "a caller which acts irreversibly on absence cannot use" get_state(). This caller acts on absence. NamespaceKey.from_db_by_name() applies no state filter, so the rotation path can hold a soft-deleted key; during a read blip the heal writes initial then created over it, and the "objects do not undelete" guard (shakenfist/baseobject.py:720) compares the same misread value, so it does not fire. In the same window the second write can instead raise InvalidStateException or StateWriteFailed out of a rotation that has already replaced the secret, so the caller never learns the new one. Fix: read through get_state_checked() and skip the heal when the read failed, and contain both writes.
    • S2, low. hard_delete_objects_per_call() (shakenfist/mariadb_hard_delete.py:676-683) ignores each delete's return value, so on a torn legacy hard delete the state row can go while the static and attributes rows stay. That already authenticated, so this change does not create the exposure -- but it removes the backstop, because such a row used to be marked deleted within the hour and is now repaired to created and kept. Only on an sf-database predating the batch RPC.
    • S3, low. The three servicers' catch-alls (shakenfist/daemons/database/main.py:4225, :4395, :4625) put str(e) in the reply details, and the new DatabaseUnavailable messages carry the SQL statement and the bound uuid. Cluster-internal, no key material. The mapping-rule servicer already declines to do this for CorruptMappingRule for the same reason.
    • S6, low. The override docstrings name the federated exchange's issuer listing without noting that the login endpoint (external_api/auth.py:3225) additionally filters on ACTIVE_STATES. Accurate for issuer_claiming_url(), overstated for the login path. Documentation accuracy only.

    Clean, and checked rather than assumed: no input makes a liveness predicate return deleted for an object its read path honours (the key readers use an inner join to the attributes table, so "attributes row exists" is exactly the question they ask); an expired key repaired to created is picked up by reap_expired_namespace_keys(), which reads ACTIVE_STATES = {initial, created}, so no expired credential is resurrected; POST /auth and token validation do not call the changed readers at all; a client cannot nominate a zombie, and _ZOMBIE_CANDIDATES is replaced each pass rather than accumulated; and no added log line, audit event or state message can carry key material.

    One unrecorded hole was fixed by this change. issuer_claiming_url() is the duplicate-URL guard on issuer creation, and a read failure used to make an existing issuer's issuer_url read as None, so the guard could pass and leave two issuers claiming one iss. It now fails closed.

    Code quality (2a)¶

    • C1, advisory (shakenfist/daemons/cluster/scheduled_tasks.py, the _repair_zombies False path). The liveness stop calls _record_sweep_stopped() but never touches SWEEP_WORK_LIST_FAILURE_STREAK. The work-list read for that type succeeded -- that is how the zombies were found -- so _record_sweep_read() (:300-303) has just reset that type's streak to zero. A pass can therefore repair nothing, hour after hour, with the gauge reading zero: the precise silence that gauge exists to break. Fix: account the False path against the streak, or add a sibling counter.
    • C2, advisory (:1657). sorted(confirmed) has no per-object resume, so a liveness read that keeps failing on the lexically first zombie blocks every later zombie of that type indefinitely. The docstring's "they are all still in _ZOMBIE_CANDIDATES, so the next pass retries them" does not mention that progress is gated on the first one recovering. Untested.
    • C3, advisory (:1664). A liveness failure that is neither DatabaseUnavailable nor CorruptMappingRule -- a Pydantic ValidationError from a NULL column, say -- is swallowed by ignore_exception(), and the object stays a candidate forever: one traceback per hour per object, no metric, no bound.
    • C4, advisory (shakenfist/mariadb.py:16679). The rewritten get_mapping_rule_attributes docstring documents DatabaseUnavailable but not CorruptMappingRule, which both layers raise.
    • C5, low. A corrupt mapping rule now persists indefinitely, with one audit event and a log line as the only notice.
    • C9, advisory. test_a_slow_type_cannot_starve_the_types_behind_it (shakenfist/tests/test_daemon_cluster_scheduled_tasks.py:3162) injects DatabaseUnavailable into the work-list read, not the liveness read, so the test whose name promises this coverage is not the one providing it. The coverage does exist, in _assert_pass_stopped_on inside test_unreadable_liveness_writes_nothing_and_retries and test_mariadb_error_on_key_liveness_read_writes_nothing.

    The divergence from phase 1's brief 1b (this plan's survey finding 8) was judged correct, independently of this plan's own view. DatabaseUnavailable out of these readers is tier-wide by construction: the direct path raises it only from OperationalError on connect or execute, and the gRPC path only after _grpc_call has exhausted its retry budget. "Skip this object and continue" would re-pay a full connect-or-retry budget per remaining zombie and per remaining type inside one job whose watchdog is petted only between jobs, and would emit a traceback per zombie. No type starves: _record_sweep_stopped() (:240-246) sets the resume marker to the type after the one that stopped the pass, and _sweep_object_types() rotates to it, so a type whose liveness read keeps failing is visited last each pass and every other type is reached. The worst case is a bounded one-pass delay.

    Also clean: STATE_CREATED is in ACTIVE_STATES for all three classes, and deleted is in no registered class's, so the audit-text branch cannot mis-describe a repair; the three overrides are deliberately separate rather than a helper wanting extraction; the fail-closed change completes the set rather than leaving two types asymmetric, matching the #3522 precedent; and the CorruptMappingRule arm returning created is right, because readers already report such a rule as unusable and deleted would free its name and hard delete it with nobody told.
