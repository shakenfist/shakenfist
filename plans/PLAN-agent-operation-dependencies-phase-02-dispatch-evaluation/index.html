    Dependency-aware agent operations phase 2: dispatch evaluation¶

    Prompt¶

    Plan the next phase of PLAN-agent-operation-dependencies.md after phase 1 landed, following the next-phase skill: verify phase 1 is genuinely complete, survey the tree for the staleness in the master plan's phase 2 section, and write this plan. Implementation is a separate ask.

    Planning effort: high. This phase turns on correctness questions that cannot be mechanically derived -- what an absent dependency means, whether a settle delay counts inside the wait budget, and where in a locked dispatch pass a state write is safe -- and it adds the first code that moves an agent operation to a terminal state nothing writes today.

    Scope¶

    In scope:

    • The dependency evaluator in the sidechannel dispatcher, between Instance.agent_operation_next() and start_instance_executor() (master plan decision 8), covering same-instance and cross-instance edges alike (decision 10).
    • The depends_on cascade to abort, writing the dependency_failure attribute phase 1 added, and exposing it on external_view() (decision 7).
    • The runs_after ordering wait, with the cluster side's warn-and-continue asymmetry preserved.
    • The per-edge settle delay.
    • The dependency-wait budget, its configuration option, and the attribute that records when a wait began (decision 2).
    • The in-process terminal-dependency cache, keyed to the dispatcher generation (decision 8).
    • One new attributes column and its migration, which the master plan did not anticipate -- see What the survey found.
    • Documentation of the two ambiguities decisions 8 and 9 require to be written down rather than fixed.

    Out of scope, explicitly:

    • Mixed-type edges with cluster operations. Declined by master plan decision 4, kept out by construction by decision 5, filed as #4824.
    • Agent-side cancellation. No executing -> abort edge is added; phase 1 deliberately omitted it and this phase does not revisit it. A dependency that fails while its dependent is already executing does nothing.
    • Client-side chain helpers and the await UX. Phase 3, in client-python.
    • The developer-guide page for the whole model. Phase 4.
    • Re-deriving the database load budget. See survey finding 1: the reads this phase adds fall in a pair the project has deliberately excluded from the budget, so there is no coefficient to amend.
    • Fixing the nine open-coded namespace ownership predicates found during phase 1's review and filed as #4887. This phase's API-layer work is confined to one bound.

    What the survey found¶

    The master plan's phase 2 row and decisions 2, 8 and 9 were written during phase 0, before phase 1 executed. Three of their factual claims are wrong, and all three change what this phase has to do. Each is corrected at source in the master plan as part of this plan's registration commit, so a later reader does not trip over them.

    1. The budget term named in decision 8 does not describe this phase's reads¶

    Decision 8 instructs that "the (GetInstanceAttributes, sidechannel) entry in shakenfist/data/database_load_budget.yaml is amended in the same phase as the code, as a code-derived term."

    That entry exists (database_load_budget.yaml:310-325) and its note is explicit about what it covers: agent_operation_next()'s uncached instance-attribute read, once per DISPATCH_CHECK_INTERVAL per agent-ready instance. This phase adds no instance-attribute reads at all. Decision 9 requires the evaluator to read a dependency's state by UUID without hydrating the object, and AgentOperation.state is a property over a GetObjectState round trip (shakenfist/daemons/queues/workitem.py:127-132 records exactly that, and the same comment appears at shakenfist/daemons/sidechannel/main.py:1179).

    The pair that grows is therefore (GetObjectState, sidechannel), and it has no entry in the budget file -- deliberately. It is a member of HARNESS_DRIVEN_PAIRS in shakenfist/deploy/shakenfist_ci/load_budget.py:389, whose preceding comment gives the reason and states the cost in terms this phase has to accept verbatim:

    The model has no term for load which scales with in-flight operations: an instance doing no agent work costs nothing here and one streaming a large put-blob costs the operation's whole lifecycle, so a per_instance_qps coefficient would just encode the rate CI's tests happen to run at, which is the hand-fitting the yaml header forbids. [...] this check can no longer see a new fixed-rate poll which reads object states [...] from the sidechannel daemon.

    So there is nothing to amend and nothing to add: inventing a coefficient for a pair the file excludes on principle would be the hand-fitting the header forbids, and amending the GetInstanceAttributes term would attribute state reads to a term about attribute reads. What this phase owes instead is a sentence in that comment naming the evaluator as a second producer of those reads, so the next person to ask why the pair is unbudgeted finds both answers in one place. That is step 2f.

    2. This phase is not schema-free¶

    The master plan's phase 2 row says the dependency_failure column "itself lands in phase 1, which is the schema phase, so this phase writes and exposes a column which already exists". That is true of dependency_failure and it is the whole of what phase 1 landed: shakenfist/schema/agentoperation_attributes.py has exactly uuid, results, last_progress, attempts, expiry_reason and dependency_failure.

    But decision 2 requires the wait budget to be "wall-clock from the first blocked evaluation, recorded as an operation attribute on first block, rather than a count of dispatcher passes". There is no such attribute. Phase 2 therefore carries a schema change after all: one nullable float column, AGENT_OPERATION_ATTRIBUTES_VERSION 5 -> 6, a migration block, a proto field with explicit presence, and the direct and gRPC accessors -- the same seven-layer traverse phase 1 did three times. It is the single largest piece of unanticipated work in this phase and it is step 2a, ahead of the evaluator that depends on it.

    3. Phase 1 published a settle ceiling this phase cannot honour¶

    Phase 1 bounds settle_seconds by config.AGENT_OPERATION_MAX_DEADLINE at shakenfist/external_api/base.py:701-709, with a comment explaining that the ceiling belongs in the API layer rather than on the model because it is a deployment policy value. AGENT_OPERATION_MAX_DEADLINE defaults to 86400 (shakenfist/config.py:460).

    Decision 2 sets the dependency-wait budget to 300 seconds. If the settle delay counts inside that budget -- and decision 2 says the budget is wall-clock from the first blocked evaluation, which a settle wait plainly is -- then every settle_seconds above 300 is unsatisfiable: the operation will always be aborted by the budget before the settle elapses. The API accepts such a value today and the OpenAPI document publishes maximum: 86400 for it.

    Nothing is broken yet, because no evaluator reads the field. Deciding what to do about it before an evaluator exists is the point of finding it now; see decision 4 below.

    What the survey confirmed¶

    Everything else in the phase 2 section holds, and three claims worth checking are exactly right:

    • The dispatcher seam is where decision 8 says. agentop = inst.agent_operation_next() is at shakenfist/daemons/sidechannel/main.py:2092 and self.start_instance_executor(...) at :2111, with a dispatcher generation check and one audit event between them.
    • The sidechannel has no defer machinery: grep -c defer shakenfist/daemons/sidechannel/main.py returns 0, so decision 8's "a blocked operation simply stays queued" is free rather than something to build.
    • dispatcher_generation exists and is already used for exactly this kind of liveness reasoning (seven uses in that file), so the terminal-dependency cache has a natural lifetime.
    • abort is in constants.FINAL_OBJECT_STATES (shakenfist/constants.py:204-209), so decision 3's sweep claim holds, and CLEANER_DELAY is 3600 (shakenfist/config.py:873), which decision 5 below turns into an argument.

    Decisions¶

    1. The evaluator runs after the generation check, not before it. The seam decision 8 names contains three things in order: the generation check, an audit event, and start_instance_executor(). Evaluation goes between the generation check and the audit event.

    This matters because evaluation writes: a cascade sets a terminal state and a first block writes an attribute. A pass that has been superseded must not write either, for the same reason it must not dispatch -- the comment at :2095-2098 says the operation stays at the head of the queue for the new generation, and a cascade abort performed by a dead generation would be a state write with no dispatcher accountable for it. Putting evaluation before the check would also emit "dispatching agent operation" for an operation that was then not dispatched.

    1. An absent depends_on dependency aborts the dependent. This is decision 9's ambiguity, and it needs an answer rather than only a caveat, because the evaluator has to do something.

    Step 2c corrected the reasoning this decision was first written with, which had the mechanics backwards. AgentOperation.delete() removes the operation's static and attribute rows and only then assigns deleted, and that state lives in a different table -- so a user-deleted dependency still has its state row and reads as deleted. It never presents as absent. The first draft of this decision argued that an absence seen during the 300-second budget must be a deletion; that is false, and reading state rather than hydrating is exactly what makes it false.

    Absence has one cause: the hard-delete sweep removed the state row, CLEANER_DELAY (3600 seconds) after the dependency reached a final state. So an absent dependency finished at least an hour ago, in one of the states the sweep collects. error is not one of them (issue #3922), so absence cannot distinguish a success from an abort or an expiry, and complete is the likeliest of the three.

    The conclusion survives the correction, on a different argument. Refusing is the safe side of the ambiguity: it declines work whose precondition probably held, where proceeding would perform work whose precondition may have failed, and a fate-sharing edge should fail safe. It is also reachable only by a dependent which sat in its instance's queue for over an hour, which its own deadline bounds. The cost is documented in step 2f and the mitigation is caller-side: keep a dependent's deadline under CLEANER_DELAY, so it cannot still be queued when the sweep runs.

    dependency_failure records state: 'missing' for this case, which is not an AgentOperation state value and is deliberately distinguishable from every real one.

    1. A missing runs_after dependency warns and proceeds, and an exhausted budget on a runs_after edge also proceeds. This mirrors shakenfist/daemons/queues/workitem.py:175-210 exactly, including its reasoning: runs_after is an ordering hint, and the cluster side already decided that a missing one must not make an object unmanageable. An operation that gave up waiting for a runs_after edge runs, and says so in an audit event. It does not write dependency_failure, which is reserved for the fate-sharing cascade.

    The asymmetry is the single most likely thing for an implementer to flatten, so the step brief says it twice and the definition of done asserts it with a test per branch.

    1. The settle ceiling is lowered to the dependency-wait budget, and the published maximum changes with it. Survey finding 3 leaves three options: accept unsatisfiable values, extend the budget by the declared settle, or refuse a settle the budget cannot honour.

    Extending the budget is excluded by decision 2's own argument: it was chosen specifically so that one caller cannot stall an instance's queue for a day, and a settle of 86400 would restore exactly that. Accepting unsatisfiable values means the API's 400s stop being the place a caller learns their request cannot work, and the operation fails 300 seconds later with an abort that reads like a dependency problem rather than a parameter problem.

    So settle_seconds is bounded by AGENT_OPERATION_DEPENDENCY_WAIT (decision 5) instead of AGENT_OPERATION_MAX_DEADLINE, in the helper at shakenfist/external_api/base.py:701, and AGENTDEPENDENCYSPEC_SCHEMA's maximum follows. This is the decision most likely to be argued with, because it tightens a published bound one phase after publishing it: a request with settle_seconds: 600 is accepted on develop today and refused after this phase. The counter-argument is that nothing can have depended on the looser bound, since no deployed release contains phase 1 and no evaluator honours the field, so the window in which the bound meant anything has not opened. A reviewer who disagrees should say so at the back brief, because reversing it after the evaluator ships is a real compatibility break rather than a correction.

    1. The budget is one configuration option, AGENT_OPERATION_DEPENDENCY_WAIT, defaulting to 300. Named for what it bounds rather than for the feature, in the manner of AGENT_OPERATION_MAX_DEADLINE. Its description states that it bounds a blocked head of an instance queue, that it is wall-clock from the first blocked evaluation and not a count of passes, that it also caps a per-edge settle delay (decision 4), and that raising it raises how long one caller's blocked chain can stall another's operations against the same instance -- which is decision 1's accepted cost, and the operator reading this option is the person who gets to re-take that trade.

    2. The settle delay is measured from the dependency's own completion, and the evaluator does not hydrate the dependency to find it. Decision 9 forbids hydration, and the state row carries no timestamp the evaluator can read without one.

    So the settle clock starts at the first evaluation that observes the dependency terminal, which is held in the terminal-dependency cache of decision 7 alongside the state. The consequence, which step 2f documents: a settle delay is "this many seconds after we noticed it finished", which is up to one DISPATCH_CHECK_INTERVAL (five seconds) later than the dependency actually finished. Phase 1's API documentation says "satisfied this many seconds after the dependency completed", which is now imprecise by up to five seconds and is corrected in step 2f rather than left to be found later.

    This decision as first written said the clock was "recorded in the same attribute decision 2 uses for the wait start", and that is not possible. The wait anchor is set on the first pass which finds an operation blocked on anything; the settle has to start when a particular dependency is seen to finish, which is later and is per dependency. One column cannot hold both. Step 2c implemented the attribute reading, which is how the defect reached the tree; the two clocks are now separate and the execution notes record it. It also cited a step 2g, which this phase does not have.

    1. The terminal-dependency cache is a plain dict on the dispatcher instance, cleared whenever the generation changes, and bounded. Terminal is absorbing, so a dependency observed terminal can never become non-terminal and the cache can never serve a stale answer in the direction that matters. It is keyed by operation UUID and holds the state string. It is cleared in start_dispatcher() alongside the generation bump, so a replacement thread starts cold, and it is capped at 4096 entries with the oldest evicted -- not because memory is tight but because an unbounded dict in a daemon that runs for weeks is the kind of thing a push audit finds.

    A cache miss is not cached: a dependency observed non-terminal is re-read every pass, which is the whole point.

    1. dependency_failure goes on external_view() in this phase, and phase 1's deliberate omission is reversed by design rather than by accident. Phase 1's definition of done asserted that dependency_failure appears nowhere in shakenfist/operations/agentoperation.py, precisely so that the field would not be published before anything wrote it. That assertion is now satisfied-and-retired: step 2d adds the property and the view entry, and the phase 1 criterion is not re-run. Whoever reviews this phase should expect that grep to return non-zero and should not read it as a regression.

    The shape is expiry_reason's: a read-only property over the attributes row (shakenfist/operations/agentoperation.py:544) and one key in the view dict (:278). Note that an instance's external_view() embeds each queued operation's whole view, so this field becomes visible on the instance endpoint too.

    1. No new capability token. Phase 1's agentoperation-dependencies token already advertises the two parameters, and master plan decision 3 makes that same token the thing which makes abort safe for a client polling its own operations. A second token for "and now they are evaluated" would advertise a behaviour change behind a parameter whose presence already implies it, and would give a client two things to check for one feature. The token's comment is extended to say that evaluation landed, so a reader of app.py is not left thinking the parameters are still inert.

    2. The evaluator is a method on the dispatcher, not on AgentOperation. The cluster side puts its walk in the work item (daemons/queues/workitem.py:143) rather than on the operation, and the cascade helpers it calls (abort_for_unsuitable_dependency, abandon_dependency_wait, cancel_for_missing_dependency) live on BaseOperation. This phase follows that split: the walk is SideChannelDaemon._dependencies_met(inst, agentop) returning a verdict, and the two state writes are methods on AgentOperation beside the expire_if_out_of_budget() precedent. That keeps the state transition and its attribute write in the class that owns the state machine, where the state_targets guard lives, and keeps the per-pass policy in the daemon that owns the pass.

    3. No retry interaction. AGENT_OPERATION_MAX_ATTEMPTS and the head-of-queue EXECUTING -> QUEUED retry from the deadlines plan are not consulted: a cascade-aborted operation never executed, so it has no attempt to retry, and abort is terminal so the retry path cannot reach it. Stated because an implementer reading attempts next to dependency_failure in the attributes model will wonder.

    Risks and mitigations¶

    • The asymmetry between depends_on and runs_after gets flattened. It is the most-copied-wrongly thing in the cluster-side original, and an implementer who factors the two walks into one helper will lose it. Mitigation: the 2c brief states it twice and asks for a four-case statement in the report; 2d adds two mutants specifically for the runs_after branches; and the definition of done asserts one test per branch. The management session checks the report's four sentences against the diff rather than against the tests.
    • A cascade writes state from a superseded dispatcher generation. Decision 1 places evaluation after the generation check for exactly this reason, and the position is one line's carelessness away from being wrong. Mitigation: the definition of done pins it with a grep for the order of the three landmarks in the pass, which is falsifiable without running anything.
    • The budget anchor gets rewritten and the budget never expires. note_dependency_wait_started() is idempotent by construction (decision 2, step 2b), but a caller could still write the attribute directly.
