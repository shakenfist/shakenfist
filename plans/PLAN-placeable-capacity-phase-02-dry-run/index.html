    Placeable capacity phase 2: the placement dry run¶

    Prompt¶

    Before responding to questions or discussion points in this document, explore the shakenfist codebase thoroughly and ground your answers in what the code actually does today. Do not speculate when you could read instead. Flag uncertainty explicitly.

    This is phase 2 of PLAN-placeable-capacity.md. Read that master plan's "Phase 2: the placement dry run" section first, its G1, G2 and G5 requirements, and phase 0's D11, D12 and D13 (PLAN-placeable-capacity-phase-00-decisions.md), which constrain what this phase may assume. This phase adds an API surface and changes no placement arithmetic.

    Citations below are into develop at d20a7d7516 unless stated otherwise. Citations into shakenfist/private-ci are into its master at dce12f6.

    Planning effort¶

    High, as the master plan specifies: the phase is small in code and load-bearing in contract. What it publishes is what every later caller reads, and the refusal vocabulary it answers in is already in production use by a consumer that reimplemented it (F2), so a different vocabulary here would be a silent incompatibility rather than a compile error. The review effort is high for the same reason.

    Scope¶

    In:

    • A stateless placement query built on phase 1's find_candidates_for_shapes(): given a multiset of requested shapes, answer whether they fit now and on which nodes, writing no state and publishing no audit events.
    • One new REST endpoint, its parameter declaration, and the structured shape schema that declaration needs.
    • One capability string (G5).
    • An apiclient method and capability probe in client-python, which is where every consumer of this reaches the API from.
    • Unit tests, OpenAPI registration, and mutation testing to prove the tests would catch the query's removal.
    • Operator and user documentation for the new surface.

    Out:

    • Shape holds (A). Phases 3 and 4.
    • Switching shakenfist/private-ci's shadow fit check from its local model to this call, and the soak that re-applies D13's test to the result. That is the other repository's work, under PLAN-placeable-claims, and it gates phase 3 rather than this phase (D9).
    • The sf-client and sf_claim shape verbs, and the affinity expression. Phase 6, per D11's "left to phase 6".
    • Any change to what a filter decides, what a stage is called, or what any event contains (G5). This phase adds a reader of the placement pipeline, not a change to it. One exception was made deliberately after the review round, and it is the only one: the affinity skip predicate now tests the namespace before it reads an instance's tags, which changes the skipped reason reported for an instance that is both tagless and foreign from no tags to different namespace. Both are true of such an instance and nothing reads the reason -- it is audit prose rather than an input to a decision. The saving is every metadata read an affinity-bearing query or create used to spend on instances in other namespaces, which on a cluster with many namespaces is most of the reads such a request makes. A request with no affinity never reached the predicate, so it saves nothing.
    • Issue #4842, the string cpus 500 at admission. Filed during this phase's survey (F9) and deliberately not fixed here: it is a create-path type error, and a phase that adds a query has no business changing what a create does.
    • Optimising the placement walk's event-payload construction, unless step 2e measures it as hot. The master plan asks for a measurement rather than a guess, and D5 records what the measurement decides.
    • Rate limiting or quota on the new endpoint beyond the shape-count bound in D10.

    What the survey found¶

    F1. The consumer this phase was written for already exists, and already scores itself. The master plan says "private-ci will call it in shadow before creating a runner's namespace and score the answer against what the job's creates actually met minutes later". That harness is built and merged: PLAN-placeable-claims-phase-03-node-fit.md is Complete (0513d69, private-ci #241). conductor/nodefit.py rebuilds the scheduler's per-node eligibility checks from the per_node mapping of GET /admin/resources, conductor/db.py:6012 (record_node_fit()) records each verdict, and conductor/db.py:5808 (get_node_fit_set_agreement()) scores them against what the creates actually met. So this phase does not build a shadow harness. It replaces a client-side reimplementation with a call, and private-ci's own plan already anticipates that ("becomes a call to it" waits on phase 5, its F6). The master plan's phase 2 section is corrected to say so.

    F2. The refusal vocabulary is already pinned by that consumer. conductor/nodefit.py's module docstring names the stages it models, in the order the scheduler applies them and under the names the scheduler reports: cpu_max_per_instance, sufficient_idle_cpu, sufficient_idle_memory, sufficient_free_disk, capacity_guard. It also names what it cannot model from /admin/resources and therefore does not try to: the disk-busy stage (sufficient_idle_disk, "whose input is not published"), the demand clause, the claim stage and the cluster stage, plus the scheduler's ordering of candidates by load, where it "packs worst-fit on memory instead". Those five omissions are the whole value of a server-side dry run, and they are also the reason this phase must answer in exactly those stage names: a prediction and a refusal are compared label for label by code that is already deployed.

    F3. The event-construction cost the master plan flags is real, and its arithmetic is confirmed. add_event_multi() returns immediately when given no targets (shakenfist/eventlog.py:46), so a dry run publishes nothing -- but every extra= payload is built by the caller before the call, so all of it is assembled and discarded. The master plan's "around fourteen times per shape" is right, and precisely: on a clean create-path walk a shape reaches five unconditional direct sites in _find_candidates_for_shape() (shakenfist/scheduler.py:1358, :1418, :1634, :1747, :1793) and nine invocations of _log_and_raise_on_error() (:1155), which emits exactly one event each, for fourteen. Four further sites fire conditionally: forced candidates (:1394), one per unknown node in a forced list (:1408), a degraded capacity read (:1466) and a narrowing that selected nothing (:1680).

    F4. Phase 1's deferred return-type question can be closed, and the answer is "leave it alone". Phase 1 documented, rather than enforced, the rule that only the heads of its per-shape candidate lists are an assignment, on the grounds that "the type to return is the one phase 2's real consumer wants". The hazard it was guarding against -- a caller walking past a head, as Instance.place_on_candidates() does when admission refuses it (shakenfist/instance.py:1549) -- cannot arise for a caller that places nothing. A dry run wants both halves: the head, because that is the node the set was costed against, and the fallbacks, because an operator asking why a set fits wants to see the room behind the answer. D7 keeps the core's signature and return type unchanged.

    F5. /admin/resources already has the per-node shape this phase would have added, and cannot carry the query. GET /admin/resources is scheduler.summarize_cluster_resources() (shakenfist/external_api/admin.py:168, shakenfist/scheduler.py:833), returning total, per_node, excluded and cluster_capacity (:621). excluded is already a per-node reason map, built from the metrics-unavailable reasons and _queue_exclusion_reason(), and its keys are advertised separately as the capability tokens cluster-capacity, cluster-resources-excluded and cluster-claims (shakenfist/external_api/app.py:440-448). What it cannot do is answer this phase's question: a per-node verdict is a verdict about a shape, and a GET with no body has no shape to be about. D6 resolves the master plan's "show the per-node answer in GET /admin/resources" accordingly, and that sentence is corrected at source.

    F6. The declaration vocabulary already has the array-of-object form the request body needs. shakenfist/external_api/base.py carries arrayofdict, arrayofdiskspec and arrayofnetworkspec (:821-829), each built on a named schema such as DISKSPEC_SCHEMA (:535) with additionalProperties: False. A shape array is the same construction. Three mechanical consequences for the brief: several 'body' parameters are merged into one rendered in: body schema (:1300-1328), so test_at_most_one_body_parameter_per_operation (shakenfist/tests/external_api/test_openapi_spec.py:555) is not a constraint on how many body fields are declared; a new structure must be registered in STRUCTURED_PARAMETERS (:109) or test_every_published_structure_or_bound_is_registered (:511) fails; and the integer fields follow the existing claim-limit declarations (shakenfist/external_api/auth.py:1569-1574), which use 'unsignedinteger'.

    F7. The real consumer holds a shape with its disks already summed. conductor/nodefit.py:205 and :417 both say so: a shape is (cpus, memory_mb, disk_gb), "with its disks summed". G1 says a shape is "what POST /instances takes: cpus, memory and the disk list, matched on the summed disk size". Both are satisfiable at once, and D2 does: the body takes a summed disk in GB, and accepts a disk_spec diskspec array as the alternative form, summed server-side by mariadb.disk_spec_virtual_gb() (shakenfist/mariadb.py:26736) -- the same helper Instance._capacity_claim() uses (shakenfist/instance.py:1198), so a dry run and a create cannot disagree about how much disk a shape is.

    F8. D11's shape vocabulary includes a key phase 1's core has no counterpart for. D11 fixes the project's shape vocabulary as cpus, memory in MB, disk in GB and count. It was written for the claim verbs, but a shape should mean one thing across the API, the CLI and the Ansible module, so D2 uses those keys. find_candidates_for_shapes() takes a flat list with no multiplicity, so count is expanded by the handler into that many identical shapes, which is also what makes D10's bound necessary.

    F9. Phase 1's deferred bug had no live home. Phase 1 recorded the POST /instances string-cpus 500 as belonging to PLAN-api-input-validation's scope. That plan is Complete (9 of 9) and never covered the site. Verified still broken on this tree: the handler passes the body value to Instance.new() untyped, _capacity_claim() returns it unchanged, and shakenfist/mariadb.py:29644 multiplies it by the float SCHEDULER_DEMAND_PER_VCPU (shakenfist/config.py:647), which raises TypeError: can't multiply sequence by non-int of type 'float'. Filed as issue #4842, and the master plan's "Bugs fixed during this work" entry now points at it rather than at a closed plan.

    F10.     Decisions¶

    D1. One new endpoint, POST /placement, namespace authenticated, with the per-node detail admin-only. A query that takes a multiset cannot be a GET, and it is a question about the cluster rather than about an instance that exists, so it does not belong under /instances/<instance_ref> where the converter would shadow it. Namespace authenticated because G3's whole premise is that ordinary callers benefit; the caller's own namespace is the context the answer is computed in.

    The per-node split is the part worth arguing about. A tenant learning which node UUIDs exist, how much room each has and which filter stage each failed is a cluster-topology disclosure that no current endpoint gives a non-admin. So a non-admin caller is answered at set level -- does the whole multiset fit, and if not, the stage that emptied the list -- and an admin caller additionally gets the per-shape ordered candidate lists. The real consumer is unaffected: private-ci's conductor already reads GET /admin/resources, so it holds admin rights today.

    D2. The request body is shapes, an array of objects with cpus, memory, disk, disk_spec, count and affinity. cpus and memory (MB) are required; disk (GB) and disk_spec (a diskspec array) are alternatives and giving both is a 400; count defaults to 1; affinity is the existing affinity document, in the prefer_*/require_* form (G4). The keys are D11's, so a shape means the same thing here as it will on the claim verbs, and disk_spec exists so a caller that already holds a POST /instances body can ask about it without summing the disks itself (F7). Summing is mariadb.disk_spec_virtual_gb(), not a second implementation.

    D3. The response names the stage, not a boolean. At set level: fits, and when false, stage and shape -- the index of the shape that ran out of candidates. For an admin caller, a shapes array in request order, each entry carrying node (the head, the node that shape was costed against) and candidates (the ordered list behind it). No new stage names are minted (G5); the values are exactly what _log_and_raise_on_error() already reports, which is what makes F2's label-for-label comparison possible.

    D4. A set that does not fit is a 200 with fits: false, not a 507. This is the decision a reviewer is most likely to dispute, because every other capacity refusal in this API is a 507 and symmetry is a real argument. It is wrong here: the question "would these fit" was answered, and answered correctly, so the request succeeded. A 507 would make a caller's error handling unable to distinguish "the cluster is full" from "the query failed", which is precisely the distinction a dry run exists to provide, and it would put a transient-retry contract (G7) on an answer that is advisory by construction. A 507 remains what a create gets. The endpoint's own failures -- a malformed body, an unreadable metrics table -- keep their ordinary status codes.

    D5. Pass no event targets, and measure before optimising. The handler calls find_candidates_for_shapes() with related_objects=None, so the walk publishes nothing: a speculative evaluation stays out of the event log, which is the behaviour phase 1 built for exactly this caller. The payload construction still happens (F3). Step 2e measures it against a real multiset; if it is hot, the guard goes once at the top of _find_candidates_for_shape() rather than at fourteen call sites, as the master plan directs. If it is not, the measurement is recorded and nothing changes -- a dict built and dropped is not a defect, and the guard would be a conditional on a correctness- critical path bought with nothing.

    Amended by the measurement, which rejected this decision's own remedy. Step 2e found that the cost is not dict assembly at all: Instance.tags is an uncached metadata read, so the payload drives database round trips, and the two preferred-tag loops read it once per tag the caller named rather than once per neighbour. The guard prescribed above removes 6,000 redundant reads of an eight-shape query on a twenty-node cluster; reading the tags into a local once per neighbour removes 8,000, costs no conditional, and leaves the guard with nothing to save. The local is what was implemented. The Results section carries the counts and the arithmetic.

    D6. /admin/resources is left alone. The master plan's instruction to "show the per-node answer" there cannot be followed literally: a per-node verdict is a verdict about a shape, and that endpoint takes no shape (F5). Publishing something shape-free instead -- the largest shape each node would currently accept, say -- would be a second, independently derived answer beside the real one, which is the failure mode _summarize_resources()'s own comments warn about twice. An operator wanting a per-node answer asks POST /placement with the shape they care about. The master plan's sentence is corrected rather than silently not done.

    D7. Phase 1's core is not changed, with one amendment made during execution. Not its signature, not its return type, not its stage names, not its events. F4 settles the question phase 1 left open in favour of the existing type.

It obtained the index without touching the core, by binary searching prefixes of the walk order -- sound, because prefix refusal is monotone, and documented as such. That was the wrong shape for three reasons, so D7 was amended to authorise one change to shakenfist/scheduler.py and shakenfist/exceptions.py: the master plan's G7 already requires a hold refusal to name "the shape and stage", so phases 3 to 5 need the index on the exception regardless and would otherwise rebuild or remove the search; a refusal is the common case for a query rather than the exceptional one, so up to six extra walks of the whole pipeline land on the path the endpoint exercises most; and recovering the order from _shapes_largest_first, a private module helper, coupled the API layer to an internal that is free to change.     D10. A bound on shapes per request, published in the declaration. count expansion means a short body can ask for a long walk, and the walk is O(shapes x candidates) with fourteen payload constructions per shape. The total expanded shape count is capped at 64, declared as a maximum on count and enforced on the sum, with a 400 naming the bound. 64 is above every real set in the callers table -- 33fl's largest is eight runners -- and far below a cost worth worrying about. Chosen as a published number rather than a configuration setting: a caller needs to know the bound to respect it, and nothing yet justifies per-cluster tuning.

    Risks and mitigations¶

    R1. A dry run that predicts admission can drift from admission. The answer is computed from the scheduler's filters, but a create is finally admitted by the guarded capacity claim, and scheduler-reservations phase 5a is in flight to flip a hard ceiling in that guard (F10). A dry run that silently stops matching is worse than no dry run, because a consumer scores against it. Mitigation: the answer is advisory by construction and documented as such (2b), the capacity_guard stage is in the vocabulary this phase answers in (F2), and private-ci's existing scoring reports a disagreement with the stage that caused it -- which is the detector. The management session checks phase 5a's merged diff against this phase's handler before phase 2's own pull request lands, and says in the Execution notes whether anything moved.

    R2. A caller treats an advisory answer as a guarantee. The race is inherent: the room can be gone before the next request. Mitigation: D4's 200-with-fits makes the answer data rather than a promise, the documentation says so in the operator guide and the user guide (2b), and the existing consumer already treats its own verdict as scoreable rather than authoritative. Checked by the management session reading 2b's prose for any sentence that could be read as a reservation -- the word to hunt for is "will".

    R3. The endpoint is a cheap request that buys an expensive walk. Mitigation: D10's published bound, enforced on the expanded total rather than on the array length, with a test that the bound is a 400 naming itself (2a) and a mutation proving the test bites (2c).

    R4. The information disclosure in D1 is drawn in the wrong place. Admin-only per-node detail may turn out to be too strict for a legitimate tenant use, or not strict enough if the set-level stage name itself leaks more than intended. Mitigation: the split is a decision in this document rather than an accident, the test suite asserts both sides of it (2a), and relaxing it later is additive. The back brief asks Michael, because it is a security boundary and not a style question.

    R5. The shape vocabulary diverges from the one phase 6 will ship. D2 takes its keys from D11, which was written for the claim verbs; if phase 6 changes its mind the API and the CLI disagree about what a shape is. Mitigation: D2 cites D11 as its source so the dependency is visible, and phase 6's planning session is told in the master plan's phase 6 section that the API keys are already published and are the constraint, not the other way around.

    The disk survivor is the instructive one. Substituting int(d.get('size', 0)) for the ledger's own helper passed every test, because every size the tests used was a plain integer -- and at the shipped validation mode the integer field refuses a fractional or string size before the handler sees it, so the rounding the helper documents is unreachable from this endpoint. What is reachable is a present-but-null size, which the schema documents as meaning "the size of the base image": the helper skips it, and a local sum evaluates int(None) and turns a documented request into a server error. That is the test which now pins the delegation, and it runs at the default rather than on an operator's rollback.

    Step 2e: what does a discarded event payload cost?¶

    The first measurement said about 1.5 ms of CPU per eight-shape query, some 23% of the walk, attributed by timing a stripped copy of the methods swapped in through __code__ so the tree was never edited. Read on its own that number says the construction is too cheap to be worth guarding.

    It was the wrong number. BaseObject.metadata is an uncached property: every access is a get_object_metadata() call, and the only attribute_memo() in the scheduler covers the requesting instance's own attributes rather than the placed neighbours whose tags the affinity payload reads. In the measurement fixture that read is a mock costing nothing, so what was timed was dict assembly with the expensive part stubbed out.

    Counting the reads instead settled it, and counts are deterministic where timings are not. For an eight-shape query against twenty nodes holding fifty instances each, repeated three times with identical results each time:

    Variant get_object_metadata calls
    As written 20,000
    Payload construction stripped out 14,000
    Tags read once per neighbour 12,000

    The distinct rows read are identical in all three, so every one of those differences is a repeat read of a row already fetched.

    The defect was worse than "four reads per neighbour", which is what it looks like from the source. The two preferred-tag loops read Instance.tags once per tag the caller named, so the cost of scoring a neighbour grew with the size of the affinity specification while the information gained stayed the same. A seven-tag preference paid seven reads of one row where one would do.

    D5 is therefore amended, and the amendment is a rejection of its own remedy on evidence. Guarding payload construction -- which D5 and the master plan both prescribed -- is the middle row: it removes 6,000 of the redundant reads and buys a conditional on the placement path to do it. Reading the tags into a local once per neighbour removes 8,000, costs no branch, and subsumes the guard entirely: measured on the fixed tree, stripping the payload now saves nothing at all, because the payload no longer issues a read. The hoist is sound for the reason the set walk already relies on -- a decision is a snapshot, a set places nothing, so no neighbour's tags can change while the walk is in progress, which is the same reasoning behind the memo that reads each node's placed instances once for the whole set.

    Two tests pin it, by read count rather than by timing, so a reintroduced repeat fails rather than merely slowing down: one asserts the exact count for a known fixture with the arithmetic in its docstring, and one asserts that the count does not move when the affinity specification names seven tags instead of one -- the per-tag growth being the part a single-tag test would have missed.

    A larger saving, left alone deliberately¶

    Two further reductions were found and not taken, both because they reach past this phase's scope rather than because they are wrong.

    The skip predicate tests i.tags before it tests the namespace, and Instance.namespace is a plain attribute while i.tags is a database read. So every query reads the metadata of every placed instance in every other namespace and then discards it -- on a cluster with many namespaces that is most of the reads it makes. Swapping the two tests would cost nothing and save all of them, but it changes which reason an audit event reports for an instance that is both tagless and foreign, and this phase changes no event payload.

    Beyond that, a per-decision metadata memo on the set walk would collapse repeated reads of one instance across shapes and stages, and would save considerably more than reading the tags into a local does. That is a change to how the set walk caches, which is the placement core's own design, and it wants its own tests and its own thought rather than a corner of this one.

And a review note from the management session asserted that the endpoint's declared 503 was never produced; step 2a disproved it by probing the running endpoint -- handle_database_unavailable is in Resource.method_decorators, so an unreachable database answers 503 for every handler, which is how the other endpoints' declared 503s are produced as well. The real defect was the declaration's wording, which promised a 503 for an unreadable capacity read; phase 1 deliberately degrades that read and answers anyway, so the declaration now says so and both halves are tested.

    One thing step 2a offered to defer was taken instead. It reported that the query accepted affinity documents the create path refuses, because the published schema types affinity as an unconstrained object, and asked whether to act. Taken: a query which answers "that would fit" about a document a create answers 400 to is the divergence this phase exists to prevent, and a mistyped constraint read as no constraint at all is worse than a refusal. The create path's validation was extracted into one shared implementation rather than copied, with its error strings unchanged.

    One extra from step 2a was kept deliberately. caller_has_admin_rights() in shakenfist/external_api/base.py splits the admin predicate out of the caller_is_admin decorator, so the endpoint's disclosure boundary and the decorator which enforces it read one definition. It is what docs/developer_guide/coding_rules.md's "Never restate a visibility predicate" asks for, and the decorator still decides on its own whether to answer 401 or 403.

    A brief given to a step contained a false premise, which the step caught. Step 2a was told flake8 here enforces 79 columns. It enforces 120 (tools/flake8wrap.sh). Nothing was mis-wrapped as a result, but the correction belongs in the record.

    Review round on the pull request¶

    One automated round, 3 document and 8 consider items, no fix. Nine were actioned and one declined. Three are worth recording beyond the commit message.

    The query advertised a stage it can never return. The module docstring, the operator guide and the user guide all listed capacity_guard among the stages an answer may carry. It is raised only at admission, and the query never reaches admission. That is worse than ordinary drift here, because the endpoint exists so a deployed consumer can score predictions against real refusals label for label, and capacity_guard is precisely the refusal a dry run cannot predict. The lists are corrected and each page now says admission-only stages reach a create's 507 and never a query.

    The disk delegation agrees with the ledger, not with the filter. _shape_disk_gb() sums with the ledger's helper so that a query and a create cannot disagree about how large a request is. For a fractional size the query predicts a gigabyte more than the filters would charge. The claim is corrected rather than the sum: making the core delegate would change what a filter decides, which this phase does not do. The divergence itself is filed as shakenfist#4853.
