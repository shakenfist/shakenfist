    Phase 3: OIDC discovery¶

    Context¶

    This is phase 3 of PLAN-oidc-authentication.md, and the first phase of that plan to change production code. Phases 1 and 2 were superseded by PLAN-auth-federation.md phase 3, and phase 0 was a decisions phase whose output was documentation.

    Phase 0 landed as pull request #4831 (merge commit 2bbe472eff, 2026-11-07) and its close-out is the first commit of this phase, per the plan-phase-landing shared block.

    What phase 3 exists for is narrow and load-bearing. Auth federation phase 3 built the verification half of an OIDC relying party: a workload arrives already holding a minted token, so nothing in the tree ever needed to start a conversation with an issuer. A human does. Both of the flows open question 9 is weighing — device code, and authorisation code with PKCE — begin by calling an endpoint at the identity provider, and a relying party is supposed to learn where those endpoints are from the provider's discovery document. Nothing in the tree fetches one.

    So phase 3 is the prerequisite of open question 9, and therefore of phase 7, and therefore of the whole human-login half of the master plan.

    Planning effort: high. This phase adds a schema migration, an outbound network fetch, a new unauthenticated endpoint and a security-critical equality check. The master plan's Agent guidance reserves high effort for exactly that list.

    Review effort: the master plan specifies none for this phase. Review at high effort anyway, for the reason in the risks section: the issuer equality check is the kind of thing that is easy to write loosely and expensive to have written loosely.

    Scope¶

    In scope.

    • Fetching and validating an issuer's OpenID Connect discovery document, and storing the three endpoints a client flow needs (authorization_endpoint, token_endpoint, device_authorization_endpoint) on the TrustedIssuer.
    • Making jwks_uri optional on issuer create and update, so that an operator can configure a provider by its issuer URL alone.
    • The two fields a flow needs that no discovery document can supply: the client identifier registered at the provider, and the OIDC scope list to request.
    • An administrative way to re-run discovery on an existing issuer.
    • A public endpoint serving the login metadata a client needs before it holds any Shaken Fist credential. See decision D7 for why this is here rather than in phase 7.
    • Unit test coverage, documentation, and API capability advertisement.

    Out of scope, deliberately.

    • Any client-side flow. sf-client is in the separate client-python repository; this repository ships only sf-ctl and sf-backup (pyproject.toml:190-191). Device code and authorisation code with PKCE are phase 7 and cannot be implemented in this checkout.
    • Minting credentials at login. That is phase 4.
    • Functional coverage against a real identity provider. That is phase 9, which stands up a containerised provider. Phase 3 ships unit tests against a stub document; the only honest test of discovery against Keycloak and Authentik is phase 9's.
    • Worked operator walkthroughs for Keycloak and Authentik. Phase 8. Phase 3 documents the fields and the mechanics, not an end-to-end provider setup.
    • Taking the JWKS location from a token. Not up for discussion, and nothing here changes it: discovery writes an issuer's fields at configuration time and validation keeps reading them from the object, exactly as today.
    • Re-running discovery automatically. See D3.
    • Tightening issuer_url to https. A real gap found by this survey, recorded as finding 6 and filed rather than fixed. See D10.

    What the survey found¶

    The master plan's phase 3 section was written on 2026-08-12 and re-checked in phase 0 on 2026-11-07. Its premises were verified again against 08c26e343b while planning this phase, and every claim phase 3 rests on still holds. That is a real result and worth saying plainly. The findings below are the detail the section does not carry, plus one gap it does not mention.

    1. Discovery is still genuinely absent¶

    grep -rn "openid-configuration\|well_known\|device_authorization\|token_endpoint" --include='*.py' across the tree returns one hit, and it is a test about guest image names. There is no discovery code to extend, so this phase is additive rather than a refactor.

    2. jwks_uri is mandatory, and the API says so three times¶

    TrustedIssuerAttributesData declares it non-optional (shakenfist/schema/trusted_issuer_attributes.py:50); _validate_issuer_arguments refuses a create or update without it and requires https on it (shakenfist/external_api/auth.py:895-920); and TrustedIssuer.update() writes all three attribute columns together with a field mask naming all three, on the stated reasoning that a new issuer_url with a stale jwks_uri is a broken issuer rather than a partly updated one (shakenfist/trusted_issuer.py:253-273). Making the field optional therefore touches the schema, the endpoint validator and the update path, and D4 has to say what the update path writes when discovery supplies some fields and the operator others.

    3. The attributes table is at version 1 and has never migrated¶

    TRUSTED_ISSUER_ATTRIBUTES_VERSION = 1 (shakenfist/mariadb.py:482), and _ensure_trusted_issuer_attributes_schema (shakenfist/mariadb.py:14827-14848) has only the create-at-version-1 branch — there is no migration step to copy. The pattern to follow is _add_missing_node_metrics_columns (shakenfist/mariadb.py:2234-2252), which takes each column's type from the table definition so the DDL cannot drift from the Pydantic model, and guards each ADD COLUMN with an existence check so re-runs are safe.

    The object's own version does not move. TrustedIssuer has initial_version = 1 and current_version = 1 (shakenfist/trusted_issuer.py:41-44), and that version describes the static row — uuid, name, version. New mutable attributes do not change its shape, so the dbo version stays at 1 and only the table version becomes 2.

    4. There is no client_id anywhere, and the master plan does not mention it¶

    This is the gap. A device-code flow posts to device_authorization_endpoint with a client_id, and an authorisation-code flow needs one too. Discovery cannot supply it: it is a registration the operator performs at the provider. The same is true of the OIDC scope list — a group claim does not appear in a token unless the client asked for the scope that carries it.

    So "discovery populates a TrustedIssuer's fields" is necessary and not sufficient. Three of the five things a flow needs are discovered; two are operator-supplied. The master plan's phase 3 section is silent on both, and this phase adds them, because a phase 7 in another repository cannot add a column to a table in this one. The master plan's section has been corrected to say so as part of this phase's planning commit.

    5. Admin-only issuer endpoints, and a public endpoint convention to copy¶

    /auth/issuers and /auth/issuers/<issuer_name> are both @api_base.caller_is_admin (shakenfist/external_api/auth.py:960-1095, routed at shakenfist/external_api/app.py:650-652). A person who has not logged in yet cannot read either, which is what forces D7.

    The convention for an endpoint that must be readable without a credential is @api_base.public (base.py:2634), used by Root, Livez, Readyz (app.py:567-598) and by AuthFederatedEndpoint (auth.py:1902-1906), whose comment is the precedent: "Unauthenticated by nature: the whole point is that the caller has no Shaken Fist credential yet". That endpoint also shows the shape of abuse resistance for a public auth route — limit_federated_body_size as a before-request hook (app.py:232-242) and federation.enforce_rate_limit (federation.py:462-489) counted before anything expensive.

    6. issuer_url is not required to be https¶

    _validate_issuer_arguments requires https on jwks_uri and says why — "a JWKS fetched over HTTP can be substituted by anyone on the path, which turns signature verification into theatre" (shakenfist/external_api/auth.py:915-919) — but applies no such check to issuer_url. Today that is only a bad idea, because issuer_url is compared and never fetched. Discovery fetches it, so the same reasoning applies with the same force.

    Tightening the existing field would be a breaking change to a live API for deployments this session cannot inspect, so it is filed rather than fixed (D10). The discovery path enforces https on what it fetches regardless, which is the part that matters here.

    7. The CA bundle union is a trap that requests will walk straight into¶

    jwks_ssl_context() (federation.py:71-118) exists because ssl.create_default_context(cafile=...) loads that file instead of the system store, so the short way of writing it would mean that configuring a private Authentik silently stopped GitHub tokens verifying. requests has the identical trap: verify='/path/bundle.pem' replaces the system store rather than adding to it. requests is a dependency (pyproject.toml:125) and is used for outbound fetches elsewhere (shakenfist/images.py:467), but no code in the tree mounts an HTTPAdapter carrying an SSLContext. D8 settles how the fetch is built.

    gunicorn_config.py:148-164 already calls jwks_ssl_context() at worker start so that a bad bundle path is a log line at deploy time rather than a failed login weeks later. Discovery inherits that warning for free by reusing the same function, and must not introduce a second bundle setting.

    8. Redirects are refused on the JWKS fetch, and operators have been bitten¶

    docs/operator_guide/authentication.md:366-380 documents that PyJWT 2.14 builds its fetch opener with redirects refused, that jwks_uri must therefore be the final URL, and that the symptom is indistinguishable from an unreachable provider. Discovery should behave the same way for the same reason, and because an operator who has read that section will expect it to.

    9. Capabilities are advertised, and a client cannot feature-detect otherwise¶

    Decisions¶

    D1. The discovery URL is built by appending to the issuer URL's path, not by inserting before it. OpenID Connect Discovery 1.0 §4.1 appends /.well-known/openid-configuration after the issuer's path; RFC 8414 §3.1 inserts it between the host and the path. The two differ for any issuer with a path, which is both of the providers phase 8 must document: Keycloak serves https://host/realms/<realm>/.well-known/openid-configuration for issuer https://host/realms/<realm>, and Authentik serves https://host/application/o/<slug>/.well-known/openid-configuration for issuer https://host/application/o/<slug>/. Append is what works against real providers, so append is what we do.

    D1a. One trailing slash is stripped before appending. Authentik's issuer carries a trailing slash and its iss claim carries it too, so an operator will configure it with the slash — correctly, because D2 compares exactly. Naive concatenation then produces .../<slug>//.well-known/openid-configuration, which many servers answer with a 404 that looks like "this provider does not support discovery". Exactly one trailing slash is stripped from the URL used for the fetch, and the configured value is left untouched for comparison. This needs a unit test of its own; see the Definition of done.

    D2. The document's issuer member must equal the configured issuer_url byte for byte, or discovery is refused. No normalisation, no trailing-slash tolerance, no case folding. This is the security property of discovery, and it is the mirror of the exact iss comparison the operator guide already explains at docs/operator_guide/authentication.md:168-172: without it, a document fetched from one place can name endpoints belonging to another, and we would hand a user's browser to whoever controls the document.

    The comparison is against the value the operator configured, not against the slash-stripped URL D1a fetched. An operator who configures Authentik without the trailing slash gets a clean refusal naming both values, which is the correct outcome: their iss comparison was going to fail at exchange time anyway, and discovery finding it at configuration time is the whole benefit.

    D3. Discovery runs only when an administrator asks. Never on the request path, never on a timer. Three places trigger it: issuer create, issuer update, and an explicit refresh. Nothing else.

    The reasoning is open question 8's, applied to a smaller case: putting the identity provider on a path that cluster operation depends on is a reliability regression sold as a security improvement. It is also what the master plan already promises — "discovery populates a TrustedIssuer's fields at configuration time, and validation keeps reading them from the object."

    The cost is that an endpoint which moves at the provider stays stale until an administrator re-runs discovery. That is not a regression: jwks_uri is operator-supplied and equally static today, and an endpoint that moves silently is a provider migration, which is an administrative event anyway. A periodic refresher is recorded as future work.

    D4. jwks_uri becomes optional, and when supplied it wins. Three cases, and the asymmetry is deliberate:

    • jwks_uri omitted. Discovery is mandatory. If it fails, the create or update fails, with the discovery error in the response. An issuer with no jwks_uri cannot verify a signature at all, so a half-created one would be worse than none.
    • jwks_uri supplied. It is written verbatim and discovery never overwrites it. Discovery still runs for the other endpoints, but it is best effort: a failure is logged, an audit event is added to the issuer, and the create or update succeeds.
    • Both, and they disagree. The operator's value wins, and the disagreement is an audit event on the issuer naming both URLs. Not a refusal, because docs/operator_guide/authentication.md:366-380 documents a case where the correct jwks_uri is deliberately not the one the document names: a provider that answers its published JWKS path with a redirect to a CDN needs the CDN path configured, and refusing that would break a deployment the documentation tells operators to build.

    The best-effort half is what keeps every existing deployment working. Every issuer configured today supplies jwks_uri, so no existing create or update changes outcome — it only gains fields and, where the provider publishes no document, an audit event.

    D5. client_id and oidc_scopes are operator-supplied, and both are optional. They cannot be discovered (finding 4). They are optional because the workload exchange does not need them: an issuer configured purely to verify GitHub Actions tokens has no client registration and never will, and requiring one would break every issuer in existence to serve a flow that issuer will never run. An issuer is login-capable when it has a client_id and a device_authorization_endpoint or an authorization_endpoint; only login-capable issuers appear in D7's listing.

    oidc_scopes defaults to openid when a client_id is set and no scopes are given, because openid is the one scope every OIDC flow must request.

    D6. Flow availability is read off the endpoints, and grant_types_supported is not stored. A provider that supports the device-code grant publishes device_authorization_endpoint (RFC 8628 §4), so its presence is the signal, and a client that finds it absent falls back to authorisation code. Storing grant_types_supported as well would mean a JSON column, a second source of truth about the same question, and a decision about what to do when they disagree.

    The limitation is real and worth writing down: a provider can publish the endpoint and not have enabled that grant for our client, in which case the flow fails at the provider with the provider's own error message. That is a configuration mistake the operator can read, which is a better failure than a client silently not offering a flow that would have worked.

    D7. A public GET /auth/login serves login metadata, and it lands in this phase. This is the decision most likely to be argued with, so here is the argument.

    The master plan puts the client flows in phase 7, in client-python. A person running sf-client login holds no Shaken Fist credential — that is the point — and /auth/issuers is admin-only (finding 5). So the metadata has to reach them from an unauthenticated endpoint, and an unauthenticated endpoint in this repository cannot be added by a phase that executes in another one. Leaving it out would make phase 3 unable to satisfy the dependency the master plan says it exists to satisfy: "neither flow can begin without the issuer's endpoints".

    It serves, per login-capable issuer: name, issuer_url, client_id, oidc_scopes, and whichever of authorization_endpoint, token_endpoint and device_authorization_endpoint are set. Nothing else — not jwks_uri, not audience, not the uuid, not the state, and not issuers that are not login-capable.

    What it discloses is which identity provider a cluster trusts for human login. That is mild: the endpoints themselves are public at the provider, and a client-visible login configuration is what every OIDC relying party publishes. It is not nothing either — it tells an attacker where to aim a phishing page — so the narrowness of the field list above is part of the decision, and the endpoint is rate limited like /auth/federated.

    D8. The fetch is a requests session with an HTTPAdapter carrying jwks_ssl_context(), redirects refused, body capped. Four parts, each for a reason the survey found:

    • The same SSL context as the JWKS fetch, via an adapter rather than verify=, because verify= replaces the system trust store instead of adding to it (finding 7). Reusing jwks_ssl_context() also means no second CA-bundle setting and the existing gunicorn worker-start warning covers discovery too.
    • Redirects refused, matching the JWKS fetch and the documented expectation it created (finding 8).
    • A response body cap, because nothing else bounds what a hostile or broken provider returns and the document is a few kilobytes. A new setting, FEDERATION_DISCOVERY_MAX_BYTES, default 65536.
    • Its own timeout, FEDERATION_DISCOVERY_FETCH_TIMEOUT_SECONDS, default the same as FEDERATION_JWKS_FETCH_TIMEOUT_SECONDS. A separate setting rather than a reuse, because that setting's own comment ties its value to the request-path hazard of pinning a gunicorn worker per queued anonymous request, and discovery runs on an admin-only path where that hazard does not exist. One setting would mean an operator who lengthens the admin timeout lengthens the anonymous one too.

    D9. The scope field is named oidc_scopes, not scopes. Phase 0's survey finding 8 recorded that "claim" already means two things in this codebase. scopes already means a Shaken Fist authorisation scope — cluster-admin, artifact.* — on namespace keys, on mapping rules and in access tokens. An OIDC scope is a different thing in a different namespace of meaning, and reusing the word would make rule.scopes and issuer.scopes look like the same concept in the same subsystem. The prefix is ugly and the collision would be worse.

    D10. issuer_url is not tightened to https in this phase. Finding 6 is a real gap and the correct fix is to require https on the field. That is a breaking change to a live admin API for deployments this session cannot inspect, which makes it a decision for Michael and not for a phase whose job is discovery. It is filed as an issue in step 3h and recorded in the master plan's Future work. The discovery fetch enforces https on the URL it actually requests regardless, so nothing in this phase fetches plaintext.

    Risks and mitigations¶

    The issuer equality check is written loosely. This is the one that matters. A startswith, a rstrip('/'), a .lower(), or an in would each turn discovery from a security boundary into a suggestion, and every one of them is a plausible thing for an implementer to write while making an Authentik trailing slash work. D1a exists to remove the motive — the slash is handled in URL construction, where it belongs, and never in the comparison. Checked by: step 3g mutates the comparison and requires a named test to fail; the management session reads the comparison itself rather than the summary, and rejects the step if the fix for the trailing slash has migrated into D2's check.

    An existing deployment's issuer stops working. Every issuer configured today supplies jwks_uri, and 3a makes that column nullable and 3c makes the field optional. A migration that drops the value, or an endpoint that stops honouring it in favour of a discovered one, would break workload exchange cluster-wide for a feature those deployments do not use. Checked by: 3a's idempotence test asserts existing rows are unchanged, and 3c's last test is specifically an unchanged workload-style create against a provider with no discovery document.

    The CA-bundle union gets written the short way. verify= is the obvious way to point requests at a bundle and it is wrong in a way that only shows up for a deployment with both a private provider and a public one — which is exactly the deployment the existing jwks_ssl_context() docstring says it was written to protect. Checked by: 3b's brief names the adapter approach and forbids verify=; the management session greps the diff for verify= before committing.

    The login endpoint grows a field. external_view() is the easy thing to return and it serves audience and jwks_uri. Checked by: 3d builds the dict explicitly and asserts the exact key set; 3g mutates it to external_view() and requires that assertion to fail.

    The documentation describes the plan rather than the code. 3f is written against four files whose current text this plan quotes, and the "four fields, all mandatory" sentence is about to become false in a way a reader will act on.
