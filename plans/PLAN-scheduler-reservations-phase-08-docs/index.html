    Scheduler reservations phase 8: documentation and the client release¶

    Prompt¶

    Before responding to questions or discussion points in this document, read the master plan (PLAN-scheduler-reservations.md), its phase 8 stub and status notes, the phase 0 decisions document (D8, D10, D11, D16, D17) and the phase 7b plan in client-python (docs/plans/PLAN-scheduler-reservations-phase-07b-client-views.md on that repository's develop). Then read the documentation this phase changes as it stands today, rather than as the stub remembers it: docs/operator_guide/scheduler.md, docs/operator_guide/database.md, docs/developer_guide/subsystem_internals.md, docs/developer_guide/database_internals.md, docs/developer_guide/standards.md, docs/user_guide/affinity.md, docs/release_notes/v07-v08.md, docs/glossary.md and ARCHITECTURE.md. Ground every claim about what the documentation says in the file, with a line number.

    All planning documents live in docs/plans/. This file follows the conventions in PLAN-TEMPLATE.md.

    Planning effort¶

    Planned at high effort in the management session, because the survey had to decide what of the stub's scope still exists to be done, and because one step is a release, which cannot be undone. Review at medium: the decisions below are narrow and each step is a self-contained documentation change with a falsifiable check.

    Scope¶

    The master plan's stub for this phase was written on 2026-05-22 and amended on 2026-08-29 (the release) and 2026-10-20 (read through 7b's commands). It describes four deliverables: an operator guide for claims and capacity, a developer-guide write-up of the guarded-UPDATE idiom (D10), user-facing affinity migration notes, and one client-python release covering phases 4b to 7b. The survey below found that the first and third already exist, written by the phases that built the features, and that the stub's real remainder is narrower and more specific than it reads.

    In scope:

    • The client-python release the stub assigns here, and the sentence in the operator guide that names the client version an operator needs.
    • Correcting docs/operator_guide/scheduler.md where it says the client cannot do what it has been able to do since 4b and 7b, and leading its claims and diagnosis sections with the commands rather than the endpoints they read.
    • The D10 write-up: the guarded-counter idiom as a pattern a future finite-resource claim can copy, which nothing in docs/ is today.
    • Release notes for what phases 3 to 7b changed, which docs/release_notes/v07-v08.md does not mention at all.
    • Glossary entries for the vocabulary the guide uses and the glossary does not define: capacity claim, coverage state, capacity ledger, scheduler capacity reconciler and guarded UPDATE.
    • Bookkeeping that the documentation audit in phase 9 should find already done: the master plan's success criteria, which still describe a node_reservations table phase 0 decided against and a batch-create API D8 deferred; and two open issues this plan's earlier phases resolved without closing.

    Out of scope, and why:

    • Phase 5's documentation. The flip from advisory to hard enforcement changes what every "advisory this release" sentence says. Phase 5 owns that delta. This phase records where those sentences are (Definition of done, item 12) so phase 5 can find them.
    • A server release. The server is at v0.8.0-rc4, and the operator guide is published from develop. The stub commits this phase to one client release only, and a server release has its own process (docs/developer_guide/release_process.md) and its own timing.
    • Changes to client-python's own pages. 7b wrote docs/cluster-capacity.md and docs/namespace-claims.md there; this phase links them and does not restate them (D3). A fact found wrong in them is fixed there as a one-line pull request, not here.
    • sfui. No capacity view exists in the web UI. 7b's Future work records it.
    • Fixing #3882 (the reconciler does not log the drift it corrects). Step 6 verifies the claim against the code and either closes the issue with evidence or leaves it open with a note. A fix is a code change and belongs to its own branch.
    • The conductor's documentation of claims. Phase 4c retired the definition-of-done item that wanted it; private-ci's own plan owns that repository.

    What the survey found¶

    Surveyed on 2026-10-30 against shakenfist 61a14af571 and client-python 44696dd (both develop). The stub's four deliverables, checked one at a time:

    F1. The operator guide exists and is substantial. docs/operator_guide/scheduler.md is 1152 lines. It carries the placement pipeline (:12), the guarded admission (:342), namespace claims with their advisory status, drawdown semantics, peak, growth and expiry, the two states, the cross-namespace listing and the refusal codes (:431-696), the configuration reference (:697), placement diagnosis from audit events (:832), the cluster-wide ledger and the exclusion reasons in /admin/resources (:945, :1005), affinity debugging (:1038) and mixed-version behaviour (:1140). The reconciler is documented for operators in docs/operator_guide/database.md:738-930. The stub's "operator guide for claims and capacity (including the two service classes and the reconciler)" was written as though none of this existed; phases 3, 4, 4a, 6, 7 and 7a each wrote their part as they landed. The stub is corrected at source in this phase's planning commit.

    F2. The guide contradicts the client three times. Each of these was true when written and is false now:

    • :444: "sf-client has no claim verbs yet, so for now a claim is created with an HTTP request rather than a command." The verbs landed in client-python#375 (phase 4b, 2026-08).
    • :495: "admin-gated like the claim verbs themselves since sf-client has no events verb for either yet", followed by two GET URLs. namespace events and namespace claim events landed in client-python#442 (phase 7b).
    • :668: "sf-client has no claim verbs, so there is no quick interactive way to confirm that the claim pathway works". Same correction as :444.

    Beyond the three false sentences, the guide never names sf-client node capacity, sf-client namespace claim list --all or the --coverage filter (grep -c 'node capacity' is 0; the only sf-client commands it quotes are instance events, instance show and instance list). Its cross-namespace listing section (:621) and its whole diagnosis section (:916-1037) are written against the endpoints. That is the stub's 2026-10-20 amendment, "read through phase 7b's commands rather than curl", and it is the operator-guide work that remains.

    F3. The "two service classes" are described but never named. The claims section explains that unclaimed placements are admitted only into what active claims have not spoken for (:466, :965), which is D17's claimed-versus-best-effort split, but neither "service class" nor "best-effort" appears in docs/. An operator cannot search for the concept. Step 2 names it once, where the behaviour is explained.

    F4. The affinity migration notes exist. docs/user_guide/affinity.md:216-242 ("The weighted form is deprecated") explains the mapping from weights to prefer_with_tag / prefer_without_tag, that magnitude is discarded, when ordering can change, and the deprecation event; scheduler.md:1084-1138 carries a script that finds instances still on the weighted form. Phase 6 wrote both. Nothing remains for this phase except a release-notes entry (F6).

    F5. The D10 write-up does not exist as a pattern. The scheduler's own instance of the idiom is documented thoroughly: docs/developer_guide/subsystem_internals.md:6-420 (the admission transaction, the demand clause, the mirrored limit arithmetic, the peak high-water mark) and the ER_CHECKREAD rule at docs/developer_guide/standards.md:91. But D10's purpose was that "future finite-resource claims (per-session floating IPs, etc.) can copy the pattern", and no page says what the pattern is independent of the scheduler: when it applies and when a UNIQUE constraint or the IPAM reservation path is the right tool instead; the three parts (materialised counters, a guarded UPDATE as the transaction's first statement, a reconciler that corrects drift and is the only creator of rows); the rules phase 0's benchmark and the later phases established (no per-decision rows, canonical write order, which MariaDB errors to retry, never an aggregate-guard INSERT ... SELECT); and how a read of the counters reports a degraded or absent row. database_internals.md already has one such pattern section, "SQL Filter-Pushdown Discipline" (:158), and the reconciler's description sits oddly inside "Cluster Operation Storage and Work Queues" (:497-530, within :403-539), which is where ARCHITECTURE.md:204-206 sends a reader looking for "the capacity tables and their reconciler".

    F6. The release notes do not mention any of it. docs/release_notes/v07-v08.md has a section for phase 00a ("Load-aware scheduling and per-node resource reservations", :1291) and nothing for guarded admission, namespace claims, the advisory ceiling, the capacity tables and their schema step, the affinity constraint form and the deprecation of weights, the exclusion reasons, the cluster ledger, the cross-namespace listing, or any of the client commands. grep -c for prefer_with_tag, namespace claim, node capacity, cluster_capacity, coverage_state and /admin/claims is 0 for each. The only affinity entries (:342-349) are the validation fixes.

    F7. The glossary defines none of the vocabulary. Its thirty-odd entries include claim only in the OIDC sense (bound claims on a mapping rule), which is the overload the glossary exists to disambiguate. Capacity claim, coverage state, the capacity ledger (cluster_capacity), the reconciler and guarded UPDATE have no entry.

    Decisions¶

    D1. This is a gap-closing phase, not the writing phase the stub describes. F1 and F4 found the operator guide and the migration notes already written. Rewriting a 1152-line guide that is mostly right would churn text phases 3 to 7a reviewed carefully, invalidate anchors other pages link, and make phase 9's audit harder to read. Step 2 therefore edits the sections F2 names and leaves the rest alone, and the definition of done is phrased as greps against the specific defects, not as "the guide is good".

    D2. The release is v0.8.4, it is step 1, and the documentation pull request does not merge until PyPI serves it. The stub's obligation is that "the guide must not merge claiming a command an operator cannot install". The cheapest way to honour it is to cut the release first and let the docs catch up, since the release's latency is a human approval and the docs' latency is writing. Patch-level because every client tag since v0.8 has been patch-level whatever it carried (v0.8.3 shipped the VDI console tokens), nothing since v0.8.3 removed or renamed a command or option (F8), and the new commands refuse cleanly against an older server through the capability tokens, so no operator is forced to upgrade the server to keep a working client. The tagged commit is client-python develop's head at the time of tagging, which the management session confirms has a successful merge-queue functional-tests.yml run before Michael pushes the tag (the gate has no override). A workflow_dispatch dry run of release.yml precedes the tag, because this is the first release through the gate (F8). Michael pushes the tag and approves the environment; nothing here can or should do either for him. This is the decision most likely to be argued with: one could hold the release until the docs are reviewed so the two land together, or call forty-two merges a minor version. The first costs a round trip for no reader's benefit, since the guide is published from develop either way; the second contradicts the repository's own tagging history.

    D3. The operator guide links client-python's pages and does not duplicate their output. 7b's plan and the master plan's 7b stub both say the client page is what "phase 8's operator guide links rather than duplicates". The guide keeps its field tables, which document the API and are what a script reads; it gains the command to run and a link to the client page for what the command prints. Reproducing node capacity's table here would put the format under two owners, and it is 7b's. Links use the full GitHub URL to the client page on develop, which is the form docs/cluster-capacity.md already uses in the other direction; nothing in docs/ links a client-python page today, so there is no precedent to match and the anchor checker only follows relative links.

    D4. The idiom write-up is a pattern section in database_internals.md, not a new page, and subsystem_internals.md keeps the scheduler's instance. F5 found the pattern slot already exists: "SQL Filter-Pushdown Discipline" is a pattern section in the same file, and ARCHITECTURE.md already sends readers to database_internals.md for the capacity tables. A new page would need a nav entry, an AGENTS.md row and a reason to be found; a section beside the pushdown discipline is found by the reader who is already looking for database patterns. The section says what to copy and links the scheduler's instance for how it was done; it does not move or repeat subsystem_internals.md:6-420. ARCHITECTURE.md:204-206 is repointed at the new section, which is where "the capacity tables and their reconciler" are now explained as a thing rather than as a paragraph inside the work-queue section.

    D5. Three release-notes sections, written for an upgrader. Each says what changed, what an operator must do (sf-ctl ensure-mariadb-schema before rolling daemons, for the tables), what they will see that is new (events, refusals, the advisory warning), and where the guide is. They go after "Load-aware scheduling and per-node resource reservations" (:1291), which is the same plan's first section, and before "Agent operations are bounded by a deadline" (:1345). Three rather than one because they are read by different people: Atomic admission and namespace capacity claims by an operator of a shared cluster, An operator-readable capacity surface by anyone who has typed curl against /admin/resources, and Affinity constraints, and the deprecation of weights by a user who writes affinity metadata. The notes link the guide and the client pages for detail and do not restate the field tables.

    D6. Five glossary entries, and the OIDC overload is named. The glossary's own rule is that an overloaded word names its sibling meaning. Capacity claim therefore carries a "Not to be confused with" pointing at the bound claims of a mapping rule, and the mapping rule entry gains the reverse pointer. Each new entry carries a "Defined in" pointer into the guide or the code, matching the existing entries' form.

    D7. The master plan's success criteria are corrected in this phase. They are documentation of the plan, this is the plan's documentation phase, and phase 9 reads them as the standard it audits against. Each false criterion is rewritten to what the plan actually decided, with the decision number, rather than deleted: a reader of the plan's history should see that batch creates were promised and then deferred.

    D8. Issue hygiene is a step, with evidence in the closing comment. #4391 is closed citing the merge that published the singleton and the client that renders it. #3882 is answered from the code: if the reconcile pass records what it corrected, the issue is closed with the line that does it; if not, the issue gets a comment saying so and stays open, and the operator guide's reconciler section gains one sentence saying corrections are not logged, so an operator does not look for a log line that does not exist.

    D9. Nothing in docs/ names a phase number. The check-plan-phase-references pre-commit hook refuses "phase 7b" in documentation outside docs/plans/. Release notes say what landed and link the master plan; they do not say which phase landed it. Every brief below repeats this because it is the error a sub-agent writing from this plan is most likely to make.
