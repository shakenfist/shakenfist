    Phase 5 -- The kerbside role moves into Kerbside¶

    Part of PLAN-kerbside-deployer.md. Phase 4 (PLAN-kerbside-deployer-phase-04-ci.md) landed in #4479 as 0016c5dad; this phase's first commit closes it out.

    Planning effort: high, as the master plan asks. The phase crosses three repositories (Kerbside, actions, Shaken Fist) and a release boundary. It changes the role's interface, and it moves a CI lane that is the only cross-repository check of the console path. Review effort: high for steps 1-2, which generalise the role, and for step 5, which changes what site.yml passes it. Medium elsewhere.

    Scope¶

    In scope:

    • The kerbside role, its systemd units and its helper scripts move into the Kerbside repository. They become the shakenfist.kerbside collection, published to Ansible Galaxy from Kerbside's release workflow (D1).
    • The role loses every Shaken Fist assumption. Its single hard-coded source becomes a required kerbside_sources list, validated per source type. Readiness, port checks and the code hash stop assuming Shaken Fist (D3, D4).
    • Shaken Fist builds its own source entry, and makes its own checks, in a new node role entry point (D3). site.yml consumes the external role as a soft dependency, pinned by a requirements file it also reads (D2).
    • A collections key in actions' deploy profiles, so a CI deploy can install collections beside Shaken Fist's (D5).
    • The tests split along the same line (D6).
    • Kerbside's sf-e2e lane deploys through the role on a Shaken Fist smoke cluster. It stops using deploy-kerbside-on-shakenfist and its own provisioning scripts (D8).
    • Docs only as far as needed to keep every page true: the collection READMEs on both sides, and pointers from the pages that describe the role today (D9).

    Out of scope, and why:

    • A non-Shaken Fist source in CI. The list accepts any type Kerbside supports, and the role's unit tests render and validate each one. A live second source is Kerbside's deployment options plan's business.
    • The full Ansible documentation page. Kerbside's PLAN-deployment-options.md phase 5 owns it and is blocked on this phase. This phase writes only the collection's README.
    • Publishing shakenfist.shakenfist to Galaxy. It has never been published (S3), and that is a release-process fix in this repository, not part of the move. It is filed (see Future work).
    • Moving Kerbside's lane onto smoke-cluster.yml. It cannot carry Kerbside's drivers (D8). #4367 stays open.
    • Closing kerbside#579, the nightly proxy-wheel build failure. It is Kerbside's, and is confirmed before the lane moves so the move is not blamed for it.
    • #4097 item 6, a shared host-subject fixture read by both repositories. Step 1 lays the Kerbside half (D6). The general fix stays with that issue.

    What the survey found¶

    Three surveys ran in parallel:

    • Shaken Fist: the role and every reference to it.
    • Kerbside and actions: the sf-e2e lane, packaging, the sources model and the deployment options plan.
    • ansible-galaxy experiments: run on ansible-core 2.15.13, 2.18.19 and 2.21.5, with the same results on all three. The scratch tree is under the session scratchpad and is not kept.

    Paths are relative to each repository's root. R is shakenfist/deploy/collection/roles/kerbside.

    S1 -- the role is mechanically self-contained, but Shaken Fist-shaped in logic¶

    Mechanically self-contained. The role is 1983 lines in 19 files. * meta/main.yml:12 declares dependencies: []. * There is no include_role, plugin, module_utils, role_path or playbook_dir use. * Every module and filter is ansible.builtin. * There is no groups[, hostvars or ansible_facts. The master plan's "reads no inventory group names and no other host's facts" is literally true.

    Shaken Fist-shaped in at least seven places beyond the variables:

    1. templates/sources.yaml:13-20 builds exactly one type: 'shakenfist' entry from deploy_name, api_url, kerbside_system_key and kerbside_sf_ca_cert.
    2. files/kerbside-check-sources.py:29,52-60 requires the Shaken Fist source's six keys, as non-empty strings, on every entry. Kerbside itself requires only source and type (kerbside/main.py:67).
    3. files/kerbside-ready.py:84-90 and tasks/register.yml:204-250 define readiness as "the source named deploy_name has fetched its signing keys".
    4. tasks/config.yml:25-33 asserts, unconditionally, that kerbside_sf_ca_cert is a PEM.
    5. tasks/bootstrap.yml:148 hashes site-packages/shakenfist_client under errexit, so bootstrap fails if the client is not installed.
    6. tasks/validate.yml holds three Shaken Fist checks:
    7. the port check against Shaken Fist's listeners when kerbside_colocated is set (:97-111, list at vars/main.yml:31-36);
    8. the loopback api_url check (:159-177);
    9. the kerbside_url == kerbside_url_on_sf_nodes check (:185-196).
    10. The flat ceiling of 30000 on every port (validate.yml:73-89) is Shaken Fist's instance console range.

    Variables. Seven of the role's options are Shaken Fist inputs: * kerbside_system_key * kerbside_sf_ca_cert * kerbside_url_on_sf_nodes * kerbside_colocated * api_url * deploy_name * kerbside_client_package

    Coupling to internal_ca. The role is implicitly coupled to Shaken Fist's internal_ca role: * vars/main.yml:11-19 hard-codes internal_ca's certificate file names; * site.yml:829-858 issues the Kerbside certificate with internal_ca between the role's bootstrap and config entry points.

    No released consumer. No Shaken Fist tag contains the role: the newest tag is v0.8.0-rc4, which predates #4465. Its interface can therefore change in the move without compatibility shims.

    S2 -- site.yml already reaches the role only through include_role¶

    Every use of the role is an include_role with tasks_from: * validate in the validate play (examples/_shared/site.yml:160-173); * bootstrap, config and register in "Deploy Kerbside" (:796-868).

    That is the only shape that survives the collection being absent. With no collection installed and an empty kerbside group: * include_role behind a false when, or in a play that matches no host, runs cleanly, and --syntax-check passes; * import_role, a play-level roles: list and import_playbook all fail at parse time, before any play runs, whatever the when.

    When an include_role of a missing role actually executes, it fails with "The role 'X' was not found". That message gives an operator no hint about what to install.

    S3 -- Galaxy¶

    • shakenfist.shakenfist is not on Galaxy, in any repository state. release.yml:202-235 publishes it only on v* tags, and no tag has been pushed since that job was added (a3357605d1, 2026-06-26). Every operator installs it from a checkout or from the server wheel (pyproject.toml:210-214 ships deploy/**).
    • The shakenfist namespace already exists, owned by mikalstill and shakenfist-bot. It publishes one collection, shakenfist.k3s, from client-python-k3s's release.yml with an ANSIBLE_GALAXY_TOKEN secret. That job is the pattern to copy.
    • No collection named kerbside exists in any namespace.
    • shakenfist.kerbside with a role kerbside builds, installs, runs, and passes galaxy-importer 0.4.44. The importer insists on requires_ansible in meta/runtime.yml.

    S4 -- how a collection can depend on another¶

    • Galaxy refuses a git URL in galaxy.yml dependencies. ansible-galaxy builds such a collection and installs its dependency happily, but galaxy-importer rejects the upload: "Invalid dependency format". A Galaxy dependency must be a namespace.name.
    • ansible-galaxy collection install -r requirements.yml accepts git (tag, branch or SHA), dir and tarball sources.
    • A git source may omit the subdirectory: ansible-galaxy scans one level down for galaxy.yml.
    • A dir path resolves against the current directory, not the requirements file.
    • A dir source installs the working tree, uncommitted edits included.
    • An installed copy satisfies a name dependency without contacting Galaxy. With a git source and a dependent in one command, the git source must come first, or resolution fails. That matters only if something declares the dependency (D2 makes sure nothing does).
    • --no-deps and --offline exist from 2.15 on.
    • Precedence when a collection is installed twice:
    • a collections/ directory beside the playbook;
    • ANSIBLE_COLLECTIONS_PATH, first entry winning;
    • the default path;
    • site-packages.

    ansible-galaxy collection list does not print them in precedence order.

    S5 -- CI installs only Shaken Fist's collection¶

    Decisions¶

    D1 -- shakenfist.kerbside, at ansible/ in Kerbside, released with Kerbside¶

    Naming and layout: * The collection is shakenfist.kerbside and the role kerbside, so the FQCN is shakenfist.kerbside.kerbside. * It lives at ansible/ in the Kerbside repository: galaxy.yml, meta/runtime.yml with requires_ansible: '>=2.15.0', README.md, roles/kerbside/. * The shakenfist namespace already exists and publishes from another repository with a working token (S3). A kerbside namespace would need creating, and buys nothing.

    Release: * Kerbside's release.yml builds the collection, versions it from the tag, and publishes it beside the PyPI packages. The job mirrors client-python-k3s's publish job, including passing the token through env:. * The release build stamps kerbside_package: "kerbside==<version>" into the role's defaults, the way stamp-proxy-version.sh stamps the proxy pin. It also stamps kerbside_collection_version into vars/main.yml (D2 reads it). * So collection 0.8.0 installs Kerbside 0.8.0 by default. That pairing is the main thing the move buys: the role and the software it deploys are reviewed, tested and released together. * The committed files are never stamped. They keep a floor (kerbside>=0.7.0) and kerbside_collection_version: unreleased. An install from a checkout, such as Kerbside's own lane (D8), never runs the release build, so it must carry a marker that says so rather than a version that looks real.

    The operator gate. Publishing needs an ANSIBLE_GALAXY_TOKEN secret in the Kerbside repository. That is the operator's to add.

    D2 -- a soft dependency, pinned by a requirements file that site.yml also reads¶

    No galaxy.yml dependency. Shaken Fist's galaxy.yml keeps dependencies: {}. A hard dependency would buy nothing and cost three things: * Galaxy refuses a git URL (S4), and Shaken Fist is not on Galaxy anyway (S3); * Kerbside is optional, and most clusters do not deploy it; * every CI install of Shaken Fist's freshly built tarball would try to resolve shakenfist.kerbside against Galaxy.

    A requirements file. Shaken Fist ships examples/_shared/requirements.yml beside site.yml. It pins shakenfist.kerbside to the compatible minor series, starting at >=0.8.0,<0.9.0. Operators who deploy Kerbside run ansible-galaxy collection install -r examples/_shared/requirements.yml. Renovate proposes the bumps (S10).

    site.yml keeps the soft-dependency shape and checks it early:

    • Invariant: only include_role. site.yml reaches the role only through include_role (S2), never import_role or roles:. The header comment states it, and the wiring test asserts it.
    • The validate play wraps its include_role in a block. The rescue turns "role not found" into a message naming the install command.
    • The version is checked before any host changes.
    • After validate, the play asserts that the installed role's kerbside_collection_version satisfies the range in requirements.yml.
    • The range is read from the file itself (lookup('ansible.builtin.file', playbook_dir ~ '/requirements.yml') | from_yaml), so the pin has one source.
    • An install from a checkout reports unreleased (D1). The check accepts it with a warning naming the installed path, so Kerbside's lane, which deploys its own pull request's role, is not refused. A real version outside the range is refused.

    This is the decision a reviewer is most likely to push back on. The alternative is a hard dependency by name, which "just works" for someone who installs Shaken Fist from Galaxy. Nobody can do that today, and the hard dependency would make every Shaken Fist install, with or without Kerbside, depend on a second collection's release.

    The soft shape costs one documented install command, for the operators who want Kerbside. If Shaken Fist is ever published to Galaxy, a name dependency can be added then without changing site.yml.

    D3 -- the seam: kerbside_sources, and Shaken Fist's entry built by the node role¶
