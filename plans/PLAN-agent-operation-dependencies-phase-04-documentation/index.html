    Dependency-aware agent operations phase 4: documentation¶

    Prompt¶

    Plan the next phase of PLAN-agent-operation-dependencies.md with the next-phase skill, after phase 3 merged as two pull requests: the client half as client-python#453 (a2c9d0d1f4) and the functional test here as #4982 (6dde443468).

    Phases 0 to 3 built the feature. An agent operation carries depends_on and runs_after edges with per-edge settle delays, the sidechannel dispatcher evaluates them between agent_operation_next() and start_instance_executor(), a dependent whose depends_on dependency failed cascades to abort with the cause in dependency_failure, the client can submit and await a chain, and two smoke tier tests prove ordering and the cascade against a real cluster on every pull request.

    What is left is decision 11: the developer-guide page for the agent operation model, and the example index. The master plan's phase 4 row also assigns the API reference vocabulary, the two documented ambiguities and the client-python-k3s adoption to this phase. The survey found that the first two are already written and that the third cannot be done here -- see below.

    Planning effort¶

    High, and the master plan asks for no particular review effort for this phase.

    That is a deliberate choice for what looks like a writing phase. The page itself is prose, but three things about it are judgement rather than typing:

    1. Four pages already carry dependency facts. A fifth which restates any of them creates exactly the drift coding_rules.md and the llm-doc-structure audit exist to prevent, and deciding what belongs where is the whole design of this phase.
    2. The worked examples teach a pattern, and the pattern the master plan names does not work. Getting that wrong ships documentation which tells a reader to build something which aborts itself.
    3. The phase has to decide what to do about the part of its own row it cannot deliver, rather than quietly dropping it.

    Scope¶

    In scope.

    • A new docs/developer_guide/agent_operations.md: the agent operation model -- one executor per instance, strict FIFO, independent outcomes, the timing budgets by reference, depends_on versus runs_after, the cascade to abort, retry -- with worked examples in client code.
    • The example index, as a section of that page, naming sibling repositories and what each exercises, with client-python-k3s first (decision 11).
    • Registration in both mkdocs.yml and mkdocs.yml.tmpl.
    • A release note for agent operation dependencies in docs/release_notes/v07-v08.md. None exists.
    • Cross-links into the new page from the four existing pages which carry dependency facts, and the removal of any fact which the new page states and one of them also states.
    • Phase 3's close-out, and this phase's registration, in the master plan's Execution table and docs/plans/index.md.

    Out of scope.

    • client-python-k3s adopting dependencies. Re-cut into phase 5 by decision 1 below, for three independent reasons the survey found. Its plan file will live in that repository.
    • Changing AGENT_OPERATION_DEPENDENCY_WAIT, its semantics, or the budget arithmetic. Decision 4 documents what ships; survey finding 5 is a limitation of a shipped design and not a defect of it.
    • Rewriting the two ambiguities documented in the API reference, or moving them. Decision 3.
    • The declined mixed-type edges (#4824), the second example application (#4825), the cluster-side dependency walk defects (#4910) and the open-coded namespace predicate (#4887). All filed, all still open, none this phase's work.
    • docs/operator_guide/agent_operations.md's tuning content. It is complete and correct; this phase links to it.

    What the survey found¶

    Phase 4's row was written by phase 0, before phases 1 to 3 executed, and five of its claims have moved. Checked against shakenfist at 47487f4207, client-python at a2c9d0d1f4 and client-python-k3s at its develop.

    1. The API reference vocabulary is already written. The row assigns "the dependency vocabulary in the API reference" to this phase. docs/developer_guide/api_reference/instances.md:989 has a full Declaring dependencies between agent operations section: the two parameters, the 400 refusals and their deliberate indistinguishability, the capability token, the evaluation semantics of both edge lists, the wait budget, dependency_failure with its two non-state sentinels, and an agentdependency object section covering settle_seconds and its ceiling. api_reference/agentoperations.md:7-14 documents dependency_failure on the operation view and links to that anchor. Phases 1 and 2 wrote them. Nothing is owed here.

    2. Both ambiguities are already written down, in that same section, as two bolded subsections: A dependent can read as queued after its dependency has failed (decision 8's lazy cascade) and A finished dependency is eventually deleted (decision 9's swept dependency, including that absence is treated as failure and that a caller avoids it by keeping the dependent's deadline under CLEANER_DELAY). The row's third item is satisfied.

    3. Four pages carry dependency facts, not one. Beyond the two above: docs/operator_guide/agent_operations.md:255-285 documents AGENT_OPERATION_DEPENDENCY_WAIT at length -- the wall-clock anchor, the settle ceiling, the FIFO stall trade-off, and that lowering it is an API change -- and docs/operator_guide/database.md:1576 and :1652-1680 document the two LONGTEXT NOT NULL columns and the stored edge shape, linking to the agentdependency anchor. The new page is the fifth, which is what makes decision 2 the design of this phase rather than a formality.

    4. docs/developer_guide/agent_operations.md does not exist, and neither does any example index: nothing under docs/ mentions client-python-k3s except audit records in docs/components/development/. Those two are genuinely owed, and after findings 1 and 2 they are the only documentation this phase owes.

    5. The worked example the master plan names cannot be built as described. This is the finding which matters.

    Decision 11 and the phase 4 row name client-python-k3s's rolling update as the worked example, "rolling update as one submitted chain". Two things are wrong with that.

    First, there is no rolling update. Cluster.update_os() (shakenfist_client_k3s/cluster.py:5651), the body of sf-client k3s update-os, calls instance_os_update() (:3157), which calls execute_and_await(instance_uuids, ['apt-get update', 'apt-get dist-upgrade -y']) (:2612). That loops commands outer and instances inner, so every node runs apt-get update concurrently, then every node runs dist-upgrade concurrently, and the whole fleet is awaited as one. Per-node ordering of the two commands is free already, from the instance's FIFO queue. Adopting dependencies there would mean writing a rolling update -- a behaviour change to a shipped command, from simultaneous to serial -- not adopting edges in an existing one.

    Second, and worse, a fleet-wide chain submitted up front does not fit the budget this plan shipped. note_dependency_wait_started() (shakenfist/operations/agentoperation.py:642) writes the anchor on the first dispatcher pass which finds an operation blocked and is idempotent thereafter, deliberately: the docstring says an unconditional write would "leave a budget which can never be exhausted". _dependency_budget_spent() (daemons/sidechannel/main.py:2227) then tests time.time() - anchor > budget. The last link of a chain is submitted at the same moment as the first, reaches the head of its own empty instance queue immediately, and is found blocked on the first pass -- so its 300 seconds must cover the entire chain ahead of it, not its own hop. An apt-get dist-upgrade alone can exceed that. A chain of more than two or three fast steps aborts its own later links on a default deployment.

    runs_after fails differently and no better: past the budget a runs_after operation runs anyway (_dependencies_met()'s asymmetry, main.py:2244-2250), so a rolling update built on it silently stops being rolling rather than failing.

    This is not a defect. The budget exists to bound the FIFO stall decision 1 accepts, and decision 2 chose 300 seconds against measurement. But it means the documentation must teach a bounded chain, and that the master plan's worked example needs decisions of its own.

    1. The client surface is unreleased. client-python's latest release is v0.8.4 (2026-10-31), which predates phase 3's merge; develop is 31 commits ahead of it. client-python-k3s depends on shakenfist_client >= 0.7.7 (pyproject.toml:58), so it cannot call agent_dependency() until there is a release carrying it and its floor is raised to that release. Making a release is Michael's.

    2. Phase 0's one external prerequisite is still met: client-python-k3s knows abort (AGENT_OP_FAILED_STATES, cluster.py:138). Nothing is blocked on it.

    Corrections for findings 1, 2, 5 and 6 are applied at source in the planning commit -- in the master plan's phase 4 row, its phase table and docs/plans/index.md -- so a later reader does not trip over them. A later step should not redo them.

    Decisions¶

    1. The master plan's phase 4 is split: documentation is phase 4 and lands now, the client-python-k3s adoption becomes phase 5, and the push audit becomes phase 6.

    Three independent reasons, any one of which would be enough. Survey finding 6: the k3s half cannot begin until a client-python release exists, which is not this session's to make and may be weeks away. Survey finding 5: it is a behaviour change to a shipped command rather than an adoption, and the chain shape the master plan assumed aborts itself, so it needs its own decisions about what to build. And it lands in a third repository, so it is a third pull request with its own plan file, review and CI.

    The alternative is to hold finished documentation behind an unreleased dependency. Phase 0 re-cut this table once already, folding the cross-instance phase into the evaluation phase, so re-cutting it is the plan's own precedent rather than a departure.

    1. Each fact keeps exactly one home, and the new page is the model, not a second API reference. Field names, parameter shapes, refusal codes and the agentdependency object stay in api_reference/; configuration options and what to tune stay in operator_guide/agent_operations.md; column types and stored shapes stay in operator_guide/database.md. The new page explains the model a caller programs against and links to those three for detail.

    Concretely, the new page must not restate the default of AGENT_OPERATION_DEPENDENCY_WAIT, CLEANER_DELAY or any other option. It names the option and links. This is checkable, and the definition of done checks it.

    1. The two ambiguities stay where they are. They are already written, well, in the API reference section, and agentoperations.md already links to that anchor. The new page links to them too. Moving them would churn a page which says it correctly and would break an anchor another page depends on.

    2. The worked examples teach a bounded chain, and the page states what a chain cannot do. The page's dependency examples are short chains of fast steps -- the canonical one being put a file, then run it, then fetch the result, where fate-sharing is the point -- and the page says plainly when a chain is racing the wait budget and when it is not. Corrected during step 4a's review, because this text was too general and the page inherited that: edges are evaluated only for the operation at the head of its instance's queue, so a dependent on the same instance as its dependency never reaches the head until that dependency is terminal and retired, is never found blocked, and starts no budget at all, however slow the dependency was. The budget bites across instances, where the dependent reaches the head of its own queue immediately and spends the budget while the operations upstream of it run. So a cross-instance chain must fit inside one budget and fleet-wide rolling work stays submit-await-submit unless an operator has deliberately raised it, while a same-instance chain needs no arithmetic.

    This is the decision most likely to be argued with, because the obvious response to survey finding 5 is that the budget semantics are wrong and should be changed: a per-link budget which started when a link's dependency finished would make fleet-wide chains work and is what a reader expects from the phrase "dependency wait".

    I think documenting it is right, for now. The anchor is where it is because of decision 1 of the master plan: a blocked operation holds its instance's queue head and everything behind it, and the budget bounds that, not the caller's patience. A per-link budget would bound each hop while leaving the total hold unbounded, which is the property decision 2 explicitly refused when it declined to let the caller's deadline be the bound. Changing it is a design change with a measurement behind it, and belongs in its own phase or plan with that measurement, not in a documentation phase. What is not defensible is shipping documentation whose worked example aborts itself, which is what the master plan's row would have produced.

    Phase 5 inherits the question, because it has to decide what client-python-k3s actually does. If the answer there is that a real rolling update needs a per-link budget, that is a finding with a concrete use case attached, which is a much better basis for changing the semantics than this phase's reasoning would be.

    1. The example index is a section of the new page, not a page of its own. Decision 11 calls for "an index section naming sibling repositories", and one page about agent operations with the examples at its end is easier to keep honest than a second page whose only content is three links. It names what each example exercises, so a reader can tell which one to read; it does not promise a second example, which is #4825's to deliver.

    2. A release note is part of this phase. None exists for agent operation dependencies -- docs/release_notes/v07-v08.md carries the cluster operation dependency notes and the deadlines notes, and nothing for this feature. The deadlines plan's documentation phase set the precedent in one commit (55fee2ef6f): page, nav in both mkdocs files, release note, cross-links.
