    Phase 2: a fair, bounded drain¶

    Parent plan: PLAN-deleted-object-sweep.md.

    Planning effort: high, as the master plan specifies. This phase changes how the elected maintainer spends its loop, adds a field to a DatabaseService RPC that a complement-set caller depends on, and adds a second RPC. Each of those is cheap to get subtly wrong.

    Decisions continue the plan's single sequence: phase 1 used D1-D6, so this phase starts at D7.

    Scope¶

    In:

    • Per-type work, drained round robin across types, so a large backlog in one type cannot starve the others (mission 2).
    • Bounded fills: one page per type, read in primary key order with a keyset cursor, through new optional fields on GetObjectsByState.
    • A type is refilled when its own work runs out, so the sweep no longer depends on a restart to see new arrivals.
    • The sweep runs every minute, with its budget set by a new configuration option (open question 3).
    • A per-type backlog gauge read from the database, replacing phase 1's queue depth gauge, which stops meaning "backlog" once the sweep pages.
    • DeleteObjectEvents observed by phase 1's timing scope.
    • Operator documentation and release notes.
    • After merge and deploy, 24 hours of sfcbr data, recorded by phase 3's planning commit.

    Out:

    • Any change to what one hard delete does. The per-entry body (hydrate, re-check, hard_delete()) moves into a helper unchanged. Making it cheaper is phase 3, and changing it here would muddy the measurement phase 3 is planned from.
    • Batch delete RPCs. Phase 3.
    • Throttling or tuning the drain of sfcbr's backlog. Phase 4. This phase sets a default budget and makes it configurable. It does not try to drain at a planned rate.
    • Paging any other GetObjectsByState caller. Bound gRPC reply sizes owns the rest.

    • 4399. Phase 1 showed it is not the sweep (see the master plan's¶

      "What phase 1 measured").

    What the survey found¶

    References are to develop at ce8d0641b7.

    1. Phase 1 is complete and its numbers are in the master plan. Merge 6537966c00 (#4572, which carried #4573) is on develop, the phase 1 worktree and branches are gone, and the metrics answer from sfcbr's leader. Brief 1d's queries were run over 24 hours ending 2026-10-20T21:23Z and recorded under "What phase 1 measured". Phase 1's definition of done items 1-6 were checked when it landed, and item 7 is met by this planning commit.
    2. The measured cost changes what phase 2 can deliver. The sweep gets 960 seconds a day and spent 974. At about 0.4 seconds an object, keeping up with 40k arrivals a day would take about four and a half hours. Fairness spreads the budget across types, but it cannot make the sweep keep up. Phase 2 should make the sweep fair, bounded and correctly sized. Phase 3 has to make it cheap.
    3. Nothing pages GetObjectsByState yet. Bound gRPC reply sizes is Not started (0 of 7). Its worked brief already names the shape: page_size and after_uuid on the request, more_available on the reply, keyset on object_uuid (PLAN-grpc-bounded-replies.md:441-452). The request today has object_type, state_values and updated_before (protos/database.proto:796-805).
    4. One caller of the unpaged read is a complement set. The servicer's docstring (shakenfist/daemons/database/main.py:734-760) explains that get_active_blob_uuids() (shakenfist/mariadb.py:7693) treats every blob not in the reply as deletable. A paged or truncated reply reaching that caller would delete blobs. The unpaged path must keep sending page_size 0, and must never see a page.
    5. Oldest first is not index-served. object_states has a primary key on (object_type, object_uuid), plus idx_object_states_type_state on (object_type, state_value) and idx_object_states_uuid (shakenfist/mariadb.py:1407-1447). No index includes update_time, so ORDER BY update_time LIMIT n would sort a type's whole final-state range (639k rows for node_inst_op) for every page. A keyset on object_uuid within one object_type walks the primary key.
    6. There is a pattern for adding an index, but this phase does not need it. object_states is versioned, and v3 added an index online with CREATE INDEX IF NOT EXISTS (mariadb.py:1671-1689). It is recorded here in case D8 is overturned.
    7. The maintenance loop can afford a larger budget. _run_due_scheduled_jobs() pets the watchdog before every job (shakenfist/daemons/cluster/main.py:990-1019). sf-cluster runs with WatchdogSec=300s (deploy/collection/roles/node/templates/sf.service:73). The loop runs a maintenance pass when 60 seconds have passed since the last one (main.py:1138). A 20 second job every minute is well inside the watchdog window. The one cost is that the other one-minute jobs (log_cluster_queue_lengths, reap_stuck_cluster_operation_jobs) run up to 20 seconds later.
    8. DeleteObjectEvents bypasses _grpc_call(). _grpc_delete_object_events() (mariadb.py:6508-6533) calls stub.DeleteObjectEvents(request, timeout=30.0) directly and only logs a failure. That is deliberate: a failed event cleanup must not fail a hard delete, and orphans are pruned daily. It is also why phase 1's scope cannot see the largest cost outside the timed RPCs.
    9. There is no count RPC, and the pattern for one is known. Nothing in mariadb.py counts object_states rows. The add-grpc-service skill (.claude/skills/add-grpc-service/) covers the proto, stubs, servicer, Monitor counter and client layers. Monitor counters are registered in the list at daemons/database/main.py:6416.
    10. The metrics phase 1 added are unreleased. No release tag contains 6537966c00 (v0.8.0-rc4 is from 2024), and docs/release_notes/v07-v08.md is the in-progress notes. So replacing cluster_deleted_object_queue_depth breaks nobody.
    11. About 75 references in the tests use the FIFO. shakenfist/tests/test_daemon_cluster_scheduled_tasks.py uses DELETED_OBJECTS_QUEUE, _fill_per_deleted_object_queue and _process_per_deleted_object_queue in PerDeletedObjectQueueTestCase (:778) and DeletedObjectSweepMixedQueueTestCase (:1092), and test_namespace_key_object.py uses one more. Step 2e rewrites them.

    • The master plan's Situation gains "What phase 1 measured", and open questions 1, 2 and 3 are answered there. Open question 2's answer replaces its earlier recommendation (oldest first) with primary key order. See D8.
    • The master plan's mission item 1 now states the bound: 24 hours.
    • The master plan's phase 2 section drops "refill when its last fill is older than a bound" and adds the backlog gauge and the DeleteObjectEvents timing. Phase 3's candidates drop the from_db() hydration, which costs about 1% of an operation's time. Phase 4 now reads phase 2's backlog gauge, not phase 1's.
    • The master plan's #4399 bullet records what phase 1 found.
    • PLAN-grpc-bounded-replies.md's dependencies note that this phase pages GetObjectsByState first.
    • The docs/plans/index.md row describes what phase 1 measured.

    Decisions¶

    D7 -- Per-type work, round robin, with the rotation kept across passes¶

    Replace DELETED_OBJECTS_QUEUE with a dict[str, collections.deque[str]] of uuids per type. The drain takes one entry from each type that has work, in the canonical order of OBJECT_NAMES_TO_CLASSES, then starts again. The position in that rotation is module state, so a pass that runs out of budget part way through the types starts the next pass at the type after the last one served. Without that, the types at the head of the order would be favoured whenever the budget cuts a round short, which is phase 1's starvation in a milder form.

    Round robin gives a type with 30 objects the same share as a type with 639k. That is what mission 2 asks for. A slow type, such as blobs at 4 seconds each, takes more of the budget per turn than a fast one, but it cannot stop the others getting a turn.

    D8 -- Pages in primary key order, through new fields on the same RPC¶

    Add to GetObjectsByStateRequest uint32 page_size = 4 (0 means unbounded, today's behaviour) and string after_uuid = 5. Add bool more_available = 2 to GetObjectsByStateReply. A paged request returns at most page_size uuids with object_uuid > after_uuid, in ascending object_uuid order, and sets more_available when there were more. The SQL asks for page_size + 1 rows to find that out without counting.

    This is the decision a reviewer is most likely to question, because the master plan recommended oldest first. Finding 5 is why it changed. Oldest first needs either a new index on the cluster's largest table, which is a migration for a sort order the mission does not need, or a sort of a whole type's range for every page, which is the unbounded read this phase removes. Primary key order is index-served, matches the shape the bounded-replies plan already specifies, and still meets mission 1: every object in a type is reached within one walk of that type's cursor. An object that arrives behind the cursor waits for the walk to wrap. During the drain, oldest first would also make it wait, behind the same backlog.

    Wire compatibility, both directions:

    • A new client sends page_size 0 from the unpaged wrapper, so an old or new server answers exactly as today. get_active_blob_uuids() and every other unpaged caller are untouched (finding 4).
    • A new client paging against an old sf-database gets the whole unordered list, because the old server ignores fields it does not know. The paged client wrapper detects that (more uuids than page_size) and returns the whole list with more_available false. The sweep then behaves like today's fill until sf-database is upgraded, and its cursor resets, so no keyset is built on an unordered list.
    • An old client never sends the new fields.

    D9 -- Refill a type when its own work runs out¶

    At the start of each pass, for each type in the rotation whose deque is empty, read one page from that type's cursor, with the existing age filter (updated_before). A page with more_available moves the cursor to its last uuid. A page without it resets the cursor to '', so the next walk picks up anything that arrived behind it. A type whose page came back empty is not read again for DELETED_OBJECT_EMPTY_RECHECK (300 seconds), so an idle cluster costs at most 29 small reads every five minutes. A restart is no longer what refills the sweep.

    Revised in review: any completed walk backs off, not only an empty page, so an object whose hard delete always fails is retried every five minutes rather than every pass. The names became DELETED_OBJECT_WALK_RECHECK and _DELETED_OBJECT_RECHECK_AT. The fill also stops starting reads at the pass's deadline. See the execution notes.

    The page size is DELETED_OBJECT_PAGE_SIZE = 500. At phase 1's costs that is several minutes of one type's share of the budget, so a type with a backlog is read about once an hour. Each reply is at most 500 uuids, about 20 KB.

    The tier-wide failure handling stays as it is. A DatabaseUnavailable during the fill stops the fill and records where to resume (_record_sweep_stopped). A per-reply None skips that type and moves on. Both are accounted through _record_sweep_read(), so the failure streak gauge keeps working. One thing is new: a pass whose fill hit DatabaseUnavailable does not drain. Each entry's first read would spend a whole _grpc_call retry budget, up to about 93 seconds in the slow shape, and fail anyway.

    Each page read runs inside rpc_timing_scope('per_deleted_object_fill', objtype), so the cost of the keyset query is visible per type (see the risk about the query plan).

    D10 -- Stay in the maintenance loop: every minute, configurable budget¶

    This answers open question 3. Register per_deleted_object_checks every minute instead of every 15. Its budget per pass, fill included, is a new option, DELETED_OBJECT_SWEEP_SECONDS, with a default of 20 and ge=1. That raises the sweep's daily time from 960 seconds to 28,800. At phase 1's costs that is roughly 70k objects a day: enough to keep up with sfcbr's 40k and start eating the backlog, but not to drain it in reasonable time. That is phase 3's job.

    The budget is a cap, not a spend. A cluster with nothing to delete finishes the job in milliseconds.

    A dedicated thread was rejected. Phase 1 shows the time goes on database commits. A thread would add concurrency against the tier that is the bottleneck, and it would need its own answer to the question this loop already answers, which is what stops a node that has just lost the election from sweeping alongside the new leader. The watchdog concern that prompted the thread option is met by the pet between jobs (finding 7).

    The configuration option exists now because phase 4 needs a throttle, and a cluster smaller than sfcbr might want less than 20 seconds a minute.

    D11 -- A per-type backlog gauge from a count, every hour¶

    With paging, the sweep holds at most a page per type in memory, so phase 1's cluster_deleted_object_queue_depth no longer measures the backlog. Replace it with

    cluster_deleted_object_backlog{object_type}

    set by a new scheduled job, publish_deleted_object_backlog, every 60 minutes. For each type it calls a new CountObjectsByState RPC (SELECT COUNT(*) ... WHERE object_type = :t AND state_value IN (...)). Every type is published, zeros included, so an alert or report can rely on the series existing. Like the other leader-only metrics it is cleared on demotion. A newly elected node publishes within an hour.

    The count has no age filter. update_time is not in idx_object_states_type_state, so an age filter would turn an index-only range count into a row lookup per match. The count therefore includes objects still inside their grace period, which is at most an hour's arrivals for non-operation types and 30 seconds' for operations. On sfcbr that is about 2,000 against 1.7M. The docs say so.

    Phase 1's gauge is removed, along with the counter that fed it. It is unreleased (finding 10). The per-pass log line keeps a remaining field, which now counts the entries held in memory.

    D12 -- Time DeleteObjectEvents without changing how it is called¶

    Factor the observation in _grpc_call()'s finally into a small helper, and call that helper from _grpc_delete_object_events() around its direct stub call, labelled DeleteObjectEvents. The direct call, its 30 second timeout and its log-and-continue failure handling all stay as they are (finding 8). Without this, phase 3 would be planned against numbers missing the largest cost for blobs and a quarter of the cost for operations.

    D13 -- The per-entry body is moved, not changed¶

    The body of today's processing loop moves into _hard_delete_deleted_object(objtype, obj_uuid, outcomes): the scope, from_db(), the state and age checks, hard_delete(), the five outcomes, the histogram observation and the exception handling. Phase 1's test_call_order_is_unchanged keeps asserting the same calls per entry. What changes is which entry comes next, not what happens to it.

    Risks and mitigations¶

    • The keyset query picks the wrong index. MariaDB might range-scan idx_object_states_type_state and sort by uuid, instead of walking the primary key. That would cost a sort of the type's final-state range per page, which is the same shape as oldest first. Mitigation: D9's fill scope publishes the page read's latency per type, and brief 2g checks it. If node_inst_op's page averages over 100 ms, add FORCE INDEX (PRIMARY) in a follow-up commit on this branch or in phase 3. The live test cannot catch this, because a test table is too small for the optimiser to choose the way it would on sfcbr.
    • More sweep work is more database load. The sweep goes from 16 minutes of work a day to up to eight hours. At phase 1's mix that is about three row-deleting commits per object, so about 2.5 more commits a second, against labqnap's 17.7 today: about 14% more. Mitigation: DELETED_OBJECT_SWEEP_SECONDS can be lowered without a release. Brief 2g compares commit and request rates before and after. The memory note on labqnap's buffer pool (sf-database watchdog stalls) is the failure mode to watch for. If it reappears, lower the budget first and investigate second.
    • The backlog count is a new hourly scan. 29 index-only range counts covering about 1.7M index entries. Mitigation: the deleted_object_backlog scope publishes each count's latency, and brief 2g reports the worst type. If one count exceeds a few seconds, stagger the types across passes.
    • Namespaces are reached for the first time. There are 45,755 of them, and Namespace.hard_delete() cascades to keys, mapping rules, inbound trusts and capacity claims (shakenfist/namespace.py:344-385). Its cost is unmeasured. Releasing claims of long-deleted namespaces is correct, and is part of what this plan exists to do, but it will change scheduler_capacity_* gauges on sfcbr as it happens. Mitigation: a single entry can overrun the budget only by its own cost, and the watchdog window is 300 seconds. Brief 2g reports the namespace cost.
    • A mixed-version window during the deploy. Mitigation: D8's compatibility rules and 2a's test of the long-reply fallback. An old sf-database answers CountObjectsByState with UNIMPLEMENTED, which is logged as a failed read and leaves the gauge unset until the upgrade completes.
    • The Loki history in the master plan stops. "Refreshed per-deleted-object queue" goes away, and with it the series the Situation table was built from. Mitigation: the backlog gauge replaces it with a better series. The master plan keeps the old table as history.
