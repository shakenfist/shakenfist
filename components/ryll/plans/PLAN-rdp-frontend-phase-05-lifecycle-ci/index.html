    RDP frontend phase 5: lifecycle and CI¶

    Master plan: PLAN-rdp-frontend.md.

    Planning effort: high. The master plan's guidance plans phases 3 to 6 at medium effort "except that phase 5's reconnect work should be planned at high effort if it touches the session orchestrator". It does: Mikal chose SPICE auto-reconnect for --rdp (decision 1), which no server mode has today, and takeover needs the RDP server's connection handling rebuilt (decision 5). Review steps 1, 3 and 4 at high effort too.

    Prompt¶

    Read the master plan's Prompt first; everything there applies. For this phase in particular:

    • The RDP side is still IronRDP 0.13.0 (ironrdp-server 0.13.0, ironrdp-acceptor 0.10.0). make fetch puts its source under .cargo-cache/registry/src/index.crates.io-*/ in the worktree, and every IronRDP file and line cited below is relative to ironrdp-server-0.13.0/ there. Read it; never build or run anything from inside it. Re-check every IronRDP claim a brief relies on before relying on it.
    • The host's FreeRDP is 3.15.0 (xfreerdp3). Debian 13, which the CI runners and the smoke image use, packages the same series; the lane prints the version it ran.
    • Builds run in Docker through the Makefile, never with a host toolchain. QEMU, Xvfb and FreeRDP for the smoke lane run in a container of their own (decision 7), never installed on the host by a step.
    • The test guest for the lane is the UEFI latency guest (make test-qemu's testdata/uefi-latency-guest.qcow2, 640 KiB): any keypress advances a fixed eight-colour cycle, one step of which is black (docs/development.md:477).

    Scope¶

    In scope:

    • SPICE auto-reconnect in --rdp: while the SPICE session is down the RDP listener and any connected client stay up, the client sees the last frame darkened, and ryll retries with the GUI's backoff and ticket rules; it exits as today once retrying is forbidden or exhausted.
    • Takeover: a new authenticated RDP connection to the same session disconnects the one being served (open question 4).
    • RDP client disconnect and reconnect, which already works (phase 4's manual test), proved by the loopback test.
    • Ctrl+C, which already shuts --rdp down cleanly (survey 4), kept working through this phase's restructure and proved with a client connected.
    • An rdp-smoke lane: FreeRDP under Xvfb against the UEFI latency guest, in CI as an advisory workflow and locally as make rdp-smoke.
    • Documentation of the user-visible behaviour and of the lane.

    Out of scope:

    • SPICE reconnect in --web and --headless, which leave a dead session up or exit today. The shared retry rules this phase moves (decision 3) make it cheaper later; recorded in Future work.
    • A text overlay explaining the outage (decision 2).
    • RDP auto-reconnect cookies (master plan Future work).
    • Joining the smoke tier, and turning the rdp feature on in release builds (open question 8). Both wait for the lane's flake record (decision 9).
    • The operator guide and parity column, which are phase 6's.
    • mstsc: no Windows machine is available, as in phases 2 to 4.

    What the survey found¶

    Checked on 2026-10-26 against the tree at 9e9e82b and ironrdp-server 0.13.0. The master plan's phase 5 section is right about what is wanted and wrong about what exists: items 1, 2, 6 and 7 below correct it. This planning commit makes those corrections at their source, in the master plan's phase 5 section and Execution row and in the docs/plans/index.md row, so a later step need not.

    Ryll side¶

    1. No server mode reconnects SPICE. --rdp ends when the SPICE connection task returns (ryll/src/rdp.rs:359-366): it stops the RDP server, which drops the client and closes the port. --web keeps serving HTTP over a dead session (ryll/src/main.rs:931-990); its "reaper" (ryll/src/web/lifecycle.rs) reaps WebRTC bridges, not SPICE sessions, so there is no --web reconnect pattern to follow. --headless exits.
    2. The GUI's retry rules are GUI-only. ryll/src/app/reconnect.rs holds the backoff (RECONNECT_BACKOFF_SECS = [1, 4, 16], :13), the ticket rules (ReconnectPolicy::forbid_retry, :95: single-use tickets and ticket-valid-until), the five-minute flap rule and the pure ReconnectState::on_disconnect transition. All are pub(super) inside mod app, which is compiled only with the gui feature (ryll/src/main.rs:1-2), and ModalVariant carries GUI wording.
    3. Each run_connection call consumes its channels. rdp.rs:283 moves event_tx, session_state, input_rx, usb_rx, webdav_rx, resize_rx, virtual_disks, share_dir and playback into the call. The RDP handles hold the other ends (SessionHandles.input_tx, resize_tx, and mouse_mode, a receiver of the first SessionState's watch), so a second attempt needs per-attempt channels behind handles that stay fixed. The event bus, mirror, cursor relay, MemoryClipboard and AudioRelay are not consumed and can outlive an attempt.
    4. Ctrl+C already works. rdp.rs:270-274 bridges SHUTDOWN_REQUESTED to the cancel flag, and the select! at :359 stops the RDP server first (server.shutdown(), :373, which sends ServerEvent::Quit and sets stopping so no new client is accepted), joins it, then cancels the renderer and the control socket. What is missing is proof with a client connected, and keeping it working once the server is restructured.
    5. The mirror does not reset between sessions. SurfaceMirror::apply_event ignores SessionInitialized (shakenfist-spice-renderer/src/surface_mirror.rs:480-493). A new session's SurfaceCreated for the primary surface replaces it, but secondary surfaces of the old session would linger.

    IronRDP side¶

    1. RdpServer::run serves one connection at a time and does not watch the listener meanwhile. Its loop select!s on the event channel and listener.accept(), then awaits self.run_connection(stream) inline (server.rs:936-990). A second client sits in the listen backlog (1024, server.rs:48) until the first leaves, so takeover cannot be built on run. run_connection is public (server.rs:719), takes any AsyncRead + AsyncWrite stream, and resets its own per-connection state, so a caller can own the listener. ConnectionHandler::on_accept and on_disconnected are called only by run, not by run_connection.
    2. The display handler's updates() is the first call after authentication in both security modes. client_loop calls it first (server.rs:1236), after the acceptor has finished CredSSP (NLA) or the credential validator (TLS). Only the first size() comes before any credential; request_initial_size() and the encoder's size() follow authentication but precede updates(). (Corrected by step 1, which also found that updates() is called again after every reactivation, so only its first call marks authentication, and that input the acceptor queued reaches the input handler just before it.) This corrects SessionProvider's doc comment (shakenfist-spice-rdp/src/lib.rs:150-156), which says IronRDP offers no hook after CredSSP: there is none for credentials, but updates() marks the moment.
    3. ServerEvent::Quit during a connection ends that connection only. In dispatch_server_events it returns RunState::Disconnect (server.rs:1102-1105); the server stops only when run's own select! receives it.
    4. Each RdpServer has its own event channel. The clipboard and sound factories get its sender once (set_sender), so with one server per connection a message queued by a leaving connection's channel backend dies with that connection's server. That closes phase 4's stale-wave hazard (its Future work: a wave or clipboard message queued as one connection ends can drop a client waiting in the backlog), which takeover would otherwise have made common.

    CI side¶

    1. No CI lane runs a QEMU guest. web-smoke (tools/web-smoke.sh, run by build-linux in ci.yml:179-183 and the merge tier's Linux leg) starts ryll --web against a stub .vv pointing at 127.0.0.1:1 and checks only that it binds and exits on SIGTERM. The master plan's "modelled on web-smoke ... against the local QEMU test server" therefore asks for something web-smoke does not do. The nearest functional lane is proxmox-functional.yml: advisory, path-filtered, its own workflow, driven by a Python standard-library script whose oracles are ryll's log lines (tools/proxmox-smoke.py).
    2. No build target makes an rdp binary. make build and make release leave the rdp feature off (Makefile:196-222); only test and lint turn it on. The lane needs a target that builds -p ryll --features rdp.
    3. The devcontainer has no QEMU, OVMF, Xvfb or FreeRDP (.devcontainer/Dockerfile:27-46). Whether the self-hosted runners expose /dev/kvm to a container is unknown.

    Decisions¶

    1. --rdp reconnects SPICE automatically (Mikal's choice at planning time). After a session has been established and then lost, ryll retries with the GUI's rules: backoff of 1, 4 and 16 seconds, no retry for a single-use ticket or past ticket-valid-until, and no retry budget for a session that lost its connection again within five minutes of exhausting one. When retrying is forbidden or exhausted, --rdp exits as it does today, with the last error. A first attempt that never reached a session also exits as today, matching the GUI's ConnectFailed, which does not retry either: it is usually a mistyped port.
    2. During an outage the client keeps its connection and sees the last frame at half brightness. The display handler sends one whole-surface update of the darkened frame when the session goes down, and the next real frame replaces it. A frozen frame alone looks like a hang. A text overlay would need a font rasteriser in the RDP crate, which is not worth one message. Input and resize requests made during the outage are dropped and counted, not queued for a session that does not exist yet. The clipboard and audio relays outlive the attempt, so clipboard text set during the outage reaches the guest's agent once it reconnects.
    3. The retry rules move out of the GUI with no behaviour change. The backoff, the ticket check and the flap rule become a module outside mod app that both the GUI and --rdp call. The GUI keeps its modal and its wording. The moved tests move unchanged, so a diff of the test bodies shows the GUI is untouched.
    4. Takeover is per session, at authentication. A connection takes over when its display handler's updates() is first called (survey 7): that is after authentication in both security modes, and before the new client is sent any pixels. It takes over only the connection serving the same SessionHandles (by Arc::ptr_eq), so a provider serving several sessions does not let one user kick another. The old connection is sent ServerEvent::Quit, its held keys are released as on any disconnect, and from the moment of takeover it no longer forwards input or takes damage from the mirror. This answers open question 4 as the master plan recommended.
    5. One IronRDP server per connection, behind our own accept loop. This is the decision a reviewer is most likely to question, since it rebuilds phase 2's server. RdpServer::run cannot accept a second client while one is connected (survey 6), so takeover is impossible on it. The alternative that keeps run, disconnecting the current client whenever a new TCP connection arrives, would let anyone who can reach the port kick the user off without a password. So shakenfist-spice-rdp binds the listener itself (keeping the port fallback, SO_REUSEADDR and readiness behaviour serve has now), builds an RdpServer for each accepted stream, and runs it with run_connection on the server thread's LocalSet. ConnectionLog's work moves into that loop, because run_connection does not call the connection handler (survey 6). Per-connection servers also give each connection its own event channel, which closes phase 4's stale-wave hazard (survey 9).
    6. Bounded pre-authentication work. Besides the connection being served, at most one unauthenticated connection runs its handshake at a time. Others wait in the listen backlog, unaccepted, as every client waits today. A connection that has not reached updates() within 30 seconds of accept is dropped. Without these, a stream of half-open connections would each hold a TLS handshake and an encoder.
    7. The smoke lane is an advisory workflow of its own. A new .github/workflows/rdp-smoke.yml runs nightly against develop, which builds the flake record, and on workflow_dispatch. Its pull_request trigger is path-filtered to the workflow file alone, so it runs on the pull request that adds it and on later edits to the lane, but not on pull requests that touch the RDP code (Mikal's choice at the back brief, to keep l runners free). A new workflow cannot be dispatched or scheduled until it is on develop, so without that trigger its first run would come after merge. It is advisory for the reason docs/ci.md gives for proxmox-functional.yml: a required check that is path-filtered never reports on other pull requests. It runs on [self-hosted, vm, debian-13-docker, l] and inside an image of its own (tools/rdp-smoke/Dockerfile: Debian 13 with qemu-system-x86, ovmf, freerdp3-x11, xvfb, xdotool, x11-apps for xwd, and python3), so the build devcontainer stays lean. QEMU starts with -accel kvm -accel tcg so it works with or without /dev/kvm. make rdp-smoke runs the same image locally.
    8. The lane's oracle is the guest's colour, seen by FreeRDP. The driver, tools/rdp-smoke.py, uses only the Python standard library, as tools/proxmox-smoke.py does, and reads the screen with xwd. It checks, in order:
    9. ryll authenticates FreeRDP (ryll's log line, with a fixed password from the driver);
    10. a frame arrives: the FreeRDP window's centre turns non-black within a deadline;
    11. input reaches the guest: an xdotool key changes the centre colour. This covers the whole path, client to ryll to SPICE to guest and back, so no ryll log line can make it pass;
    12. client reconnect: FreeRDP is killed and restarted, and check 3 passes again;
    13. takeover: a second FreeRDP connects, the first exits, and check 3 passes through the second;
    14. SPICE reconnect: QEMU is stopped and restarted on the same port; the client stays connected, the centre goes dark, and check 3 passes again within the backoff budget;
    15. Ctrl+C: SIGINT to ryll with the client connected; ryll exits 0 within 5 seconds and FreeRDP is disconnected.

    As in proxmox-smoke.py, each check prints a PASS or FAIL summary line, and a failure caused by the environment (QEMU not booting, Xvfb not starting) is reported as a harness failure, not a ryll defect. 9. Joining the smoke tier waits for a flake record, and the criterion is set now: fourteen consecutive green nightly runs, with no rerun needed. Moving the lane into ci.yml's smoke tier, and open question 8's release-build question, are then proposed in a later pull request. Writing the criterion down now stops "once it has a flake record" from meaning whatever is convenient later. 10. No new command-line flags. The retry budget is the GUI's and is not configurable. A user who wants --rdp to exit on the first SPICE loss can use a single-use ticket. Add a flag if an operator asks. 11. SessionHandles gains one field for decision 2: a watch::Receiver<bool> saying whether the SPICE session is up. It is filled at every construction site, as phase 4's fields were. A library user with no reconnect passes a receiver that is always true.
