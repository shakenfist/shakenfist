    RDP frontend phase 1: renderer prep¶

    Master plan: PLAN-rdp-frontend.md.

    Planning effort: low. The master plan asks for high, and the Execution notes record the choice to proceed anyway. It asks for high because this phase changes renderer internals that every mode depends on (the display surface, the playback channel, the crate's feature set and public API) and has to coordinate with Kerbside's transcoding spike. No review effort is set by the master plan; review at high effort, because steps 5 and 6 change the published crate's API.

    Prompt¶

    Read the master plan's Prompt first; everything there applies. For this phase specifically, read before acting:

    • shakenfist-spice-renderer/src/display/surface.rs and src/surface_mirror.rs (damage, steps 1 and 2).
    • shakenfist-spice-renderer/src/session.rs (run_connection at :193, run_headless at :646, the fan-out and mirror tasks at :883-935, plan_channel_links at :1151) and ryll/src/main.rs run_web (:514-1010).
    • ryll/src/web/inputs.rs run_input_relay (:132-314) and the pointer block in ryll/src/app/mod.rs (:4536-4630).
    • shakenfist-spice-renderer/src/channels/playback.rs and src/audio_sink.rs.
    • Every Cargo.toml in the workspace, the Makefile (lint at :277), and AGENTS.md Cargo feature gating.

    Builds and tests run in Docker through the Makefile (make build, make test, make lint), never with a host toolchain. Line references below are against develop 7690e1e; re-find them rather than trusting them once earlier steps have landed.

    Scope¶

    In scope, closing the master plan's renderer gaps 1 to 4:

    • Damage tracking on DisplaySurface, with a bounded rectangle region a consumer takes in one call.
    • A shared pointer translator in the renderer, used by --web and the GUI.
    • A shared event-bus helper for the forwarder and mirror-apply tasks, used by --web and headless.
    • A slim renderer build: features for usbredir, webdav, the H.264 encoder, H.264 decode and mozjpeg, so a consumer can link display decode alone.
    • Device-free playback: a run-time playback mode that hands a sink Opus packets, raw PCM and decoded PCM without opening a cpal device, and --web switched to it.
    • A make lint check that keeps the slim build compiling and slim.
    • Documentation of the above.

    Out of scope:

    • Any RDP code or IronRDP dependency (phase 2).
    • Mono and 4-bit cursor decode (gap 6, phase 3).
    • Multi-monitor (gap 5, future work).
    • Changing headless's audio behaviour: it keeps local output. See decision 9.
    • Pruning ryll/Cargo.toml's own unused direct dependencies (see Future work); this phase prunes only the renderer's.
    • Fixing #398 (H.264 from spice-server's gstreamer never decodes); decision 6 relies on it only as evidence.
    • Adding wheel support to --web, which has none (see What the survey found, item 9).

    What the survey found¶

    Surveyed on 2026-10-20 against develop 7690e1e. The master plan's gap list is substantially right. These items correct or sharpen it; the false claims are fixed at their source in the master plan and the index.md row in this planning commit, so later steps need not redo that.

    1. openh264 is pulled in by H.264 decode, not only by the encoder. openh264 = "=0.9.8" is a non-optional dependency of shakenfist-spice-compression, used by H264VideoDecoder (video.rs:266-477, selected by for_stream at video.rs:174). Gating the renderer's encoder alone leaves openh264-sys2 (a C++ build with cc and nasm) in the tree. Separating it is possible: a build without H.264 decode must also stop advertising DISPLAY_CODEC_H264, and H264Offer::Off already does exactly that (link::display_channel_caps, protocol link.rs:744-749; preferred_video_codecs, display.rs:170-176). MJPEG decode does not depend on it. The master plan said only that the encoder pulls openh264; corrected.
    2. The renderer turns on more C builds than the master plan listed. It depends on the compression crate with default features plus encode, so it always builds mozjpeg (vendored libjpeg-turbo) as well as openh264. The pure-Rust jpeg-decoder fallback already exists, so mozjpeg can be a feature.
    3. Ten renderer dependencies are unused. rsa, sha1, rand, tokio-rustls, rustls-pemfile, webpki-roots, byteorder, async-channel, thiserror and http-body-util have no references in the renderer's src/ or tests/ (checked by grep), and nor does http. bytes is used only by tests/webrtc_h264_smoke.rs. They can be deleted, no feature needed. nusb is used only under cfg(target_os = "linux") but is an unconditional dependency on every target.
    4. The audio gap is worse than "a tap, not a sink". The tap fires before decode and whether or not a device opened (playback.rs:1156-1221), but the playback channel exists only with the audio feature (channels/mod.rs:6, session.rs:456, :1158-1161). So a --no-default-features ryll serves --web with no audio at all, and a default build serving --web also plays the guest's audio out of the server's own speakers, or, with no device, retries cpal every 30 s for nothing (playback.rs:540-554). The sink never sees decoded PCM, START/STOP or format changes (audio_sink.rs:29-42). Its only implementor is WebOpusSink (ryll/src/web/audio.rs:51-117).
    5. The playback channel offers Opus by accident. Playback links with DEFAULT_OTHER (protocol link.rs:706-712), whose bits are the main channel's migrate caps; on the playback channel those same bits mean CELT_0_5_1 | OPUS (constants.rs:130-135, :221-234). Ryll cannot decode CELT (playback.rs:1199-1219). Not in the master plan; step 6 gives playback its own caps constant.
    6. The forwarder and mirror-apply tasks exist twice, not once: in run_web (main.rs:803-845) and in run_headless (session.rs:883-935), with two separate EVENT_BROADCAST_CAPACITY constants (session.rs:87, web/server.rs:34), both 1024. RDP would be the third copy. The master plan named only run_web; corrected.
    7. The two pointer translators disagree. The GUI (app/mod.rs:4536-4555) suppresses a repeated position in both mouse modes; the web relay (web/inputs.rs:208-233) suppresses only zero deltas in server mode. The GUI places button events at the last hover position; the web relay takes the button's own coordinates and records them as the next delta origin without telling the guest the pointer moved (web/inputs.rs:237-264). In server mode SPICE's MOUSE_PRESS carries no position, so that movement is lost. The inputs channel already sends MOUSE_POSITION before every press and release (inputs.rs:750-830), which covers client mode.
    8. Damage rectangles exist on six events, not four: ImageReadyChroma and ImageReadyAlpha carry them too. The draw ops clamp to the surface and to clip lists inside DisplaySurface (surface.rs:70-402), so that is where the exact written rectangles are known.
    9. --web has no mouse wheel. BrowserMsg has no wheel variant and app.js sends none; the GUI maps the wheel to button 4/5 press-release pairs (app/mod.rs:4596-4618). docs/multi-mode-parity.md has no wheel row, so the gap is unrecorded. Out of scope here (the translator in step 3 gives both frontends the same wheel mapping to call); recorded in Future work.
    10. ChannelEvent::UsbDevicesChanged is never emitted (channels/mod.rs:450-452, #[allow(dead_code)]), and it is the only thing tying usb::UsbDeviceInfo into the always-present event enum.
    11. No CI lane builds the renderer slim. make lint runs a slim clippy for the compression crate only (Makefile:280). cargo-deny runs with --all-features, so it never sees a slim tree.
    12. Kerbside's side of the hand-over is not merged. The master plan says Kerbside's phase 3 plan "has been updated to match". That update is kerbside PR #581, still open on 2026-10-20. Kerbside's spike step 3a has partly reached ryll already: the LZ4 and JPEG image encoders landed (6895658, 8dc590b). Its slim-features part has not, so this phase does not collide with it.

    Decisions¶

    1. Damage lives on DisplaySurface, beside the dirty bool, and is independent of it. Each draw op records the sub-rectangles it actually wrote, after clamping to the surface and the clip list, into a bounded DamageRegion. A new surface starts fully damaged, as it starts dirty. take_damage() returns the region and clears it; consume_dirty() keeps its meaning and does not touch the region, and vice versa. RealFrameSource and the GUI texture cache are unchanged. Independence costs nothing: the region is bounded, so a surface whose damage nobody takes holds at most MAX_DAMAGE_RECTS rectangles. Putting damage in DrawOutcome instead was rejected: it would hand the merging and bounding to every consumer, which is what the master plan's "goes in the renderer" rules out.
    2. The region merges and bounds deterministically. A new rectangle contained in an existing one is dropped. Two rectangles merge when their bounding box's area is no more than the sum of their areas, so a merge never adds pixels that neither covered beyond their overlap; merging repeats until no pair qualifies. Past MAX_DAMAGE_RECTS (32), the whole region collapses to its bounding box. This is simple, testable and good enough for RDP, which re-diffs in 64x64 tiles anyway (master plan, The RDP side).
    3. A lagged mirror marks everything damaged. When the mirror's bus subscription reports Lagged, the shared helper (decision 4) calls a new SurfaceMirror::mark_all_damaged(), which sets every surface fully damaged and dirty. The pixels have already diverged; this makes every consumer resend the whole surface, rather than trusting a region that is missing the draws it never saw.
    4. One event-bus helper, in the renderer, used by --web and headless now. EventBus::new(capacity) creates the broadcast sender and the mirror and takes the mirror's subscription at once. Callers take their own subscriptions with subscribe(), then call start(event_rx), which spawns the forwarder and the mirror-apply task and returns their handles. Splitting construction from start preserves run_web's rule that every long-lived consumer subscribes before events flow (main.rs:724-735). The two capacity constants become one, session::EVENT_BROADCAST_CAPACITY.
    5. One pointer translator, synchronous, mode passed per call. PointerTranslator in the renderer (src/pointer.rs) holds only the last position. It takes the mouse mode as an argument on each call, so the GUI (synchronous, mode in self.mouse_mode) and the web relay (async, mode in a watch) both use it without sharing a runtime type. The unified behaviour:
    6. A move to the last position sends nothing, in either mode (the GUI's behaviour). For --web this drops duplicate MOUSE_POSITION messages in client mode, which the guest ignored anyway.
    7. In server mode the first move after a reset is a zero delta and sends nothing; later moves send MouseMotion.
    8. A button event that carries a position different from the last one, in server mode, is preceded by the MouseMotion delta to it, then recorded as the new origin. This changes --web behaviour, deliberately: today the movement is silently dropped (survey item 7). The existing test a_button_position_becomes_the_next_delta_reference is updated to expect the delta. Client mode needs no extra event, because the inputs channel already sends a position with every press.
    9. A button event with no position (the GUI) uses the last position.
    10. wheel(clicks) turns signed wheel clicks into button 4 or 5 press-release pairs at the last position, as the GUI does today; the egui-specific click accumulator stays in the GUI.
    11. reset() forgets the position (the GUI calls it on reconnect, app/mod.rs:1160).
    12. openh264 decode becomes a feature; a build without it offers no H.264. The compression crate gains h264-decode = ["dep:openh264"], default on, and encode gains dep:openh264 explicitly. In a renderer build without h264-decode, run_connection and DisplayChannel::new force H264Offer::Off, which already drops both the cap bit and the codec preference; the protocol crate's DEFAULT_DISPLAY and its logging test do not change. MJPEG stream decode is untouched. The cost of dropping H.264 decode in a slim build is nil in practice: H.264 from spice-server's gstreamer encoder does not decode in ryll at all today (#398), and the default preference already asks for MJPEG first.
    13. The renderer's feature set. All default-on, so a plain dependency on the crate builds what it builds today:
    Feature Pulls in Gates
    audio cpal, rtrb local audio output only (narrowed, decision 8)
    usbredir nusb (Linux), shakenfist-spice-usbredir usb, channels::usbredir
    webdav dav-server, hyper, hyper-util webdav, channels::webdav
    encoder compression encode (openh264-sys2, jpeg-encoder) encoder::h264, encoder::task

    The renderer depends on the compression crate with default-features = false and the decoder features it always needs (quic, glz, lz, lz4, jpeg). Gating follows the audio precedent (session.rs:226, :456, :1158-1161): plain-data types stay ungated so run_connection and run_headless keep one signature in every build (UsbCommand, WebdavCommand, ShareDirConfig, VirtualDiskConfig, every snapshot, every other ChannelEvent variant), and plan_channel_links skips a compiled-out channel with a logged reason. FrameSource, FrameRef, RealFrameSource, SyntheticFrameSource, EncodedFrame and EncoderControl stay ungated (the last two move out of the files that need openh264), because shakenfist-spice-webrtc's production code needs only those. even_dimensions moves out of the compression crate's encode module so it is available without the encoder (web/inputs.rs uses it for viewport rounding). The dead UsbDevicesChanged variant is deleted rather than having its types moved. ryll names the features it needs explicitly (it already uses default-features = false), and shakenfist-spice-webrtc takes encoder only as a dev-dependency. These names become public API on crates.io, which is why they are settled here rather than by the implementer. 8. Playback is always compiled; only local output is a feature. opus-decoder is pure Rust and small, while cpal pulls ALSA, so the split that matters is decode versus device. PlaybackChannel and opus decode become unconditional, and audio gates only the cpal audio thread and its ring. run_connection's opus_sink: Option<Arc<dyn OpusPacketSink>> parameter becomes playback: PlaybackOutput, with two variants: - Local: today's behaviour. In a build without audio, the channel is not linked, as today. - Sink(Arc<dyn PlaybackSink>): never spawns the audio thread and is linked in every build. Notification suppression keys off this variant instead of opus_sink.is_some() (playback.rs:1383).

    The trait is renamed PlaybackSink, since it is no longer only about Opus, and gains on_start(PlaybackFormat), on_stop() and on_decoded_pcm(&[i16], rate, channels), all with default no-op bodies beside the existing on_opus_packet and on_pcm_samples. Decode keeps running in both variants, as it does today, so the control socket's stats.playback.packets_decoded keeps its meaning (docs/control-socket-protocol.md). Decoding only on demand was rejected for that reason; Opus decode of one stereo stream is cheap. The rename is a breaking API change, which is acceptable at 0.x and needed anyway by the signature change. 9. --web switches to Sink; headless and the GUI stay on Local. That --web should not open a local audio device is the master plan's requirement. Headless today really does play audio locally when a device exists, and whether that is a feature or an accident is not this phase's call. It is recorded in Future work rather than changed silently. 10. Playback gets its own caps constant. A DEFAULT_PLAYBACK in the protocol crate, OPUS only, and default_channel_caps uses it for the playback channel. The only wire change is dropping the CELT bit, which ryll cannot decode. Phase 4 will want to choose Opus or PCM per client, and that starts from a named constant rather than a borrowed one. 11. The slim build is checked in make lint, which CI already runs. A new tools/check-slim-renderer.sh, run in the devcontainer by make lint, does three things. It clippies the renderer with --no-default-features --all-targets. It checks the renderer with each feature enabled on its own. It runs cargo tree -p shakenfist-spice-renderer --no-default-features -e normal,build and fails if any of openh264, openh264-sys2, mozjpeg-sys, nusb, dav-server, hyper, cpal or alsa-sys appears. A separate CI job was rejected: the lint job exists and this costs it a renderer build.

    Risks and mitigations¶

    • A missed cfg breaks a feature combination nobody builds. Mitigation: step 7's per-feature checks run in every make lint. The management session reviews step 5 by running the slim clippy itself, not by reading the report.
    • Feature unification hides a missing feature in ryll. A workspace build unifies features, so ryll forgetting to request webdav would still build under make build. Mitigation: make check-windows builds -p ryll alone. The management session also runs cargo check -p ryll and cargo check -p ryll --no-default-features alone after step 5.
    • The pointer change regresses the GUI. The GUI's pointer block is egui-coupled and has no unit tests. Mitigation: the translator's behaviour for the GUI's calls (button with no position, motion) is identical to today's by construction. The management session runs the GUI against the local QEMU test server after step 3, and checks hover, click, drag and wheel in both mouse modes (a guest with and without vdagent).
    • The server-mode catch-up delta surprises a --web user. Mitigation: it only fires when a button arrives at a position no move reported, which the browser rarely does. Decision 5 records it as deliberate, and the PR description calls it out.
    • Damage tracking slows the draw path. One add per written sub-rectangle, with at most 32 rectangles to scan. Mitigation: none needed beyond keeping add linear; the management session rejects a quadratic-per-pixel design in review.
    • The playback refactor breaks local audio in the GUI. The cpal thread code moves but should not change. Mitigation: step 6 runs in a worktree, the existing playback.rs tests move with their code, and the management session plays guest audio through the GUI after step 6.
    • Kerbside's spike step 3b wants a different damage API. Mitigation: the API (decision 1) is a plain region taken under the mirror lock, which is what spike 3b's brief describes. After this phase merges, the management session points kerbside PR #581 (or its successor) at the merged API.
    • Publishing. Feature names and the PlaybackSink rename are breaking for crates.io consumers of 0.3.0. Mitigation: acceptable at 0.x; the next release notes must list them. tools/package-check-verify.sh (cargo package --workspace) in CI catches a manifest that does not package.

    Future work¶

    • Headless audio. Headless still plays audio locally when a device exists, and retries cpal when none does. With PlaybackOutput in place, a headless discard or sink mode is a one-line choice; whether headless should play audio is a product decision (decision 9).
    • ryll/Cargo.toml declares crates it never uses directly: nusb, dav-server, hyper, hyper-util, http, http-body-util, lz4_flex, image, jpeg-decoder, flate2, socket2, rsa, sha1, byteorder, tokio-rustls, rustls-pemfile, webpki-roots and async-channel (per the survey; http:: hits in ryll/src are axum::http). Pruning them does not affect a renderer consumer, but tidies ryll's own tree.
    • Web mouse wheel (#594, survey item 9): add a wheel message to app.js and the relay, through PointerTranslator::wheel.
    • GUI server-mode pointer grab (#592). In server mouse mode the GUI sends relative deltas from host hover positions without grabbing or warping the pointer, so guest acceleration makes the two cursors drift until parts of the guest display cannot be reached (see Results). spice-gtk grabs the pointer in server mode. This predates the phase; the RDP frontend will meet the same problem in server mode.
    • The protocol crate's TLS provider (#593). shakenfist-spice-protocol depends on tokio-rustls with default features, which pulls in aws-lc-rs and aws-lc-sys (a cmake C build), while ryll itself installs ring as its rustls provider. Choosing one provider in the protocol crate (probably ring, with default-features = false) would take the last C build out of the slim renderer and stop ryll building two crypto libraries. Check what Kerbside's proxy expects before changing it.
    • cargo-deny on the slim tree: it runs with --all-features, so it audits a superset. Probably fine; noted in case a licence ever differs between the two trees.
