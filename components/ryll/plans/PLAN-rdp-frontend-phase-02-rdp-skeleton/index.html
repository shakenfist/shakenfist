    RDP frontend phase 2: RDP skeleton¶

    Master plan: PLAN-rdp-frontend.md.

    Planning effort: xhigh (the master plan asks for high). This is the phase that turns on RDP security negotiation, IronRDP's concurrency model and the back-pressure between a slow RDP client and the SPICE session, and it is where the plan learns most. No review effort is set by the master plan; review at high effort, because step 7 changes the ryll binary's CLI and step 1 adds a crate that will be published.

    Prompt¶

    Read the master plan's Prompt first; everything there applies. For this phase in particular:

    • The RDP side is IronRDP 0.13.0 from crates.io (ironrdp-server 0.13.0, ironrdp-acceptor 0.10.0, ironrdp-pdu 0.9.0, released 2026-07-10). Its source is github.com/Devolutions/IronRDP at tag ironrdp-server-v0.13.0, and every file and line cited below for IronRDP is relative to that tree. Check it out read-only, in a directory of its own: it is downloaded code, so read it, never run its build scripts or examples from inside it. Re-read the cited file before building on a claim.
    • Read ryll/src/main.rs run_web (:514-990) end to end: it is the shape run_rdp copies, with a different transport.
    • The renderer pieces this phase drives are the ones phase 1 landed: DisplaySurface::take_damage (display/surface.rs:540), SurfaceMirror (surface_mirror.rs), EventBus (event_bus.rs), PointerTranslator (pointer.rs), PlaybackOutput::Sink (playback_sink.rs) and run_connection (session.rs:211).
    • Builds run in Docker through the Makefile, never with a host toolchain. The ryll-dev image is absent on this host at planning time, so the first make target rebuilds it.

    Scope¶

    In scope, the master plan's phase 2 as surveyed:

    • A new publishable library crate, shakenfist-spice-rdp, over ironrdp-server 0.13.0: a display adapter fed by the mirror's damage, an input adapter over the renderer's input sender and PointerTranslator, credential checking, TLS (self-signed or supplied), and a runner that hides IronRDP's !Send server behind a thread of its own.
    • One renderer addition: an InputEvent that sets the guest's lock keys, so RDP's Synchronize reaches the inputs channel.
    • ryll --rdp behind a default-off rdp cargo feature, with --rdp-host, --rdp-port, --rdp-user, --rdp-password, --rdp-security and --rdp-tls-cert / --rdp-tls-key, printing the address, credentials and certificate fingerprint at launch the way --web prints its URL. A control socket is allowed, as in --web.
    • Keyboard with the extended flag, lock keys, mouse buttons and the vertical wheel in both mouse modes; relative mouse motion where the client sends it.
    • DisplayUpdate::Resize when the guest changes its own resolution, so the stream does not stall (moved here from phase 3; see What the survey found, item 8).
    • A loopback integration test that drives the server with IronRDP's own client connector, so the handshake is proven in CI without an RDP client.
    • A manual test with FreeRDP (and mstsc where available) against the desktop guest, with the negotiated security and codec, bytes per second and CPU for three workloads recorded in Results, and open questions 1, 2, 3 and 7 answered in the master plan.
    • The documentation a new CLI surface needs now: the flags in docs/configuration.md, the feature in docs/development.md and AGENTS.md, and a line in the parity page's mode table. The operator guide, the parity column, ARCHITECTURE.md and the README link are phase 6.

    Out of scope:

    • Cursor shapes and client-driven resize (phase 3). This phase sends no pointer updates at all; the client draws its own arrow.
    • Clipboard and audio (phase 4). Guest audio is discarded in --rdp for now rather than played on the server host.
    • Takeover by a new connection, SPICE reconnect handling and the rdp-smoke lane (phase 5). With IronRDP's own accept loop a second client waits in the TCP backlog until the first disconnects; decision 4 says why that is accepted for now.
    • H.264 through EGFX, multi-monitor, Unicode key events (dropped with a warn_once!, open question 5).
    • Making --web and --headless mutually exclusive (#601, found by the survey; --rdp declares its own conflicts).
    • Fixing IronRDP's loss of the middle button (survey item 4); this phase records it and waits for the next release.

    What the survey found¶

    Surveyed on 2026-10-21 against develop 27f2a2d and IronRDP 0.13.0 (ironrdp-server-v0.13.0, commit 11a0810c) and master 66bfd60e (2026-10-20, 502 commits past the tag). The master plan's phase 2 section is right about the shape of the work. These items correct or sharpen it; the false claims are fixed at their source in the master plan's Situation, Open questions and Execution sections and in the index.md row in this planning commit, so later steps need not redo that.

    1. IronRDP's development branch is master, not main. The repository's default branch is master; 62246b3, which the master plan read, is in its history. The claims the plan marks (main) are claims about that branch.
    2. 0.13.0 cannot offer TLS and NLA together. The builder's security choice is one of with_no_security, with_tls or with_hybrid (crates/ironrdp-server/src/builder.rs:72-98), and RdpServerSecurity::flag() advertises SSL for the first and HYBRID | HYBRID_EX, without SSL, for the second (server.rs:293-305). The acceptor intersects that with what the client requested and refuses an SSL-only client of a hybrid server with HYBRID_REQUIRED_BY_SERVER (crates/ironrdp-acceptor/src/connection.rs:414-433). A TLS server accepts a client that asked for SSL | HYBRID | HYBRID_EX, which is what mstsc sends. The master plan's recommendation to "offer Hybrid and TLS together so the client chooses" is not available; decision 2 picks TLS.
    3. 0.13.0 already has a CredentialValidator, and in TLS mode it is the check, not an authorisation layer on top. server.rs:178-194 defines it; client_accepted (server.rs:1350-1369) runs it on the Client Info PDU's credentials and answers a rejection with ServerSetErrorInfo before closing. It is not consulted for CredSSP connections, where NTLM uses the pre-loaded Credentials. Without a validator the acceptor compares the Client Info credentials to the pre-loaded pair with plain struct equality, including the domain field (connection.rs:693-713); mstsc fills a domain and FreeRDP may not, so that path is wrong for us and decision 2 uses a validator that ignores the domain.
    4. 0.13.0 loses the middle button and the horizontal wheel on the standard mouse PDU. From<MousePdu> for MouseEvent (crates/ironrdp-server/src/handler.rs) tests LEFT_BUTTON, RIGHT_BUTTON and VERTICAL_WHEEL and turns everything else into Move; PointerFlags has MIDDLE_BUTTON_OR_WHEEL and HORIZONTAL_WHEEL (crates/ironrdp-pdu/src/input/mouse.rs:107-114) and neither is matched. master fixes both and reshapes the enum into Move, Button { x, y, button, pressed }, ButtonRel, scroll variants and RelMove. The middle button does arrive through the relative-mouse PDU (MouseRelPdu) and FreeRDP's ainput channel, both of which 0.13.0 maps fully. The master plan's claim that 0.13.0's mouse events are "flat per-button variants plus move and vertical wheel" is incomplete: 0.13.0 has MiddlePressed, Button4Pressed, Button5Pressed, Scroll { x, y } and RelMove { x, y } too (handler.rs:17-33); the gap is in the conversion from the standard PDU, not in the enum.
    5. RdpServer is !Send in 0.13.0 as well. SoundServerFactory (sound.rs:5) and CliprdrServerFactory (clipboard.rs:5) carry no Send bound and RdpServer holds them boxed (server.rs:434-456), and run_connection clones an Rc internally (server.rs:1300). IronRDP's own README and its end-to-end test run the server inside a tokio::task::LocalSet (crates/ironrdp-server/README.md, crates/ironrdp-testsuite-extra/tests/e2e.rs:280-290). The master plan's "check 0.13.0" is answered: it needs a LocalSet or its own thread. Decision 3 gives it a thread.
    6. 0.13.0 advertises relative mouse input. The server's input capability set includes MOUSE_RELATIVE and MOUSEX (crates/ironrdp-server/src/capabilities.rs, input_capabilities), so a client that supports it (FreeRDP 3's relative-mouse option; mstsc is to be tested) can send MouseRelPdu, which arrives as MouseEvent::RelMove. Open question 3's "if the pinned IronRDP offers relative-mouse input, try it" is therefore a phase 2 test, not a wish.
    7. IronRDP's framebuffer is seeded only by a full-desktop bitmap, and its diff assumes four bytes per pixel. bitmap_update_framebuffer (crates/ironrdp-server/src/encoder/mod.rs:318-331) creates the framebuffer when a BitmapUpdate is at (0, 0) with the desktop's size and otherwise only patches an existing one; bitmap_diffs (:240-275) diffs against it with find_different_rects_sub::<4> and, with no framebuffer, treats the whole bitmap as changed. A bitmap that exceeds the desktop size is dropped with a warning (:379-386). So the first update after connect (and after a resize) must be the whole surface, and every later rectangle must lie inside the current desktop size. PixelFormat::RgbA32 is honoured by the planar encoder (encoder/bitmap.rs:101-110) and by RemoteFX, which reads channels through the format (encoder/rfx.rs:185-201); its channel order is [0, 1, 2, 3] = R, G, B, A (crates/ironrdp-graphics/src/image_processing.rs:168), the same bytes DisplaySurface keeps (surface.rs:37). No swizzle is needed, as the master plan hoped.
    8. A guest-driven resolution change needs Resize in this phase, not phase 3. Item 7 means that once the primary surface changes size the display adapter must emit DisplayUpdate::Resize (which deactivates and reactivates the connection, server.rs:1047 and accept_finalize :1736-1750) before any bitmap, or every later update is dropped.     Decisions¶

    1. IronRDP 0.13.0 from crates.io, slimmed, and the workspace MSRV goes to 1.89. The crate depends on ironrdp-server = { version = "0.13", default-features = false, features = ["rayon", "helper"] }: rayon parallelises RemoteFX encoding, helper gives TlsIdentityCtx for PEM files, and dropping qoi/qoiz keeps two private codecs and a second zstd-safe out of the tree (survey item 12). Nothing from master is needed for the MVP; the one thing it fixes that this phase wants, the middle button (survey item 4), is recorded in Future work and tracked by an issue step 4 files, and is re-examined at the next IronRDP release. A git pin was rejected: deny.toml denies unknown git sources, a crate with a git dependency cannot be published, and every IronRDP minor has broken the server API, so churn is cheaper to absorb one release at a time. All IronRDP-facing code lives in shakenfist-spice-rdp; ryll sees only this crate's types. The workspace rust-version becomes 1.89 (survey item 13).
    2. TLS-only by default; NLA on request; one credential pair; the domain is ignored. --rdp-security tls (default) builds with with_tls and a CredentialValidator that compares username and password and ignores domain (survey item 3); the server's pre-loaded credentials are left unset so the acceptor's struct-equality check never runs. --rdp-security nla builds with with_hybrid and set_credentials, because CredSSP's NTLM needs the plaintext pair; it refuses TLS-only clients, which is IronRDP's behaviour and is documented. The username defaults to ryll and the password to 24 random alphanumeric characters minted per launch and printed, both overridable by flag; this is --web's per-launch token in RDP clothing. This reverses the master plan's "offer both" because 0.13.0 cannot (survey item 2), and picks TLS over NLA because TLS is the mode every client speaks and the only one where our validator sees the password. Open question 2 is updated with this evidence and the mstsc result from step 8.
    3. The RDP server runs on its own OS thread with a current-thread tokio runtime, inside the crate. RdpServer and its futures are !Send (survey item 5), so shakenfist-spice-rdp::serve spawns a thread, builds the runtime and server there, and returns a Send handle with shutdown() (sends ServerEvent::Quit) and join(). The SPICE side stays on ryll's multi-thread runtime; the two share Arc<tokio::sync::Mutex<SurfaceMirror>>, mpsc senders and watch receivers, all of which work across runtimes. RemoteFX encoding then never competes with SPICE decoding for a worker. A LocalSet on the caller's runtime was rejected because it would make the crate's API !Send for every consumer.
    4. One connection at a time, through IronRDP's own accept loop, for now. RdpServer::run is used as is (survey item 10): a second client waits in the backlog until the first disconnects. Takeover, which the master plan's open question 4 wants, needs our own accept loop around run_connection and belongs to phase 5 with the rest of the lifecycle work. Phase 2 documents the wait. The listener binds --rdp-host (default 127.0.0.1, as --web-host) and --rdp-port: when the flag is absent, 3389 is tried by binding and releasing a probe listener and, if that fails, port 0 is used and the real port is read back with ServerEvent::GetLocalAddr; when the flag is given, its port is used or the launch fails.
    5. The display adapter is a damage-paced reader of the mirror, not a queue of bitmaps. MirrorDisplay implements RdpServerDisplay: size() is the primary surface's size (or --rdp's fallback 1024x768 before the first surface, corrected by a Resize once it exists). updates() returns MirrorUpdates, whose next_update:
    6. keeps a VecDeque<DisplayUpdate> of pending updates and returns the front if there is one;
    7. otherwise waits one tick of a tokio::time::interval (DAMAGE_POLL_INTERVAL, 16 ms), locks the mirror, and if the primary surface's size differs from the last size it sent, clears pending damage knowledge, pushes Resize(new size) and a full-surface bitmap; if the surface has not yet been sent in full, pushes a full-surface bitmap (survey item 7); otherwise calls take_damage() and, for a non-empty region, copies the bounding box's rows once into a Bytes and pushes one BitmapUpdate per rectangle, sliced from that copy with the box's stride and the rectangle's offset, format RgbA32;
    8. drops the lock and returns the front of the deque. Cancel safety (survey item 9) holds by construction: the only awaits are the tick and the lock, both before any damage is taken, and everything taken is in self before the function returns. A lagged mirror marks every surface damaged (phase 1, decision 3), so recovery is the ordinary full-surface path. PointerPosition is never sent (qemu-rdp's experience, master plan); cursor shapes are phase 3. The 16 ms poll was chosen over a wake-up from the mirror task because EventBus exposes none and a bus subscription cannot be ordered after the mirror's apply; if step 8's latency numbers say the poll costs too much, a Notify from the mirror task is the follow-up, recorded in Future work.
    9. The session seam is a provider trait plus a slot. SessionHandles { surface_mirror, input_tx, mouse_mode, resize_tx, label } is what the adapters need from a SPICE session; SessionProvider is fn session(&self, credentials: &Credentials) -> Result<Arc<SessionHandles>, Rejected>, called by the TLS-mode validator (and at connect for NLA, with the configured pair), and the chosen handles go into a SessionSlot the display and input adapters read. ryll's SingleSession provider holds one pair and one SessionHandles. The crate's docs say what survey item 11 found: 0.13.0 needs the desktop size before authentication, so a provider with sessions of different sizes must resize after choosing or run one process per session, which is what the master plan's Moving to Kerbside already plans.
    10. Input mapping. SpiceInputHandler implements RdpServerInputHandler (synchronous, Send), holding a PointerTranslator, the watch::Receiver<u32> for the mouse mode (read with borrow()), the mpsc::Sender<InputEvent> (try_send; a full queue drops the event, counts it and warns once, because the handler cannot await) and a wheel remainder:
    11. Pressed { code, extended } → KeyDown(make_scancode(base, false)) with base = if extended { 0xE000 | code } else { code }, as the GUI builds its scancodes; Released likewise with true.
    12. Synchronize(flags) → InputEvent::KeyModifiers(flags.bits() & 0x7): Scroll, Num and Caps Lock share SPICE's bit layout (survey item 15).
    13. Move { x, y } → translator.motion(mode, x, y); RDP coordinates are desktop pixels, which are surface pixels.
    14. LeftPressed and friends → translator.button(mode, mouse_buttons::LEFT | MIDDLE | RIGHT, pressed, None).
    15. VerticalScroll { value } → wheel clicks: value is in rotation units, 120 per notch for ordinary wheels; the handler accumulates the remainder and emits translator.wheel(clicks) per whole notch, so a high-resolution wheel neither spams nor stalls.
    16. RelMove { x, y } → in server mode MouseMotion { dx, dy } directly; in client mode added to the translator's last position, clamped to the surface, and sent through motion. Scroll { x, y } uses y as vertical units and drops x.
    17. Button4Pressed/Button5Pressed, UnicodePressed, UnicodeReleased and horizontal scroll → dropped with a warn_once! each (open question 5; SPICE has no horizontal wheel and no mask bit for the side buttons).
    18. ryll wiring mirrors run_web. A default-off rdp cargo feature on ryll (rdp = ["dep:shakenfist-spice-rdp"], open question 8), make lint and make test compile it, release builds do not. run_rdp builds the same scaffolding as run_web (main.rs:514-990): byte counter, traffic, snapshots, pedantic observer, EventBus, SessionState, run_connection with PlaybackOutput::Sink(DiscardPlayback) (a no-op sink; phase 4 replaces it with rdpsnd) and the optional control socket with the same SessionHandles the web path builds, then calls shakenfist_spice_rdp::serve and waits for Ctrl+C or the server's exit, shutting down in run_web's order. --rdp conflicts with --web and --headless at parse time. The launch prints, with the audit-allow-println marker web/server.rs:439 uses: RDP: <host>:<port>, user: <user>, password: <password>, security: tls|nla, and certificate SHA-256: <fingerprint> for a generated certificate.
    19. TLS identity. With --rdp-tls-cert and --rdp-tls-key (both or neither, by clap requires), IronRDP's TlsIdentityCtx::init_from_paths loads them (it also derives the public key NLA needs). Without them, rcgen 0.14 generates a self-signed certificate for --rdp-host and localhost at launch, as web/server.rs:1060 does in tests, and the crate prints its SHA-256 fingerprint so a user can match what the client shows. The certificate is per launch and never written to disk; a stable certificate is what the two flags are for, and the operator guide (phase 6) will say so.
    20. Testing. Each adapter has unit tests against the renderer's real types (a SurfaceMirror with a test surface, a PointerTranslator, an mpsc). A loopback integration test in shakenfist-spice-rdp/tests/ starts the server with with_no_security on 127.0.0.1:0, connects with IronRDP's own client connector, completes the handshake, receives the seeding bitmap and sends one key, asserting the InputEvent that reaches the mpsc. The precedent is crates/ironrdp-testsuite-core/tests/server/autodetect.rs (no security) and crates/ironrdp-testsuite-extra/tests/e2e.rs (the client loop). FreeRDP against the desktop guest is the manual test, run by the management session with Mikal, and tools/rdp-measure.sh (step 8) records bytes per second from ss -tin and CPU from /proc/<pid>/stat for the three workloads of open question 7.
    21. What this phase changes in the master plan. Survey items 1, 2, 3, 4, 5, 6, 8, 11, 13 and 14 are corrected at their source in the planning commit. Open questions 1, 2, 3 and 7 get their evidence-based answers in the close-out commit of step 9, once step 8 has run.

    Risks and mitigations¶

    • A stock client refuses the TLS-only server or its self-signed certificate. mstsc warns on an untrusted certificate and offers to continue; FreeRDP needs /cert:tofu or /cert:ignore. If mstsc's default policy refuses TLS-only servers outright, --rdp-security nla exists and decision 2 is revisited; the management session checks the result before step 9.
