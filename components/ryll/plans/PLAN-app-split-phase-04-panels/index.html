    Phase 4: Split the draw code into app/ui/¶

    Master plan: PLAN-app-split.md.

    Planning effort¶

    Planned at high effort. The phase looks like the moves phases 2 and 3 did, and most of it is, but three parts are not. Nesting a module under app/ needs a visibility form neither earlier phase used, and getting it wrong is a compile error in every step at once. The status bar is a single 373-line ui.horizontal closure that cannot move as one function. And the central panel sets two flags that later blocks read, so it is the one block whose extraction changes a signature rather than just a location.

    Review effort belongs on draw order. Everything else here is checkable by script; the order the panels and windows are drawn in is a contract with egui that no test in this repository exercises.

    Scope¶

    In:

    • ryll/src/app/ui/ -- a new module directory with mod.rs and ten children: cursor.rs, dialogs.rs, keys.rs, notifications_panel.rs, region_select.rs, stats_bar.rs, surface.rs, traffic_panel.rs, usb_panel.rs, webdav_panel.rs.
    • Reducing eframe::App::ui to the sequence of calls that drives them, with the draw order stated in a comment where it is load-bearing.
    • The &mut self resize callers maybe_send_monitors_resize and send_pending_guest_size, plus the viewport-fit block at the top of ui, which join the pure helpers phase 2 already moved to app/resize.rs (survey finding 7).
    • The eight tests in app/mod.rs that belong to moved code, moved verbatim with it.
    • ARCHITECTURE.md's ryll/src/ tree, app/mod.rs's file-header comment, and one line in AGENTS.md for the visibility rule a nested module introduces (decision 3).

    Out:

    • logic, on_exit and the impl eframe::App for RyllApp block itself, which stay in app/mod.rs (decision 2). logic is 156 lines but under 100 once comments are discounted, so phase 6's lint will not flag it and this phase does not touch it (survey finding 8).
    • RyllApp::new (243 lines by clippy's count) and connection.rs's reconnect (154). They are the only two functions in app/ that phase 6's lint will flag once ui is gone; new is phase 5's field regrouping and reconnect is phase 6's own problem (survey finding 9).
    • Enabling clippy::too_many_lines. This phase runs it by hand as a done-criterion; phase 6 wires it into make lint.
    • clipboard, trigger_paste, push_notification, push_connection_event, handle_cadence and window_focused, which stay in app/mod.rs (decision 8).
    • Any behaviour change. Panels keep reaching into self exactly as they do today; grouping those fields is phase 5.

    What the survey found¶

    Surveyed against develop at 32d8b22, after #714 (phase 3) and

    717 (its review follow-ups) merged. ryll/src/app/mod.rs is 3,230¶

    lines, of which ui is 1,691 (lines 1241-2931).

    1. The master plan's file list does not cover ui. Its nine files account for about 1,100 of the 1,691 lines. The central panel -- the surface itself, 149 lines at 2364-2512 -- has no file in the list, and neither does the viewport-fit block at the top. The full inventory, with the destination this phase gives each block:

    Four items outside ui move with their blocks: handle_input (928-962), release_guest_keys (963-974) and keep_keyboard_for_guest (1055-1063) to keys.rs; send_pending_guest_size (994-999) and maybe_send_monitors_resize (1000-1040) to resize.rs; default_arrow_cursor (2935-2985) to cursor.rs; and TRAFFIC_VIEWER_MAX_ENTRIES / TRAFFIC_VIEWER_REFRESH_MS (83, 86) to traffic_panel.rs. Phase 3's scope section already promised the last two and default_arrow_cursor to this phase, and all three are referenced only from app/mod.rs, so nothing else has to change to move them. The master plan's phase 4 section has been corrected to name surface.rs and to stop implying the list is complete.

    1. "each a fn draw_*(&mut self, ui: &mut egui::Ui)" is wrong for half of them. egui 0.35 unified the panel types and made Panel::show take &mut Ui, but Window::show still takes &Context. Six blocks need the root &mut Ui: the status bar (Panel::bottom(…).show_collapsible(ui, …), 1444), the traffic, notifications, USB and WebDAV side panels (Panel::right(…).show(ui, …) at 1767, 1859, 2070, 2284) and the central panel (2370). The four windows -- bug report, paste error, protocol gaps, reconnect modal -- take ctx and never touch the root ui, and neither do the hotkeys, the region overlay, the cursor overlay or the viewport fit, which work through ctx.input, ctx.output_mut and ctx.layer_painter. The master plan's section has been corrected. Both signatures are safe to pass together: ctx is a borrow of the ctx_owned clone made at 1249, not of ui, which is why that clone exists.

    2. Nesting needs a visibility form phases 2 and 3 never used. The twelve existing children of app/ are siblings of mod.rs, so pub(super) makes an item visible to app and therefore to every sibling. From app::ui::stats_bar, pub(super) means visible in app::ui only -- not in app, where ui itself lives and does the calling. The form that works is pub(in crate::app), which grants exactly the scope pub(super) grants a direct child: module app and all its descendants. A probe compiled in the ryll-dev container confirms all three cases this phase needs -- a grandchild's inherent method called from app, the same method called from a sibling of ui (app::screenshots), and a grandchild calling a private method of app -- and is recorded in decision 3.

    3. Only two locals escape their block. pointer_on_surface and open_channel_bug_report are declared at 2365-2366, written inside the central panel, and read afterwards at 2509 and 2926. Every other local in ui -- is_maximized, show_stats, stats_frame, streaming_state, panel_frame, dialog_held, paste_triggered, modifiers, dialog_action, paste_dialog_action, wants_reconnect -- is read only inside the block that declares it, so every other extraction is a pure move of a { … } body.

    4. The status bar cannot move as one function. 1392-1764 is one ui.horizontal closure (1445) whose right-hand group is a nested with_layout(right_to_left, …) (1536). At 373 lines it would be the largest function in app/ the moment it landed, so it splits along the boundaries the code already has: metrics 1446-1535, volume 1537-1551, streaming indicator 1552-1636, agent indicator 1637-1645, bandwidth sparkline 1646-1679, bell 1680-1707, and the ☰ menu of panel toggles 1708-1763. The streaming_state classification at 1405-1434 is logic, not drawing: it can push a notification, and the comment at 1401-1404 records that it must run before the bell draws so the bell sees it on the same frame. It becomes a method called at the top of the status bar's draw, which keeps that ordering by construction.

    5. The cursor code is in two pieces, separated in the draw order. The texture setup and overlay are 2771-2836; hiding the host cursor is 2922-2928, after the protocol gaps window and the reconnect modal. cursor.rs therefore gets two entry points called at their present positions, not one.

    6. Phase 2 moved the resize helpers but left their callers. app/resize.rs holds six free functions (compute_auto_resize, compute_outgoing_resize, resolution_notification_due, send_guest_size, auto_fit_size_acceptable, is_primary_surface) and twelve tests, but the &mut self methods that call them -- maybe_send_monitors_resize, send_pending_guest_size -- and the viewport-fit block in ui stayed in mod.rs. Finishing that seam costs 74 lines and no new file.

    7. logic does not need this phase. It is 156 lines at 1085-1240, but the inline work in it is three short blocks (ticket-expiry warning, auto-reconnect tick, resolution notification) and the rest is comments and delegation. Counted the way clippy::too_many_lines counts -- non-blank, non-comment body lines -- it is under 100 and the lint will not flag it. An earlier verbal estimate in this session said phase 4 should cover logic as well as ui; measurement says otherwise.

    8. Phase 6's baseline, measured with the lint itself. Running cargo clippy --frozen -p ryll --features gui,digest-decode -- -W clippy::too_many_lines in the devcontainer reports three functions under ryll/src/app/: ui (1,389/100), RyllApp::new (243/100) and connection.rs's reconnect (154/100). After this phase the first is gone and nothing new exceeds 100, which leaves phase 6 two call sites in app/ to decide about rather than three -- plus six elsewhere in ryll (bugreport.rs twice, capture.rs, web/signalling.rs and main.rs twice) and twenty-five in the sibling crates, which is phase 6's scoping problem and not this phase's.

    9. Eight tests in mod.rs, five of which move. The three cursor tests and their surface_contains_pointer helper (3063-3131) go to cursor.rs; the two status-button tests with key_press and status_button_clicks (3132-3206) go to keys.rs, which is where keep_keyboard_for_guest -- the function they exercise -- is going. Note that surface_contains_pointer is a replica of the containment test, written inside the test module: those three tests pin egui's behaviour, not this crate's, which is worth knowing before treating them as coverage of cursor.rs. The two logic tests and volume_control_round_trip stay (decision 9).

    10. One method needs the cross-subtree form. release_guest_keys is called from app::screenshots (screenshots.rs) as well as from the hotkey block, so once it is in app::ui::keys it is the one moved item whose caller is neither app nor a descendant of app::ui. pub(in crate::app) covers it; the probe in finding 3 includes exactly this case.

    11. The tree does not currently pass its own lint, for reasons that predate this phase. make lint fails on develop under rustc/clippy 1.100.0 (2026-11-09) with needless_range_loop in shakenfist-spice-usbredir/src/messages.rs, and the CI Lint lane has failed on every pull request since the devcontainer image picked that toolchain up -- the last green run is #717's merge-queue run. The code is unchanged since the crate was extracted; clippy is what moved. It is nothing to do with app.rs, so this phase does not fix it: filed as ryll#722 with the one-line fix. It does gate the phase's pull request, because that pull request cannot go green until #722 lands, and it gates pre-commit run --all-files locally for anyone with a current image.

    Nothing else the master plan's phase 4 section claims turned out to be wrong: the nine file names it gives are all sound as far as they go, the draw-order constraint it names is real and already commented at 1392, and the panels do all still reach into self the way it says.

    Decisions¶

    1. app/ui/ as a nested directory, not flat app/ui_*.rs files. The master plan said app/ui/ and the alternative has got worse since: flat would put 23 files in one directory and would shelve ten ui_*.rs draw files next to ui_state.rs, which is state, not drawing. The cost is decision 3.

    2. ui stays in app/mod.rs; the impl eframe::App for RyllApp block is not moved. A trait impl cannot be split across files, so moving ui's new body into app/ui/mod.rs would drag logic and on_exit with it -- 180 lines of per-frame logic into a module called ui, and window_focused and two tests after them. Keeping the block whole has a price: because ui lives in app and the draw methods live in app::ui::*, pub(super) is not enough for them. That is decision 3, and it is the cheaper of the two prices.

    3. Every method ui calls across the boundary is pub(in crate::app), and nothing is wider. The master plan's decision 7 says "pub(super) and nothing wider"; this is the same scope with a different spelling -- module app and its descendants -- so it honours that decision rather than relaxing it. pub(in super::super) is also legal and was rejected as harder to read. No pub(crate) and no bare pub is added anywhere in app/ui/. Verified by probe before planning:

    mod app {
    pub struct RyllApp { n: u32 }
    mod screenshots {
        pub(super) fn save(a: &mut super::RyllApp) { a.release_guest_keys(); }
    }
    mod ui {
        mod keys {
            impl crate::app::RyllApp {
                pub(in crate::app) fn release_guest_keys(&mut self) { self.n += 10; }
            }
        }
    }
}

    compiles and runs, as does the grandchild calling a private method of app. Children import what they need explicitly -- use crate::app::RyllApp; and so on -- matching phase 2's convention; no file-scope use super::*; glob is introduced, because the workspace has none.

    1. The central panel returns what escapes it; it does not grow two RyllApp fields. draw_surface returns a small SurfaceOutcome { pointer_on_surface: bool, open_channel_bug_report: bool } declared in surface.rs. Adding fields would push against phase 5, whose whole job is to shrink the struct, and would turn two frame-scoped flags into state with a lifetime longer than the frame.

    2. The status bar splits into seven draws plus a classification method along the boundaries in survey finding 5. This is the one step that is not a block move, and the one where the diff will not read as a pure relocation: the bodies are unchanged but their indentation and their closure nesting are not.

    3. Draw order is the contract. The call sequence in ui after this phase is, exactly: keyboard-focus gate, viewport fit, hotkeys, traffic refresh, status bar, traffic panel, notifications panel, USB panel, WebDAV panel, surface, bug report window, paste error window, region select, cursor overlay, protocol gaps window, reconnect modal, hide host cursor, observe_ui_state. Note the first two: the keyboard focus gate sits before the viewport fit today and the hotkeys after it, which is why keys.rs keeps two entry points instead of one (step 4f). The comment in ui says why the status bar must precede the central panel (egui reserves panel space in draw order) and that the window order is z-order. No step may reorder these, including the two steps that would read more naturally grouped -- the four windows are not adjacent and dialogs.rs's four methods are called at four separate points.

    4. The resize callers go to app/resize.rs, not under ui/. They are the missing half of a seam phase 2 opened, and the viewport fit is not drawing: it reads the viewport and sends a display size. resize.rs reaches 526 lines, within the 800-line ceiling the phase keeps.

    5. keys.rs takes the input subsystem, not just the hotkeys. The master plan scoped it to "the global hotkey handling at the top of ui", which is 89 lines that call straight into handle_input, release_guest_keys and keep_keyboard_for_guest -- and the two tests that exist for any of this exercise the last of those. Splitting them across two files would leave the tests pointing at a different module from the code. clipboard and trigger_paste stay in mod.rs: they are clipboard plumbing that the Ctrl+Alt+V arm happens to call, and a descendant can call an ancestor's private method unchanged.

    6. volume_control_round_trip stays in mod.rs. It pins VolumeControl's get/set contract because RyllApp::reconnect must not reset the user's slider. The slider is in the status bar, but the behaviour it guards is in connection.rs, so neither stats_bar.rs nor a move makes it more findable than leaving it where the author put it.

    7. One commit per step, each one compiling. Every step removes its block from ui and inserts the call in the same commit, so the tree builds at each one and the move check can run against HEAD~1. No step leaves a method defined but uncalled.

    Risks and mitigations¶

    1. A reordered draw changes what the user sees, and no test notices. Panel space reservation and window z-order are both positional, and this repository has no test that renders a frame. Mitigation: decision 6 writes the order down in the plan; the reviewer diffs the final call order in ui against the block order in git show develop:ryll/src/app/mod.rs before the last commit; and the move check proves no line inside a block moved relative to its neighbours. Residual risk is real but small, and it is the one thing in this phase worth a manual run against the desktop test guest -- see the back brief.

    2. Extracting a closure body hits the borrow checker. The bodies run inside ui.horizontal(|ui| …) and Panel::show(ui, |ui| …) closures that capture &mut self while ui is separately borrowed. Calling self.draw_x(ui) from inside such a closure is fine -- self and the closure's ui are disjoint -- but a sub-method that needs both the closure's ui and the outer ctx must take ctx as a parameter rather than reach for ui.ctx(), which borrows ui. That is why line 1249 clones the context, and the comment explaining it stays. Mitigation: the compiler, and the step briefs say which parameters each method takes.

    3. The move check is weaker here than in phase 3. Reindentation changes every moved line, and steps 4b and 4c add function headers and a struct. Mitigation: the check strips leading whitespace before comparing, and the definition of done enumerates what the diff may report. For 4b and 4c the reviewer additionally compares the token multiset of the whole diff, as #714's review did, rather than relying on the line check alone.

    4. Moving an item silently breaks a rustdoc intra-doc link. Phase 3 broke three and no lint caught them until cargo doc was run by hand; #717 added the rustdoc lane to make lint for exactly this. Mitigation: make lint now fails on rustdoc::broken_intra_doc_links, and step 4f's brief names it.

    5. app/ui/ is not covered by the gui feature lane. It would be invisible to CI if the gate were wrong. Mitigation: mod ui; sits inside mod app, which main.rs gates on gui, so the files inherit it and need no attribute of their own; and make lint's -p ryll --features gui,digest-decode lane (added in phase 3) compiles them with warnings denied.

    6. A sub-agent "tidies" a body while moving it. Mitigation: the briefs say verbatim, the move check is run per step, and the management session reads each diff rather than the report.
