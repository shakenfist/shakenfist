    RDP frontend phase 4: clipboard and audio¶

    Master plan: PLAN-rdp-frontend.md.

    Planning effort: medium, as the master plan's guidance asks for phases 3 to 6: both features follow patterns phases 1 to 3 set (a renderer-side relay, a session handle, an IronRDP factory registered in build_server). Review steps 1 and 2 at high effort all the same: the survey found that IronRDP drops the whole RDP connection when either channel is sent a message in the wrong state, so a sequencing mistake there disconnects the user rather than merely losing a paste.

    Prompt¶

    Read the master plan's Prompt first; everything there applies. For this phase in particular:

    • The RDP side is still IronRDP 0.13.0: ironrdp-server 0.13.0, ironrdp-cliprdr 0.7.0, ironrdp-rdpsnd 0.9.0, ironrdp-acceptor 0.10.0, all already in Cargo.lock. make fetch puts their source under .cargo-cache/registry/src/index.crates.io-*/ in the worktree, and every IronRDP file and line cited below is relative to the crate directory there. Read it; never build or run anything from inside it.
    • The SPICE clipboard reference is spice-gtk at /srv/src-reference/spice/spice-gtk (src/spice-gtk-session.c for line endings). No FreeRDP or qemu-rdp source is available locally; claims about FreeRDP are checked in the manual test, not assumed.
    • The host's FreeRDP is 3.15.0 (xfreerdp3), built with WITH_OPUS=ON and WITH_DSP_FFMPEG=ON (xfreerdp3 /buildconfig), so it can decode Opus audio.
    • Builds run in Docker through the Makefile, never with a host toolchain.

    Scope¶

    In scope:

    • Text clipboard both ways between the RDP client's CLIPRDR channel (CF_UNICODETEXT) and the session's MemoryClipboard, which the renderer's main channel already ferries to and from the guest's vdagent.
    • Audio playback through the RDP client's RDPSND channel, from the renderer's device-free PlaybackOutput::Sink: Opus passed through unchanged when the client accepts Opus, decoded 48 kHz PCM when it does not.
    • --rdp always creating the session's MemoryClipboard (today only with --control-socket), shared by the RDP client and a control socket.
    • The loopback test extended to see clipboard text cross both ways and an audio wave arrive, decoded by IronRDP's own client-side channels.
    • A manual FreeRDP test against the desktop guest, recorded in Results.
    • Documentation of the user-visible changes.

    Out of scope:

    • Rich clipboard formats (images, HTML) and file copy (master plan Future work).
    • Microphone, audio volume and RDPSND Close/SetVolume (decision 10).
    • Resampling or re-encoding audio: a SPICE stream that is not 48 kHz stereo is not played (decision 7).
    • New command-line flags (decision 1).
    • Line-ending conversion inside the renderer for guests that announce CRLF, which is a gap in every mode, filed as #624 (decision 5).
    • mstsc: no Windows machine is available, as in phases 2 and 3.

    What the survey found¶

    Checked on 2026-10-25 against the tree at 2edb002 and the pinned IronRDP crates. The master plan's phase 4 section is short and broadly right; what follows is what it did not say, plus four corrections, which this planning commit makes at source (the master plan's Prompt, What ryll already gives us, gap 4, the IronRDP Channels bullet, open question 6 and the phase 4 section, and the index.md row).

    Ryll side¶

    1. The device-free audio path exists. Phase 1 replaced the tap with PlaybackOutput::Sink(Arc<dyn PlaybackSink>) (shakenfist-spice-renderer/src/playback_sink.rs:52-106). A sink gets on_start(PlaybackFormat), on_opus_packet before decode, on_decoded_pcm after it (always 48 kHz), on_pcm_samples for a raw-PCM server, and on_stop. It opens no device in any build. Correction: the master plan still names OpusPacketSink, which phase 1 renamed, and lists gap 4 as open.
    2. --rdp discards audio today. ryll/src/rdp.rs:42-48 defines DiscardPlayback, a sink that drops every packet, and :224 hands it to the session.
    3. --rdp makes a MemoryClipboard only with a control socket (ryll/src/rdp.rs:189-206), and gives the same one to the control socket's handles (:352-356). Without a socket the main channel gets no clipboard at all.
    4. MemoryClipboard (shakenfist-spice-renderer/src/clipboard.rs:53-160) is what an RDP backend needs: set_host_text for what the RDP client copied, text() to answer a paste request, and subscribe_guest_copies(), a watch that changes on every guest copy (with its length, not its text). The main channel polls it every 500 ms and grabs the guest's clipboard when the host text changes.
    5. The main channel passes clipboard text through unconverted. spice-gtk converts line endings when the guest announces VD_AGENT_CAP_GUEST_LINEEND_CRLF (spice-gtk-session.c:812, :1002); ryll defines the constants (shakenfist-spice-protocol/src/constants.rs:758-759) and reads neither. Filed as #624. The renderer's host-side text is therefore LF text, as on a Unix host.
    6. SessionHandles (shakenfist-spice-rdp/src/lib.rs:68-87) is built at eight sites: ryll/src/rdp.rs:241, tests/loopback.rs:194, and tests in input.rs (:524, :903), display.rs (:789, :1479), auth.rs (:177) and server.rs (:620, :775, :816). A new field touches every one.

    IronRDP side¶

    1. Both channels plug in as factories on the builder: with_cliprdr_factory(Option<Box<dyn CliprdrServerFactory>>) and with_sound_factory(Option<Box<dyn SoundServerFactory>>) (ironrdp-server src/builder.rs:175-183). Each factory gets the server's event sender once, from RdpServer::new (server.rs:522-527), and builds a fresh backend for every connection (attach_channels, server.rs:668-681). The backend talks back by sending ServerEvent::Clipboard(..) or ServerEvent::Rdpsnd(..) on that sender, which is the same unbounded sender RdpServerHandle::shutdown sends Quit on.
    2. ironrdp-server re-exports too little. It re-exports CliprdrServerFactory, RdpsndServerHandler, RdpsndServerMessage and SoundServerFactory (src/lib.rs:24, :40), but not CliprdrBackend, CliprdrBackendFactory, ClipboardMessage, the clipboard PDU types, AudioFormat, WaveFormat or NegotiatedFormat. The crate must depend on ironrdp-cliprdr 0.7 and ironrdp-rdpsnd 0.9 directly; both are already in Cargo.lock through ironrdp-server, so this adds edges, not crates (as phase 3 did for ironrdp-displaycontrol).
    3. A message sent in the wrong state drops the connection. dispatch_server_events (server.rs:1081-1165) applies each event with ?. RdpsndServer::wave fails until the client's formats have arrived and a format has been chosen (ironrdp-rdpsnd src/server.rs:184-189); CliprdrServer::initiate_paste and submit_format_data fail until the channel is Ready (ironrdp-cliprdr src/lib.rs:573-583, :773-776, :857-858). Any of those failures ends the RDP connection. initiate_copy never fails on the server side (:816-830).
    4. When each channel becomes usable. The server starts its static channels once, on the first activation (server.rs:1384-1394): rdpsnd sends its formats, cliprdr its capabilities and Monitor Ready. cliprdr turns Ready, and calls the backend's on_ready, when the client's first Format List arrives (lib.rs:665-670), which a client sends straight after its capabilities. rdpsnd calls the handler's choose_format and then start when the client's Training Confirm arrives (src/server.rs:319-363), and stop when the channel is dropped at the end of the connection (:386-390).
    5. The server chooses the audio format, not the client. choose_format is given the formats both sides support, in the server's preference order (src/server.rs:79-115, negotiate_formats :240-259); a client expresses preference only by leaving formats out of its reply. Formats match on tag, channels, rate, bit depth and the extra-data blob, ignoring the two derived fields (:271-277). Opus is defined as WaveFormat::OPUS (0x704F, src/pdu/mod.rs:198) with no encoder, as the master plan says. Correction: the master plan's open question 6 says "let the client pick".
    6. IronRDP keeps only the last four waves of a batch. dispatch_server_events drops the oldest waves when more than four are queued at once (server.rs:1083-1097). A burst of short waves after any stall (a large RemoteFX frame being written, a reactivation) loses audio.
    7. Events are not drained during a handshake. Between connections the accept loop reads the event channel and discards clipboard and sound events (server.rs:936-955); inside a connection the client loop dispatches them (:1300-1322). During a handshake nothing reads the channel, and it is unbounded. A backend that sends only after its channel has started sends nothing then.
    8. Reactivation keeps the channels but loses client PDUs. A deactivation-reactivation (every resize since phase 3) moves the static channels into the acceptor and back (server.rs:1739-1753), so channel state survives and start is not called again. While it runs, the acceptor drops any client PDU it does not expect (ironrdp-acceptor src/connection.rs:812-839), static channel PDUs included. Phase 3's two-second hold on the first resize (FIRST_RESIZE_GRACE) keeps the first reactivation clear of both channels' initial handshakes; a client copy made during a later reactivation would be lost.
    9. IronRDP's client side can drive both channels for the loopback test: ClientConnector::with_static_channel (ironrdp-connector src/connection.rs:155), the client Cliprdr in ironrdp-cliprdr, and Rdpsnd with an RdpsndClientHandler (ironrdp-rdpsnd src/client.rs:13-28, :58-75).

    Decisions¶

    1. No new flags; the library's opt-out is a None. Both factories are always registered, so every client is offered both channels. SessionHandles gains clipboard: Option<Arc<MemoryClipboard>> and audio: Option<Arc<AudioRelay>>; a session with None answers nothing on that channel (the clipboard backend ignores the client, the sound handler declines every format). ryll --rdp always fills both. Reasoning: in ryll the operator and the user are the same person, and every RDP client already has a switch for each (FreeRDP's -clipboard and /sound, mstsc's local resources tab), so a server flag would duplicate one the user already has. The None is the knob a Kerbside gateway needs to apply its firewall policy's permitted_channels per session. If an operator asks for a server-side switch, it is a two-line follow-up.
    2. One MemoryClipboard per session, shared. --rdp makes it unconditionally, gives it to the main channel, to SessionHandles.clipboard and, when there is one, to the control socket. Its two writers already keep host and guest text apart.
    3. The client's copies are fetched eagerly. When the client announces a Format List containing CF_UNICODETEXT, the backend asks for the text at once and stores it with set_host_text. The SPICE side of ryll has no delayed rendering for host text (ClipboardBackend::get_text is a synchronous read), so a lazy fetch would need renderer work for little gain. The cost is one transfer per client copy, which the GUI also pays by polling the host clipboard.
    4. On connect, the client's clipboard wins. A client sends its current clipboard as its first Format List, and decision 3 pushes it to the guest. Guest copies made before the client connected are not offered to it; guest copies made afterwards are, each as a Format List with CF_UNICODETEXT, and the text is read from MemoryClipboard::text() only when the client asks for it. This is what an RDP session to Windows does, and the reverse would overwrite the user's local clipboard every time they connect.
    5. Line endings are converted at the RDP boundary. CF_UNICODETEXT is Windows text (CRLF, NUL-terminated UTF-16LE); the renderer's host-side text is LF (survey 5). Text from the client has CRLF turned into LF; text to the client has every LF not already preceded by CR turned into CRLF. This matches what the GUI sends a guest from a Unix host. Converting for CRLF guests is the renderer's job, for every mode (#624).
    6. Never send a message the channel can refuse. From survey 9: the clipboard backend sends SendInitiatePaste and SendFormatData only after on_ready, and the sound handler sends a wave only between start and stop. Anything that would break the rule is dropped with a debug! rather than sent. This is the rule the review checks first, and the unit tests pin it.
    7. Audio formats: Opus first, then PCM, both 48 kHz stereo. The handler advertises Opus (0x704F, 2 channels, 48000 Hz) and then PCM (WAVE_FORMAT_PCM, 2 channels, 48000 Hz, 16 bit), and choose_format takes the first common one. Opus costs nothing to pass through and is a few tens of kbit/s; PCM is 1.5 Mbit/s, which matters on the constrained networks this mode exists for. Only 48 kHz stereo is offered because decoded Opus is 48 kHz and nothing in ryll resamples. A SPICE stream that does not fit the chosen format (a raw-PCM server at another rate or channel count, or raw PCM when the client chose Opus) is not played, with a warn_once!. Spice-server and QEMU send 48 kHz stereo Opus, so this is the rare case.
    8. Audio reaches the RDP thread through a relay on the session. A new AudioRelay in shakenfist-spice-rdp implements PlaybackSink and publishes on a small tokio::sync::broadcast channel; it also keeps the stream's current PlaybackFormat, so a client that connects mid-stream knows it. ryll passes the same Arc<AudioRelay> as the session's PlaybackOutput::Sink and as SessionHandles.audio. The sound handler, on start, takes the session from the slot, subscribes, and spawns a forwarder task on the server thread that turns relay items into waves; stop aborts it. Subscribing at start means no stale audio is ever queued and nothing is sent before the channel can take it (decision 6); the broadcast's lag drops old audio rather than growing. The relay lives in the RDP crate, beside spawn_cursor_relay, so a gateway gets it with the crate. The rejected alternative, a sink holding the connection's sender directly, is simpler but ties the session to a connection and bypasses the session seam.
    9. One Opus packet per wave; PCM in 20 ms waves. FreeRDP decodes one Opus packet per wave, so packets are not merged. Decoded PCM is gathered into waves of at least 960 frames (20 ms) before sending, and flushed on on_stop, because spice-server also sends 256-sample packets, and survey 12 means four 5 ms waves are all the slack a stall gets.
    10. No Close and no SetVolume. A SPICE stop sends nothing; the client stops hearing waves. SetVolume fails unless the client set the volume flag, and that failure would drop the connection (survey 9), for a feature SPICE does not give ryll anyway (PLAYBACK_VOLUME is not advertised).
    11. Wave timestamps count milliseconds of audio sent since the forwarder started, wrapping at u32::MAX, derived from sample counts rather than the wall clock.

    Risks and mitigations¶

    • A channel message in the wrong state drops the client (survey 9). Mitigation: decision 6 makes the gate structural; briefs 1 and 2 test each "nothing before ready/start" case and mutation-check the gates; the loopback test keeps the connection alive across both channels; the management session reviews every send site in steps 1 and 2 against survey 9 before committing.
    • Static-channel PDUs lost in a reactivation leave a connection's clipboard stuck before Ready, or its audio never negotiated (survey 14). Mitigation: phase 3's first-resize hold covers the initial handshakes; step 4 checks both channels after a resize; a later loss is recoverable for the clipboard (the next client copy turns the channel Ready) and is recorded rather than fixed for audio.
    • Audio drops under display load, because IronRDP keeps only four waves of a batch (survey 12). Mitigation: 20 ms PCM waves (decision 9); step 4 listens during the video workload and records what happens. If Opus's short packets drop audibly, the follow-up is to prefer PCM or to merge packets, and it is recorded in Future work, not fixed in this phase.
    • FreeRDP does not echo the Opus format byte for byte, so Opus is never common and PCM is used. Mitigation: step 4 records the chosen format; PCM still plays; a mismatch is recorded with what FreeRDP sent.
    • Large clipboard text. Neither direction is capped beyond what MemoryClipboard and IronRDP already allow. Mitigation: none in this phase; step 4 notes any problem with a large paste, and a cap goes to Future work if needed.
    • Clipboard content in logs. Mitigation: brief 1 logs byte counts only, as the main channel does; the management session greps the diff for logged text.
    • Conflicts with phase 5, which has not started and edits the same files. Mitigation: whichever merges second rebases.
