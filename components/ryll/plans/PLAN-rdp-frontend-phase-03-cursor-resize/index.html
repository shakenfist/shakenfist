    RDP frontend phase 3: cursor and resize¶

    Master plan: PLAN-rdp-frontend.md.

    Planning effort: high, as the master plan's guidance asks for a phase that turns on protocol details (RDP pointer wire formats, IronRDP's capability exchange and reactivation) and a correctness question (a desktop size negotiated before the display handler can serve it). Review at high effort: step 3 changes when the client is told which desktop size, and a mismatch there drops the connection.

    Prompt¶

    Read the master plan's Prompt first; everything there applies. For this phase in particular:

    • The RDP side is still IronRDP 0.13.0 (ironrdp-server 0.13.0, ironrdp-pdu 0.9.0, ironrdp-acceptor 0.10.0, ironrdp-displaycontrol 0.8.0, ironrdp-graphics 0.9.0). make fetch puts their source under .cargo-cache/registry/src/index.crates.io-*/ in the worktree, and every IronRDP file and line cited below is relative to the crate directory there. Read it; never build or run anything from inside it.
    • The SPICE reference is spice-gtk at /srv/src-reference/spice/spice-gtk (commit 112f480, 2026-10-20). src/channel-cursor.c set_cursor (:340-480) and src/spice-util.c spice_mono_edge_highlight are the reference for every cursor format this phase decodes.
    • Phase 5 (lifecycle and the rdp-smoke lane) is planned and run in parallel by another session. Both phases touch shakenfist-spice-rdp/src/{lib,display,server}.rs and the master plan's Execution table; whichever merges second rebases, and neither closes out the other.
    • Builds run in Docker through the Makefile, never with a host toolchain.

    Scope¶

    In scope:

    • Renderer: decode SPICE MONO, COLOR4 and COLOR16 cursors, and honour the AND mask that follows COLOR32 pixels, as spice-gtk does. Every mode benefits.
    • RDP cursor shapes: the session's current cursor shape reaches the RDP client as DisplayUpdate::RGBAPointer, scaled down to fit 96x96 when larger; SPICE hide becomes HidePointer, and show resends the shape.
    • RDP resize: the client's desktop size from its Client Core Data, and later display-control monitor layouts, become DisplaySize::Requested on the session's resize channel, aligned as the GUI aligns them. The guest's answer already becomes DisplayUpdate::Resize (phase 2).
    • The loopback test extended to see a pointer update decoded by IronRDP's own client, and a Core Data size reach the resize channel.
    • A manual FreeRDP test against the desktop guest, recorded in Results.
    • Documentation of the user-visible changes.

    Out of scope:

    • PointerPosition (the master plan leaves it out on qemu-rdp's experience; the manual test records server mouse mode's behaviour so a later phase can decide).
    • LargePointer (IronRDP 0.13.0 never sends it; see the survey) and the pointer cache (CachedPointer): every shape goes out with cache index 0.
    • COLOR8 cursors, which spice-gtk does not decode either.
    • Multi-monitor layouts: only the primary monitor of a layout is used (master plan Future work).
    • Headless cursor tracking (docs/multi-mode-parity.md marks it missing; unchanged).
    • The two input items phase 2 deferred (Future work there).

    What the survey found¶

    The master plan's phase 3 section was written before phase 2 ran. Checked against the tree and IronRDP 0.13.0 on 2026-10-22; corrections are made at the source (the master plan's gap 6 and phase 3 section, and the index.md row) in the planning commit, so later steps need not redo them.

    1. The renderer refuses more than gap 6 says. decode_cursor_pixels (shakenfist-spice-renderer/src/channels/cursor.rs:537-548) decodes only ALPHA, COLOR24 and COLOR32; MONO, COLOR4, COLOR8 and COLOR16 log cursor: unsupported cursor type and emit nothing, so every mode keeps whatever shape it had. Gap 6 names only mono and 4-bit. The test test_unsupported_cursor_types_return_none asserts the refusal of all four and must change.
    2. COLOR32 ignores its AND mask. spice-gtk reads a 1-bit mask after the pixels for COLOR32, COLOR16 and COLOR4 (channel-cursor.c:360-460): a set bit makes the pixel transparent, or, where the colour is white, an inverting pixel that RGBA cannot express and spice-gtk approximates with a checker (get_pix_hack, :329-332). Ryll treats COLOR32's fourth byte as padding and makes every pixel opaque (cursor.rs:541, :572-578), so a COLOR32 cursor shows its transparent area as an opaque block. Not in the master plan; fixed here because it is the same mask code. spice-gtk indexes the colour formats' mask by pixel number with no per-row padding (get_pix_mask, :324-327), while the mono masks have a row stride of (width + 7) / 8 (mono_cursor, :308-322); the two agree only for widths that are multiples of 8.
    3. No shared cursor state exists. SurfaceMirror ignores cursor events (surface_mirror.rs:269-272); the GUI reads its own channel (ryll/src/app/mod.rs:1770-1783) and --web subscribes a relay to the event bus (ryll/src/web/cursor.rs:70, subscribed at ryll/src/main.rs:754). ryll/src/rdp.rs creates the bus (:213) and subscribes nothing for cursors, and SessionHandles (shakenfist-spice-rdp/src/lib.rs:64-78) has no cursor field. A decoded shape is ChannelEvent::CursorShape(CursorImage) with top-down, straight-alpha RGBA pixels (channels/mod.rs:566-574); hide and show are ChannelEvent::CursorPosition { visible }, sent on every move as well (cursor.rs:253-278).
    4. IronRDP's RGBAPointer is a 32 bpp TS_POINTERATTRIBUTE, not RGBA. rgba_pointer (ironrdp-server-0.13.0/src/encoder/mod.rs:185-205) sends data unchanged as the XOR mask with xor_bpp: 32 and an empty AND mask. IronRDP's own client decoder reads it as bottom-up rows (ironrdp-graphics-0.9.0/src/pointer.rs:194, :220-224) of B, G, R, A with straight alpha (:401-404). So the RDP adapter must flip rows and swap red and blue.
    5. An oversized pointer drops the client. The only size check is the wire format's: each mask at most u16::MAX bytes with an even scanline length (ironrdp-pdu-0.9.0/src/basic_output/pointer/mod.rs:70-109), so 32 bpp tops out near 127x127. A larger one fails to encode, and the error aborts the client loop (ironrdp-server-0.13.0/src/server.rs:1060). The server does not advertise the Large Pointer capability set (capabilities.rs:5-17) and never sends LargePointer, so by MS-RDPBCGR the client expects at most 96x96. The master plan's "larger than 96x96 needs LargePointer or scaling" leaves only scaling on 0.13.0, and it is mandatory.
    6. request_initial_size does not see the client's size by default. It is called from the capability loop only when the client's Bitmap capability set has desktop_resize_flag (server.rs:1407-1417), with the size from the client's Confirm Active, which echoes the server's own Demand Active size (MS-RDPBCGR 2.2.1.13.2; builder.rs:239-243). The size the client wants is only in its Client Core Data, which the acceptor reads when the builder sets with_honor_client_desktop_size(true) (builder.rs:236-263; ironrdp-acceptor-0.10.0/src/connection.rs:516-541, range 200..=8192). The master plan's "the client's initial desktop size via request_initial_size" needs that flag. The encoder is still built from size() (server.rs:1482), so the display handler must reconcile the two.
    7. request_initial_size runs again on every reactivation (server.rs:1739-1749 rebuilds the acceptor and reruns client_accepted), with the client's echo of the size it was last told. Forwarding that to the guest would replace the size the client asked for with the guest's old size.
    8. Display control needs no opt-in. The DVC is attached in attach_channels (server.rs:683-688) with caps of one monitor; request_layout receives a DisplayControlMonitorLayout (ironrdp-displaycontrol-0.8.0/src/pdu/mod.rs:213) whose entries have is_primary() and dimensions(). A layout outside 200..=8192 or with an odd width fails to decode and never arrives (:367-379). It is called on spawn_blocking with the display mutex held (server.rs:352-356), so it must not await.
    9. Phase 2's adapter already reconciles one mismatch. ClientSize (shakenfist-spice-rdp/src/display.rs:44-91) records the size the client was told; MirrorUpdates starts from it and makes its first update a resize when the surface differs (display.rs:225-234). Honouring the Core Data size is the same situation, provided ClientSize records the negotiated size rather than the one size() reported before the handshake.
    10. Resize alignment differs by mode. The GUI and the control socket round down to a multiple of 8, minimum 8 (align_monitor_dimension, shakenfist-spice-renderer/src/channels/main_channel.rs:135-137); --web rounds to even (ryll/src/web/inputs.rs:238-258). The main channel debounces requests for 200 ms and holds one made before the agent connects (main_channel.rs:1360-1460).
    11. The loopback test turns pointers off (enable_server_pointer: false, tests/loopback.rs:206-209) and sets a client desktop size (:173) that the server currently ignores.

    The master plan's other claims for this phase hold: hide maps to HidePointer, layouts arrive through request_layout, and a guest-driven size change is already DisplayUpdate::Resize.

    Decisions¶

    1. Decode as spice-gtk does, inverting pixels included. MONO through spice_mono_edge_highlight; COLOR4 with its 16-entry palette; COLOR16 as 15-bit RGB; COLOR32 with its mask. Where the mask marks a white pixel as inverting, use spice-gtk's checker approximation, since CursorImage is RGBA and no frontend can draw XOR. Matching spice-gtk pixel for pixel means a cursor looks the same in ryll as in remote-viewer, which is the comparison users make. COLOR8 stays refused. The mask row stride follows spice-gtk exactly (no padding for colour formats); the step's tests use widths that are and are not multiples of 8 so the choice is pinned.
    2. Cursor state reaches the RDP crate as a watch channel on SessionHandles. A new cursor: watch::Receiver<CursorState> field, where CursorState holds the latest shape (if any) and whether it is visible. A relay in shakenfist-spice-rdp (pub fn spawn_cursor_relay(broadcast::Receiver<ChannelEvent>)) turns the event bus into it, changing the watch only when the shape or visibility changes, not on every move. It lives in the RDP crate rather than in ryll so that Kerbside, which builds its own SessionHandles, gets it too. A watch coalesces: a client that is behind gets the latest shape, never a backlog. A lagged broadcast receiver logs once and carries on; the next shape corrects it.
    3. Pointer updates ride the display update stream. IronRDP has no other path. MirrorUpdates checks the watch on each poll and queues the pointer update ahead of that poll's bitmaps. A new stream (every connection and every reactivation) sends the current shape first, or HidePointer if hidden, because a reactivated client starts from its default pointer.
    4. Scale large cursors down to fit 96x96, keeping the aspect ratio, nearest-neighbour, with the hotspot scaled the same way and clamped inside the image. 96x96 rather than the wire format's ~127x127 because the server does not advertise Large Pointer support, so a conforming client may refuse anything bigger. Rows are flipped to bottom-up and red and blue swapped; straight alpha is kept; the scanline (width * 4) is always even. Cache index 0 every time.
    5. Honour the client's Core Data size with with_honor_client_desktop_size(true), and make MirrorDisplay::request_initial_size do three things: record the negotiated size in ClientSize (so the stream's first update is a resize to the surface's size whenever they differ, which is phase 2's existing path), send DisplaySize::Requested for it, aligned, on the session's resize channel, and return it. This is the decision most likely to be argued with. Without an agent in the guest it costs one extra deactivation-reactivation per connection (client size, then the guest's size) compared with leaving the flag off. The alternative, never learning the client's size until it sends a display-control layout, means a fullscreen client gets the guest's size and keeps it unless the client happens to send a layout, which mstsc and FreeRDP do not promise to do at connect. A reactivation at connect is cheap; a session stuck at the wrong size is the visible failure resize exists to fix.
    6. Only the first request_initial_size of a connection asks the guest. Later calls are reactivation echoes (survey item 7) and only update ClientSize. The first call is told apart by a per-connection flag reset where ClientSize is forgotten (on accept, server.rs:510).
    7. Layouts use the primary monitor, or the first entry when none is flagged primary (decoding does not insist on one), aligned the same way, sent with try_send because the callback cannot await. A full resize channel drops the request and logs once; the next layout supersedes it anyway.
    8. Align as the GUI does: align_monitor_dimension, a multiple of 8, which also satisfies RDP's even-width rule. The guest may then be up to 7 pixels narrower or shorter than the client window; the client shows the server's size, which is what it does today.
    9. A client without desktop_resize_flag is not handled specially. IronRDP's acceptor adopts the Core Data size whatever the flag says, but then never calls request_initial_size, so ClientSize keeps the guest's size and the stream sends nothing to correct the client. Such a client cannot follow a resize anyway; every client in the master plan's list sets the flag. Recorded under Risks.
    10. Hold a connection's first resize for two seconds (added after step 5; Mikal's choice). A reactivation during the dynamic-channel handshake strands those channels for the whole connection, and IronRDP gives no signal that the handshake has finished. So for FIRST_RESIZE_GRACE after accept the update stream holds a resize for a size mismatch, and the bitmaps that would not fit, while still sending pointer updates; if the guest adopts the size the client was told meanwhile, no resize is needed at all. The rejected alternative was serving the guest clipped into the client's size with no initial resize: more invasive, and a client without an agent would keep a wrong-size desktop.

    Risks and mitigations¶

    • The negotiated size and the encoder disagree and the client drops. Honouring Core Data makes the client's desktop the client's size while the encoder is built from the surface's. Mitigation: ClientSize records the negotiated size so the first update is the resize (brief 3's "no bitmap before the resize" test), the loopback test runs the whole sequence with IronRDP's client (brief 4), and the management session runs FreeRDP at a size different from the guest's (step 5).
    • A client without desktop_resize_flag is told its own size and sent the surface's bitmaps (decision 9). Mitigation: none in code; the manual test notes the flag FreeRDP sends, and if a tested client lacks it, step 3 is revisited before the PR.
    • Pointer bytes in the wrong order show a garbled or upside-down cursor that unit tests restating the encoder would not catch. Mitigation: brief 4 asserts on IronRDP's client-side decode, and step 5 checks the cursor visually.
    • Mono cursors are untested against a real guest. The desktop guest (XFCE) sends alpha cursors. Mitigation: unit tests against spice-gtk's algorithm; step 5 records which formats the guest sent (the renderer's debug log), and a Windows guest test is recorded as not done if none is available.
    • Reactivation drops the display-control channel and later layouts never arrive. Mitigation: step 5 resizes the FreeRDP window after the first reactivation and checks the guest follows.
    • Conflicts with phase 5, which edits the same files. Mitigation: whichever merges second rebases; the conflict is in code both sessions understand, and neither phase closes out the other.
