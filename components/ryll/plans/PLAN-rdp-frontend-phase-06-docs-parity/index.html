    RDP frontend phase 6: documentation and parity¶

    Master plan: PLAN-rdp-frontend.md.

    Planning effort: medium, as the master plan's guidance sets for phases 3 to 6: this phase documents what phases 1 to 5 built and changes no code. Review step 3 (the parity column) at high effort, because a wrong cell there reads as a fact about the product.

    Prompt¶

    Read the master plan's Prompt first; everything there applies. For this phase in particular:

    • Describe the code, not the plans. Phases 1 to 5 recorded their designs in docs/plans/, and some of those plans were corrected as the work went; the code on develop is the authority. Every behavioural claim a step writes is checked against the source it describes, and the brief names the files.
    • The RDP side is IronRDP 0.13.0 (ironrdp-server 0.13.0). make fetch puts its source under .cargo-cache/registry/ in the worktree; read it there when a claim depends on it, and never build or run anything from inside it.
    • --rdp is a reachability fallback, not a better path. Every page that introduces it says so, in the words the crate README and docs/configuration.md already use.
    • Builds, where a step needs one, run in Docker through the Makefile, never with a host toolchain.
    • No plan, phase, decision or survey-item citations in code or in docs outside docs/plans/.

    Scope¶

    In scope:

    • docs/rdp-frontend.md, an operator guide matching docs/web-frontend.md where the two modes overlap.
    • docs/rdp-mode-internals.md, matching docs/web-mode-internals.md in purpose, much shorter in length.
    • An RDP column in docs/multi-mode-parity.md, every cell filled, and the page's "three modes" framing updated.
    • ARCHITECTURE.md (seven crates, four modes, the new crate's boundary), README.md (one usage example and one link), docs/index.md, docs/features.md.
    • Moving the behaviour prose out of docs/configuration.md's RDP Mode section into the guide, leaving the flag table.
    • The crate README's claim about which clients it serves.
    • The master plan: answers to open questions 5 and 8 as far as they can be given, phase 5's deferred items lifted into the master plan's Future work, and a record of the success criteria this phase can check.

    Out of scope:

    • Any code change. If a step finds a defect while checking a claim, it records it (file and line, what is wrong) and the management session files an issue; the doc describes the code as it is.
    • Turning the rdp feature on in release builds (open question 8). Phase 5 set the criterion, fourteen consecutive green nightly runs of the RDP smoke lane, and that record does not exist yet.
    • Kerbside's documentation. The survey found nothing there to change (item 9).
    • Testing new RDP clients, unless Mikal can supply one at the back brief (decision 6).

    What the survey found¶

    Checked against develop at 280c047.

    1. docs/rdp-frontend.md and docs/rdp-mode-internals.md do not exist. docs/configuration.md:76-129 holds the only user-facing description of the mode, and says "An operator guide is to come" (:82).
    2. docs/multi-mode-parity.md has no RDP column. It lists RDP as a mode (:26, "the column lands with the operator guide") but the matrix (:78 on) has three columns, GUI, Headless and Web, and about 120 rows, plus a Web frontend (--web mode) section of web-only rows. Its opening line (:3) says "three delivery modes".
    3. ARCHITECTURE.md does not mention RDP at all. It says the workspace has 6 crates (:24) and lists them without shakenfist-spice-rdp; the mode table (:52-56) and "All three modes ship" (:58) know three modes; the Where the detail lives table (:9-20) has no RDP row; Crate boundaries (:81-91) explains why shakenfist-spice-webrtc is separate but not the RDP crate, which is separate for the same reason and is also behind a default-off feature.
    4. README.md and docs/index.md do not mention --rdp. README.md:73 has a --web usage example and :88 a link to the web guide; docs/index.md's Documentation Index (:83) links the web guide only. docs/features.md:64 has a Web mode bullet and no RDP one.
    5. No released binary has --rdp. The rdp feature is default-off and make release leaves it out (AGENTS.md:236- 238, ryll/Cargo.toml:58-62). The latest release, v0.3.0 (2026-10-17), predates the shakenfist-spice-rdp crate, which is not on crates.io. An operator has to build from source today (make release-rdp, or cargo with --features rdp; docs/development.md:587 covers the developer side).
    6. Only FreeRDP has been tested. Every phase's Results tested FreeRDP 3.15.0 on Linux and recorded mstsc as not tested, for want of a Windows machine (PLAN-rdp-frontend-phase-02-rdp-skeleton.md:1105, phase 3 :614, phase 4 :567). The crate README (shakenfist-spice-rdp/README.md:4-6) says the crate serves "mstsc on Windows, FreeRDP, and the RDP apps on macOS, iOS and Android", which is a claim of reach no test backs. The master plan's first success criterion names mstsc.
    7. Open question 5 (Unicode key events) was implemented but never answered. shakenfist-spice-rdp/src/input.rs:411-417 drops UnicodePressed/UnicodeReleased with a warn-once, as the recommendation said, and a test covers it (:848). Open question 8 (packaging) waits on the smoke lane's record (item 5).
    8. Phase 5's deferred items live only in its phase plan. Its Future work lists SPICE reconnect for --web and --headless, a text overlay for the outage frame, the lane's promotion, reporting a red nightly, replaying a resize made during an outage, per-peer limits on the pre-authentication slot, and a cap on reconnects to a server that drops every session. None is in the master plan's Future work, which is what outlives the plan.
    9. Kerbside needs nothing. The master plan's last success criterion asks that Kerbside documentation mentioning RDP out point here. On Kerbside's develop, nothing outside docs/plans/ mentions RDP, and the superseded docs/plans/PLAN-rdp-gateway.md and its index row already link to this plan. The Framing item under Moving to Kerbside covers Kerbside's docs for when the code moves.
    10. What docs/configuration.md already gets right. Its RDP prose (:84-117) is accurate as of phase 5: cursor, resize, clipboard, audio, takeover and reconnect. It is in the wrong place for its length, not wrong; the guide takes it over (decision 3).

    The master plan's phase 6 section is accurate as far as it goes; this survey adds items 5 to 8. They are recorded in the master plan's phase 6 section in the planning commit.

    Decisions¶

    1. The operator guide follows docs/web-frontend.md's outline where the modes overlap, and leaves out what --rdp does not have. Sections: what it is and when to use it (the fallback framing first); quick start, starting with getting a binary that has the mode (item 5); clients (decision 6); what works and what is lost; credentials and security modes; certificates; one client at a time and reconnect, summarised with a link to docs/session-lifecycle.md rather than repeated; what it costs (the phase 2 measurements, as numbers with their date and build); running it as a service; troubleshooting; a security note; the CI smoke lane. No reverse-proxy section: RDP is not HTTP.
    2. A short internals page, not none. The master plan made it conditional ("if the internals warrant it"). They do: the per-connection IronRDP servers behind ryll's own accept loop, the takeover rules, the display handler's damage and outage paths, input back-pressure, and the reconnect supervisor's per-attempt channels are design that today lives only in phase plans, and ARCHITECTURE.md needs a page to point at. Aim for a few hundred lines, organised by module, each section naming the invariant a change must keep, not a narrative of how it was built.
    3. docs/configuration.md keeps the flags, the guide keeps the behaviour. The RDP Mode section becomes one paragraph (what the mode is, that it needs the rdp feature, a link to the guide) plus the flag table. The behaviour prose moves to the guide, so no fact about the mode is stated on two pages. The --rdp row's description is cut to match.
    4. The parity column states what an RDP client can reach. A cell reads available only when a stock RDP client can use the feature through --rdp; a feature ryll offers only to its own operator (a control socket verb, --capture) is judged as the Web column judges it, by what the mode wires up. "n/a — intrinsic" needs a reason in parentheses, as elsewhere. RDP-only features (security modes, takeover, outage frame, auto-reconnect) get an RDP frontend (--rdp mode) section beside the web one, with every column filled. Existing rows that describe reconnect behaviour (Reconnect / Lifecycle) are checked for the new mode, not just extended.
    5. README gets one example and one link, nothing more. README is a pitch: ryll --rdp --file connection.vv under Usage, with a line saying it needs a build with the rdp feature, and the guide under Documentation. No feature bullets.
    6. Clients: say what was tested, and nothing more. The guide lists FreeRDP 3.15.0 as tested, with the flags that matter (/cert:tofu, /dynamic-resolution, /sound, /sec:nla), and lists mstsc and the Microsoft Remote Desktop / Windows App clients as expected to work and untested. The crate README is reworded the same way.
