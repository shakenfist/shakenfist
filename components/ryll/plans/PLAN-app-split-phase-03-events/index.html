    Phase 3: Events, connection lifecycle and the bug-report flow¶

    Master plan: PLAN-app-split.md.

    Planning effort¶

    Planned at medium effort. Five of the seven steps are moves with no behaviour change, verified by the same move-check script phase 2 used. The two that are not -- turning the ChannelEvent match into a dispatcher, and replacing its wildcard arm -- carry the phase's only real risk, so the review effort belongs there rather than spread across the moves.

    Scope¶

    In:

    • ryll/src/app/connection.rs -- the connect/reconnect/disconnect lifecycle and the auto-snapshot task lifecycle.
    • ryll/src/app/events.rs -- process_events and the per-frame drain helpers that bracket it, then split into one handle_* method per arm group so the match becomes a dispatcher.
    • ryll/src/app/trigger_snapshot.rs -- the trigger snapshot, the eframe window shot, and the region-selection state machine.
    • ryll/src/app/bug_report.rs -- dialog open, submit, the pending report, the poll/write/flush path, and the disconnect snapshot.
    • ryll/src/app/screenshots.rs -- the manual screenshot save path (survey finding 5 claims it for this phase).
    • Replacing the ChannelEvent match's _ => {} arm with explicit arms (decision 5).
    • Correcting ARCHITECTURE.md's ryll/src/ tree, which is already stale (survey finding 6).

    Out:

    • Anything the eframe::App::ui body draws. Panels, dialogs and overlays are phase 4; this phase moves the state machines and flows those panels drive, not the drawing.
    • default_arrow_cursor and the TRAFFIC_VIEWER_* constants, which phase 4 takes with the cursor and traffic panels.
    • Grouping RyllApp's fields into sub-structs. Methods moved here keep reaching into self exactly as they do today; phase 5 changes that.
    • push_notification and push_connection_event, which stay in mod.rs (decision 4).
    • The two ChannelEvent variants the GUI ignores. Decision 5 makes the omission explicit and reviewable; it does not start handling them.

    What the survey found¶

    Surveyed against develop at f56b371, after #501 (phase 2) merged. ryll/src/app/mod.rs is 5,592 lines.

    1. Every item the master plan's phase 3 section names still exists, and none of them touches egui. reconnect, reconnect_manual, handle_critical_disconnect, handle_connection_failed, build_connection_runtime, process_events, begin_trigger_snapshot, PendingBugReport, generate_bug_report, finish_bug_report, poll_pending_bug_report, file_notification_bug_report, maybe_write_disconnect_snapshot and validate_region are all present. Across the whole phase-3 region there are exactly two egui:: mentions in live code, both in observe_ui_state (mod.rs:2359): its ctx: &egui::Context parameter and the egui::Popup::is_any_open(ctx) call beside it. The only others are an egui::Rect in a comment in reconnect. So these are clean moves, not a decoupling exercise.

    2. The master plan names an audio arm group that does not exist. ChannelEvent has thirty variants and not one of them is audio: volume and mute travel through volume_control, not the event queue. The arm groups actually present are session lifecycle, display draw ops, display mark, cursor, monitors config, ping/RTT, error, USB, WebDAV, paste, notification and disconnect. The master plan's phase 3 section is corrected in this commit.

    3. The master plan's last phase-3 bullet is already done. It asks for the comments in surface_mirror.rs, session.rs and bugreport.rs that name app.rs to be updated. Phase 1 removed the "mirrors process_events" comment from surface_mirror.rs entirely, and phase 2's step 2e repointed session.rs:18, session.rs:62, bugreport.rs:35 and bugreport.rs:857 at ryll/src/app/. git grep -n 'app\.rs' -- ':!docs/plans/' finds nothing. The bullet is struck from the master plan in this commit.

    4. process_events has shrunk, and the eframe::App impl has grown a second half. The master plan's Situation table says process_events is ~610 lines; it is 487 (mod.rs:1539-2025). eframe::App now has both logic (mod.rs:3200, 156 lines, which is what calls process_events) and ui (mod.rs:3356, ~1,685 lines). The test module at the foot of mod.rs is 454 lines, not ~1,020, as phase 2 moved most of it out. Two modules the master plan never mentions have appeared since it was written -- app/agent_state.rs (209 lines) and app/ui_state.rs (285) -- both landed by other plans. None of this changes phase 3's scope, but phase 4's should be re-surveyed against logic as well as ui.

    5. screenshot_paths is the one pure item no phase has claimed. Phase 2's finding 4 left it "for phases 3 and 4 as planned", but the master plan's phase 4 list (stats_bar, traffic_panel, notifications_panel, usb_panel, webdav_panel, dialogs, region_select, cursor, keys) has no home for it. screenshot_paths (mod.rs:782), save_screenshots (mod.rs:3070), open_screenshot_dialog (mod.rs:3102) and the five screenshot_paths_* tests are egui-free -- the dialog is rfd, a native panel -- so they are a phase-3 move, not a phase-4 one. Decision 6.

    6. ARCHITECTURE.md's ryll/src/ tree is stale already. Its app/ listing (ARCHITECTURE.md:172 onwards) omits agent_state.rs and ui_state.rs, which have been on develop since phase 2 landed. Step 3g fixes that as well as adding this phase's files.

    7. The ChannelEvent match ends in _ => {} (mod.rs:1973). Two variants fall into it. DigestUpdated is turned into the control socket's digest_updated wire event by shakenfist-spice-renderer/src/control/server.rs, and exists only under the renderer's digest-decode feature. ChannelsAvailable is consumed by nobody: session::connect learns the channel list from a oneshot that the main channel fires immediately before emitting the event (channels/main_channel.rs takes channels_avail_signal and then emits; session.rs awaits channels_avail_rx), so the event is informational. The GUI is right to ignore both, but a wildcard means the next variant is also ignored silently -- which is the shape of failure this whole plan exists to make visible. Decision 5.

    Corrected during step 3g: this finding originally said session.rs consumed the ChannelsAvailable event, and did not notice that DigestUpdated is feature-gated. The second error is why the step's single arm does not compile.

    1. Three continue statements sit inside the SessionInitialized arm (mod.rs:1589, 1597, 1640). They are the only control-flow escapes in the whole match, and extracting that arm into a method turns each into a return. Risk 1 covers this.

    2. No duplication with the renderer crate in the phase-3 region. Phase 1 already lifted the one real case (the draw-op dispatch) and the display arm is now a thin wrapper over self.surfaces.apply_event. reconnect_policy.rs already holds the SPICE retry rules with no GUI dependency, and phase 1's finding 6 settled that the GUI's ReconnectState stays in ryll. Nothing here wants to move to the renderer.

    The master plan's phase 3 section is corrected in this commit for findings 2, 3 and 5, and its Situation table for finding 4.

    Decisions¶

    1. Five files, not the master plan's three. The master plan proposed events.rs, bug_report.rs and connection.rs. The bug-report material measures ~1,124 lines, which would create exactly the kind of oversize file this plan exists to remove and would breach the master plan's own success criterion of roughly 800 lines. It splits on a real seam: capturing evidence (trigger snapshot, window shot, region selection) happens at dialog-open time and is driven by the UI, while assembling and writing the report happens at submit time and is driven by crate::bugreport. So trigger_snapshot.rs (~563 lines) and bug_report.rs (~561) rather than one file. screenshots.rs (~194) is finding 5. Measured sizes:
    File Lines Was
    app/connection.rs ~574 new
    app/events.rs ~584 new
    app/trigger_snapshot.rs ~563 new
    app/bug_report.rs ~561 new
    app/screenshots.rs ~194 new
    app/mod.rs ~3,176 5,592

    mod.rs stays oversize until phase 4 removes ui.

    1. Move first, restructure second, in separate commits. Step 3b moves process_events verbatim into events.rs; step 3c then splits it into handle_* methods. Doing both in one commit would make the move check useless on the file that most needs it, and would leave a reviewer unable to tell a moved line from an edited one. The cost is one extra commit in which events.rs contains a 487-line function.

    2. The auto-snapshot thread's whole lifecycle lands in connection.rs, including the spawn. Today the spawn is ~75 lines inlined in the SessionInitialized arm while retire_auto_snapshot_task, signal_auto_snapshot_retire and reap_auto_snapshot_threads are separate methods. Step 3c extracts the spawn as spawn_auto_snapshot_task(&mut self, interval_secs: u64) on connection.rs, called from handle_session_initialized. The alternative -- leaving the spawn in events.rs -- splits a four-part lifecycle across two files for no reason beyond where the code happens to sit today.

    3. push_notification and push_connection_event stay in mod.rs. They have 22 and 12 call sites respectively, spread across every module this phase creates and the ui body that phase 4 will split. They are small, they touch no state but the notification store, and putting them in any one of the new files would make the other four depend on it. A notify.rs is defensible once phase 4 has moved the ui call sites; it is premature now.

    4. The wildcard arm is replaced with explicit arms, in its own commit. ChannelsAvailable and DigestUpdated get a named arm with a one-line reason pointing at the consumer that does handle them (finding 7), and the _ => {} goes. After that a new ChannelEvent variant is a compile error in the GUI rather than a silent no-op. This is a behaviour-preserving edit, not a move, so it is step 3g and not folded into 3b or 3c -- the move check must stay meaningful. It is also the one decision a reviewer may argue with: it makes the renderer crate's event enum a breaking-change surface for the GUI, and someone adding a variant for headless mode alone must now touch events.rs to say so. That is the point.

    Risks and mitigations¶

    1. The continue to return conversion in handle_session_initialized. A break would silently stop draining the event queue for that frame; dropping the escape entirely would re-announce the session and respawn the auto-snapshot thread on every duplicate SPICE_MSG_MAIN_INIT, which is the exact bug classify_session_initialized exists to prevent. The session-init tests in app/session_init.rs cover the classifier but not the arm that acts on it, so they would not catch this. Mitigation: the step 3c brief calls it out explicitly; the management session reads the diff of that arm line by line before committing, and checks grep -n 'break' ryll/src/app/events.rs is empty.

    2. A move that quietly becomes an edit. Five of the seven steps claim to be pure moves, and a sub-agent that reflows a line or "tidies" an import while moving it makes the claim false and the review much more expensive. Mitigation: the move-check script under Definition of done, run by the sub-agent on its own diff before handing back, and again by the management session.

    3. Explicit arms turn out to be unmaintainable in practice. If the renderer crate's ChannelEvent grows variants that only headless or web mode care about, every one costs a GUI edit. Mitigation: that cost is the intended signal, and it is one line. If it becomes genuinely painful the arm can go back to _ in one commit, and the master plan's close-out notes should record it if so.

    4. mod.rs is still 3,176 lines after this phase. A reviewer may reasonably read that as the phase having failed. Mitigation: decision 1's table states the expected size, and ui alone is ~1,685 of the remainder -- phase 4's work, by design.

    5. Seven commits on one branch is a lot to review. Mitigation: each commit is one file's worth of movement with a subject that says so, and the five move commits can be read with the move check rather than by eye. Steps 3c and 3g are the two that want real attention, and they are last-but-one and last.
