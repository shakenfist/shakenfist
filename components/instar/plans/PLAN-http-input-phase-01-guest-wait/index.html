    HTTP input phase 1: the guest I/O wait¶

    Status: Not started¶

    Master plan: PLAN-http-input.md.

    Planning effort¶

    High. The change itself is small -- a bounded loop becomes an unbounded one -- but it removes the only place in the codebase where a call-table I/O outlives the call that issued it, and the guest side is bare-metal no_std code with volatile MMIO where a wrong memory ordering is invisible until it corrupts an image. Review effort: high for steps 1a and 1e, which touch the virtio request path and the host's error rendering respectively.

    Decisions already taken by the operator¶

    From the master plan, resolved 2026-11-18:

    1. Open question 5: the spin budget is a real defect, reproduced by measurement, and phase 1 is a bug fix rather than enabling work.

    Taken when this phase was planned, 2026-11-18:

    1. The guest waits indefinitely, and there is no host deadline. Not a watchdog thread, and not a TSC-bounded guest wait. The survey below explains why a host deadline cannot be enforced by either thread that services the queue.
    2. Issue #849 is out of scope. The leftover output file after a failed convert needs a per-failure keep-or-unlink policy measured against qemu-img, which is its own argument.
    3. This phase shares a pull request with the master plan, as PR #921 did for multi-extent VMDK phase 1. The branch is http-input-phase-01-guest-wait.

    Scope¶

    In scope:

    • Removing MAX_WAIT_ITERATIONS from src/core/src/virtio.rs do_request, and with it the send_error("timeout", ...) path. Closes #923.
    • Making a guest I/O failure legible from the host without --verbose: a reserved send_error marker for an I/O failure, the host decoder capturing it, and convert and dd rendering it by name with an exit code measured against qemu-img rather than guessed. Closes #924.
    • The LUKS inner-format probe in src/operations/convert/src/main.rs that treats a failed read as "no inner format", which the master plan asked this phase to read carefully. It is a real defect of a different shape than the master plan guessed; see the survey.
    • A test that proves a slow host read no longer fails an operation, and that it would have before.

    Out of scope, with reasons:

    • #849, the leftover output file (decision 3).
    • Queue depth greater than one. The master plan's Future work owns it. This phase makes a slow read survivable, not fast.
    • The VMM's logging defaults. The survey found that no logger is installed at all without --verbose, so every diagnostic record in the VMM is discarded by default, not only guest I/O errors. That is wider than #924 and wants its own issue; this phase fixes the error the user sees rather than the log they do not.
    • The other operations' I/O error sites. Step 1d audits all 13 and records what each one's host side does with it; it converts only the ones whose host side currently drops the detail, which the survey found to be convert and dd.

    What the survey found¶

    The master plan's phase 1 section was written before any of this was measured. One of its claims is wrong, and five things it does not mention change the shape of the work.

    The one wrong claim, corrected at source in this phase's planning commit. The section said the fix was to "move the deadline to the host where it can be generous and per-request". There is no host deadline to move it to. src/vmm/src/io_thread.rs passes 100 ms to epoll_wait, and the comment there says why: so the loop can re-check the running flag. Nothing times a request, anywhere in the VMM. Building one is not a move, and decision 2 says not to build one.

    Why a host deadline is not cheap. Two paths service a virtio queue. The I/O thread polls the ioeventfd when IoEvent::register succeeds; when it fails the VMM falls back to processing the queue from the vCPU exit, which is process_queue_for_device, called from 16 operation run loops. Both call process_queue, which calls self.backing.read_at synchronously. So the thread that would notice a request was late is the thread blocked inside the read. A deadline needs a third thread whose only job is to watch -- new privileged machinery, in the process holding /dev/kvm, to catch a case (a wedged VMM) that no reproduction in this repository has ever produced.

    The guest already waits forever on the host elsewhere. src/core/src/serial.rs read_config spins unbounded, in two loops, waiting for the host to send the device configuration at startup. An unbounded wait on a trusted host is therefore already the pattern for one of the two channels between them, which is the strongest argument that decision 2 is consistent rather than novel.

    The abandon path breaks a documented invariant, which is the finding most worth reading. docs/guest-architecture.md says the shared read-modify-write bounce sector in the planner executor is "safe because all call-table I/O is synchronous and steps execute serially", and that Ordering barriers are a no-op because "issue order is completion order". The timeout is the only place where a call-table I/O is not synchronous: do_request returns false while the host is still working on the request it has no way to cancel. Compounding it, do_request addresses its header, data and status buffers at fixed addresses -- DMA_POOL_BASE, DMA_POOL_BASE + 16 and DMA_POOL_BASE + 16 + sector_size -- for every request, while rotating only the descriptor slot. So after a timeout two requests are in flight against one set of buffers. Nothing has gone wrong yet because the host services the queue serially and completes in order, so the guest's next wait still observes its own bytes. That is safety by accident of serialisation, and it holds only while nothing in the VMM ever services two requests concurrently -- which is exactly what the master plan's Future work proposes to change. Removing the abandon path removes the hazard before anything depends on it.

    #924 is two layers deep, not one. Guest messages are formatted by format_message and logged with debug! at 16 sites, and Level::Error records go the same way. The logger is installed in one place, inside if verbose, and that is the only set_boxed_logger call in the VMM. So without -v there is no logger at all and the record is discarded before its level is considered. Separately, SerialDecoder's capture chain names six guest refusals -- cpu-exception, DifferencingRefusal, VhdFooterChecksumRefusal, InvalidL2EntryRefusal, DataFileEntryRefusal, MalformedL2EntryRefusal -- and no I/O failure, so nothing is kept for execute_convert to render in place of "convert operation failed". That generic string is the only "... operation failed" in the VMM; every other operation already fails with a sentence.

    What #924 must capture is not "timeout". Once step 1a lands, do_request never reports a timeout. A genuine host read error still fails the request through the virtio status byte, and the operation is what reports it: convert sends send_error("convert", "input", read_sector, 1) followed by send_complete("convert", bytes_read, false). Capturing "timeout" would therefore fix a message that step 1a deletes. The marker has to be the operation's own I/O failure, which is what outlives this phase and what a remote backing store will report in phase 3.

    The LUKS probe at src/operations/convert/src/main.rs is a defect, but not the one the master plan guessed. It wrote that the &&-chained read_input_sector "may be a silent-zero-fill bug". It is not: the probe reads the first payload sector to look for QCOW2 magic, and on a failed read it silently skips the magic check and falls through to the flat LUKS path. That path then re-reads the same sector -- payload_offset is 0, so its read_sector equals the probe's payload_sector -- and treats a failure there as fatal, with send_error and a failed completion. So a wrong answer needs one read to fail and the identical read to succeed moments later, which is precisely what a transient timeout provides and nothing else in the tree does. The output would then be a LUKS-wrapped qcow2 decrypted and written out as a flat image, at exit 0. It is reachable only through the defect step 1a removes, which is why it belongs in this phase and not in a later one.

    Test infrastructure does not exist for this, and a missing tool here is a silent pass. strace appears in no Dockerfile and no CI workflow in the repository, and the Python suite runs both on the host (make test-integration) and in a container (make test-container). An injection test that skips when strace is absent would therefore be green everywhere and run nowhere -- the shape of the libvhdi oracle problem, where make test-container-core passed for want of an environment variable. Step 1b has to add the tool where the suite runs and make its absence loud. The harness's own subprocess timeouts (30 s by default in tests/base.py) are what keep an unbounded guest wait from hanging CI.

    Nothing else in the master plan's phase 1 section was wrong.

    Decisions¶

    1. The wait becomes unconditional. do_request spins on the used ring until the completion arrives, with spin_loop() kept as the hint. The timed_out flag, the budget constant and the send_error("timeout", ...) branch all go. do_request keeps returning false for the status-byte failure path, which is a completed request that failed, not an abandoned one.

    2. No host deadline, and no guest backstop. Decision 2 of the operator's set. The honest statement of the consequence is that a VMM which loses a completion hangs the guest until the user interrupts it, where today it fails after about 1.3 s with a misleading message. That trade is worth taking: a lost completion is a VMM bug with no reproduction, a slow read is an everyday event with a reproduction in #923, and the current behaviour turns the everyday event into the symptom of the rare one.

    3. A reserved marker for an I/O failure, following the refusal pattern. Add shared::IoFailure with an OPERATION string distinct from every real operation name and from the six existing markers, its NUL-terminated twin for the call table, and documented meanings for device (which device failed) and sector. This is the InvalidL2EntryRefusal shape exactly, including the unit test that asserts the C string matches the Rust string. The guest's I/O error sites send that marker instead of their own operation name.

    4. The host renders it in the returned error, not in a log. The decoder captures the marker; execute_convert renders it in place of "convert operation failed". This follows compare's existing wording, which names the image and the offset and says what did not happen: "compare: reading the second image, ref.raw, failed at virtual offset 327680 (0x50000); the images were not compared". The logging defaults stay as they are (see Scope).

    5. The exit code is measured, not chosen. compare uses qemu-img's read-error code. What qemu-img convert exits with on a read failure is a question about another tool, and this repository has a standing rule that such claims are measured or cited rather than asserted. Step 1e measures it with an injected read error and records the number in this plan before using it.

    6. The LUKS probe propagates the failure. A failed probe read becomes an error, not a skipped branch. The fix is small; the reasoning for why it was reachable is what the commit message has to carry, because a reader looking at the diff alone will see a failure path added for a read that is retried successfully two screens later.

    The decision most likely to be argued with is 2. "Wait forever" reads as a worse answer than "wait longer", and a reviewer may reasonably ask for a generous TSC-based bound as cheap insurance. The argument against is that a bound is a number nobody can derive: the guest cannot distinguish a host that is slow from a host that is stuck, and any number large enough not to fail a legitimate slow read on a loaded 16-worker CI host is also large enough that a genuinely wedged VMM looks like a hang anyway. The bound would buy a better message in a case that has never been observed, at the cost of keeping the abandon path -- and the abandon path is what breaks the synchrony invariant the shared executor relies on.

    Findings¶

    1. copy reports a failed read as success. Every send_error path in copy returns early, skipping the send_complete(..., true) at the end of its run, and run_copy neither requires a completion nor inspects one: it breaks on HLT, logs "Copy operation completed successfully!" at debug level and returns Ok(()). A copy whose input read fails therefore exits 0, prints nothing, and leaves a short output. That is a success-shaped wrong answer, not a wording problem, and it needs its own issue and a host-side fix.
    2. A host read error reaches the guest as a hang, not a status byte. VirtioBlockDevice::do_read propagates a BackingStore::read_at failure with ?, so process_request returns Err without writing the used ring, and the I/O thread discards it (if let Ok(io_stats) = device.process_queue(...)). Measured: a single injected EIO on any read of the input image makes convert spin forever (three indices tried, each killed at 25 s), with no error and no completion. The pre-step-1a budget would have ended that wait with the misleading "timeout"; now nothing ends it. So the I/O-failure marker is raised today only when the device completes a request with an error status, which validate_io_request does for an out-of-range request -- the reproduction used below. Giving a backing-store error a status byte belongs with the VMM work, and it is what makes the marker reachable for the case the master plan cares about.
    3. The status argument's old convention was redundant and not even consistent. It duplicated device (1 for input, 2 for output) except in convert_native_luks, where an output write failure passed 1. Every converted site now passes 0, as IoFailure documents.
    4. Step 1e must keep the refusal branches ahead of the I/O branch. Eleven of the converted sites report a false return from qcow2::read_chain_virtual_cluster, which fails for a structural refusal as well as for a failed request; the refusal markers are the specific signal and already come first in execute_convert, run_compare and run_bench. Appending the I/O branch after them preserves that order. A structural failure with no marker of its own will render as an I/O failure, which is the same claim the operation already makes when it passes device = "input".

    Reproduction used¶

    With no way to deliver a failed read through the device (finding 2), the marker was exercised through the completed-but-failed path: a 1 MiB qcow2 whose second L2 entry was repointed to a cluster-aligned host offset past the end of the file, so validate_io_request answers the guest's read with IOERR. Before this step, instar -v convert -O raw on it logged [ERROR] error op=convert device=input sector=1 status=1; after it, [ERROR] error op=io-failure device=input sector=1 status=0. The user-visible error is unchanged in both cases -- Error: "convert operation failed", exit 1 -- which is step 1e's half.

    Measurements¶

    qemu-img convert's exit code on a source read error¶

    Measured 2026-11-18 (AEDT) on kasm, qemu-img 10.0.13 (Debian 1:10.0.13+ds-0+deb13u1), against an 8 MiB qcow2 written from /dev/urandom:

    strace -f -qq -e trace=pread64 -e inject=pread64:error=EIO:when=N \
    -o /dev/null qemu-img convert -O raw src.qcow2 out.raw
    when rc out.raw stderr
    6 1 8388608 qemu-img: error while reading at byte 6291456: Input/output error
    8 1 8388608 qemu-img: error while reading at byte 0: Input/output error
    10 1 8388608 as the first
    12 0 8388608 injection landed past the last image read

    Three conclusions, which settle decision 5:

    • Exit 1, which is what instar's convert already exits. So this phase changes the message and not the code, and compare's exit 4 is not the precedent to follow -- that is qemu-img compare's own read-error code, from a vocabulary convert does not share.
    • The offset is reported in decimal bytes, with no hex and no sector number. instar's compare gives both decimal and hex, which is the house style this phase follows instead.
    • qemu-img keeps its output file, at full declared size. That is evidence for #849's keep-or-unlink question -- qemu's answer on this failure is to keep -- recorded here for whoever takes that issue, and not acted on in this phase.

    Note for anyone reproducing it: injecting on read does not reach qemu-img's image data at all, because it reads the source with pread64 from several threads. #923's recipe is written for instar, which seeks and reads.

Killed only by the new the_recorded_reason_drops_the_errno_number_but_keeps_other_wording, which is the finding: both tests that provoke a real backing-store failure produce errors with no " (os error N)" suffix (the write case is BackingStore's own "write at offset 512 + 512 bytes exceeds capacity 1000"), so neither exercised the parsing they were nominally about.

    Two of the round's changes are deliberately not covered by a test, which is recorded here rather than left to be rediscovered. The used-ring length is no longer counted for a failed request, and nothing reads that field -- the guest never looks at the used element's length -- so no test can distinguish the fix from its absence; it is correctness against the virtio spec for a future multi-request path. And the wait's exit condition now tests that the used index moved rather than that it reached one value, which at queue depth one is the same condition, so it is hardening for the depth increase in Future work rather than a behaviour change.

    Back brief¶

    Before executing any step of this plan, please back brief the operator as to your understanding of the plan and how the work you intend to do aligns with that plan.

    One gate within the phase: step 1e's wording and exit code are cheap to propose and expensive to redo once tests assert on them, so the management session agrees the error sentence and the measured exit code before step 1e's tests are written.
