    Phase 1: pin qemu-img's behaviour, build the structural oracle, correct the doc¶

    Phase 1 of PLAN-bat-population.md. Read its Situation, Open questions and the phase 1 paragraph of "Sequencing rationale" first; this file assumes them.

    Planning effort: high. Every later phase copies what this phase pins, and tests what it builds with the comparator this phase writes. A wrong pin or a comparator that shares a misreading with the emitter it will judge is invisible to qemu-img info, which is the whole reason the comparator exists.

    Decisions already taken by the operator¶

    • Every open question in the master plan is resolved with its recommendation adopted (Michael Still, 2026-10-21). In brief: preallocation of vmdk, vpc and vhdx is qemu parity, a no-op with metadata refused (1); monolithicFlat create is in, host-only, in phase 3 (2); create, convert and measure all gain fixed VHDX, convert writing blocks in place (3); the BAT is never materialised (4); #626 and #645 are closed by this plan, and #797, #798 and #799 are its three filed defects (5); resize refuses a fixed VHDX (6); dynamic VHDX does not honour block_state_zero in this plan (7); create's default block_state_zero is qemu's, on (8). The master plan records each resolution under its question.
    • This plan runs alongside PLAN-654, not after it. The only file both edit is the check op; see "What the survey found" for what #801 moved.

    Scope¶

    In:

    • A sweep of all 80 static qemu-img builds in instar-testdata over every qemu behaviour this plan copies, recorded as a committed, machine-checkable pin file in this repository, plus a summary table in this plan.
    • The structural VHDX comparator (tests/helpers/vhdx_structure.py), importable by the integration tests and by scripts/differential-fuzz.py, with tests that pin its reading of qemu-written images to values derived from qemu source and SPEC(VHDX).
    • A CI test that re-measures a bounded set of versions, and the host qemu-img, against the pin, and fails when the testdata gains a build the pin does not cover.
    • The docs/create.md:395 correction, as this phase's first commit after the plan.
    • Settling the master plan: the open-question resolutions, the stale line citations and claims the survey found, and the sweep's findings if any contradict the Situation.

    Out:

    • Any change under src/. #626, #797, #798 and #799 are fixed in phases 4 and 5; the temptation to fix one while its reproduction is on screen is what this line exists to resist.
    • Fixtures and baselines in instar-testdata (phase 2). Nothing in this phase commits to instar-testdata.
    • Wiring the comparator into the differential fuzzer's create and convert ops (phase 11). This phase only guarantees the fuzzer can import it.
    • Replacing the four ad hoc VHDX parsers already in the test suite (see the survey) with the new helper. Recorded in the master plan's Future work.
    • docs/create.md's other wrong future-work bullets (the default block size, the preallocation "BAT-population pattern", the monolithicFlat reason). Each changes in the phase that changes the behaviour it describes: 5, 3 and 3.

    What the survey found¶

    Surveyed on 2026-10-21 against the worktree at 7a47f9f4 (two plan commits on d08841e3, develop after #801). Measurements used the static builds in instar-testdata/qemu-img-binaries/x86_64/<version>/qemu-img (testdata at cf67642bbb), the host's qemu-img 10.0.13 (Debian 1:10.0.13+ds-0+deb13u1), and the instar binary in the primary clone (src/target/release/instar, built from da9f043f, mtime 2026-10-19 12:29; nothing VHDX-related changed between that commit and d08841e3).

    The master plan's phase 1 premises¶

    • 80 static builds, all executable. ls qemu-img-binaries/x86_64 | wc -l is 80: 6.0.0 to 10.2.0, every patch release from 7.2.0 on, every directory holding an executable qemu-img. qemu-sources/ carries 6.0.0, 6.0.1, 6.1.0, 6.1.1, 6.2.0 and 7.0.0 only, so 7.0.0 is the newest tree a claim can be cited to, as the master plan says.
    • tests/helpers/ exists and is the right home. It holds __init__.py (load_manifest_images), comparators.py, info_json.py (NESTED_INFO_DIVERGENCE at :33), qcow2_subclusters.py (PLAN-654's fixture builders, the precedent for a pure helper with its own test module), snapshot_readback.py and types.py. Pure-helper unit tests live in tests/test_helpers.py.
    • The fuzzer already shares a helper this way. scripts/differential-fuzz.py:41-47 puts tests/ on sys.path and imports helpers.snapshot_readback. A new helper is importable the same way provided it imports nothing from tests/base.py. _normalise_create_info (:1547), op_create (:1651) and the picker docstring with the backwards default-block-size claim (:1587) are where the master plan says.
    • No reusable VHDX parser exists, but four fragments do. tests/test_create.py:111-176 (_vhdx_active_data_write_guid, _vhdx_bat_region), tests/test_info_safe.py:360-415 (metadata table walk), and tests/test_differencing.py around :2384-2530 (region table, CRC-32C, first BAT entry) each parse just what one test needs, and none reads File Parameters' LeaveBlocksAllocated bit or classifies BAT entries. scripts/create-vhd-testdata.sh:1191 has a CRC-32C as well. A structural comparator is new code; folding the fragments into it is out of scope (above).
    • The libvhdi oracle is not available here. tests/base.py:496 (_require_vhdiinfo) and :537 (_require_pyvhdi) gate it, and CI installs it in the devcontainer, but vhdiinfo is not on this host. Whether libvhdi reports a fixed VHDX as fixed is therefore unmeasured; step 1b records it if the devcontainer can be used.
    • qemu-img map is not a BAT oracle for VHDX. On 10.0.13 and on 6.0.0, map --output=json of a fixed 64 MiB image reports one extent, "data": true, "zero": false, with no offset, for both the all-ZERO default image and the FULLY_PRESENT one. The vhdx driver has no block-status callback, so map cannot see BAT state; the comparator has to read the BAT itself.
    • generate-baselines.py and detect-profiles.py are where the master plan says: CREATE_CASES at :404, the stale "vhdx is dynamic-only in instar; qemu defaults match" at :455, and generate_create_baseline at :1542, which records only qemu-img info JSON, so it cannot carry a structural pin without a new output type. detect-profiles.py groups versions by identical stdout/stderr/meta triples per output type. Read-only here.
    • A precedent for running the static builds in CI exists. tests/test_cow_cross_version.py runs five pinned versions live and skips when the binaries are absent; tests/stestr-timing.txt:719-721 shows it running in CI (6.85 to 28.76 s), and tools/ci/prepare-testdata.sh:261 pulls all LFS objects, binaries included.
    • docs/create.md:395 reads "VHDX subformat=fixed (not emitted by qemu-img either)." It is the only such claim in docs/ (grep for "not emitted by qemu" and "fixed vhdx"). The target table at :60 says vhdx is dynamic only, which is true of instar.
    • The three defects are filed. #797 (check, partial last block), #798 (resize, hybrid) and #799 (no 64 TiB ceiling) are open and labelled bug; #626's title has already been corrected to say it breaks reading qemu images. The master plan's Open issues table still said "(new)" for all three and its success criteria said "the three issues phase 1 files"; both are corrected in the master plan by this planning commit.

    SPEC(VHDX), which the master plan asked phase 1 to cite¶

    [MS-VHDX] revision 8.0 (2024-04-23), the PDF and DOCX downloaded from the Microsoft Open Specifications page on 2026-10-21. The BAT formulas are images in both (DOCX word/media/image8.bin to image11.bin), so a text search of the PDF finds the prose and not the arithmetic.

    • 2.5 BAT. "Payload Blocks Count = Ceil(VirtualDiskSize / BlockSize)"; "Sector Bitmap Blocks Count = Ceil(Payload Blocks Count / Chunk Ratio)"; "For dynamic and fixed VHDX, the last BAT entry MUST locate the last payload block of the virtual disk. The total number of BAT entries ... can be calculated as Total BAT Entries = Payload Blocks Count + Fl((Payload Blocks Count - 1) / Chunk Ratio)"; for differencing, "Sector Bitmap Blocks Count * (Chunk Ratio + 1)". So the spec agrees with qemu's vhdx_calc_bat_entries (block/vhdx.c:868-882) and #626's diagnosis, on both halves.
    • 2.6.2.1 File Parameters. "LeaveBlockAllocated (1 bit): Specifies whether blocks can be unallocated from the file. If this field is set to 1, the implementation SHOULD NOT change the state of any blocks to a BLOCK_NOT_PRESENT state, and the implementation MUST NOT reduce the size of the file to a value lower than would be required to allocate every block. This field is intended to be used to create a fixed VHDX file that is fully provisioned. Ignored if HasParent is set." That settles open question 6's request for the spec text: resize adding NOT_PRESENT entries under the bit (#798) is what the spec says not to do.
    • 2.5.1.1 lists PAYLOAD_BLOCK_ZERO as valid in a fixed VHDX (footnote 8), and NOT_PRESENT/UNDEFINED/UNMAPPED as acceptable to read but not to transition to in a fixed file (footnote 6).
    • No file-growth rule. qemu's comment at block/vhdx.c:902-907 says "The VHDX spec states that the image file can only grow in blocksize increments"; revision 8.0 says no such thing (the only "increment" in the text is the log's sequence number). The partial last block (#797) is a qemu tolerance of its own past output, not a spec rule instar has been enforcing.

    Decisions¶

    1. The pin lives in this repository, as tests/golden/qemu-create-pins.json, grouped by outcome. The shape is {"versions": [...], "cases": {name: [{"versions": [...], "result": {...}}, ...]}}: each case holds one group per distinct result, so a version boundary is two groups and "no boundary" is one group listing all 80 versions. result is always rc and a filename-normalised stderr, plus, per case kind, the comparator's summary (VHDX), file length and the mode-identity booleans (preallocation), or the normalised descriptor (monolithicFlat). Later phases consume it through tests/helpers/qemu_pins.py (expected(case, version=None), which with no version demands a single group and raises if there is a boundary), so a phase 7 test asserting "instar's fixed image equals the structure every qemu version writes" is one comparator call against the pin rather than 80 qemu runs. Why not instar-testdata's expected-outputs/, the house home for cross-version qemu output: that tree holds qemu-img's stdout, and the thing to pin here is a parse of the image, made by a parser that lives in this repository; a testdata copy would either import across repositories or duplicate the parser. The derived profiles/ there have also been silently wrong twice, and a 13-group-per-case JSON with an explicit version list is easier to review by eye than 80 directories.
    2. The sweep tool lives in instar tools/, as tools/sweep-qemu-create.py, next to probe-qemu-versions.sh. It imports the comparator and the case table from tests/helpers/ the way the fuzzer does, takes --testdata (default ../instar-testdata), --versions (default: every directory under qemu-img-binaries/x86_64), --scratch, and either --write PIN or --check PIN. --check re-measures the named versions and exits non-zero on any difference from the pin, naming the case, version and field. Nothing is written to instar-testdata; that repository takes direct commits to main and nothing in this phase needs one.
    3. One case table, shared. The cases are defined once, in tests/helpers/qemu_pins.py (CASES), and run by one function (run_case(qemu_img, case, workdir)), which both the tool and the CI test call. The case list is in step 1c's brief and is the master plan's phase 1 list made concrete; adding a case later is a table row plus a re-run of the tool.
    4. The comparator is a parser plus a summary plus a diff, and it compares only deterministic fields. parse_vhdx(path) returns a frozen dataclass; summarise(structure) returns a JSON-able dict; structural_diff(a, b) returns a list of human-readable differences, empty when equal. Compared: file length; both region tables (entries in order, and whether the two copies agree); the active header's log offset and length; metadata items present and their offsets; block size, logical and physical sector size, virtual disk size; the LeaveBlocksAllocated and HasParent bits; chunk ratio; the BAT region's capacity; every BAT entry, run-length encoded as (first_index, count, kind, state, first_offset, stride) where kind is payload, sector_bitmap or padding (past SPEC(VHDX) 2.5's entry count). Not compared: GUIDs, sequence numbers, checksums, the creator string, and allocated bytes (st_blocks differs between ext4, xfs and tmpfs); allocation is exposed as a separate field for relative assertions only. Malformed input raises VhdxParseError, never IndexError or struct.error, because the fuzzer will feed it instar output that may be wrong.
    5. The comparator is checked against qemu's arithmetic, not against instar. Its tests assert, on qemu-written images, the values that block/vhdx.c and SPEC(VHDX) 2.5 predict (data start bat_offset + bat_length + 5 MiB, :1708; file length; entry count; states and offsets), computed in the test from the cited formulas. It is never tested against an instar-written fixed VHDX, because there is none yet and because the emitter it will judge must not be its reference. If the devcontainer's libvhdi can read a qemu fixed image, step 1b records what it reports as a second, independent reading; it is not a gate.
    6. CI re-measures a bounded set, and enforces coverage. tests/test_qemu_create_pins.py runs every case on 6.0.0, 6.2.0 (the toolsVersion boundary), 8.2.0 and 10.2.0 when the binaries are present, and on the host qemu-img against the group of the newest pinned version at or below it, skipping with a reason where the host lacks a driver (skip_unless_qemu_supports). It also fails when qemu-img-binaries/x86_64 holds a version the pin does not list, with a message naming the tool to re-run, so the pin cannot silently fall behind the testdata. The full 80-version run is the tool, run by hand, as generate-baselines.py is.
    7. The doc correction is step 1a, its own commit, before anything else. It replaces only the :395 bullet, with what qemu-img actually writes and the fact that instar refuses it today. It does not claim a version range: the claim "qemu-img emits fixed VHDX" is already measured on 14 versions including both ends, and the sweep only widens it. If step 1d were to find a version that refuses, the bullet gains a qualifier in step 1f.
    8. This phase lands on bat-population-phase-01-pin, with the master plan. The master plan is not on develop yet, and this branch already carries it. Phase 1's Merged cell will therefore record the merge commit of the pull request that carries the master plan and this phase together, as PLAN-differencing's phase 1 did.

    The decision most likely to be argued with is 1: putting a cross-version qemu pin in instar's tests/golden/ rather than in instar-testdata's expected-outputs/, which is where every other per-version qemu result lives and which detect-profiles.py already knows how to group. The case for the house pattern is consistency and a single place to look. The case against, for this pin, is that what is pinned is not qemu's output but a reading of qemu's image by a parser in this repository, so storing it in testdata either splits the parser from its results across two repositories with no shared review, or copies the parser; and phase 10, which does need per-version create baselines in testdata, can still generate them there with this comparator if the operator prefers, using the pin as the cross-check that its derived profiles are right.

    Risks and mitigations¶

    • Correlated error between the comparator and a future emitter. If the parser misreads, say, the interleave rule, and phase 6 writes the same misreading, every phase 7 test passes. Mitigated by decision 5: the comparator's tests assert qemu-written images against values computed from cited qemu lines and SPEC(VHDX) 2.5 formulas, before any instar fixed output exists, and the management session re-derives a sample of those expected values by hand when reviewing step 1b.
    • A plausible-but-wrong qemu claim in a brief. This repository has recorded it repeatedly. Every claim in the briefs above is cited to qemu-sources/7.0.0 or measured in the spot sample; step 1d's sweep is the 80-version check; the management session re-runs --check on two versions of its own choosing before accepting the pin.
    • Spurious boundaries from host load. Concurrent KVM load has made qemu commands fail here before. Mitigated by step 1d's rule: replay a suspected boundary alone before believing it.
    • A pin that falls behind the testdata. New static builds arrive in instar-testdata over time. Mitigated by decision 6's coverage test, which fails CI until the pin is regenerated.
    • Filesystem-dependent allocation. st_blocks differs between ext4, xfs and the tmpfs /tmp on Debian 13. Mitigated by decision 4: allocation is never compared absolutely, only "same as off" and, later, "same as qemu's on the same filesystem".
    • Large sparse files in CI. The 131041M fixed case is 128 GiB apparent, well under ext4's 16 TiB ceiling, and tmpfs counts only allocated pages, so it should be harmless. Step 1e reports rather than weakens if it is not.
    • Scope creep into src/. The read defects reproduce in seconds and their fixes look small. Mitigated by the scope line and the git diff -- src/ check in step 1f and the definition of done.
