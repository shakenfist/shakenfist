    Phase 10: cross-version matrix and derived-profile validation¶

    Phase 10 of PLAN-bat-population.md. Read its Situation (in particular "A standing caution about the baseline tooling", which is this phase's reason to exist) and the phase 10 paragraph of "Sequencing rationale". Also read the phase 2 plan's decision 5, which moved both pieces of work here and says why, and the phase 3 plan's decision 5, which moved the monolithicFlat and preallocation create cases here for the same reason. This file assumes them.

    Two repositories are in play. instar-testdata owns the generator, the baselines and the derived profiles, and takes direct commits to main rather than merge requests. instar owns the mirror of the generator's case list and the tests that consume the baselines. The ordering between them is decision 3, and it is the part of this phase most likely to go wrong.

    Planning effort: medium, as the master plan sets for phase 10 ("only tests"). The work is running established tooling and reading its output; what needed judgement was deciding how to generate a handful of baselines without rewriting thousands, and that is settled in decisions 1 and 2.

    Review effort: high. The master plan's caution is that this exact procedure has produced silently wrong derived profiles twice, so the review that matters is of the validator and of the before/after file counts, not of the baseline bytes.

    What the survey found¶

    Surveyed on 2026-11-06 against instar develop at 56a6303c (phase 9 merged as 3b74ba8d, #877) and instar-testdata main at d2f9467719. The master plan's phase 10 premises hold, but the survey found four things the paragraph does not say, and two of them change the shape of the phase. Corrections to the master plan's phase 10 paragraph and to the index.md row are made in this planning commit, so a later step does not redo them.

    The generator cannot be aimed at one image or one case¶

    instar-testdata/scripts/generate-baselines.py takes --version, --manifest, --arch, --all-images, --output-type, --command and --no-commit (:3100-3136). There is no --image and no --case filter, and nothing skips an output that already exists: the per-version loop walks every image load_test_images returns (:1004-1016) and overwrites. So "add baselines for phase 2's five fixtures" is today the same command as "regenerate every safe image's baselines", and "add the fixed VHDX create cases" is the same command as "rewrite all 108 create baselines for all 80 versions".

    That matters twice over:

    • The baselines are a long way behind the manifest. instar's tests/manifest.json holds 218 images, 124 of them safety: safe. expected-outputs/check-human/raw/10.0.0/ holds 38, and expected-outputs/qemu-img-json/raw/10.0.0/ holds 71; the check-human version-map.json is stamped 2026-08-29. A plain --command check run would therefore add roughly 86 images' baselines across 80 versions as a side effect, un-skipping tests across the suite that have never run. That is issue #845's territory, not this phase's (see Out of scope).
    • Regenerating create baselines rewrites 400 files to no purpose. qemu-img writes a random VMDK cid on every create, so the five vmdk create cases' stdout differs on every run and across every version (measured: create-info-json/vmdk/10.0.0/1M-default.stdout.txt vs 10.0.1's differ in exactly one line, "cid"). A full --command create run would change 400 vmdk baseline files and then all 80 create profiles, with no information in the diff.

    Decision 1 adds the two filters.

    create-info-json's 80 profiles are the VMDK cid, and are harmless¶

    expected-outputs/create-info-json/ has 80 profiles for 80 versions -- no deduplication at all -- while check-human, map-human, map-json, measure-human and measure-json each have exactly one profile for all 80. Both looked like the "silently wrong profiles" failure mode and neither is:

    • The single-profile types are genuine. Sampled 6.0.0 against 10.2.0 for three images in each of check-human, map-human and measure-json: byte-identical every time. qemu-img's check, map and measure output really has not moved across those images in nine releases.
    • The 80 create profiles are the cid. detect-profiles.py's hash_version_multi_bucket (:203-236) deliberately hashes only return_code and timed_out out of each meta.json, so timestamps are excluded -- but it hashes stdout whole, and the five vmdk cases' stdout carries the random cid. Confirmed by computing the hash for 10.0.0 and 10.0.1 directly and diffing every contributing part: the only differences are those five files, in that one field.

    Nothing consumes the redundancy incorrectly -- instar's tests/helpers/info_json.py:39 already strips cid and parent-cid for vmdk before comparing -- so this is recorded in Future work, not fixed here. It does mean the validator must accept 80 create profiles as correct, and that adding a sixth vmdk create case (monolithicFlat) will not make it worse.

    The two historical profile failures, and what a validator must check¶

    Both are in instar-testdata's history, both are fixed, and both describe the check this phase should automate:

    • ec01915058 ("detect-profiles: fix preserve-baseline corruption"): the preserve-hand-maintained-baselines path compared ids at mismatched granularity, so it matched nothing, flagged every image as hand maintained, and stamped one stale snapshot into every regenerated profile -- 41 of 44 images wrong while raw/ stayed correct. Its verification was "regeneration now produces profiles byte-identical to raw/ for 154/154 sampled checks".
    • 03c379a08a ("Stop the profile copy silently dropping outputs"): copy_multi_bucket_version_to_profile flattened buckets under bare filenames, so create-info-json's five buckets all contributing a 1G-default left only the last in sorted order. 36 files in, 25 out, no warning. The fix qualifies a basename with its bucket only for output types where basenames collide, which is why create-info-json profiles hold vhdx-16M-fixed.stdout.txt while map-json profiles hold bare image ids.

    Neither check is committed anywhere. There is no validator script, no make target for one, and instar-testdata has no CI of any kind (no .github/, no .gitlab-ci.yml, no pre-commit config), so a validator here is a tool a human or an agent runs, not a gate. Decision 4 defines it.

    Smaller findings, all verified¶

    • CREATE_CASES holds none of this plan's output. Both copies -- instar-testdata/scripts/generate-baselines.py:404 and its mirror at instar/tests/test_create.py:2572 -- are identical today and have no vhdx fixed case, no vmdk monolithicFlat case, and no non-qcow2 preallocation case. vhdx's comment still reads "vhdx is dynamic-only in instar", which phase 7 made false. vhd already has 1M-fixed and 16M-fixed, so the fixed-subformat baseline shape is established.
    • test_create_cases_match_baselines asserts set equality in both directions (instar/tests/test_create.py:2741-2774), which is what makes the cross-repo ordering a real problem rather than a cosmetic one. It skips only when a target has no baselines at all, and vhdx has 80 versions of them.
    • TestProfileSelectionMatrix hardcodes six expected info profile names (instar/tests/test_version_detection.py:268-276), so a shifted info profile boundary breaks it. Measured whether phase 2's fixtures would shift one: qemu-img info --output=json on vhdx-fixed-16M.vhdx is identical for 6.0.0 and 7.2.19, and identical again for 8.0.0, 10.0.0 and 10.2.0, differing between them only by the children block qemu added in 8.0.0 -- an existing boundary (profile-8-0-0). So no new boundary is expected. Verify, do not assume: step 10d runs detect-profiles.py --dry-run and compares the profile list before and after.
    • The $FILENAME normalisation will not cover a monolithicFlat baseline. generate_create_baseline substitutes the literal tmp path (:1636-1639). A monolithicFlat create writes a second file whose name is the stem plus -flat.vmdk, which that literal will not match, so the baseline would embed a host-specific path; and the generator deletes only tmp_file (:1676), so the extent leaks into tmp on every version. Both are fixed in step 10a.
    • info and check baselines are flat; map, measure, dd, resize and create are bucketed. expected-outputs/check-human/ and qemu-img-{human,json}/ hold raw/<version>/<image>.* where raw means "all formats"; map-*, measure-* and create-info-json hold <format-or-target>/<version>/... where a sibling raw/ means "the raw format". The word means two different things in the same tree. detect-profiles.py's own docstring (:9-34) documents only the first shape and is stale.
    • There is no baselines-create or baselines-map Makefile target, although three other targets' comments cite "the same policy as baselines-create" (Makefile:197, :209, :223). Those two commands have only ever been run by hand. Step 10a adds them.
    • Phase 2's five fixtures are registered and ready. All five are in instar/tests/manifest.json as safety: safe, run_in_ci: true, with sha256 values, and none has a baseline anywhere under expected-outputs/. All 329 LFS objects in the testdata clone are materialised.

    Decisions¶

    1. Add --image and --case filters to the generator rather than mass-regenerate. Both repeatable, both matching exactly (no globbing), both erroring if a given id or case name matches nothing -- a silent no-match filter would produce a green run that generated nothing, which is the hardest kind of failure to notice: the command succeeds, prints per-version progress, and leaves the tree unchanged. --image filters the manifest-derived image list; --case filters the per-target case list for --command create (and is accepted for any case-driven command, so resize and dd inherit it). This is the decision that makes the phase possible at all: without it, "add five fixtures' baselines" is a ~10,000-invocation run that un-skips suite-wide tests, and "add ten create cases" is a 400-file no-op diff. The alternative -- generate everything and accept the fallout -- was rejected because the fallout is exactly issue #845, which deserves its own phase with its own review.

    2. Four commands get fixture baselines: info, check, map, measure. These are the four phase 2 named as skipping the new fixtures (tests/test_info_safe.py:75-82, test_map.py's and test_measure.py's "no baseline meta" skips). dd, resize, amend, bitmap, snapshot-list, rebase, commit and compare are not added: they are case-driven or qcow2-only matrices, not per-image ones, and nothing in instar reads a per-image baseline for them for a VHDX source.

    3. instar-testdata pushes only once the instar branch is finished, and the red window is accepted, not engineered around.     Risks and mitigations¶

    • The --image or --case filter silently matches nothing, and a green run generates no baselines. It would be invisible: the generator prints per-version progress and exits 0 either way. Mitigation: decision 1 requires both filters to exit non-zero on a no-match, and 10a's verification is a file count, not a successful exit. The management session re-runs one filtered invocation and checks git status --porcelain | wc -l itself.
    • A regeneration moves an info profile boundary and breaks the hardcoded matrix. tests/test_version_detection.py:268-276 names six profiles. Planning measured that phase 2's fixtures should not move a boundary, but measured on one fixture. Mitigation: 10d captures the profile list before and after and stops rather than committing if it changed; 10e has an explicit conditional step to update the matrix with measured names.
    • The red develop window outlasts one queue cycle. Decision 3 accepts about 76 minutes. If the instar PR needs a second round the window doubles, and other people's PRs fail meanwhile for a reason that is not theirs. Mitigation: nothing is pushed to testdata until 10e has run green locally against the local testdata tree; the push and the PR are a single management-session action; and if the PR does go red, reverting the testdata commit is one git revert and a push, which is the documented fallback, not a judgement call.
    • The validator passes because it checks nothing. A validator that resolves names wrongly reports "0 mismatches" over an empty comparison, which looks exactly like success -- and this phase exists because this family of bug has shipped twice. Mitigation: 10c must report files-compared counts (an empty comparison is visible as a zero), and must demonstrate a caught corruption and a caught deletion. The management session repeats one of the two deliberate corruptions.
    • A new create case diverges from qemu and gets masked. The cheapest way to make TestCreateBaselineMatrix green is a KNOWN_WRITER_DIVERGENCES entry, which would silently retract part of phase 7 or phase 3. Mitigation: decision 7 forbids adding entries in this phase, and 10e's brief says a divergence is a finding to escalate.
    • The monolithicFlat baseline embeds a host path and is unusable on another machine. Mitigation: 10a fixes the substitution and verifies it by hand on one version; 10b greps the generated baseline for /tmp and for the username before committing.
