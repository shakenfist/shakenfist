    Multi-extent VMDK phase 4: the descriptor emitter¶

    Status: Complete¶

    Master plan: PLAN-multi-extent-vmdk.md.

    Planning effort¶

    Medium. Every byte this phase emits was measured by phase 1 and is committed in tests/golden/qemu-create-pins.json, and the crate that should hold the emitter already holds three like it, so neither the target nor the home is a judgement call. Two things kept it above mechanical: the buffer contract the existing emitters carry is unusual and load-bearing (decision 2), and the oracle this phase tests against is a hand-copied literal, which makes "the emitter agrees with the test" worth nothing unless something independent ties the literal to the pin (decision 8).

    The master plan's Planning effort paragraph did not name phase 4 at all. Corrected at source to medium as part of this phase's planning commit.

    Decisions already taken by the operator¶

    From the master plan, resolved 2026-11-16: sequential extent rotation rather than simultaneous output devices (question 1), and the read-side ceiling inside this plan as phase 3 (question 2).

    Neither binds this phase. Rotation is a write-path mechanism and this phase writes no bytes to any file; phase 3 is landed and its parser is what reads this phase's output back in a test.

    Open question 3 is not resolved, and this phase turns on it. It asks whether multi-extent output emits qemu's ddb.* lines; the master plan recommends yes for the new subformats and no retrofit of the old ones, and the phase intent says phase 4 "carries the ddb.* decision from open question 3". Decision 4 below adopts that recommendation and states its cost. It is the first item of the back brief, because reversing it later is six lines of emitter and one table of literals, and reversing it after phase 5 ships a user-visible subformat is a changed output format.

    Open questions 4 and 5 -- extent path derivation and whether instar imposes an extent-count limit -- are reserved to the operator in the master plan and are deliberately not needed here. Decisions 5 and 6 scope the emitter so that it answers neither: it is handed a decomposed stem and formats names from it, and it imposes no count of its own. Phase 5 is the phase that cannot start until both are resolved.

    Scope¶

    In:

    • src/crates/vmdk: a no_std, panic-free emitter for the twoGbMaxExtentSparse and twoGbMaxExtentFlat descriptor files, including the ddb.* block.
    • The pure function from a virtual size to a split geometry: extent count, each extent's sector count, and the CHS triple the ddb.* lines carry.
    • The -s%03d / -f%03d extent-name rule, formatted from a decomposed output stem.
    • Unit tests whose expected bytes come from the pinned qemu descriptors, and a check that ties those literals to the pin file.
    • Reading the emitter's own output back through phase 3's parse_descriptor_extents.
    • Filing the ddb.* retrofit issue the master plan's open question 3 asks this phase to file, and the issue for the four duplicated descriptor builders the survey found.
    • docs/vmdk/vmdk-extents.md: the naming rule and the geometry derivation, as format reference.

    Out:

    • Any create or convert wiring, any CLI subformat= value, any CreateConfig change. The emitter ships with no production caller; phase 5 is its first.
    • Extent paths on a filesystem, and what happens when a target already exists (open question 4, phase 5).
    • Any instar-side extent-count or size limit (open question 5, phase 5).
    • Sparse extent binary headers, grain directories and grain tables (phases 9 and 10). The survey measured that a split-sparse extent's reserved descriptor region is written as zeros, so no second descriptor is emitted anywhere; see below.
    • Retrofitting ddb.* onto monolithicSparse, streamOptimized and monolithicFlat. An issue, not a change.
    • Unifying the four existing descriptor builders. An issue, not a change.
    • A random CID. instar writes the constant fffffffe everywhere and this phase does the same; the divergence is already documented.
    • twoGbMaxExtent* as a backing file, excluded by the master plan.

    What the survey found¶

    Checked against the tree at 394302f8, with phase 3 landed as 64e6fbc6.

    The bytes are already pinned, and nothing has to run qemu¶

    Phase 1 added fourteen vmdk-multi-{sparse,flat}-* cases to tests/golden/qemu-create-pins.json, over all 80 static builds. Each case records the descriptor text with the CID and extent names replaced by placeholders, the extent names, the extent file lengths, and a parsed structure. The sizes covered are 1 MiB, 2 GiB, 2049 MiB, 4 GiB, 5 GiB and 21 GiB in both subformats -- twelve distinct (size, subformat) pairs -- plus a pre-existing-extent case in each subformat at 5 GiB, which brings it to fourteen. The two existing-extent cases record the same descriptor as the plain 5 GiB case of their subformat, so what they add is the evidence that an obstruction where an extent goes does not change the descriptor.

    Every case has exactly two version groups, split at 6.2.0, and the only difference is one line: ddb.toolsVersion = "2147483647". tests/test_qemu_create_pins.py already asserts that this is the one boundary (VMDK_MULTI_LAST_OLD, VMDK_MULTI_FIRST_NEW), so a future qemu change in this area fails a test rather than going unnoticed.

    The 6.2.0-and-later descriptor, for 5 GiB sparse:

    # Disk DescriptorFile
version=1
CID=<hex>
parentCID=ffffffff
createType="twoGbMaxExtentSparse"

# Extent description
RW 4194304 SPARSE "<stem>-s001.vmdk"
RW 4194304 SPARSE "<stem>-s002.vmdk"
RW 2097152 SPARSE "<stem>-s003.vmdk"

# The Disk Data Base
#DDB

ddb.virtualHWVersion = "4"
ddb.geometry.cylinders = "10402"
ddb.geometry.heads = "16"
ddb.geometry.sectors = "63"
ddb.adapterType = "ide"
ddb.toolsVersion = "2147483647"

    The flat form differs in four places and no others: createType, the FLAT keyword, a trailing 0 start offset on each extent line, and -f%03d in place of -s%03d.

    The geometry rule, including the part the plan did not raise¶

    heads is always 16 and sectors always 63. cylinders is total_sectors / (16 * 63), truncating. Confirmed against five pinned sizes: 2048 sectors gives 2, 4194304 gives 4161, 4196352 gives 4163, 8388608 gives 8322, 10485760 gives 10402, 44040192 gives 43690.

    The question the master plan did not raise is whether qemu clamps cylinders to the 16-bit 65535 a real CHS geometry allows. It does not, and no new measurement was needed to find out: phase 2's custom/format-coverage/vmdk-split-sparse-33g.vmdk is qemu-written and carries ddb.geometry.cylinders = "68656", which is exactly 69206016 / 1008. So the derivation is a plain truncating divide with no cap, and the 33 GiB fixture is a committed witness for a value past the 16-bit boundary.

    The buffer contract is deliberate, documented and in use¶

    All four existing descriptor builders share one put closure that advances its cursor past the end of the buffer but copies only when the write fits, so the return value is the length the descriptor needs whatever buffer it was given. That is snprintf semantics, and it is relied on: vmdk_flat_descriptor in src/vmm/src/main.rs:16988 calls vmdk::build_flat_descriptor(&mut [], ...) to measure, allocates, and calls it again to write, with a comment saying so.

    This matters because the one thing a split descriptor makes unbounded is its length. A caller that writes without measuring gets a silently truncated descriptor today for a fixed-length descriptor that always fits; for 64 extents it gets a file that names some of its extents.

    "One emitter used by both" is not what this phase inherits¶

    The master plan's phase intent says "one no_std, panic-free emitter in the crates that writes a multi-extent descriptor from a geometry, used by both create and convert". The second half describes a destination, not a starting point. Today there are four builders in two crates:

    Builder File Writes
    build_descriptor src/crates/vmdk/src/lib.rs:226 monolithicSparse
    build_flat_descriptor src/crates/vmdk/src/lib.rs:266 monolithicFlat
    build_streamoptimized_descriptor src/crates/vmdk/src/lib.rs:186 streamOptimized
    build_vmdk_descriptor_with_backing src/crates/create/src/lib.rs:1024 either sparse kind, with a parent

    The fourth re-implements the first; its own comment says why ("the stock builder hardcodes parentCID=FFFFFFFF and has no hook for the parent filename"), and it carries a second copy of format_u64 named format_u64_decimal. Unifying them would touch every VMDK instar writes and is not this phase's business. Step 4e files it.

    qemu writes the same ddb.* block for monolithicFlat¶

    Which means instar's monolithicFlat output diverges from qemu's today, not merely inconsistently with its own future output. vmdk-flat-64M pins the full ddb.* block with cylinders = "130", by the same rule. The divergence is documented, in docs/quirks.md ("VMDK descriptors omit qemu's DDB lines") and in docs/create.md's Future work, and PLAN-bat-population.md carries it as future work too.

    What does not exist is a GitHub issue: gh issue list --search ddb --state all returns nothing. So the issue open question 3 asks this phase to file is genuinely still to file, and the retrofit that eventually closes it has to rewrite that docs/quirks.md section as well as the descriptors.

    The naming rule already has an implementation to factor¶

    vmdk_flat_extent_path in src/vmm/src/main.rs:16934 implements qemu's filename_decompose (cited to block/vmdk.c:2279-2316): take the basename after the last /, split it at its last ., and join <prefix> + suffix + <postfix>. It also refuses a name that is not UTF-8 or that holds ", CR or LF, which qemu writes verbatim -- instar's addition, because the descriptor records the name as a quoted string on a line of text.

    The split rule is that same decompose with -s%03d or -f%03d in place of -flat. So this phase factors a rule rather than inventing one, and the refusal above is a property phase 5 inherits, not something to re-decide.

    %03d is a floor, not a cap¶

    Phase 1's probe for open question 5 measured four builds writing 1000 extents at 2000 GiB with the thousandth line verbatim RW 4194304 SPARSE "image-s1000.vmdk", and 16384 extents at 32 TiB. So the width is a minimum and the index runs past three digits unpadded.

    A split-sparse extent's reserved descriptor region is zeros¶

    Measured for this plan, on vmdk-split-sparse-33g-s001.vmdk: the VMDK4 header gives descriptor_offset_sectors = 1 and descriptor_size_sectors = 20, and all 10240 bytes of that region are zero. qemu reserves the space in every split-sparse extent and writes nothing into it. So the only descriptor text a split image contains is the standalone descriptor file, and this phase's emitter is never asked for a second, embedded copy. Phase 10 needs the same fact when it writes those headers.

    Rust-side golden literals are the house pattern, and unguarded¶

    Decisions¶

    1. The emitter lives in src/crates/vmdk, as one function over a kind parameter. build_split_descriptor(buf, offset, &SplitLayout) -> usize, with the subformat a field of the layout. The two subformats differ in four places and nowhere else, so two functions would be two copies of the ddb.* block and the extent loop. The crate is already the home of the other three emitters, it is no_std with no alloc, and both the host (phase 5) and the guest (phases 10 and 11) can link it.

    2. Keep the measure-then-write buffer contract; do not return a Result. The function returns the length the descriptor needs, and copies only the prefix that fits. Three reasons: it is the contract of all four existing builders, so a fifth with different semantics would leave two contracts in one crate; it is what the one live host caller is written against, with a comment saying so; and snprintf semantics are a correct API rather than a workaround -- the hazard is a caller that ignores the return value, not the contract.

    Amended at the back brief, 2026-11-24: keep snprintf semantics for now, and file an issue to revisit whether the interface should be done the idiomatic Rust way -- a Result, or a writer the caller feeds -- across all five builders rather than only the new one. Step 4e files it, and this plan does not pre-empt its answer.

    The cost is real and worth stating. Today no caller can get it wrong, because every descriptor is a fixed length that fits any buffer anyone would pass. A split descriptor is as long as its extent count makes it, so from this phase on a caller that does not measure writes a file that names some of its extents and no error is raised. The mitigations are in the definition of done: the written length must equal the measured length at 1, 2, 17 and 1000 extents, a test must assert that a one-byte-short buffer produces the needed length rather than a panic or an overrun, and phase 5's plan must state that its caller measures first.

    Note what "truncated" means here, because the first draft of this plan got it wrong and step 4b's tests corrected it. A put copies all of its bytes or none of them, so a short buffer does not hold the first len - 1 bytes of the descriptor: it holds every line that fitted whole, and nothing of the line that did not. That is the behaviour of all four existing builders too. It makes a silently truncated descriptor more likely to parse as valid, not less, since it ends at a line boundary -- which is a reason the caller must measure, not a reason to prefer byte-level truncation.

    3. Geometry is computed from the size, not passed in. split_layout(virtual_size_bytes, kind) -> SplitLayout yields the total sector count, the extent count, each extent's sector count, and the CHS triple. All of it is a pure function of the size, every pinned case agrees, and letting a caller supply cylinders invites two callers deriving it differently -- which is how instar came to have four descriptor builders. heads and sectors are the constants 16 and 63; cylinders truncates and is not clamped, which the 33 GiB fixture witnesses at 68656.

    4. Emit the 6.2.0-and-later ddb.* set, including ddb.toolsVersion = "2147483647", unconditionally. This adopts the master plan's recommendation on open question 3.

    Reasoning: 76 of the 80 pinned builds write that set, the pinned 10.2.0 build is the oracle this plan targets throughout, and the descriptor is compared byte-for-byte, so omitting six lines means either a weaker oracle or a documented divergence on output that does not exist yet.

    Not making it conditional on a version, although instar has a version-profile mechanism: resolve_output_profile in src/vmm/src/main.rs:14063 says it is "shared by every subcommand whose output is version-dependent -- info, map and snapshot". That mechanism shapes reported output, not written image bytes, and create does not take --qemu-version at all. Inventing a first image-bytes version knob for six lines would be a larger change than this phase, and a worse default than matching current qemu.

    The cost: instar's VMDK descriptors become inconsistent with each other -- the new subformats carry ddb.*, the three old ones do not -- until the retrofit lands. The master plan already accepts this and assigns the documentation to phase 17. A second, smaller cost: output for a 6.0.x or 6.1.x target carries one line that version never wrote. Nothing in instar targets a qemu version for written bytes today, so there is nothing for that to break, but it is a divergence and phase 17 should list it rather than only the ddb.* inconsistency.

    5. The emitter derives extent names from a decomposed stem. It takes prefix and postfix byte slices -- the output basename split at its last dot, exactly as vmdk_flat_extent_path splits it -- and formats <prefix>-s001<postfix> itself. It is handed neither a path nor a list of names.

    Reasoning: the name is a qemu-parity fact that appears in the bytes this function emits, so it belongs next to them and should be testable without a filesystem. The path the caller opens, and what the caller does about a name that is not UTF-8 or that holds a quote, stay with the caller -- which is open question 4, and phase 5's.

    6. The emitter imposes no extent-count limit. The index formats at minimum width three, zero-padded, and runs past three digits unpadded, matching the measured image-s1000.vmdk. Any instar limit is open question 5 and belongs where a refusal can be raised before a file is opened, which is phase 5.

    There is a second consequence, found by step 4b: the emitter loops once per extent, so a u64::MAX virtual size means 2^33 iterations. It neither panics nor overflows, but it would run for hours. Phase 5's caller therefore has to bound the size before it measures, not only before it writes -- the measuring pass walks every extent too. That is the same refusal open question 5 asks phase 5 to decide, so it costs phase 5 nothing extra, but it is a correctness requirement on the caller rather than a nicety.

    Note the asymmetry this leaves, deliberately: instar will be able to write a descriptor with more extents than it can read, because the read side is capped at MAX_CHAIN_EXTENTS (64) by the size of the guest config page. Phase 5 is where that becomes a user-visible decision and it is listed in the master plan's Future work. It is recorded here so phase 5's planner does not meet it as a surprise.

    7. CID=fffffffe, as every other instar VMDK. qemu writes a random CID, which cannot be matched; the pin replaces it with a placeholder for exactly that reason. Parity with instar's own output is worth more than a pretence of parity with qemu's randomness, and the divergence is already documented in docs/quirks.md against #566.

    8. The oracle is the pin file, copied into Rust literals, with a new Python guard tying the two together. The literals follow the house pattern and its stated reason. The guard is a Python test that, for every vmdk-multi-* pin case, re-derives the descriptor text the 6.2.0-and-later group records and asserts it appears verbatim in the Rust test source.

    Reasoning: without it, the phase's whole oracle is a copy a sub-agent made, and the most likely way for this phase to be wrong is for the same agent to derive both the emitter and its expectations from the same misreading. The guard is the only part of the verification that an emitter bug cannot also satisfy. Scoped to the split literals; extending it to the VHDX literals it would also fit goes to Future work rather than growing this phase.

    9. No user-visible change, so no user documentation beyond format reference. docs/vmdk/vmdk-extents.md gains the split naming rule and the geometry derivation, because they are facts about the format that a human reading that page wants. docs/quirks.md, docs/create.md and docs/format-coverage.md change in phase 5, when a split subformat first becomes reachable from the command line. There is no changelog to add an entry to: the repository keeps none, and a no-changelog pre-commit hook over git ls-files stops one coming back, because older plans in docs/plans/ still say to write one. Release notes go on the GitHub release; see "Releases" in docs/development.md.
