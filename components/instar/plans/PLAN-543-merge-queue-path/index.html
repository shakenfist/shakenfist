    PLAN-543: Cut the merge queue's critical path¶

    Status: Complete¶

    Every step in the Execution table is done. Steps 1 to 6 and 8 landed in #671 (merged as eea59b99), with step 5's measurement recorded under Execution ("The step-5 measurement"). Step 7's two halves landed in #673 (merged as 673233f3), the second once the conductor gate cleared; the step 7 row records both and the evidence for the gate. The post-merge work is recorded under Execution ("The step-7 measurement" and "The second push audit").

    A red nightly that was not the disk. On 18 Oct the six VHD tests this plan moved off the merge queue failed on all seven distros (#780 to #786), each in a fraction of a second with instar info returning Invalid argument (os error 22). That was the first nightly to read the testdata disk, and the merge queue cannot see those six tests, so the disk was the obvious suspect -- and wrong. The cause was #778: Debian's 6.12.113 kernel, which reached the CI runner images in the same window, rejects KVM_SET_SREGS when the VMM sets no guest CPUID. The evidence is a pair of nightlies that both read the disk: run 39080337878 on 81423f22 failed every leg, and run 39178562519 on b0e1f249 passed every leg (six tests in 662 s on Debian 13), with only #779 and #788 -- the #778 fix -- between them. It is recorded here because the coincidence will recur: a nightly-only test set means a regression that lands alongside an infrastructure change is first seen together with it.

    other half.

    Situation¶

    Issue #543 records a run of checks_timed_out ejections of green pull requests from instar's merge queue -- five of them tabulated in its 2026-10-10 update. The cause was found that day and fixed in private-ci#66: the provisioner walked CI_IMAGES then CI_SIZES in declaration order, so any queued xs/s/m/l job took the fleet's free slot ahead of every xl job, however long the xl job had waited. Oldest-queued-first replaced that.

    PR #652's ejection on 2026-10-12 was the first after the fix, and so the measurement #543 said instar's CI changes were on hold for. The fix did what it was designed to do, and it is not enough. Queue wait per xl matrix job, before (15 merge groups, 09-30 to 10-09) and after (6 merge groups, 10-10 to 10-12):

    Before After
    Jobs measured 105 40
    Median wait 90 min 121 min
    p90 wait 352 min 188 min
    Max wait 524 min 236 min
    Never scheduled 0 2

    Fair ordering removed the starvation -- p90 nearly halved, the worst case more than halved -- but added no capacity, so the distribution converged on the mean rather than shifting down, which is why the median rose. Throughput is unchanged. The same convergence now shows on the front of the critical path, where the two debian-13, s jobs used to clear in about three minutes:

    s job wait Before After
    Median 3 min 11 min
    p90 10 min 54 min
    Max 49 min 99 min

    652's run holds both of the worst post-fix observations:¶

    build-and-test waited 99 minutes and package-build 54, so 153 of its 362 minutes were spent before the matrix was even queued. The run itself finished success 58 minutes after the ejection, 420 minutes after its merge group was created.

    What the survey found: there is no data copy to cache¶

    The first thing to check was whether each leg pays a large fixed cost before testing -- a testdata clone, an image pull, a package install -- that a cache could remove. It does not. Step times from the Debian 12 leg of run 38206699440:

    Step Time
    Set up job, checkout 7 s
    tools/ci/prepare-testdata.sh 88 s
    Resparsify test images 6 s
    tools/ci/install-docker.sh 21 s
    Download the package artifact 5 s
    Run the suite on debian:12 2539 s

    Inside that last step, pulling debian:12 and installing the package plus its test prerequisites -- 418 packages, because qemu-utils drags in most of a desktop -- accounts for about three minutes. The suite itself reports Ran: 3588 tests in 2349.5103 sec.

    So about three minutes of a forty-two minute leg is setup. A perfect cache of every byte fetched before the suite starts would buy two minutes. This is not where the time is.

    The testdata step deserves its own note, because the obvious fix for it is already written and dead. tools/ci/prepare-testdata.sh has two branches: update a cache at $TESTDATA_CACHE (/srv/ci/cached/instar-testdata) in place, or clone fresh into the workspace. The job log takes the second every time --

    No cache at /srv/ci/cached/instar-testdata, cloning fresh...
Cloning into '/srv/ci/_work/instar/instar/instar-testdata'...
Updating files: 100% (769672/769672)
Filtering content: 100% (308/308), 7.46 GiB | 133.88 MiB/s, done.

    -- because the sfcbr runners are fresh VMs, so nothing persists at that path and the update-in-place branch never fires. Each leg checks out 769,672 files and pulls 7.46 GiB of git-LFS content, taking a median of 82 seconds across 28 legs (72 s to 129 s).

    Seven legs per merge group is about 52 GiB of LFS transfer, and the five pull-request jobs that also prepare testdata add roughly 37 GiB per pull request. That is a real cost and worth removing, but it is not this plan's cost: the legs run in parallel, so it is about 80 seconds of the critical path. Recorded under Deferred work, where it belongs -- it is a runner-image change, not an instar change.

    Where the time is: one worker, and six tests¶

    The suite runs at --concurrency 4. Per-worker figures from the same leg, with the execute totals derived from the per-test lines and agreeing with stestr's own Worker Balance block to the second:

    Worker Execute Wall
    0 2197 s 39:09
    3 1490 s 24:53
    2 1367 s 22:49
    1 913 s 15:14

    The leg's wall time is worker 0's wall time, and workers 1 to 3 finish between 14 and 24 minutes earlier and then idle. Even distribution of the 5967 seconds of execute time would be 1492 seconds per worker, so roughly twelve minutes of every leg is scheduling imbalance rather than work.

    The imbalance has a single cause. Worker 0 drew all three VirtualPC tests:

    Test Time Worker
    TestConvertVhdToQcow2Roundtrip.test_virtualpc_vhd_qcow2_roundtrip 609 s 0
    TestConvertVhdToRaw.test_convert_virtualpc_vhd 505 s 0
    TestConvertVhdCompare.test_compare_virtualpc_vhd_vs_raw 310 s 0

    That is 1424 of worker 0's 2197 seconds. tests/.stestr.conf sets only test_path and top_dir, and the stestr repository is created fresh under /tmp in each container, so stestr has no prior timings to bin-pack from and these land wherever the split puts them. The same imbalance appears in a local run of the suite on this host (1520 tests on one worker against 510 on another), so it is systematic, not a property of CI. It has simply never mattered, because the suite takes six minutes locally.

    Those three tests have three Hyper-V siblings, and the six together are half the suite:

    Class Tests Execute
    TestConvertVhdToQcow2Roundtrip 2 1233 s
    TestConvertVhdToRaw (hyperv, virtualpc) 2 1064 s
    TestConvertVhdCompare (hyperv, virtualpc) 2 648 s
    Subtotal 6 2945 s of 5967

    By module, test_convert is 5045 of the 5967 seconds in 248 of 1684 timed tests; everything else in the suite is under a thousand seconds. The remaining 30 tests of the convert-vhd partition are 45 seconds in total.

    The two fixes are the same fix, twice¶

    Removing those six tests changes the per-worker picture to 866 / 808 / 773 / 577 seconds against an even split of 756 -- a worst worker 15% over even, instead of 47% over. The imbalance is caused by the six tests, so the two findings above are one finding. In sequence:

    Worst worker Leg
    Today 2197 s 42 min

    Balancing first does deliver about twelve minutes, because the six tests are still there to be balanced. But once they move, balancing is worth about another ninety seconds.     Why packing is no longer first¶

    The first draft of this plan packed the seven legs into three jobs to cut xl acquisitions from seven to three. That is still a real lever -- with ordering fair, acquisition count is what the critical path is made of -- but it is now second order. At a 42-minute leg, seven legs through instar's effective share of about three slots is three waves, and the matrix stage of run 38206699440 took 235 minutes. At an 18-minute leg it is about 54 minutes for seven legs in three waves against about 48 for three packed groups in one. The gap mostly closes on its own, so packing is a decision to take after the measurement in step 5, not before it. The packing analysis is preserved under Deferred work so it does not have to be redone.

    Mission and problem statement¶

    Get the merge group's critical path far enough under the 360-minute check_response_timeout_minutes that a busy fleet does not eject green pull requests, by removing work from the gate rather than rearranging it. Change which tests gate a merge; change nothing about what is tested, only when.

    Target, with every term measured in step 5 rather than assumed: build-and-test 21 min, package-build 7 min, a matrix leg about 18 min, and seven legs through three slots about 54 min, for a critical path near 85 minutes of work against the 420 observed. The queue wait is not in instar's gift and the capacity direction in #543 remains its complement.

    Decisions¶

    1. Seed stestr with timing data, as a guard rather than an optimisation. Without it the scheduler cannot bin-pack, so any future test over a few minutes recreates the single-slow-worker failure mode, invisibly -- the suite just gets slower. Worth about ninety seconds once Decision 3 lands, and worth having anyway for that reason.

    It must be derived, not hand-maintained. This repository has already been bitten by hand-maintained figures drifting (the mutation harness's case counts drifted three review rounds running, and are now computed). A committed timing file refreshed by the nightly job in Decision 2 satisfies that: the nightly runs the suite anyway, so it can publish the timings it measured.

    1. A nightly cross-distro job, in the shape of differential-fuzz.yml: schedule: plus workflow_dispatch, issues: write, and a failure that files or updates an issue. A nightly whose red is only visible in the Actions tab is not a safety net, so the issue-filing step is part of the job and not a follow-up.

    Settled while building it, and recorded here because the back brief asks for the workflow-file question in writing:

    • Its own file, .github/workflows/nightly-matrix.yml. needs: cannot cross workflow files, and package-build is gated to merge_group || workflow_dispatch, so a scheduled job could not consume its artifact from either side of that boundary. The nightly builds its own packages, as differential-fuzz.yml builds its own binaries. Adding schedule: to functional-tests.yml would also fire every job there whose condition begins always(), starting with can_enqueue.
    • Two shapes of leg, because D1 and D3 pull against each other. D1 assumes the nightly runs the whole suite and can therefore publish the timings it measured; D3 makes it run six tests. Both hold: seven distro legs run the six moved tests, which is the coverage, and one more leg runs the whole suite on Debian 13, which is the measurement. That leg is redundant as coverage and is not there for coverage -- it is the only job left in CI that executes the whole suite in a single stestr repository, so it is the only place the timing file can be derived from. The workflow says so, because a reader will otherwise delete it.
    • The measurement leg does not seed the timings it measures. stestr keeps one duration per test id and only the tests that execute update theirs, so a seeded repository hands back the seeded figure for everything that did not run: a deleted test's duration would live on forever, and a test that silently stopped running would never lose its old one. Setting STESTR_TIMING_OUT therefore turns seeding off for that run, which costs it an unbalanced partition and nothing else.

    • The refresh is a pull request, never a push to develop, and only when the measurement moved materially. "Materially" is defined on each test's share of the suite's weight rather than on seconds, because stestr's bin packing is scale-free: a uniformly slower runner changes every number in the file and not one scheduling decision. One test moving two points of the suite's weight (about 100 seconds, against a worker's quarter share of 25 points), or a tenth of the weight relocating between tests, is material. Everything else is noise, and the file is only a scheduling hint -- a stale one degrades packing gradually and can never make a run wrong -- so the default is silence.

    • The six heavy VHD conversion tests move off the merge gate and run nightly on all seven distros. They are the Hyper-V and VirtualPC roundtrip, to-raw and compare cases.

    This is the decision that costs something, and the cost is real: those conversions are where a distro's qemu-img is most likely to differ from instar, which is close to the matrix's reason for existing. Three things make it the right trade anyway. They already run on every pull request through integration-convert-vhd on debian-13, so an instar-side regression is caught at PR time regardless of this change. The distro axis moves when a distro ships a new qemu, not when instar changes, so a per-merge cadence is far finer than the signal. And a nightly surfaces a distro divergence within 24 hours, against a status quo where the whole queue intermittently ejects green work and nothing lands at all.

    Only the six move, not the convert-vhd partition: its other 30 tests are 45 seconds, and moving them would buy nothing while making the merge-queue selector harder to read.

    1. The merge-queue matrix gets an explicit selector, and the nightly gets its complement, both expressed as Makefile test-container-* targets like the existing three so that tools/ci/check-test-partition.py reads them from the one place they are defined.

    2. Extend the partition guard to the merge queue and the nightly. It discovers pull-request jobs today, so the six tests staying claimed by integration-convert-vhd keeps it green and it would not notice the matrix selector dropping something no other queue job covers. The silent loss of a whole module from the gate is this plan's worst failure mode and has no symptom -- CI goes green faster. The guard must assert that the merge-queue selector and the nightly selector together cover what the matrix covers today.

    Bugs fixed during this work¶

    • A failed resparsify replaced a good image with a truncated one, and exited zero. Found by comparing the eight inline copies of the step before replacing them with a shared script. Six of the eight ran cp --sparse=always and mv as two unconditional statements, so a copy that failed part way -- ENOSPC being the realistic case on a 7.5 GiB tree -- was followed by an mv that moved the partial file over the original. The step then exited zero, because mv succeeded. The two newest copies had cp && mv and were correct. No copy propagated failure at all: find -exec does not fail on a non-zero child, and a while loop reports only its last command. The shared script takes the &&, adds the failure propagation neither form had, and its self-test asserts that an image survives a failed copy.
    • The partition guard was discovering a prose comment as a CI job, and the comment was one this branch added two commits earlier. The timing-seed explanation in functional-tests.yml contains the words "stestr run", which the guard's job discovery matched as an inline invocation; it then read the following prose as that job's selectors, giving it the bare words so, already, recorded and in. Those match a large slice of the suite, so the guard would have reported a genuinely orphaned test as claimed. Discovery now ignores matches inside YAML comments, with a regression test whose fixture carries the same shape of prose. Worth recording for how it was found: not by reading the guard, but by extending it and watching what it claimed to see.
    • The narrow resparsify skipped images the update's reset had just re-expanded. Found by review of the pull request, and nearly dismissed: the first measurement said git reset --hard leaves a stat-dirty entry alone, and it was wrong because it used the inode as the signal. Git overwrites an existing path in place, so the inode survives a rewrite and reports every file as untouched. With mtime as the signal and an unchanged, clean-stat control beside it, the opposite shows: the reset does rewrite an entry whose content is identical but whose index stat data is stale, and the disk build leaves exactly that state behind because resparsifying is a cp and a mv. Under LFS those files return fully allocated, and no diff of the two trees names them, so the narrow list missed them and the disk quietly gave back part of its saving. prepare-testdata.sh now unions the stat-dirty set into the list -- which costs nothing, the reset having already written them into the overlay -- and warns, because the real fix is a git update-index --refresh on the side that builds the disk. tools/ci/test-testdata-changed-files.sh pins all of it against a real git, including that the tree diff alone would have missed it.
    • A new test passed on this machine and had never once passed in CI. tools/ci/test-testdata-changed-files.sh builds local repositories with git init, and this developer has init.defaultBranch=main set where the runners leave it unset. On a runner the bare repository's HEAD therefore pointed at an unborn master while the push created main, and git clone reports that as "you appear to have cloned an empty repository" -- a warning, not an error -- so the script carried on and failed three assertions later with a confusing find: no such directory. Three rounds of review were reported with "gates green" on the strength of a local run; ci-tooling had been red since the commit that added the file, and the steps after it never ran at all. The test now neutralises GIT_CONFIG_GLOBAL and GIT_CONFIG_SYSTEM, pins every branch name explicitly, and checks the clone produced a tree at the point it clones rather than letting the failure surface downstream. The general lesson is narrower than "run CI": a test whose subject is a tool's behaviour must not inherit that tool's ambient configuration, because the developer's configuration is part of what it is measuring.
