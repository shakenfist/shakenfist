    HTTP input phase 3: the remote backing store¶

    Status: Not started¶

    Master plan: PLAN-http-input.md.

    Planning effort¶

    High. The phase puts a child process inside the lifetime of the privileged one for the first time in instar's history, and the two things it has to get right -- which descriptors cross the exec boundary, and that the child is reaped on every exit path including the panicking ones -- are both the kind of mistake that does not show up in a passing test. Review effort: high for step 3b, the spawn and the reap, which is the step where a wrong answer leaves either a leaked descriptor in an untrusted process or a zombie in every run.

    Decisions already taken by the operator¶

    From the master plan, resolved 2026-11-18:

    1. Open question 3: the cache, the coalescing and the readahead all live in the fetcher. The VMM's read_at stays one round trip, so this phase adds no buffering of its own.
    2. Open question 8: the fetcher is found the way the guest .bin files are -- the executable's own directory first, then /usr/lib/instar/ -- and is packaged at mode 755.

    From phase 2, 2026-11-19, and binding here:

    1. The fetcher takes descriptor numbers, not paths. The privileged side opens the image and the fetcher inherits it. There is no path argument and no fallback that accepts one, because such a fallback is the hole phase 4's confinement would have to leave open.
    2. Nothing the fetcher says to the privileged side is text. A failure is a Status value, and the sentence the user reads is written on this side from that value. The fetcher's stderr is for diagnostics and never becomes part of the protocol.

    Taken when this phase was planned, 2026-11-25: decisions 5 to 14 below.

    Scope¶

    In scope:

    • Recognising a URL on an instar input, accepting file:// and refusing every other scheme by name.
    • BackingStore reading through a fetcher: a third Storage variant wrapping phase 2's FetchClient.
    • The fetcher's lifecycle: spawned before /dev/kvm is opened, handed exactly two descriptors, and reaped on every exit path including a panic.
    • instar info file:///path working end to end through the socket, with output byte-identical to instar info /path.
    • The integration test that proves it, and the mutations that prove the tests bite.

    Out of scope, with where each belongs:

    • Every read-only operation other than info -- decision 5. Phase 7 owns the operation scope and the refusal-by-name policy across the whole CLI surface.
    • Host-side reads of the input that are not the device's bytes -- the VMDK flat-descriptor preflight, the LUKS probe, and metadata.blocks() for the disk-size column. A file:// input still has a path, so these keep working untouched; phase 5 is where the host loses the path and has to route or refuse them (see What the survey found, finding 6).
    • Confinement. No Landlock, no seccomp, no namespaces, no rlimits. Phase 4. This phase only avoids handing the child anything phase 4 would then have to take away.
    • Any network code at all. Phase 5. The grep in the definition of done keeps it out.
    • Progress reporting, deadlines, caps and --spool. Phase 8. The client's existing 60-second reply timeout is what this phase ships with.
    • Issue #932. It was fixed by #945, not by this phase -- see finding 1.

    What the survey found¶

    Five of the master plan's claims about this phase were written before phases 2 and 3 of two different plans landed, and three of them are now wrong. All three have been corrected at source in PLAN-http-input.md and docs/plans/index.md as part of the commit that adds this file; a later step does not need to redo it.

    1. #932 is already fixed, by #945, not by this phase. The master plan said twice -- in the phase 3 section and in Future work -- that this phase "should also fix #932, the virtqueue error the host cannot read that hangs the guest". #945 ("Five failures that never reached the user", merged 2026-11-22 as 8ed88fc9) carries Fixes #932 and the fix: src/vmm/src/io_thread.rs gained FatalIoError, which records the failure and signals the vCPU out of KVM_RUN so the run fails with the recorded reason. The issue is CLOSED. io_thread.rs:107 and its tests name the issue, so the fix is identifiable rather than inferred. Corrected at source.

    2. BackingStore is no longer a plain struct, so the polymorphism is already there. The master plan said it "holds a File, a capacity, a size and a sparse flag, with no enum, trait or indirection -- so 'gains a second kind' means introducing the polymorphism as well as the remote implementation". That was true on 2026-11-19. It stopped being true on 2026-11-21, when #938 (multi-extent VMDK phase 3) landed b6f13211 "Let a backing store span several files", which added a private enum Storage { Single(File), Concatenated(Vec<ConcatMember>) } inside the struct (src/vmm/src/backing.rs:40-53). BackingStore::read_at already dispatches on it and already early-returns for the non-Single arm (src/vmm/src/backing.rs:235-240). So this phase adds a third variant to an existing enum, which touches none of the roughly forty BackingStore call sites. Corrected at source.

    3. The VMM has never spawned a child, and that claim still holds. The only Command::new under src/vmm/src/ is version.rs:166, qemu-img --version, which runs to completion and is read for its output. There is no pre_exec, no waitpid, no signal handling and no descriptor passing anywhere to extend. Everything in step 3b is new code.

    4. Kvm::new() is called at eighteen separate sites in main.rs, one per operation path, not once in a shared setup function. "Started before /dev/kvm is opened, reaped on every exit path" therefore has eighteen places to be got right if it is written as explicit calls, which is decision 7's whole argument for putting the reap in a Drop instead. Not a correction -- the master plan did not say either way -- but it is the fact that shapes the phase.

    5. The integration point in run_info is two lines, because the size already travels separately. VirtioBlockDevice::new(backing, size_bytes, sector_size, ...) (src/vmm/src/virtio/block.rs:131-137) takes the device's size as its own argument rather than asking the backing store for it, and run_info fills it from std::fs::metadata at main.rs:14193-14194 before opening the store at main.rs:14212. A remote input needs nothing more than a different pair of values there. There is also already a helper in the file returning exactly the shape this phase wants -- -> Result<(BackingStore, u64), Box<dyn Error>> at main.rs:5025 -- so the signature is not a novel one.

    6. The host reads the input path for three things besides the device's bytes, and a file:// input keeps all three working because it still resolves to a path: std::fs::metadata(&args.input) for the apparent size and metadata.blocks() for the disk-size column (main.rs:14193-14201), resolve_vmdk_flat_descriptor in the preflight above it (main.rs:14185), and the LUKS probe when --luks-passphrase is given. This is why the phase's end state is worth having as an oracle and also why it is not yet the hard problem: the device's bytes cross the socket, while the metadata does not. Phase 5 is where the path goes away and each of the three has to be routed through the client, derived from the protocol, or refused. Recorded in the master plan's Future work as part of this phase's planning commit.

    7. The fetcher already refuses a non-regular file (src/fetch/src/main.rs:241-245), so the failure mode exists but arrives as a dead socket and an exit code rather than a sentence. Decision 11 puts the refusal on the privileged side first.

    8. Everything phase 2 built is where this phase needs it. FetchClient::read_at(&mut self, offset: u64, buf: &mut [u8]) -> io::Result<()> (client.rs:225) is byte-for-byte BackingStore::read_at's signature; it already zero-fills past the advertised capacity, wholly and partly (client.rs:237-248), exactly as the local store does past the end of its file; capacity() and block_size() are readable (client.rs:178-183); SeqPacketSocket::pair() exists and impl From<SeqPacketSocket> for OwnedFd (socket.rs:397) is how the child's end is handed over. The default reply timeout is 60 seconds (client.rs:71).

    9. No URL or scheme handling exists anywhere in the VMM. A grep for file://, scheme and url across src/vmm/src/*.rs finds nothing outside documentation comments. InfoArgs.input is a String (main.rs:7181), not a PathBuf, so a URL reaches run_info untouched and nothing has to change in the clap definition.

    10. get_binary_dir() already resolves to the right directory for the fetcher, but keys on the wrong file. It searches INSTAR_BIN_DIR, then the executable's directory, then /usr/lib/instar, and takes the first that contains core.bin (main.rs:3877-3897). instar-fetch is installed in /usr/lib/instar/ and built into src/target/release/ alongside core.bin in both cases, so get_binary_path( "instar-fetch") lands correctly today -- but it does so because core.bin is its sentinel, and its doc comment says it returns the directory of "the instar guest binaries (.bin files)". Decision 10 keeps the function and fixes the comment rather than adding a second resolver.

    One thing the survey could not settle: whether kvm-ioctls 0.25 opens /dev/kvm with O_CLOEXEC. The crate source is not on this host (no native Rust toolchain by policy, and the registry lives in a container volume), so step 3b verifies it in the devcontainer and records the answer. The phase does not depend on it either way -- decision 6 orders the spawn before the open, which costs nothing and holds regardless -- but it decides whether that ordering is the only protection or a second one.

    Decisions¶

    1. Only info accepts a URL in this phase. The master plan's phase 3 line says "the read-only operations accept a URL", plural, while its end state names one: instar info file:///path working end to end. This phase does the second. The mechanism it builds is a helper any operation can call, and phase 7 -- which already owns "URLs accepted only by read-only operations and refused by name everywhere else" -- extends acceptance to the rest in one place with one policy.

    This is the decision most likely to be argued with, so the argument against it, put properly: wiring the other read-only operations is mechanical once the helper exists, and leaving it undone means instar check file:///x fails with "No such file or directory" until phase 7 lands, which is a worse error than a refusal. The answer to the second half is decision 9, which makes every unwired operation say what is actually wrong. The answer to the first half is that "mechanical" here means eighteen Kvm::new() sites with their own input-opening preambles (finding 4), every one of which would be edited again in phase 7 when the policy lands -- and that none of it would be exercised by anything, because there is no HTTP backend yet and the file:// oracle proves the mechanism once, not six times.

    1. The fetcher is spawned before Kvm::new(). The child cannot inherit a descriptor the parent has not yet opened, so ordering is a guarantee that does not depend on anyone remembering O_CLOEXEC. It is free: nothing in the operation paths needs the VM before the input.

    2. The reap lives in a Drop, not in eighteen call sites. The remote source owns the Child and the FetchClient together, and its Drop closes the socket and then waits for the child. That is what makes "reaped on every exit path" true for the paths nobody writes down -- a ? return halfway through an operation, a panic inside the vCPU loop, a std::process::exit further out (which it does not cover, and decision 8 handles).

    The wait is bounded, because a Drop that blocks forever is worse than a leaked process: close the socket, which makes the fetcher's recv return zero and it exits zero; poll try_wait() for up to two seconds; then SIGKILL and a blocking wait(). A fetcher that needs the SIGKILL is a bug in the fetcher, so that path writes one line to stderr naming the pid and the elapsed time.

    1. A remote input refuses to coexist with std::process::exit. Drop does not run on exit, so any operation wired to a remote input must return through main rather than exiting under it. run_info already does. The definition of done greps for process::exit on the info path to keep it that way, rather than trusting that it stays true.

    2. A URL is recognised by its scheme, and every scheme but file is refused by name. An input matching ^[A-Za-z][A-Za-z0-9+.-]*:// is a URL; file is served, and anything else -- https, http, s3, nbd -- is refused with a sentence naming the scheme and saying instar does not accept it yet. Anything that does not match is a path, exactly as today, so a file called weird:name still opens.

    The refusal is the point as much as the acceptance. Until phase 5 lands, instar info https://example.com/disk.qcow2 would otherwise fail with No such file or directory, which tells the user their file is missing rather than that the feature is not built. One grep-able table of schemes, in one module, is also what phase 5 edits to turn https on and phase 7 edits to vary it by operation.

    1. file:// is parsed by hand, and narrowly. Accepted: file:// or file://localhost, followed by an absolute path. Refused with a reason: a non-empty, non-localhost authority (file://evil.example/x), a relative path, a query, a fragment, and any % escape. No url crate: phase 2's definition of done established that cargo tree -p instar names no new third-party crate, and keeping that property is worth more than percent decoding that nothing yet needs. Phase 5 adds a real URL parser when it adds a protocol that needs one, and it will be parsing in the fetcher where the parse is cheap to get wrong.

    2. The privileged side opens the file, checks it, and refuses first. It resolves the path, opens it read-only, fstats it, and refuses a non-regular file itself -- the fetcher's own refusal (finding 7) is a backstop, not the user's error message. The capacity the device is given comes from the client's init reply, not from that fstat, because that is the number phase 5 will have; the fstat length is asserted against it in a test, which is a free cross-check of the protocol while there is still a local file to check against.

    3. The child gets exactly five descriptors: 0, 1, 2, and the socket and file at 3 and 4. SeqPacketSocket::pair() sets SOCK_CLOEXEC on both ends and Rust's File::open sets O_CLOEXEC, so the two the child needs are placed with dup2 inside a pre_exec closure, which clears the flag on the new descriptor as a side effect of duplicating. The closure calls dup2 and nothing else: it runs after fork in a process that may hold locks it can never release, so it allocates nothing, takes no lock, and formats no string. A test reads /proc/<pid>/fd of a live fetcher and asserts the set is exactly {0,1,2,3,4}.

      Corrected during step 3b: the parent stages both descriptors clear of 3 and 4 before it forks. On the path an operation takes, the image is opened first and gets 3 while the socketpair gets 4 and 5, so the two descriptors the child needs sit on the numbers they have to land on: a dup2 of the socket onto 3 closes the image, and the matching dup2 of the image onto 4 then copies the socket a second time. No ordering of the two calls escapes it, because each call's target is the other's source. So the parent duplicates both onto numbers at or above 5 with F_DUPFD_CLOEXEC first, which leaves the closure the two dup2 calls this decision requires and nothing more, and lets exec close the staged copies by itself. The child's stdin and stdout are /dev/null rather than inherited for the same reason the socket carries no text: a hostile child holding instar's stdout could write into a document the user parses. Its stderr is inherited, per decision 13.

    4. The fetcher's stderr is inherited. In this phase the only peer the fetcher has is instar itself, so the one-line-per- refused-request rate the master plan warns about is set by the VMM's own requests and is bounded by them. Phase 5 is where the bytes start coming from a server, and phase 8 owns the user-facing failure surface; the master plan's Future work records that whatever routes this stderr into a log then owns a rate a peer sets. Inheriting also means a fetcher diagnostic is visible in a failing test's output, which is worth a lot in the phase that debugs the mechanism for the first time.

      Corrected during step 3d's review, on the operator's call: the child's stderr follows the caller's --verbose. Inherited unconditionally it is not only a diagnostic channel, because the fetcher says two things on a run that goes well -- what it is serving, and that its peer closed the socket -- so every instar info file:///path printed two lines of internal chatter that the same command on a local path does not print. Measured on a 721 KB qcow2: two lines on stderr for the URL, none for the path, stdout byte-identical either way. The tests still ask for the diagnostics, which is where the reasoning above holds, and an operation passes its own verbosity. Nothing is lost on a failure: the privileged side writes those sentences itself, from a status rather than from the child's text.

    5. A remote store refuses writes rather than silently dropping them. Storage::Remote makes write_at return an io::Error naming the input as read-only, is_sparse() false, and size() the advertised capacity. Nothing in this phase can reach write_at -- the device is built read-only -- so the refusal is there for phase 7, when an operation with an output gets a remote input and a wrong turn would otherwise write into a None.

      Corrected during step 3c's review: sync succeeds, it does not refuse. This decision originally refused both. A guest's VIRTIO_BLK_T_FLUSH reaches BackingStore::sync through the FLUSH arm of VirtioBlockDevice::process_request, which -- unlike the OUT arm beside it -- has no read_only guard, and a read-only local store answers it by fsync-ing a descriptor with nothing dirty, which succeeds. Refusing on a remote store would therefore make a device fail a request the same device backed by a local file satisfies, which is the one divergence this phase exists to avoid. Nothing on this side buffers a byte that a success could be lying about: the protocol only reads. The guest's flush() in src/core/src/virtio.rs is what sends it, and bench carries an ERROR_IO_FLUSH, so this is reachable code in the operations phase 7 adds rather than a hypothetical.

    Risks and mitigations¶

    Risk Mitigation
    A Drop that blocks forever: the fetcher ignores the closed socket and wait() never returns, so every instar run hangs at the end instead of exiting Decision 7's bounded wait -- two seconds of try_wait(), then SIGKILL. Step 3b's test asserts the child is gone within the window, so the bound is tested rather than assumed. The management session reads that test, because it is the one test here whose absence would not fail anything
    A zombie per run: Drop is skipped on a path nobody wrote down The Drop is the mechanism, not a call site (decision 7), so the paths that need no author are covered. The one it does not cover is std::process::exit, which decision 8 greps for on the info path
    A descriptor the child should not have crosses the exec -- the worst outcome in the phase, because phase 4 then confines a process that already holds it Decision 12 plus step 3b's /proc/<pid>/fd test, which asserts the whole set rather than the absence of one descriptor. The ordering of decision 6 means /dev/kvm is not open yet whatever O_CLOEXEC says
    pre_exec does something unsafe between fork and exec -- allocates, takes a lock, formats an error -- and deadlocks a run under load, rarely The closure is dup2 and nothing else, which is the review item for step 3b. A diagnostic in there is the specific thing to reject
    The phase proves less than it looks like it proves, because a file:// input still has a local path and the host still stats it Said plainly in the scope and in finding 6, and recorded in the master plan's Future work for phase 5. What this phase proves is the mechanism: the device's bytes cross the socket. That is what makes it the oracle for every later phase, and it is worth having for that alone
    instar info file:///x and instar info /x differ in some field nobody checks The definition of done is byte-identical stdout in both output formats, over a spread of fixtures, which is a stronger claim than any field-by-field check and cheaper to write
    The merge-queue distro matrix only runs in merge_group, so a matrix-only failure cannot be caught on the pull-request gate Nothing in this phase can be matrix-specific except the /proc test, which is Linux-only and so is instar. The run still exits non-zero, so nothing passes that should fail, and it is not new -- TestInfoMultiFileVmdk and the chain tests use subTest the same way -- but the guard cannot classify a failing run whose failures came out of a subTest, only a passing one. Worth knowing before reading a red CI log and concluding a worker died.
    • The comparison carries the exit status and the output's length. Two failed runs produce two empty streams that compare equal, so each of the three spellings is asserted to exit 0 and to have printed something as part of the comparison, not in a separate test. The removed-staging mutant is what this caught: every URL run exited 1 with an empty stdout, which a bare equality of stdout would have passed.
    • The two streams are kept apart. test_a_default_run_is_silent_on_stderr_either_way asserts a default run says nothing on stderr for the path and for both URL spellings, which is what stops decision 13's gating regressing. A comparison of the two streams combined would both hide that and break under --verbose, where the fetcher's two lines are there by design.

    The capacity's source is unkillable in this phase, and no test was written to pretend otherwise. For a file:// input the two expressions are the same number by construction: the fetcher's capacity is metadata.len() of the descriptor it was handed, and the host's metadata is a stat of the same file moments earlier. Swapping one for the other changes no byte of output, so no comparison of outputs can see it. Measured rather than argued: with the mutation applied, the five integration tests pass (Ran: 5, 0 failed) and make test-rust passes 3129 tests, the same counts as the unmutated tree. The only way to make them differ is to grow the file between the stat and the spawn, which is a test whose only purpose would be to fail.

    What enforces the choice instead is two things. First, fetch::tests::the_advertised_capacity_is_the_hosts_file_length asserts the equality directly, which is the cross-check decision 11 asked for -- it is a statement about the protocol, and it is worth more than a test of which expression run_info happens to use. Second, in phase 5 there is no metadata to fall back on: an input with no local path cannot be stated, so the mutation will not compile there, and the only size available is the advertised one. The decision is therefore load-bearing for the phase after this one rather than for this one, and recording it as a survivor is the honest result.

    Back brief¶

    Before executing any step of this plan, please back brief the operator as to your understanding of the plan and how the work you intend to do aligns with that plan.

    Three gates, all cheap to agree and expensive to redo:

    1. Decision 5, info only. Agree it before step 3a, because it is the shape of the whole phase and the one a reviewer is most likely to want widened. Widening it later is additive; narrowing it after six operations are wired is not.
    2. Decisions 7 and 12 together -- the reap in a Drop and the two descriptors at 3 and 4 -- agreed at the end of step 3b before 3c and 3d build on them. This is where a wrong answer is expensive: phase 4 confines the process this step spawns, and a descriptor that crosses the exec by accident is a hole the sandbox is then built around.
    3. Decision 9's refusal table, agreed before step 3d wires it in. It is the user-visible surface of a feature that does not exist yet, phase 5 turns a row of it on and phase 7 varies it per operation, so the shape of the table matters more than any sentence in it.
