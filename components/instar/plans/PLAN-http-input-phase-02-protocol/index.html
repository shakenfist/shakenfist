    HTTP input phase 2: the fetch protocol and a file-backed fetcher¶

    Status: Not started¶

    Master plan: PLAN-http-input.md.

    Planning effort¶

    High. Nothing here is mechanical. The phase introduces the only new untrusted parse in the privileged process, it needs a socket type Rust's standard library does not provide, and every layout and vocabulary choice it makes becomes a compatibility surface that phases 3 to 6 build on and that tests will assert against. Review effort: high for steps 2a and 2d, which are the parser and the adversarial tests respectively.

    Decisions already taken by the operator¶

    From the master plan, resolved 2026-11-18:

    1. Open question 1: a plain framed protocol that borrows virtio-blk's model and not its mechanism. No shared memory, no virtqueue over memfd, no real NBD, no serialisation library -- #[repr(C)] headers with explicit bounds checks. The fetcher gets one socket and nothing else.
    2. Open question 2: SOCK_SEQPACKET, 64 KiB default block size, with a ceiling negotiated at init rather than assumed. The survey below corrects the number this question quoted.
    3. Open question 3: the cache, the coalescing and the readahead all live in the fetcher. The VMM's read_at stays one round trip.
    4. Open question 8: the fetcher is found the same way the guest .bin files are -- the executable's own directory first, then /usr/lib/instar/ -- and is packaged at mode 755.

    Taken when this phase was planned, 2026-11-19: decisions 5 to 12 below.

    Scope¶

    In scope:

    • A new host-side library crate holding the wire format: the #[repr(C)] headers, their encode and decode with explicit bounds checks, the typed status vocabulary, and the SOCK_SEQPACKET socket type.
    • instar-fetch, a workspace binary that serves a single file over that protocol and contains no network code at all.
    • The VMM-side client, with a read_at-shaped API, so that phase 3 wires in something that has already been tested rather than something written for the first time at the point of integration.
    • A libFuzzer target for the decoder, registered in all three lists tools/ci/check-fuzz-targets.sh compares.
    • The build and packaging changes that make make instar produce the fetcher and the .deb/.rpm ship it.
    • docs/crates/fetch-protocol.md, following the one existing page in that directory.

    Out of scope, with reasons:

    • Anything that reads a URL. No scheme parsing, no file://, no CLI surface on instar at all. Phase 3 owns the CLI and BackingStore; this phase's fetcher takes file descriptors, not names.
    • BackingStore itself. The client is a standalone type in this phase. Making BackingStore polymorphic is phase 3's first act and the survey found it is a larger change than the master plan implies.
    • Process lifecycle: spawning, reaping, supervision, exit paths. Phase 3. This phase's tests spawn the fetcher themselves, which is not the same thing as the VMM owning one.
    • Confinement. Phase 4. Decision 10 below is chosen partly to make phase 4 cheaper, but installs no sandbox.
    • Several requests outstanding. The wire format carries request ids and permits out-of-order replies from day one (decision 11), so that phase 6 needs no protocol change; the client issues one at a time and the fetcher is single-threaded.
    • A reason string on the wire. Decision 8 refuses one, and says why.

    What the survey found¶

    Read against a8387ffe on 2026-11-19. Four of the master plan's claims about this phase were wrong or imprecise, and three of them change what the phase does. Everything here was corrected at its source in the same commit that added this file, so a later step need not redo it.

    The datagram ceiling is not what open question 2 says¶

    The question states that "the measured wmem_max of 212992 caps a single datagram near 256 KiB here". Measured on this host with an AF_UNIX/SOCK_SEQPACKET socketpair:

    Condition SO_SNDBUF Largest single datagram
    Fresh socketpair, untouched 212992 212960 (208.0 KiB)
    After setsockopt(SO_SNDBUF, 4 MiB) 425984 425952 (416.0 KiB)

    So the claim is wrong in both directions. At the default, 256 KiB does not fit -- the ceiling is 208 KiB. After an explicit setsockopt it does, because the kernel clamps the requested value to wmem_max and then doubles it, giving 2 * wmem_max - 32. Neither number is derivable from wmem_max by inspection, and a host with wmem_max of 65536 would cap a datagram at 128 KiB - 32 even after asking for more.

    This is why decision 6 derives the ceiling from the SO_SNDBUF the kernel actually granted rather than from any sysctl, and why 64 KiB is the default: it is the only size that fits everywhere without asking for anything.

    Rust's standard library has no SOCK_SEQPACKET¶

    std::os::unix::net offers UnixStream (SOCK_STREAM) and UnixDatagram (SOCK_DGRAM) and no way to ask for anything else. Neither nix nor socket2 appears in src/Cargo.lock, so a SEQPACKET socket means either a new third-party dependency in the privileged process or a libc::socketpair call behind a safe wrapper. libc 0.2 is already a dependency of instar, and src/vmm/src/ioevent.rs is the established pattern in this repository for exactly this shape -- a raw libc call in an unsafe block, wrapped in a type that owns the descriptor. Decision 5 takes that route. The toolchain lives in Docker, so this was not compile-checked on the host; step 2a's first act is to confirm it, and to say so if std has grown the capability since.

    64 KiB does match the guest's request size¶

    This premise held up, and it is worth recording because the arithmetic in the master plan's intent depends on it. One guest request transfers exactly sector_size bytes -- src/core/src/virtio.rs read_sector refuses a buffer shorter than sector_size and do_request moves that many -- and every read-only operation defaults --sector-size to 65536: InfoArgs, MapArgs, CheckArgs, CompareArgs, ConvertArgs, MeasureArgs and CopyArgs all carry #[arg(long, default_value = "65536")] in src/vmm/src/main.rs. MAX_SECTOR_SIZE in src/shared/src/lib.rs:721 is 65536 and is the ceiling, not the request size.

    The 512-byte sector sizes in the tree belong to resize, bitmap, amend and create -- all operations phase 7 refuses a URL for anyway. Open question 3's phrase "the coalescing of 512-byte requests" therefore describes a case that cannot reach a remote source; what the fetcher's cache is actually for is repeated and overlapping 64 KiB reads, which a format parser walking a chain does constantly. Corrected at source.

    BackingStore is not yet a thing that can gain a second kind¶

    src/vmm/src/backing.rs:15 is a plain struct BackingStore { file: File, capacity, current_size, sparse }. There is no enum, no trait, no indirection. read_at(&mut self, offset: u64, buf: &mut [u8]) -> io::Result<()> fills the whole buffer or errors. Phase 3's sentence "BackingStore gains a second kind" is a bigger change than it sounds, and it has one consequence for this phase: the client's API is specified to match that signature exactly (decision 7), so phase 3's work is introducing the polymorphism, not also designing the remote side's shape.

    The VMM has never spawned a child process¶

    The only Command::new anywhere under src/vmm/src/ is version.rs:166, running qemu-img --version. There is no descriptor-passing code, no reaping, no supervision, no signal handling for a child. Phase 3's lifecycle work is greenfield. It is also why this phase stops where it does: a client tested against a fetcher the test spawned is a different and much smaller claim than a fetcher the VMM owns.

    make instar will not build a new binary by itself¶

    src/build.sh:337-339 builds the VMM with a cd vmm followed by cargo build --release -- package-scoped, not workspace-scoped. A new workspace member is simply not built. The packaging asset lists are in src/vmm/Cargo.toml ([package.metadata.deb] assets at line 69, [package.metadata.generate-rpm] at line 101) and name every artefact explicitly. So the fetcher needs: a build block in build.sh, a line in its closing summary, and a row in each of the two asset lists at mode 755 rather than the 644 the guest .bin files use.

    get_binary_dir() in src/vmm/src/main.rs:3550 needs no change at all: it keys off the presence of core.bin and get_binary_path simply joins a name onto the directory it returns, so get_binary_path("instar-fetch") already resolves the way open question 8 assumed.

    Where the protocol must not live¶

    src/shared is #![no_std] with zero dependencies and is linked by the bare-metal guest: it is the guest ABI and the fetch protocol has no business in it. crates/guest-protocol is a standalone crate (deliberately not a workspace member) using micropb and heapless for the guest's variable-shape serial messages, which is the contrast open question 1 draws and it is accurate. It also sets the precedent this phase follows for documentation: docs/crates/guest-protocol.md is the only page in docs/crates/, and it is registered at docs/index.md:230.

    Guards a new crate, test and fuzz target must satisfy¶

    • A new workspace member needs [lints] / workspace = true to inherit unwrap_used = "warn", the way src/crates/qcow2 and src/vmm do. A non-member would have to declare it directly, as crates/guest-protocol does.
    • A new Python test module must be claimed by a pull-request job or tools/ci/check-test-partition.sh fails.
    • A new fuzz target must appear in three places that tools/ci/check-fuzz-targets.sh compares for exact equality: the .rs file under src/fuzz/fuzz_targets/, a [[bin]] stanza in src/fuzz/Cargo.toml, and the TARGETS=(...) array in .github/workflows/coverage-fuzz.yml. It also wants a row in docs/testing.md.

    932 (a virtqueue error the host cannot read hangs the guest) is the¶

    one that matters. Phase 1 made the guest's wait unbounded and made the host complete a failed request with IOERR, which is what makes a remote read's failure survivable at all -- a fetcher that dies becomes an io::Error from the client, an IOERR completion, and a failed operation with a sentence that names the image. But an error the host cannot read still hangs, and phase 3 multiplies the ways the host can fail to answer. This phase does not fix it; the plan records that phase 3 should, and the risk table says why it is phase 3's problem rather than this one's.

    Decisions¶

    1. A libc::socketpair behind a safe wrapper, not a new dependency, and not a filesystem socket. std cannot make a SEQPACKET socket, so one unsafe block is unavoidable unless socket2 or nix joins the privileged process's dependency tree, which is a poor trade for one syscall. src/vmm/src/ioevent.rs shows the shape: a raw call, checked, wrapped in a type that owns the descriptor and closes it on drop.

    It is a socketpair rather than a bound path in the filesystem because the VMM is the fetcher's parent. There is no name for anything else to connect to, no directory to choose, no mode to get wrong, and nothing for phase 4's Landlock policy to have to permit. SOCK_CLOEXEC on creation, and the fetcher's end is dup2'd to a fixed descriptor number.

    1. 64 KiB default, with what each side can carry measured from the granted SO_SNDBUF. Both ends ask for a buffer large enough to carry the protocol's largest block, read back what the kernel granted, and the init exchange settles on the smaller of the two achievable maxima -- capped at the 64 KiB default, not at the 256 KiB maximum. No sysctl is read and no number is assumed. The survey explains why the measurement is necessary: the value in open question 2 was neither the default ceiling nor the reachable one.

    Corrected 2026-11-19, during step 2f's review. This decision originally said "capped at 256 KiB", which contradicted open question 2's "64 KiB default" -- and the code followed the decision, so a well-provisioned pair negotiated 256 KiB and DEFAULT_BLOCK_SIZE was used only by tests. The operator confirmed the 64 KiB default. A larger block buys nothing while a guest request is at most 64 KiB: it only changes how a larger read is divided, and holds four times the receive buffer for payloads that never arrive. The 256 KiB maximum stays the figure the headers and the requested socket buffers are built to reach, so phase 6 raises one constant rather than the protocol.

    1. The client's API is read_at(&mut self, offset: u64, buf: &mut [u8]) -> io::Result<()>. Identical to BackingStore's, so phase 3 introduces polymorphism over an interface that already matches on both sides. Errors surface as io::Error, which is what phase 1's last_io_error plumbing records and renders.

    2. A typed status vocabulary, and no free-form reason string on the wire. The status is an enum the privileged side owns, rich enough to be actionable -- OK, BAD_REQUEST, UNSUPPORTED, OUT_OF_RANGE, SHORT_READ, IO_ERROR, and reserved space for the ones phase 5 needs (NOT_FOUND, FORBIDDEN, RANGE_UNSUPPORTED, SOURCE_CHANGED, NETWORK, TIMEOUT). The VMM maps each to a sentence it wrote itself.

    This is the decision most likely to be argued with, so here is the argument. A reason string is the obvious way to tell a user that a server returned 404, and refusing one looks like it throws away the diagnostic that matters. But the fetcher is the untrusted side of the partition, a string from it is attacker- influenced text, and phase 1 just finished building the path that renders a failure reason straight into the user's terminal -- terminal_safe_path exists in src/vmm/src/main.rs precisely because a path can carry escape sequences, and a reason string would need the same treatment plus length bounds plus encoding validation, in the privileged process, for every message. A fixed enum costs one match and cannot carry a payload at all. The diagnostic is not lost: the fetcher has its own stderr, which phase 3 can route into the VMM's log, and #931 is the issue that makes the VMM's log visible without --verbose. If phase 5 finds the enum genuinely insufficient, extending it is a one-line change to a crate the VMM owns -- which is a much better position than having to retrofit sanitising onto a string that tests already assert on.

    1. Little-endian on the wire, explicitly. The socket never leaves the machine, so native order would work, but an explicit to_le / from_le costs nothing on x86_64, makes the header layout a documented fact rather than a property of the build host, and means the fuzz corpus is portable.

    2. The VMM opens the file; the fetcher inherits the descriptor. In this phase instar-fetch receives two descriptor numbers -- the socket and the file -- and opens nothing. It takes no path. Resolving a path is an exercise of the invoking user's authority and belongs on the privileged side; and a fetcher that never opens a file is one phase 4 can confine to no filesystem access whatsoever, which is a stronger and cheaper sandbox than one that must be permitted to open the image. Phase 5 adds --url alongside, for a backend that needs a socket instead of a file.

    3. Request ids and out-of-order replies in the wire format from the start, with a single-threaded fetcher and one request outstanding. The hinge, not the door. Phase 6 needs concurrency; the protocol that would have to change to get it is the expensive thing to change, and the implementation that would have to change is cheap. A reply carries the id it answers and the client matches on it rather than assuming order, so phase 6 changes only how many are in flight.

    4. A magic and a version in the init message, and a mismatch is a hard failure naming both versions. The fetcher is found by probing the executable's directory and then /usr/lib/instar/, so a developer build talking to a packaged fetcher -- or the reverse -- is a real mistake that will happen. It is cheap to detect exactly and miserable to debug as a protocol desync.

    Why not NBD, and why not a virtqueue¶

    Open question 1 asks that this comparison be recorded where a reviewer will find it, because the shape chosen here is NBD's and the mechanism it rejects is one the repository already has working code for.

    Not a virtqueue, even though the pieces are present. virtio-queue 0.18 and vm-memory 0.18 are already dependencies, src/vmm/src/ioevent.rs already does eventfd notification, and SCM_RIGHTS over the socket would pass a memfd and an eventfd without trouble. It would work, and it would hand the untrusted fetcher a writable mapping shared with the privileged process, where whoever controls the ring controls indices the VMM dereferences. That is the memory-corruption channel the whole partition exists to remove, and defending it means writing adversarial-ring validation in privileged code -- the same class of work as the existing virtio boundary audit -- to save a copy that does not matter: a 256 KiB memcpy is tens of microseconds against tens of milliseconds of network.

    Not NBD, even though NBD is exactly this shape. NBD is offset-addressed reads over a socket with request handles and out-of-order replies, and nbdkit's curl plugin is an off-the-shelf implementation of most of this feature. Speaking real NBD means parsing a negotiated protocol -- option haggling, structured replies, an extensible handshake -- from an untrusted peer, in the privileged process. The few fixed-size headers here are a far smaller surface, small enough that step 2e can fuzz the whole decoder. Steal the shape; do not link the protocol.

    And not micropb, unlike the guest serial channel. crates/guest-protocol uses protobuf because the guest's results are variable-shape messages with optional fields. This channel carries fixed-size headers and raw bytes, so a serialisation library buys nothing and adds a dependency and a decoder nobody in this repository has fuzzed.

The review also suggested treating a ShortRead status as a zero-fill, and that part was declined. The local store's current_size is read once at open, so a file that shrinks underneath it fails with UnexpectedEof rather than reading as zeros -- which is exactly what the client already does with ShortRead. Zero-filling it would substitute zeros for image data the guest then parses as truth, on the word of the untrusted side.
    22. The glibc floor was a sixth place that enumerates what instar ships, and the Makefile's packaging guards were a seventh. tools/ci/check-glibc-floor.sh defaults to the instar binary and both call sites invoked it with no argument, so the fetcher would have shipped in the .deb, the .rpm and the release tarball without ever being checked against the published GLIBC_2.31 promise. Both call sites now check it too, in the same window immediately after make instar that the existing comment explains. Sweeping the class then found that make deb and make rpm pre-flight-check for instar and core.bin but not for the fetcher their own asset lists name, so a missing fetcher would have surfaced as a cargo-deb asset error rather than the Makefile's own sentence; both guards now name it. The new check was then run both ways on this host, which measured why the existing placement comment matters for the fetcher too. The release-image instar-fetch needs at most GLIBC_2.30 and passes; the same path after make test-rust has run needs GLIBC_2.34 and fails, because the dev image relinks bin targets into the same src/target/release/. So the fetcher's check belongs in the same window as instar's -- immediately after make instar -- and would report the build image rather than the release image anywhere later.
    23. Three documented fuzz-target counts were left stale by step 2e. docs/testing.md said "44 targets" in two places and docs/security-audits.md said 44 in a third, while the tree has 45 and check-fuzz-targets.sh agrees with the tree. The counts are corrected, and the target is now in FAST_TIER as well -- a decoder of four fixed-size headers saturates in seconds and has no business holding a deep-tier slice. Nothing checks the prose counts against the tree, which is why they drifted; that gap is filed as an issue rather than fixed here, because the guard's own test rig builds a synthetic tree with no docs/ in it.
    24. Implementing the per-read deadline found a trap in set_recv_timeout itself. SO_RCVTIMEO takes a timeval, and {0, 0} means no timeout to the kernel, so any timeout under a microsecond -- including the Duration::ZERO a caller might pass meaning "give up at once" -- silently removed the bound instead of tightening it. It is refused now, and the deadline logic gives up a millisecond early rather than relying on that boundary.
    25. A fetcher that refuses at startup is seen as one of two errors, and the test says so. The new pipe test first asserted UnexpectedEof and failed with ConnectionReset: whether the client's send of the init request loses to the fetcher's exit decides which. Both mean the same thing and a caller has to treat them alike, so the test accepts either and records why.

    26. One pre-existing test failed once on this host and passed on re-run: socket::tests::a_datagram_of_the_derived_maximum_really_sends, with ENOBUFS. A 416 KiB datagram needs an order-7 skb allocation, and /proc/buddyinfo showed no free order-7 block in the Normal zone at the time. It is host memory fragmentation rather than a defect, and it cannot reach a real exchange, where the negotiated block is 64 KiB. Worth knowing before anyone raises DEFAULT_BLOCK_SIZE in phase 6: the largest datagram the protocol permits is not always allocatable.

    27. The automated review's second round, 2026-11-19 (AEDT). One fix, one document, eight consider, one informational -- down from four fix. Both of the first two were taken, six of the consider items were taken, two were declined, and no third round was asked for. The reason for stopping is in the counts: three of the eight consider items are about code the first round added, which is the point at which the generator is reviewing its own suggestions rather than the change.

    28. Note 26's flake became the round's one fix item, and the reviewer was right. A test that fails for a reason unrelated to the code under test still has to not fail, whatever the cause. An ENOBUFS send is now treated as the host declining a high-order allocation rather than as a derivation error -- but the test does not simply pass in that case: it falls back to a datagram of DEFAULT_BLOCK_SIZE + READ_REPLY_LEN, which is what the protocol will actually ask of the socket, and asserts that it round trips. Fragmentation costs the stronger assertion, not the test.
    29. The receive side was bounded and the send side was not. SOCK_SEQPACKET blocks a send whose datagram will not fit in the peer's receive buffer, so a peer that stops reading holds the privileged process in the kernel exactly as a peer that stops answering does. SO_SNDTIMEO now carries the same bound as SO_RCVTIMEO, set from what remains of the read's deadline, and the error names which half missed it. With one request in flight a 32-byte request always fits, so no client call can reach this today; the proof is therefore at the socket, where a test fills a 2 KiB buffer that nothing is reading and watches the send give up instead of blocking.
    30. An oversized request was the second shape answered with silence, which made the module header wrong. MSG_TRUNC reports the length that was really sent while the kernel keeps the head of the datagram -- and the head is where the request id lives, so there was an id to answer by all along. SeqPacketSocket now exposes both readings: recv refuses an oversized datagram, which is what the privileged side wants, and recv_allowing_overlong reports the prefix it kept, which is what a side that owes an answer needs. The fetcher refuses it by id and keeps serving. One shape is still answered with silence, and it is the one the header describes: a datagram too short to carry an id.
    31. A limit that cannot bind is worse than no limit, because the next reader has to work out whether it can. The ceiling a refusal names was ours.min(MAX_BLOCK_SIZE), and ours can never exceed MAX_BLOCK_SIZE because the negotiation caps its answer at DEFAULT_BLOCK_SIZE. The min is gone and the invariant it was standing in for is now a test over a spread of datagram ceilings, which is the version that keeps holding if DEFAULT_BLOCK_SIZE moves.
    32. Two items were declined. One asked for tests of the fetcher's serve loop, init handshake and refusal paths, on the grounds that they have none; the serve loop and the init exchange are in fact covered end to end against the real binary by every test in src/fetch/tests/end_to_end.rs, and the gap that was real -- a hostile client, as opposed to the hostile peers the client is tested against -- is closed by the oversized-datagram test this round adds. The other asked for the file descriptor's readability to be checked at init beside its type. A pipe is refused because it cannot answer any positional read, so serving one means failing every request; a write-only descriptor fails loudly on the first read with the errno attached, which is a parent-side mistake reported where it happens. The check would add a syscall and a second way to be wrong about F_GETFL on an unusual descriptor.
    33. The mutation harness now extracts its own source text. Two of the six round-one definitions had gone stale against the tree -- one line was rewritten by clippy's manual_is_multiple_of, another by note 31 -- and a stale definition fails as an assertion in the middle of a run. build-mutations.py locates each mutation by a start and end marker, extracts the exact span from the file as it is now, checks it is unique, and writes mutations.json. There is also no revert any more: several mutations delete a guard, so reverting means finding an empty string, which matches everywhere -- and finding out that way deleted a guard that had to be put back by hand. Restores come from the pristine copy, and check proves a definition still fits without writing anything.
    34. CI's one red job on this head is not this change's. test_qemu_create_pins failed on prealloc-vpc under qemu-img 10.2.0 with modes.full.same_bytes_as_off: True != False. That test runs only the static qemu-img builds from instar-testdata, so no instar code is involved. The cause is in the pin harness: volatile_mask() decides which bytes are volatile by observing four preallocation=off images created within 1.1 s of each other, which moves only the low byte of the VHD footer's creation timestamp, so the byte above it -- which changes once every 256 seconds -- is not masked. A run that straddles that boundary compares two images differing at an unmasked offset. Measured with the harness's own volatile_mask() and same_content(): inside one 256-second block the comparison holds, across a wrap it does not, and the offsets that escape are 26 and 2074. Filed as #939.
