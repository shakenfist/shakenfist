    Multi-extent VMDK phase 1: pin qemu's output¶

    Status: Complete¶

    Master plan: PLAN-multi-extent-vmdk.md.

    Planning effort¶

    High. Everything later in the plan rests on these measurements, and this repository has a history of sub-agents asserting plausible but wrong qemu-img capabilities. Review effort: high for steps 1a and 1c, which touch a pin that gates CI across 80 qemu builds.

    Decisions already taken by the operator¶

    From the master plan, resolved 2026-11-16:

    1. Sequential extent rotation, not simultaneous indexed output devices.
    2. The read-side extent ceiling is fixed inside this plan, as phase 3.

    Neither decision constrains this phase, which writes no instar code. Open questions 3 to 6 remain open; this phase's measurements are what settle 4 (extent path rules) and 5 (the maximum extent count), and it must report on them rather than decide them.

    Scope¶

    In scope:

    • Extending the existing qemu-img pin infrastructure to cover twoGbMaxExtentSparse and twoGbMaxExtentFlat create, across all 80 static builds in instar-testdata/qemu-img-binaries/x86_64/.
    • A VMDK structural parser for tests and, later, the differential fuzzer, in the shape of tests/helpers/vhdx_structure.py.
    • Making the pinned descriptor able to prove an extent naming scheme and ordering, which today it cannot (see the survey).
    • Measuring, and recording in this plan: per-extent sector counts for sizes that are and are not multiples of 2 GiB, the ddb.* values and how geometry is derived, qemu's behaviour when a target extent file already exists, and the maximum extent count with the refusal past it.

    Out of scope:

    • Any change under src/. This phase writes no instar behaviour; its deliverable is an oracle. git diff --name-only origin/develop...HEAD -- src/ must be empty at the end of it.
    • Deciding the extent path rules or the maximum instar will support. Those are open questions 4 and 5, and the operator resolves them with this phase's measurements in hand.
    • Reading twoGbMaxExtent* images, which is phase 3, and the structural comparison arm of the differential fuzzer, which is phase 16. This phase builds the parser those depend on and no more.
    • Retrofitting ddb.* onto instar's existing VMDK output (open question 3).

    What the survey found¶

    The master plan's phase 1 intent is stale in one load-bearing way: it reads as though a cross-version sweep must be established, and describes the per-version builds as the thing to use. All of that already exists. PLAN-bat-population-phase-01-pin.md built it, and this phase extends it rather than starting one. Corrected at source in the master plan and in docs/plans/index.md as part of the planning commit; a later step should not redo that.

    What exists today, verified present:

    File Lines What it is
    tests/helpers/qemu_pins.py 817 CASES, run_case, load_pin, expected, the normalisers
    tools/sweep-qemu-create.py 183 the sweep: --write/--check, --versions, --cases, --scratch, --jobs
    tests/golden/qemu-create-pins.json 1712 the pin, shaped {versions: [...], cases: {name: [{result, versions}, ...]}}
    tests/test_qemu_create_pins.py 119 the CI check
    tests/helpers/vhdx_structure.py 714 the VHDX structural parser, the model for this phase's VMDK one

    instar-testdata/qemu-img-binaries/x86_64/ holds 80 builds, 6.0.0 through 10.2.0, as the master plan said. There is a KIND_VMDK_FLAT case kind already (qemu_pins.py:51, cases at :197 and :200) which captures a normalised descriptor and one extent length.

    The gap that matters. normalise_descriptor (qemu_pins.py:504-511) replaces every extent filename with a single placeholder. Run against the 3-extent descriptor measured for the master plan:

    CID=$CID
RW 4194304 SPARSE "$EXTENT"
RW 4194304 SPARSE "$EXTENT"
RW 2097152 SPARSE "$EXTENT"

    The sector split survives, which is most of what matters, but the names do not. A pin built on this normaliser cannot tell -s001.vmdk from -001.vmdk, cannot catch extents emitted in the wrong order, and cannot catch a descriptor pointing at the wrong file. Since proving the naming scheme is a stated goal of this phase, the placeholder has to carry an index. Decision 1 takes that up.

    The second gap. _run_vmdk_flat (:513-522) measures exactly one extent, through _prealloc_measured_file({'measure': 'flat-extent'}, image). Multi-extent needs a list of per-extent lengths, and the extent paths should come from parsing the descriptor rather than from reconstructing qemu's naming, so that a wrong name shows up as a missing file rather than being silently regenerated.

    There is no VMDK structural parser. tests/helpers/ holds vhdx_structure.py but no VMDK equivalent. qemu-img info cannot tell a correct extent split from a wrong one, which is the same reason PLAN-bat-population-phase-01-pin.md built the VHDX comparator in its phase 1 rather than later. Step 1b builds it here for the same reason.

    Measurements already in hand, taken 2026-11-16 against the host qemu-img 10.0.13 (Debian 1:10.0.13+ds-0+deb13u1) and recorded in the master plan's Situation: both subformats create successfully; naming is <stem>-s%03d.vmdk and <stem>-f%03d.vmdk; a 5 GiB image splits 4194304 / 4194304 / 2097152 sectors; flat extents are the full 2 GiB in length but sparse on disk; 40 GiB yields 20 extents; and qemu writes a ddb.* block that instar emits for no subformat. The existing pin confirms the ddb.* block is captured for vmdk-flat-64M, so the machinery already records it. Nothing in the survey contradicted the master plan's Situation.

    Decisions¶

    1. The extent placeholder becomes index-aware, and the existing pin is migrated textually rather than re-swept. normalise_descriptor numbers placeholders from 1 in descriptor order ($EXTENT1, $EXTENT2, ...). Every existing pinned descriptor has exactly one extent line, so the migration is a deterministic replacement of "$EXTENT" with "$EXTENT1" in tests/golden/qemu-create-pins.json, and step 1a proves it by re-running --check over a three-version sample rather than re-running 80 builds for a rename.

    This is the decision most likely to be argued with. The alternative is a second normaliser used only by the new case kind, which touches no existing pin and carries no migration risk at all. It is rejected because two normalisers for one concept drift: the next person to fix a descriptor-normalisation bug fixes one of them. The migration is mechanical, the sampled --check catches it if it is not, and a wrong migration fails CI loudly rather than silently weakening an oracle. If review disagrees, the second normaliser is a clean fallback and nothing downstream changes.

    1. Pin cases stay small; the extent ceiling is measured once and recorded in this plan, not in the pin. The pin runs in CI, and creating hundreds of files per case per version across 80 builds is not affordable. Pinned cases are capped at 11 extents (21 GiB, which is also past the 15-extent read ceiling phase 3 removes, so phase 3 has a pinned case to prove itself against). The ceiling is probed once on a four-version sample (6.0.0, 7.2.0, 8.2.0, 10.2.0) and written into Sweep results.

    This decision was written expecting the %03d naming to imply a ceiling near 999 extents, and the probe to find qemu refusing past it. It does not: %03d is a minimum field width, 1000 extents are named -s1000.vmdk and created without complaint, and 16384 work too. The conclusion stands and the reason changes -- a large case is kept out of the pin because it costs thousands of files per version, not because it would pin a boundary.

    1. Extent paths come from the descriptor, not from qemu's naming rule. The new runner parses extent filenames out of the descriptor before normalising it, then stats each. A wrong or missing extent then surfaces as a null length rather than being papered over.

    2. The VMDK structural parser covers what the fuzzer will need, and stops there. Descriptor fields (version, CID presence, parentCID, createType), per-extent kind, declared sector count, actual file length, and for sparse extents the VMDK4 header fields that define layout: magic, version, flags, capacity, grain size, descriptor offset and size, GD and RGD offsets, overhead. Grain contents are not parsed; phase 16 compares structure, and content parity is already covered by flattening both sides to raw.

    3. Flat cases are safe to pin at these sizes. A 2 GiB flat extent is sparse on disk (measured: a 5 GiB flat image occupies 4 KiB), so an 11-extent flat case costs kilobytes, not 22 GiB. The runner still deletes each image after measuring, as run_case already does.

    Steps¶

    One commit per step, each passing pre-commit run --all-files after git add (the gate cannot see untracked files).

    Step Effort Model Isolation Brief for sub-agent

EXTENT_PLACEHOLDER (:60) becomes a prefix; keep the name or rename it, but update every use.     The extent ceiling¶

    Probed on 6.0.0, 7.2.0, 8.2.0 and 10.2.0, both subformats.

    There is no extent-count ceiling to find. %03d is a minimum field width, not a cap: past 999 the names simply grow a digit. At 2000 GiB every one of the four builds writes 1000 extents, rc 0, empty stderr, and the thousandth descriptor line is verbatim

    RW 4194304 SPARSE "image-s1000.vmdk"

    on 6.0.0 and on 10.2.0 alike. At 32 TiB all four builds write 16384 extents, rc 0, empty stderr, 16384 RW lines in the descriptor, in 12-14 s each. At 1 PiB 10.2.0 does not refuse either: it was still creating extents when a 60 s timeout stopped it, 70168 of the 524288 the size implies.

    The only refusal past it is qemu-img's generic size parser, not the vmdk driver, and it is identical on all four builds and both subformats:

    qemu-img: Invalid image size specified. Must be between 0 and 9223372036854775807.

    So the practical limit on a split VMDK is the filesystem's inodes and the operator's patience, not qemu. That is a measurement for open question 5, which this phase does not resolve.

    A pre-existing file where an extent goes¶

    Two cases, one per subformat, drop a 1 MiB file where the second extent goes -- image-s002.vmdk and image-f002.vmdk -- with a second hard link to it under a name no extent uses, then create a 5 GiB image over it. Both writers are measured rather than one inferred from the other, because the flat writer extends each extent to its full declared length where the sparse one writes a header.

    It is not a refusal. On all 80 builds qemu returns rc 0 with empty stderr and writes the image exactly as it does without the obstruction: the same three extents, the same names, the same lengths 327680 / 327680 / 196608. The kept link reports the length of the extent and not of the 1 MiB file it used to name -- 327680 bytes for the sparse case, 2147483648 for the flat one -- so qemu truncated the existing file in place rather than unlinking it and creating its own. Any other hard link, and any open descriptor, follows the image.

    The two subformats differ only in direction. ftruncate is what sets an extent's length either way, so the sparse case shrinks the 1 MiB file to 320 KiB and the flat case grows it to 2 GiB. Neither reports anything, and neither leaves the original contents reachable under the old name.

    This is a measurement for open question 4 -- what instar should do with a file already sitting where an extent goes -- which this phase records and does not resolve. What qemu does is not by itself what instar should do.

    Risks and mitigations¶

    Risk Mitigation
    1a's pin migration silently corrupts an existing oracle The migration is a single deterministic substitution with before/after grep -c counts in the commit message, and a sampled --check across three versions must pass. If review prefers zero risk, decision 1's fallback is a second normaliser. The management session re-runs the --check itself rather than trusting the report.
    The sweep's spurious failures get attributed as version boundaries Known failure mode in this repository under host load. Step 1d re-runs any boundary case alone on the versions either side before recording it, and reports rather than writes when a result contradicts the master plan.
    80 versions × new cases is slow enough to tempt shortcuts Decision 2 caps pinned cases at 11 extents and keeps the ceiling probe to a four-version sample. --jobs exists but concurrency is what causes the spurious failures above, so step 1d runs at the default of 1 and the wall time goes in Sweep results.
    A green stestr run that ran almost nothing Every step that runs tests checks "Ran: N" against the expected count rather than the exit code. A subunit attachment over 4 MiB kills a worker and the run still exits 0.
    The parser in 1b is written against one qemu version's layout 1b asserts against host-written images and 1d then exercises it across 80 builds through the sparse cases; a layout difference shows up as a pin group rather than as a silent misparse. Only the sparse ones: a flat extent has no header to read, so every flat case pins a null structure and the parser's flat path is covered by tests/test_vmdk_structure.py against the host alone.
