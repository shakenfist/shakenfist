    Phase 12: cross-cutting documentation¶

    Phase 12 of PLAN-bat-population.md. Read its phase 12 paragraph and the "Constraints that apply throughout" section, in particular the rule that every qemu-img behaviour claim is either cited to instar-testdata/qemu-sources/ or measured with the static builds, and the rule that code and user documentation do not cite this plan's phase, step or decision numbers.

    This phase writes no code. It carries the documentation that belongs to no single phase, after phases 1 to 11 each updated the pages their own change touched.

    Planning effort: medium. The master plan allows it, and the survey agrees: there are no design decisions here, the shape is a set of factual corrections to five named pages. The one part that is not mechanical is the pair of quirks entries, which assert what qemu-img does and so must be measured before they are written rather than reasoned about.

    Review effort: medium, with one exception. A wrong claim in docs/quirks.md is expensive: it is the page the next person trusts when deciding whether a divergence is known, so a divergence described backwards there is worse than one left undocumented. The review that matters is of the two new quirks entries against their transcripts, not of the roster edits, which are checkable by grep.

    What the survey found¶

    The master plan's phase 12 paragraph was written before phases 1 to 11 executed. It names five targets; the survey found one of them needs nothing, one needs a different edit from the one described, and one of the three quirks it lists is already written. File and line references are against 41f74d40.

    The per-phase constraint held, and that is the finding¶

    The master plan requires every phase that changes user-visible behaviour to update the documentation describing it in the same pull request, with phase 12 for the cross-cutting pages only. That held. Counting mentions of the fixed subformat:

    Page Owner subformat=fixed mentions
    docs/create.md phase 7 7
    docs/convert.md phase 8 3
    docs/measure.md phase 9 3
    docs/quirks.md phases 7-9 6
    docs/format-coverage.md phase 12 0
    docs/format-internals.md phase 12 0

    docs/create.md mentions preallocation 20 times; the output side of docs/format-coverage.md mentions it zero times, its only occurrence being in the resize table. The staleness is exactly where the master plan predicted it would be, which is a real result and worth stating: phase 12 is a documentation phase with a genuine, bounded backlog rather than a sweep looking for work.

    docs/format-internals.md claims dynamic-only output and a flat 32 MiB block size¶

    Its vhdx section opens:

    Microsoft VHDX Virtual Hard Disk v2 (Hyper-V). Supported:
- Dynamic VHDX: BAT-based block allocation with 32 MiB blocks (input,
  output, check)

    Both halves are now false:

    • Fixed output is missing. create -f vhdx -o subformat=fixed landed in phase 7 and convert -O vhdx --subformat fixed in phase 8, and measure answers for a fixed target since phase 9. The word "fixed" does not appear in the file.
    • "32 MiB blocks" is right only for one size band. vhdx::default_block_size in src/crates/vhdx/src/lib.rs returns 64 MiB above 32 TiB, 32 MiB above 100 GiB, 16 MiB above 1 GiB and 8 MiB at or below 1 GiB. 32 MiB is the answer for the 100 GiB to 32 TiB band only. docs/convert.md already states the scaled rule correctly, so the two pages disagree with each other today.

    The rest of the section -- the CRC-32C, metadata, overlap-rule and region-cap prose -- is current and is not to be rewritten.

    docs/format-coverage.md names no VHDX subformat on the output side¶

    Two places:

    • The "Conversion Output Format Support" table's vhdx row says "Dynamic VHDX, configurable block size (1MB-256MB ...)". Its block size clause is correct, including the scaled default; its subformat claim is not.
    • The "Output side" prose under the parity tables names vmdk's three subformats ("monolithicSparse, streamOptimized and monolithicFlat") but names no VHDX subformat, and says nothing about the no-op preallocation accepted on vmdk, vpc and vhdx since phase 3.

    The vhdx | ✓ cell in the create/convert-output/dd-output roster table is still accurate and does not need a subformat column.

    ARCHITECTURE.md's creatable roster omits monolithicFlat and fixed¶

    Creatable target formats are raw, qcow2, vmdk (monolithicSparse and
streamOptimized), vpc (dynamic and fixed) and vhdx (dynamic).

    Two omissions: vmdk gained host-only monolithicFlat in phase 3, and vhdx gained fixed in phase 7. Note that vpc already reads "(dynamic and fixed)", so the sentence's own form shows what the vhdx entry should look like.

    The master plan frames this target as "ARCHITECTURE.md if the shared layout function changes the component description". That trigger does not fire: the phase 5 shared layout function did not change how the component is described. What is stale is a factual roster, which is a smaller and different edit. ARCHITECTURE.md is loaded into every session, so this phase corrects those two entries and adds nothing.

    docs/quirks.md is missing two divergences and already has the third¶

    The master plan lists three for this phase. Measured against the tree:

    Divergence State
    convert's in-place fixed layout vs qemu's default already written
    -o log_size missing
    dynamic block_state_zero missing

    The first is covered: docs/convert.md states the fixed output is the layout of qemu-img create -o subformat=fixed,block_state_zero=off and points at the "VHDX partial last block" section of docs/quirks.md, which exists and discusses the block_state_zero layouts at those sizes. Phase 8 did this work. Nothing to add.

    The other two are real and undocumented:

    • log_size is accept-ignored. parse_create_o_options (create) and parse_o_options (measure) in src/vmm/src/main.rs both match ("vhdx", "log_size") to a bare accept-ignore arm, with the comment "log_size stays accept-ignored". instar writes qemu's default log size whatever the option says. The only occurrence of log_size in docs/quirks.md today is inside a pasted qemu-img create transcript, which is not a documented divergence. convert does not parse -o at all -- it takes --subformat -- so this divergence is create and measure only, and the entry should say so.
    • block_state_zero is parsed for a dynamic image and then not read. parse_create_o_options parses it for both subformats deliberately, because qemu-img rejects a non-boolean value for both, with the comment "Only a fixed image reads it". So create -f vhdx -o subformat=dynamic,block_state_zero=off is accepted and changes nothing. parse_o_options accept-ignores it for measure entirely, which is correct and not a divergence: a fixed target is dense either way, so the measured numbers do not depend on it.

    What phase 12 must measure, not assume. Both entries above describe instar. Neither says what qemu-img does, and the plan deliberately does not guess: whether qemu-img honours log_size by writing a different log region, and what it does with block_state_zero=off on a dynamic image, are the facts the entries turn on. They are measured with the static builds in step 12b before a word of either entry is written.

    Corrected at source¶

    The master plan's phase 12 paragraph and the docs/plans/index.md row are corrected in this phase's first commit, so the next reader does not re-derive the above: CHANGELOG.md is recorded as already complete, the ARCHITECTURE.md trigger is restated as a roster correction, and the convert-layout quirk is marked as written in phase 8. A later step does not need to redo this.

    Decisions¶

    1. CHANGELOG.md is out of scope. The survey found every phase from 7 to 11 wrote its own [Unreleased] entry, including fixed create, fixed convert, fixed measure, the cross-version baselines and the fuzzing. There is nothing to add, and the alternative -- rewriting correct entries into a single summary -- would lose the per-change detail a reader of the released changelog wants.

    2. ARCHITECTURE.md gets a two-entry roster correction and nothing else. Not the component-description review the master plan's wording implies. The page is loaded into every session, so a documentation phase is exactly the wrong moment to let it grow.

    3. The two quirks entries are measured before they are written, and each cites the qemu-img version it was measured with. This is the master plan's standing constraint, and it is the reason 12b is a separate step at a heavier model than the roster edits: the cost of a wrong entry here is paid by whoever next triages a VHDX divergence.

    4. An audit step runs first and changes nothing. 12a enumerates every documentation claim about VHDX output capability, VHDX block size, and the creatable/convertible format rosters, across docs/, README.md, AGENTS.md, ARCHITECTURE.md and .claude/skills/. The edit steps then work from that list.

    This is the decision most likely to be argued with, because the survey already found the five pages that are wrong and an audit looks like re-doing it. The argument for it is the one phase 11 learned three times over: the survey checked one axis -- the words "fixed" and "preallocation" -- and found the per-phase pages clean on that axis, which is not the same as clean. The "32 MiB blocks" claim is the proof. It was not found by looking for "fixed"; it was found by reading the section that the first finding pointed at, and nothing in the survey rules out a third page carrying the same number. A grep for the shape costs one cheap step and converts "the five pages I found" into "the pages that make this class of claim". If 12a's list is just the survey's five, that is a one-line result and the phase proceeds unchanged.

    1. docs/format-internals.md gains the VHDX layout facts but does not duplicate docs/convert.md. The per-format page says what the fixed layout is -- every payload entry FULLY_PRESENT at its fixed offset, the data start, zero blocks left as holes -- and points at docs/convert.md and docs/create.md for the command surface. Two pages describing one option is how they come to disagree, which is the defect this phase is fixing.

    Risks and mitigations¶

    • A measured claim in 12b is wrong, or is measured with the host qemu-img instead of a pinned build. This is the expensive failure: it lands a confident, wrong statement on the page people trust. Mitigation: the management session re-measures one case from each of 12b's two entries with a pinned build before committing, and rejects the step if a transcript is missing or its version is unstated. The brief names the pinned-build requirement explicitly because the host binary is the path of least resistance.

    • 12b cannot measure something and fills the gap by reasoning. A plausible sentence about qemu is indistinguishable from a measured one once it is on the page. Mitigation: the brief says to report the gap instead, and the definition of done requires a version string beside each claim, which a reasoned claim cannot produce.

    • The documentation phase grows into a rewrite. Five pages of factual corrections is a small change; docs/quirks.md alone is over 5,000 lines and invites tidying. Mitigation: each brief states what not to touch, 12e is told to stop and report rather than widen, and the definition of done counts changed files.

    • The docs-line-references hook rejects an edit late. It covers docs/ excluding docs/plans/, and since de08bfa6 it catches prose forms -- "(line NNN)", "lines NNN-NNN", "at line NNN" -- as well as file.rs:NNN. The prose half is the trap: it is newer than most of this plan's phases, so a habit formed earlier in the plan passes review and fails the gate. Mitigation: both editing briefs name it and say to name functions and constants instead; it runs in pre-commit, so the gate catches it before review rather than in CI.

    • Two of 12c, 12d, 12e run at once and collide in the gate. They touch different files but share one worktree and all run pre-commit run --all-files. Mitigation: the step plan says they run in sequence, and says why.

    Measurements¶

    Every qemu-img claim this phase added was measured against the pinned static builds under instar-testdata/qemu-img-binaries/x86_64/. The host qemu-img was never used. Transcripts are in this session's scratchpad under step-12b/transcripts/, covering log_size and dynamic block_state_zero at 10.2.0 and 6.0.0, their structural comparisons at 16 MiB and 4 GiB, the edge cases, and a sweep of all 80 builds (sweep-all-versions.txt, 80 versions x 9 probes).

    log_size is honoured by qemu-img: the header's LogLength and the bat and metadata region offsets move with it, carrying the file length, and nothing else changes. A value that is not a whole MiB is rounded up rather than refused; log_size=0 is refused and leaves a zero-length file.

    block_state_zero=off is honoured by qemu-img on a dynamic image, which this plan had not assumed either way: every payload BAT entry becomes PAYLOAD_BLOCK_NOT_PRESENT instead of PAYLOAD_BLOCK_ZERO, and nothing else changes. instar accepts the option and ignores it for a dynamic image, so this is a real divergence rather than a shared no-op.

    The management session re-measured one case from each entry independently on 6.0.0 and reproduced both, and separately measured the preallocation parity that 12d and 12f assert, because the brief had asserted it without evidence. That measurement is worth recording for the next person, because byte comparison is the wrong oracle and says so loudly: every qemu-img create writes fresh random identifiers, so two creates with the same mode differ too. With identical output filenames and the per-creation fields accounted for, off, falloc and full are indistinguishable -- vmdk differs only in its CID, vpc in its unique ID and the footer copy of it, vhdx in the two header write GUIDs and one metadata GUID, and all three VHDX modes compare structurally equal through tests/helpers/vhdx_structure.py. metadata is refused on all three formats.
