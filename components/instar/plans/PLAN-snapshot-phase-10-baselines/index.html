    PLAN-snapshot phase 10: cross-version baselines¶

    Prompt¶

    Before responding to questions or discussion points in this document, explore both repositories thoroughly. In instar-testdata (sibling checkout ../instar-testdata relative to the instar clone's parent; primary clone, no worktree): scripts/generate-baselines.py (the COMMANDS registry, generate_map_baseline as the closest template, run_qemu_img, find_manifest — note it prefers the PRIMARY instar clone's manifest over worktrees), scripts/detect-profiles.py, the Makefile baseline targets, expected-outputs/map-human/ as the freshest layout example, and the custom/ fixture tree. In instar: tests/manifest.json (the image registry both repos share), the snapshot harnesses under tools/, and the snapshot sections of docs/quirks.md. Do not speculate about either repo when you could read it instead.

    Phase plans for the parent master plan live alongside it in docs/plans/ and are named PLAN-snapshot-phase-NN-<descriptive>.md. The master plan is PLAN-snapshot.md. This is phase 10 of fourteen.

    I prefer one commit per logical change, and at minimum one commit per phase. This phase spans two repositories — see "Commit logistics" below; the instar-testdata side follows that repo's own multi-commit convention (scripts → outputs → profiles), observable in its git log.

    Situation¶

    Phases 1–9 completed the snapshot subcommand end-to-end with seven live verification harnesses. Phase 10 freezes the cross-version baseline matrix: snapshot-bearing qcow2 fixtures checked into instar-testdata, a snapshot-list command in the baseline generator, raw qemu-img snapshot -l captures for all 80 qemu-img versions (6.0.0 → 10.2.0), and deduplicated profiles. Phase 11's integration tests then compare instar against the version-keyed profiles, the same way info / check / map tests do today.

    Empirically established facts (planning probes)¶

    1. Output drift across the matrix is exactly two families (probed on 6.0.0 / 6.2.0 / 7.2.0 / 8.2.2 / 9.1.0 / 10.2.0 against one frozen fixture):
    2. Old format (6.0.0 through at least 8.2.2): ID width 10, VM SIZE / VM CLOCK with spaces, 2-digit clock hours (00:00:00.000), no double space before the clock column.
    3. New format (at least 9.1.0 onward): the layout instar implements (underscored VM_SIZE / VM_CLOCK, 4-digit clock hours, the phase 4 column geometry). The break is somewhere in (8.2.2, 9.1.0] — qemu 9.0's dump_one_snapshot rework. detect-profiles.py will find the boundary mechanically; expect ~2 profiles for snapshot-list-human (more only if a subtler drift hides between the probe points — fine either way, but >4 warrants investigation, see step 10d).
    4. ID assignment is stable back to 6.0.0: the oldest matrix binary assigns max(id)+1 and allows duplicate names, identical to 10.x (probed: two -c first calls under 6.0.0 yield IDs 1 and 2, both named first). The master plan's worry about cross-version ID-assignment drift does not materialise within this matrix.
    5. Fixtures are version-portable: a fixture created by 10.2.0 lists correctly under 6.0.0 (qcow2 v3 snapshots are compatible the whole way back across the matrix).
    6. The DATE column renders in local time — the generator currently sets no TZ; the snapshot-list path must pin TZ=UTC in the subprocess environment (and phase 11's instar invocations must match). With frozen fixtures the dates are frozen bytes, so TZ-pinned output is fully deterministic.
    7. The baseline pipeline: generate-baselines.py produces expected-outputs/<type>/<format>/<version>/ <image-id>.{stdout.txt,stderr.txt,meta.json} per version; detect-profiles.py groups byte-identical versions into profiles/profile-X-Y-Z/ with a version-map.json; raw captures are never deleted. The testdata repo's commit convention per command (from its log): a scripts commit, an expected-outputs: add <cmd> baselines for 80 qemu-img versions commit, then Regenerate output profiles.
    8. The manifest lives in instar (tests/manifest.json), discovered by the generator via sibling-directory glob where the primary instar clone wins over worktrees — baseline generation from an agent worktree must pass --manifest explicitly or the new fixtures will be invisible.

    Fixture set (new manifest tier: tag snapshots)¶

    All generated by a new instar-testdata/scripts/create-snapshot-testdata.py, written into instar-testdata/custom/snapshots/, then date-normalised (the script binary-patches every snapshot entry's date_sec/date_nsec to fixed constants, e.g. 2026-01-01 00:00:00 UTC + 0ns, so regeneration is byte-deterministic and the DATE column is a stable, known string under TZ=UTC). The creating binary is the newest in the matrix (pinned by path, recorded in the script). Eleven fixtures:

    id content
    snap-qcow2-v3-one v3, 64 KiB clusters, 128 KiB data, one snapshot
    snap-qcow2-v3-two v3, data + divergent write between two snapshots (the workhorse: shared and unshared clusters)
    snap-qcow2-v3-sixteen sixteen snapshots — instar's v1 cap boundary (list works; phase 11 uses it for the create-refusal path)
    snap-qcow2-v2 qcow2 v2 (compat=0.10), one snapshot
    snap-qcow2-extl2 extended-L2 image, one snapshot
    snap-qcow2-512 512-byte clusters, two snapshots
    snap-qcow2-backing overlay-with-backing (relative backing path per the existing chain-fixture convention used by the rebase/commit baselines), one snapshot
    snap-qcow2-dupname two snapshots, same name (IDs 1, 2)
    snap-qcow2-namecollision id=1,name="2" + id=2,name="x" — the −a/−d matching-asymmetry fixture for phase 11
    snap-qcow2-longname one 200-byte name (TAG column overflow / shift behaviour) and one ID patched to 4 digits (ID column width behaviour)
    snap-qcow2-vmstate hand-patched metadata: vm_state_size_large = 1 MiB, vm_clock_nsec = 3661500000000 (renders 1:01:01.500-family values), icount = 12345 — the only fixture that exercises non-zero VM_SIZE / VM_CLOCK / ICOUNT rendering, including size_to_str drift across versions

    The hand-patched fields in the last two fixtures are pure metadata (no VM-state clusters exist); qemu-img check stays clean and every matrix version lists them — the fixture script asserts both (check-clean under the newest binary, list-clean under the oldest). Manifest entries (instar tests/manifest.json) follow the existing schema: id, path, format: qcow2, safety: safe, run_in_ci: true, description, tags (["qcow2", "snapshots", ...] plus variant tags), sha256.

    One existing no-snapshot qcow2 (qcow2-v2 or similar small image) is additionally included in the snapshot-list baseline run to pin the empty-table behaviour (no output, exit 0) — one image, not the whole 58-image qcow2 roster (57 × 80 empty stdout files would be noise).

    Baseline matrix¶

    snapshot-list-human only: 12 images (11 fixtures + 1 empty-case) × 80 versions ≈ 2880 small files, comfortably under the map tree's size. JSON is not baselined here — --output=json is an instar extension with no qemu source of truth (open question 1).

    What phase 10 does not change¶

    • instar source code: nothing. Every binary byte-identical.
    • Existing baselines and profiles for other commands.
    • The seven instar harnesses (re-run once as a sanity gate, since tests/manifest.json is shared state).

    Commit logistics (two repositories)¶

    • instar-testdata (work on a branch named snapshot-baselines; do NOT push — the operator reviews and pushes): commit 1 = fixture script + fixtures + generator/Makefile changes ("scripts: add snapshot-list baselines machinery (PLAN-snapshot 10).") — or split script/fixtures if cleaner; commit 2 = "expected-outputs: add snapshot-list baselines for 80 qemu-img versions."; commit 3 = "Regenerate output profiles." Follow that repo's observed message style plus the standard Signed-off-by / Co-Authored-By / Prompt conventions.
    • instar (the current worktree/branch): one commit — manifest entries + master-plan row update + quirks note.
    • The phase plan file itself is committed to instar before implementation, per the running convention.

    Mission and problem statement¶

    After phase 10 lands:

    • instar-testdata carries 11 frozen, deterministic, check-clean snapshot-bearing fixtures and expected-outputs/snapshot-list-human/ raw captures for all 80 versions plus deduplicated profiles.
    • For every fixture, instar snapshot -l (TZ=UTC) is byte-identical to the newest-format profile's baseline — verified in this phase by direct diff, and wired into CI by phase 11.
    • Regenerating the baselines is byte-deterministic (stdout/stderr; meta.json timestamps excepted, matching the existing convention).

    Open questions¶

    1. JSON baselines: qemu has no snapshot -l --output=json¶

    The master plan's snapshot-list-{human,json} profile pair assumed both could be captured from qemu-img; JSON cannot. Working answer: defer JSON to phase 11 as instar-side golden files (tests/ owns its goldens; a self-baseline catches schema regressions, which is all a self-baseline can do). The master plan's baseline-strategy section is annotated accordingly by step 10f. Alternative rejected: teaching generate-baselines.py to run an instar binary — the testdata repo's generation flow must not depend on instar build artefacts.

    2. Mutation baselines ("-c then -l" pairs per version)¶

    The master plan suggested capturing post-create listings under each version to catch ID-assignment / column drift. Working answer: drop them. Mutating modes print nothing (no stdout to baseline); column drift is already captured by listing frozen fixtures under every version; ID assignment is probe-confirmed stable across the whole matrix (fact 2); and post-op image equivalence is validated live by the phase 6–8 harnesses today and phase 11/13 going forward. A generation-time mutation would also embed the generation wall-clock in the output, breaking determinism for no new coverage. Annotated in the master plan by step 10f.

    3. Where does the old-format divergence get documented?¶

    instar's -l output is byte-exact against the ≥9.x format only. Working answer: one quirks paragraph (step 10f): instar tracks the modern format; pre-9.x qemu-img renders the same data in an older layout, captured in the baselines as separate profiles; phase 11 compares instar against the newest profile and uses older profiles only to validate the captures themselves. (Same posture the existing qemu-img-human six-profile family implies for info.)

    4. Does the backing-file fixture need its backing image checked in?¶

    Working answer: yes, alongside it in custom/snapshots/ with a relative backing reference, following whatever the existing rebase/commit chain fixtures do — read one of those first and copy the convention exactly (path form, manifest representation). If the existing convention stores the backing as its own manifest entry, do the same (it then needs its own sha256 and an entry-level tag so the snapshot-list run does not list a snapshot-less backing — or it serves as the empty-case image, killing two birds).

    Agent guidance¶

    Execution model¶

    All implementation work is done by sub-agents, never in the management session. Single sonnet agent — the same calibration as phase 9: discovery is pinned (the probes above), the work is scripting + generation + bookkeeping. The agent's instar worktree isolates the instar side as usual; for instar-testdata the agent works in the PRIMARY clone on a new local branch snapshot-baselines (no worktree tooling exists there — keep git status clean apart from intended changes, and never touch main). Verify the instar worktree is based on the snapshot branch head first (every prior phase started on the wrong base; git reset --hard snapshot if so). Never push either repo.

    Management session review checklist¶

    • Read the fixture script, the generator diff, and the manifest entries.
    • Fixture determinism: re-run the fixture script, sha256s unchanged.
    • Baseline determinism: regeneration changes only meta timestamps.
    • The eleven instar-vs-newest-profile diffs are empty.
    • Profile grouping matches the two-family expectation (or the investigation explains why not).
    • No instar binary changes; harnesses green.
    • instar-testdata main untouched; the three commits sit on snapshot-baselines with conventional messages.
    • Independent spot-check: list one fixture under three matrix binaries by hand and diff against the committed raw baselines.

    Success criteria¶

    • The snapshot-baselines branch in instar-testdata carries the three conventional commits (fixtures+script, raw outputs, profiles) and is ready for operator review/push.
