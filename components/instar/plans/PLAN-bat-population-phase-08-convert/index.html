    Phase 8: convert -O vhdx --subformat fixed¶

    Phase 8 of PLAN-bat-population.md. Read its Situation ("What qemu-img actually emits", "What instar does today" and "Large outputs and the host"), open question 3 (convert writes blocks in place, no block_state_zero on convert), and the "Phases 8 and 9" paragraph of "Sequencing rationale" first. Also read the phase 6 plan's decisions 3 to 5, which define vhdx::layout, VhdxLayout::fixed_data_start / fixed_file_length and vhdx::fill_fixed_bat, and the phase 7 plan's decisions 1 and 5, which this phase mirrors for convert. This file assumes them.

    Planning effort: high, as the master plan sets for phase 8 (the convert writer's size and the guest/host boundary it crosses). The output's only external check is a structural comparison against a live qemu-img convert.

    Decisions already taken by the operator¶

    Every open question in the master plan was resolved with its recommendation adopted (Michael Still, 2026-10-21). The ones this phase carries out:

    • Open question 3: convert -O vhdx --subformat fixed writes blocks in place -- every payload BAT entry FULLY_PRESENT at fixed_data_start + block_idx * block_size, all-zero blocks left as holes, file length fixed_data_start + virtual_size. This is qemu's -o subformat=fixed,block_state_zero=off layout, not qemu's default convert-to-fixed layout (which appends new data after the preallocated region and leaves the rest ZERO). Convert exposes no block_state_zero; the divergence from qemu's default is documented.
    • Open question 4: never materialise a fixed BAT. The guest streams the BAT entries one buffer at a time with vhdx::fill_fixed_bat, as create does, instead of the dynamic path's in-memory bat_buf. The output device's capacity comes from the layout.

    None of these is revisited here.

    Scope¶

    In:

    • The host CLI. --subformat fixed (and dynamic) accepted for -O vhdx. The -o subformat=fixed path through apply_create_overrides is a create-only parser and does not apply to convert; convert takes only --subformat (survey).
    • The config. A new ConvertConfig flag bit carries the fixed signal to the guest. Convert has no subformat field in its config and needs none (decision 1). The struct layout does not change.
    • The host output file. For a fixed vhdx convert the host sizes and opens the output at vhdx::layout(...).fixed_file_length, sparse, before the guest runs, and maps EFBIG to a by-name refusal, exactly as phase 7's create does (decision 2).
    • The guest. convert_to_vhdx gains a fixed branch that streams the BAT through one buffer with vhdx::fill_fixed_bat and writes each non-zero payload block at its fixed offset, leaving zero blocks as holes (decision 3). The dynamic path is unchanged byte for byte.
    • Tests. Structural comparison of instar's fixed convert output against a live qemu-img convert -O vhdx -o subformat=fixed,block_state_zero=off of the same input, through tests/helpers/vhdx_structure.py; qemu-img compare identical; instar check clean; the 2 TiB case; the qemu-unreadable partial-last-block-past-first-chunk geometry (structure + instar check only). Mutation cases.
    • Documentation. docs/convert.md, docs/quirks.md (the in-place vs qemu-default convert-to-fixed divergence), convert --help, and CHANGELOG.md.

    Out:

    • measure. measure -O vhdx -o subformat=fixed is phase 9 and keeps its "not yet supported" refusal until then. Convert's output is measure's oracle, which is why measure follows convert.
    • Cross-version baselines. The fixed convert cases across every profile are phase 10. This phase proves it against the host qemu-img (one version); phase 1 found the structure version-independent.
    • Fuzzing. The differential fuzzer's convert picker learns the fixed subformat in phase 11.
    • docs/format-coverage.md. Its convert output-side rows and notes are phase 12's.
    • block_state_zero on convert. Future work (open question 3). The fixed convert layout is always the in-place one.
    • convert -O vpc fixed output. instar converts to dynamic VHD only; Future work.
    • The dynamic convert writer's in-memory-BAT silent failure (src/operations/convert/src/main.rs:4462). Fixed convert avoids it by streaming, but the dynamic path keeps its in-memory bat_buf. The survey confirms whether the dynamic silent path is reachable from the CLI and records the answer (decision 6); fixing it is Future work.

    What the survey found¶

    All references are to origin/develop at d88c6e37 (phase 7 merged as 03269d7f, #858). qemu claims are cited to instar-testdata/qemu-sources/7.0.0/block/vhdx.c or measured with the host qemu-img 10.0.13. No instar binary was built for this survey; step 8a's brief measures convert.bin.

    Phase 6 and 7 left convert almost everything it needs¶

    • vhdx::layout(virtual_size, block_size, false) already returns fixed_data_start and fixed_file_length (src/crates/vhdx/src/lib.rs:4134, :4141), and vhdx::fill_fixed_bat(&layout, state, first_entry, buf) (src/crates/vhdx/src/lib.rs:4374) fills a buffer of BAT entries from an index range. Both are in the vhdx crate, which convert already links (convert_to_vhdx calls vhdx::layout, vhdx::build_bat_entry, vhdx::PAYLOAD_BLOCK_FULLY_PRESENT, vhdx::METADATA_ITEMS_MIN_OFFSET). VhdxSubformat, VhdxPlan and plan_vhdx live in the create crate, which convert does not link; convert does not use them and computes its geometry directly from vhdx::layout, as it does today.
    • The host's compute_output_capacity (src/vmm/src/main.rs:13957) already sizes VHDX convert output from vhdx::layout(vsize, block_size, false) (phase 5). For a dynamic convert it returns payload_blocks * block_size + data_start. For a fixed convert the capacity is fixed_file_length; this is the only new branch the capacity needs (the master plan's "capacity estimate replaced by the shared layout" is already done for dynamic).

    convert_to_vhdx builds its BAT in memory and packs payload¶

    convert_to_vhdx (src/operations/convert/src/main.rs:4382):

    • allocates bat_buf after the staging buffer and zero-fills it to all NOT_PRESENT (:4459-4470), refusing with "convert: VHDX BAT too large for scratch" and a successful completion if it does not fit (:4462-4466);
    • packs payload blocks sequentially from payload_start (next_free_offset), writing only non-zero blocks, and records each as a FULLY_PRESENT BAT entry at the packed offset (block_file_offset = align_up(next_free_offset, MB_ALIGN), vhdx_payload_bat_index(block_idx, chunk_ratio), vhdx::build_bat_entry(PAYLOAD_BLOCK_FULLY_PRESENT, block_file_offset), :4756-4762);
    • writes bat_buf out to the BAT region last, in oss-sized chunks ("Rewrite BAT with actual offsets", from :4900).

    The fixed path replaces all three: the BAT entries are a pure function of the index (FULLY_PRESENT at fixed_data_start + block_idx * block_size), so they stream through one buffer with fill_fixed_bat and need no bat_buf; payload blocks are written at their fixed offsets, not packed; and the file length is fixed_file_length, not the end of the last packed block.

    The host refuses --subformat for anything but vmdk¶

    --subformat is validated at src/vmm/src/main.rs:14080-14102: a non-empty --subformat on non-vmdk output is refused with "--subformat is only supported with VMDK (-O vmdk) output", and the vmdk arm admits monolithicSparse, streamOptimized, monolithicFlat. ConvertArgs.subformat (src/vmm/src/main.rs:7382-7386, struct at :4978) has a value_parser of ["", "monolithicSparse", "streamOptimized", "monolithicFlat"] -- it does not accept dynamic or fixed, so convert --subformat fixed is refused by clap before the host code runs. CreateArgs.subformat (:7478-7485) already carries dynamic and fixed (phase 7). Phase 8 adds them to ConvertArgs.subformat's parser and its doc comment, and opens the host gate to vhdx.

    Convert carries no subformat field to the guest¶

    ConvertConfig (src/shared/src/lib.rs:2606) has no vhd_subformat or vmdk_subformat field. The vmdk monolithicFlat subformat is handled entirely on the host (is_vmdk_flat_output retargets the guest at raw and the host writes the descriptor, :14439); monolithicSparse and streamOptimized are distinguished by other means in the sparse writer. So the fixed signal must travel as a flag bit. ConvertConfig's flags use bits 0-5 (FLAG_SKIP_ZEROS .. FLAG_DD_WINDOW) and 31 (FLAG_VERBOSE), so bits 6-30 are free (:2697-2718). One bit, FLAG_VHDX_FIXED = 1 << 6, is all this phase needs: convert's fixed layout is always block_state_zero=off, so no second bit for the block state (unlike create, which carries FLAG_VHDX_FULLY_PRESENT for its block_state_zero=off variant).

    The error paths keep a zero-byte output¶

    Every convert_to_vhdx failure arm calls send_complete(..., false) (:4463, :4475, and the layout-error arm at :4428), whose comment notes that without a failed completion the host keeps an empty output file. A failed instar convert already leaves a zero-byte file (master plan Future work); the fixed path inherits that and does not change it.

    The tests and docs that see this¶

    • TestConvertToVhdx (tests/test_convert.py:3426) holds convert's VHDX round-trip tests; tests/test_vhdx_structure.py and tests/test_vhdx_fixed_fixtures.py hold the structural comparator and the fixed-fixture builders. The new fixed-convert class goes beside TestConvertToVhdx and reads through tests/helpers/vhdx_structure.py.
    • docs/convert.md:85-103 describes vhdx as dynamic-only output and lists --subformat as a vmdk option; :110-133 cover differencing. The --subformat help on ConvertArgs (:7382-7386) names vmdk subformats only.

    Decisions¶

    1. The fixed signal is a ConvertConfig flag bit, not a subformat field. ConvertConfig::FLAG_VHDX_FIXED: u32 = 1 << 6 in src/shared/src/lib.rs, with its host mirror CONVERT_CONFIG_FLAG_VHDX_FIXED beside the others at src/vmm/src/main.rs:119-127. The host sets it only for -O vhdx with --subformat fixed. Convert's fixed layout is always block_state_zero=off (open question 3), so one bit is enough and no block_state_zero flag is added. ConvertConfig's size and field offsets do not change, and the existing layout assertions must still pass unchanged.

    2. The host extends the fixed output to fixed_file_length at open, and maps EFBIG by name. This mirrors phase 7 decision 1, for the same three reasons (the filesystem failure is the host's to report; the guest cannot make the file the wrong length when the device capacity is the layout's file length; it is what qemu does). For a fixed vhdx convert the host computes vhdx::layout(out_vsize, block_size, false) and opens the output with capacity layout.fixed_file_length, sparse (set_len before the guest runs). An EFBIG from that becomes convert: a fixed VHDX of <virtual size> bytes needs a <file length>-byte file, which the filesystem holding '<filename>' cannot store, followed by the OS error, matching phase 7's create message in shape. compute_output_capacity gains a fixed argument (or a sibling that returns fixed_file_length); for dynamic output it is unchanged.

    This is the decision a reviewer is most likely to dispute, for the same reason it was in phase 7: the master plan's prose leaves file extension unspecified for convert, and a reader might expect the guest to extend the file as the dynamic packed writer effectively does by writing its last block. Host extension is chosen to keep the create and convert fixed paths identical in where the file length is decided, and because the guest's capacity check then catches a host/guest layout disagreement.

    1. The guest streams the BAT and writes payload in place. When FLAG_VHDX_FIXED is set, convert_to_vhdx:

    2. computes layout.fixed_data_start and fixed_file_length from the same vhdx::layout call it already makes;

    3. checks the device capacity is at least fixed_file_length before writing anything, failing with a failed completion if not;
    4. streams the BAT with vhdx::fill_fixed_bat(&layout, PAYLOAD_BLOCK_FULLY_PRESENT_state, first_entry, buf) one buffer at a time, writing each slot's sectors into the BAT region, exactly as create's emit_vhdx_fixed_bat does -- no bat_buf, no ALLOC_HEAP_BASE ceiling check, so the fixed path cannot hit the dynamic path's "VHDX BAT too large for scratch" failure;
    5. writes each non-zero payload block at fixed_data_start + block_idx * block_size (not packed), leaving zero blocks as holes so the file stays sparse;
    6. reports fixed_file_length as the bytes-written / file-size-after the host prints.

    The streaming lives in one #[inline(never)] function beside the dynamic path, for the x86_64-unknown-none codegen reason the create, commit and bitmap ops document (src/operations/amend/src/main.rs:211). The dynamic path keeps its bat_buf and packing, byte for byte unchanged.

    1. Convert exposes no block_state_zero, and the divergence is documented. instar convert -O vhdx --subformat fixed always produces the in-place (block_state_zero=off, every entry FULLY_PRESENT) layout. qemu's default qemu-img convert -O vhdx -o subformat=fixed appends new data after the preallocated region and leaves the untouched entries ZERO (Situation: a write to a ZERO-state block allocates at end of file). instar's layout equals qemu's -o subformat=fixed,block_state_zero=off, which is the oracle the tests use. docs/quirks.md records that instar's convert matches qemu's block_state_zero=off convert, not its default.

    2. The oracle is a live qemu-img convert, compared structurally. A new class TestConvertVhdxFixed in tests/test_convert.py, beside TestConvertToVhdx, for each input (a raw and a qcow2 source with a mix of zero and non-zero blocks):

    3. runs instar convert -O vhdx --subformat fixed and qemu-img convert -O vhdx -o subformat=fixed,block_state_zero=off of the same source to separate outputs;

    4. asserts structural_diff through tests/helpers/vhdx_structure.py is empty for every structural field (region table, File Parameters LeaveBlocksAllocated, block size, every BAT entry, file length), with no masking;
    5. asserts qemu-img compare reports the two identical, and instar check and qemu-img check both exit 0;

    6. asserts --subformat fixed on a non-vhdx target, and a --subformat value the parser does not know, are refused.

    7. The dynamic silent-failure reachability is settled, not fixed. Step 8a determines whether the dynamic bat_buf ceiling (:4462) is reachable from the CLI (a large dynamic VHDX at a small --block-size of a source big enough to need a BAT past the scratch budget), by computing the smallest --block-size / source size that trips it and checking the host does not refuse first. The finding is recorded in the master plan's Future work (and an issue filed if the operator's permission allows); fixed convert's streaming is not a fix for the dynamic path.

    Risks and mitigations¶

    • A fixed convert image that is structurally right and still has the wrong data. The structural comparator sees the BAT and regions, not payload. qemu-img compare against qemu's own fixed convert (decision 5) covers the data for the small cases; instar check and a convert -O raw round-trip cover the large ones. The management session spot-checks one round-trip to raw equals the source.
    • The dynamic convert path changes by accident. The cmp against a d88c6e37 build in 8a's brief, repeated by the management session on one size.
    • The host and guest disagree about the fixed layout. Both call vhdx::layout with the same out_vsize and block_size. The guest's capacity check (decision 3) catches a host that sized the device too small; the structural comparison catches a file of the wrong length. The management session confirms the host passes the guest the same block_size it sized the device with.
    • convert.bin grows past the 768 KiB cap. make check-binary-sizes after 8a; 8a reports the size before and after. The filler is already compiled in the vhdx crate convert links, so the addition is the one new guest function plus the branch.
    • The 16 TiB test skips everywhere CI runs. Acceptable (a host-filesystem fact), but the RLIMIT_FSIZE variant exercises the EFBIG path on any filesystem, and the skip reason names the probe.
    • Host contention looks like a regression. Replay any failure alone (--concurrency 1) before attributing it.
