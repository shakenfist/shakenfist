    Differencing phase 18: the push audit¶

    Prompt¶

    Plan phase 18 of PLAN-differencing.md, the mandatory push audit. Phase 17 landed in 60e4381c (#659), which completes the plan's substantive work: seventeen phases that pinned the semantics, built parent-locator parsing, wrote two emitters, closed a silent parent-ignoring read, built sector-granular composition in the guest for VHD and VHDX, rolled it out across the chain-walking operations, settled which operations still refuse, tested and fuzzed the result, and documented it.

    This phase runs PUSH-AUDIT.md over all of it. The phase plan is the deliverable; implementation is a separate ask.

    Planning effort¶

    High, and the survey earned it. The audit instrument is broken in a way that would have produced a green audit of nothing, and the breakage is not the one the previous push-audit phase in this repository found and fixed.

    Review effort: medium. The plan proposes no behaviour change. The judgement is in Decision 1, which spends a step repairing tooling before auditing anything, and in Decision 3, which overrides the runbook's own recommended models.

    Scope¶

    In scope. PUSH-AUDIT.md run over the union of what put phases 1 to 17 on develop, plus the repair to the audit scripts that running it over a merged plan requires, plus triage and disposition of every finding.

    The range is seventeen merge commits in instar, taken from the master plan's Merged column:

    8b81a0f 1a677c77 42e879f f981374 9a80776 882d098 99d7d24 c416abd
044ad77 036252f c66f8b2 b4ae7fc d677823c 7fef1321 f14554cf d7a4973f
60e4381c

    plus 01153800, which is already on this branch: it rewrites comments phase 4 wrote and is differencing work by content even though it post-dates phase 17's merge. Nothing else on this branch is in scope — the close-out commit 09f6ecca is bookkeeping.

    Out of scope.

    • Fixing anything the audit finds that is not a defect this plan introduced. Findings against pre-existing code are reported and filed, not fixed here.
    • The nine open issues phases 11 to 17 handed over (#628, #632, #641, #642, #643, #651, #653, #654, #658). The audit may add to that list; it does not work it.
    • The remaining PLAN-* citations in src/ that 01153800 left behind. They are provenance for measured byte layouts and need the measurements inlined or rehomed, which is a documentation task of its own; see Deferred work.
    • REVIEWS.md, per the plan-phase-landing shared block.

    What the survey found¶

    Three findings, in descending order of how much they change the phase.

    The audit scripts would have audited nothing¶

    Every diff-scoped check in both scripts derives its file set from git diff develop...HEAD:

    • tools/audit/wave1.sh:112 (long lines in changed Rust) and :140 (adversarial fixtures added in the wrong repository).
    • tools/audit/wave2-mechanical.sh:24, 38, 47, 51, 58, 89, 103, 120, 130 — which is every one of its nine checks.

    On a push-audit branch that range does not mean what the checks assume. Every phase has already merged, so it covers only what this branch itself adds. Measured on this branch, after the close-out and the comment cleanup: 3 files, 12 insertions, 9 deletions, one Rust file — against the 103 files and 30 Rust files the phase is supposed to audit. The checks are not vacuous, which would at least look odd; they are scoped to roughly two hundredths of a percent of the work and report cleanly on it.

    Each script guards on git rev-parse --verify develop, which succeeds, so nothing warns. For a plan whose phases have all merged and which carries no commits of its own the range is empty, and the output is then indistinguishable from a clean audit — the exact hazard the plan-push-audit-phase shared block names, "a diff against the default branch is empty and would read as a clean audit", sitting unfixed inside the instrument built to execute that block. This branch escapes the empty case only by accident, because the close-out commit happens to ride on it.

    The previous push-audit phase in this repository did not catch it. PLAN-fuzz-autofix-phase-02-push-audit.md:212-218 records wave2-mechanical.sh as empty and explains it by content — "this plan added no Rust and the range holds only plan documents" — which was true and which is why the structural cause went unnoticed. That phase reconstructed a patch by hand for its judgment agents (its Decision 1) and left the scripts computing from develop...HEAD.

    Differencing is where the difference bites. It changed 30 Rust files and added five fuzz targets, so the checks for new unsafe blocks, new .unwrap()/.expect(), new #[test] counts, VMM-boundary unsafe, and misplaced adversarial fixtures are all checks with something real to find. Hence Decision 1.

    The wave 2 judgment briefs in PUSH-AUDIT.md carry the same expression in prose (2a's says "the diff (git diff develop...HEAD)"), so they mislead a sub-agent in the same direction.

    This survey finding was then under-acted on: the first implementation added the exit-code row to the runbook's table and left all five briefs saying git diff develop...HEAD, which the second review round caught. Fixing the scripts without fixing the runbook they are documented in would have left the next push-audit phase reading the wrong scope from the prose while the scripts resolved the right one. PUSH-AUDIT.md now defines the audit scope once, under The audit scope, says that a push-audit phase must pass --commits-file and why, and each of the five briefs tells its sub-agent to read the patch the management session hands it rather than recomputing a diff of its own.

    That fix then needed a third round, because the recipe it pointed the briefs at was itself wrong: git diff <merge>^1 <merge> > scope.patch covers one merge, and run once per merge the > truncates, so only the last survives. Measured on a two-merge scope, the union is 7,733 lines and the hand-rolled recipe produced 4,261 of them with nothing to say it had -- the same subset-read defect as the original finding, reintroduced one layer out by the fix for it. The recipe is now tools/audit/scope-patch.sh, which uses the library, writes the banner to stderr so the patch on stdout stays clean, refuses an unresolved scope, and is covered by four cases in test-audit-scope.sh including a comparison against the recipe it replaced.

    A fourth round then found the same shape again, in the tests themselves. Every history-dependent case -- the line-attribution check the file's own header called decisive, the scope-patch.sh union and truncation comparisons, and the only end-to-end run of a valid --commits-file through a wave script -- took a SKIP branch in the ci-tooling job, which checks out at fetch-depth: 1. CI therefore never ran any of them, and a SKIP that always fires is a pass standing in for a check that never happened: this phase's headline defect, inside the tests written to prevent it. Every case is now built on a generated fixture repository, the scripts that resolve their own repository root are copied into it, and no suite has a SKIP branch left. The same round also found that the line-attribution awk cut any path at its first space (f2 with space.rs became f2) and read an added line whose content began with ++ as a file header, dropping it and attributing everything after it to an invented path -- both wrong-but-plausible locations of exactly the kind it was written to stop reporting, and neither covered by its fixtures.

    The union of merge ranges exists, and is complete¶

    Unlike the fuzz-autofix precedent, which had no range to audit and reconstructed one commit by commit, this plan's Merged column was filled as each phase landed. Verified row by row: phases 1 to 17 all carry a cell, and the master plan's claim at :28-32 that the column is "filled in as each phase lands, not reconstructed afterwards" is true.

    Measured scope:
    Merge commits 17 in instar, 3 direct commits in instar-testdata
    Patch lines 54,821 added or removed
    Distinct files 103
    By area 39 docs/, 30 src/, 16 tools/ and scripts/, 7 tests/, 4 .github/workflows/

    For comparison the fuzz-autofix audit read 7,887 lines. This is 6.9 times that, which is what drives Decision 2.

    One trap worth naming because the survey fell into it: phase 2's Merged cell holds four commits across two repositories, and the instar one is last, after a semicolon — instar-testdata 77f5f589f0 + 623a30866f + 3eed61bf75 (direct to main); instar 1a677c77 (#552). The first pass of the sizing read the instar-testdata shas, missed 1a677c77, and silently left 1,764 insertions out of scope. Every other row holds one sha.

    The instrument's other known breakage is already fixed¶

    tools/audit/inline-script-check.awk is the one mechanical check with something to say about a YAML-and-bash diff, and the fuzz-autofix audit found it broken three ways: NR where it meant FNR, a head -20 truncation, and block tracking that ended at the first blank line. All three are fixed, each named in the awk's own header comment at :15-18, the last by 7e83a0d0 ("End run-blocks at the first real dedent"). Phase 18 does not need to repair it, which the precedent did as its step 1.

    Two things inherited rather than discovered¶

    • Workflow run: blocks are unchecked for unquoted variables. .github/actionlint.yaml:26-29 disables SC1090, SC2046, SC2086 and SC2143 for .github/workflows/*.yml, and the shellcheck pre-commit hook is scoped files: ^(scripts|tools)/ (.pre-commit-config.yaml:56). Differencing touched four workflows, so their run: blocks are checked by nothing. The precedent recorded this as applying to "every remaining workflow"; phase 18 inherits it. Confirmed against both config files, not assumed.

    Unusually for this skill, the survey found no false claim to fix in the master plan. Phase 18 has no prose bullet in the phase list — it appears only as the Execution table's last row, as the statement at :28-32 that the plan carries the mandatory audit, and as a success criterion at :878.     Decisions¶

    1. Repair the scripts before running them, rather than working around them in the briefs. The precedent's approach — reconstruct a patch by hand, hand it to the agents, leave the scripts alone — produced a correct audit and left the next plan to rediscover the same thing. Nine mechanical checks silently reporting clean is a defect in a tool whose entire purpose is to be trusted before a push, and every future push-audit phase in this repository inherits it.

    So step 1 gives both scripts an explicit scope: a --range or --commits-file argument naming what to audit, defaulting to today's develop...HEAD so the ordinary pre-push use is unchanged. It must also report the resolved file count and refuse an empty set rather than reporting zero findings. "No changed files" and "no findings" have been indistinguishable in this tool's output since it was written; printing the count is what makes a wrongly-scoped run visible, and on this branch the wrong scope is a small set rather than an empty one, so the empty-set refusal alone would not have caught it.

    This is the one decision a reviewer might argue with: it spends a step on tooling inside a phase whose job is to audit, and a push audit is not obviously the place to fix the auditor. The argument for doing it here is that the alternative is auditing with an instrument known to be broken, and that the repair is small, local, and testable — tools/audit/ already carries test-inline-script-check.sh, so the pattern for a test exists.

    1. Partition the judgment agents by dimension, not by phase. At 54,821 lines no agent reads the whole patch well, so it has to be split. Splitting by phase is the obvious cut and it is the wrong one: the shared block's stated reason for auditing the accumulated diff is to catch "what the phases did to each other — the duplicated helper that only exists once phases three and six have both landed, the doc page that phase two made wrong and phase five never revisited". Seventeen per-phase agents reproduce exactly the per-phase audit the block forbids.

    Splitting by dimension keeps each agent's cross-phase view intact within its own concern, and the dimensions already map onto file areas that barely overlap: 2a and 2b read src/ and tests/, 2c reads docs/, 2d reads the parser and host-resolution paths. Each agent gets the union patch restricted to its paths and the current state of those files, because a patch shows what changed and not what the tree now says.

    1. Override the runbook's recommended models for 2a, 2b and 2d. PUSH-AUDIT.md specifies sonnet at medium effort for 2a. That setting is calibrated for a single pull request's diff. Three of the four dimensions here are reading a seventeen-phase accumulation in which the findings worth having are structural, so they go to opus at high effort. 2c stays on sonnet at high effort: phase 17 swept the documentation six commits ago, so its cross-page consistency is freshly established and the brief can name exactly what was settled.

    Stating this explicitly because a sub-agent handed the runbook will otherwise read its model table as authoritative and this plan's as a suggestion.

    1. 2d gets the longest brief and the most scepticism. Differencing parses parent locators out of untrusted image headers and the host then resolves them into filesystem paths. The plan deliberately built adversarial fixtures for this — vhd-diff-locator-dotdot, -etc-passwd, -unc, -url, -overlong, -conflicting — which means the attack surface is known and the question is whether the code's answer to each is still what phase 4 decided. Issue #658, filed during phase 17, is a live example of a resolution rule being less obvious than it looks.

    2. No agent is spawned for instar-testdata. Its phase 2 contribution is 14 LFS pointers and nothing else; there is no source to review. What is worth checking is on the instar side and goes into 3b's brief: that every fixture those commits added is still referenced by tests/manifest.json, and that none has been orphaned by later phases the way vhd-diff-base.vhd was in 623a30866f. Recorded here so a reader does not read the omission as the cross-repo obligation being skipped.

    3. Findings are triaged in the management session, not by the agent that found them. Each agent reports; step 4 assigns every finding blocking, advisory-fix-now, or filed-as-issue. Agents that fix what they find produce a diff nobody planned, and this phase's whole value is the judgement about which findings matter.

    Risks and mitigations¶

    Risk Mitigation
    The repaired scripts change behaviour for ordinary pre-push use, and nobody notices until a real push Step 1's test asserts the default path is unchanged, and the default stays literally develop...HEAD. The option is additive.
    Step 2 transcribes the commit list wrongly and the audit silently reads a subset Step 2 checks the materialised patch against 54,821 lines and 103 files before anything reads it. That number is in this plan, measured, and a mis-transcription moves it. This is also why the scripts must refuse an empty set rather than report clean.
    An agent reports the runbook's recommended model and effort as authoritative and under-reads its dimension Decision 3 states the override and the reason; each brief carries its own effort and model in the step table, which is what the implementer follows.
    3a-3d collectively miss a cross-dimension defect, since the partition is by concern Step 4 reads all four reports together, and the one question the partition cannot answer — does a documented claim match the code — is already answered elsewhere: phase 17's definition of done required the compose/refuse split to be checked against the refusal sites rather than a sibling document.
    The audit finds a defect in code a phase deliberately decided Nine issues are already open from phases 11 to 17 and the plan's Decisions record the choices. Step 4 checks a finding against the deciding phase's plan before calling it a defect; a disagreement with a recorded decision is filed, not fixed.
    Agents assert plausible-but-wrong format or tool capabilities, which this repository's history says they do The master plan's standing warning applies: cite-or-measure for every claim about what libvhdi, Hyper-V or qemu accepts, and step 4 re-measures a sample before accepting it.

    Negative results worth recording¶

    A push audit that reports only findings does not tell a reader which ground was covered. These were measured, not read.

    • The refusal invariant holds. Phase 4 established that a refusal must never depend on whether the parent file happens to exist, because the opposite leaks filesystem existence to whoever supplied the image. Each refusal site was run twice over the same image, once with the named parent absent and once with a real parent planted at exactly the path the image names: check, measure and map gave byte-identical messages and rc=1 both times.
    • No filesystem-existence oracle. Four crafted VHDs naming an existing file, a missing file, an existing directory and a missing directory all produced identical reasons. An out-of-allowlist absolute reference is never probed; a .. escape is judged from its spelling.
    • Every VhdState::init / VhdxState::init caller refuses or composes. This is the check phase 14 made necessary by removing VhdxState::init's own rejection. All callers enumerated and, where reachable, executed. None forgot.
    • Chain depth and cycles: one choke point, guarded. All 11 walks go through discover_backing_chain, which runs the circular and depth checks before each hop. Measured with a self-referencing VHD, a two-image cycle and a 41-deep chain. No bypass found.
    • No unbounded allocation from a length field, and the padded BAT bound is correct including its off-by-one: for g groups the last bitmap entry sits at padded - 1 and the check is >=.
    • Terminal and bidi injection neutralised in the parent field this plan made user-visible.
    • The libvhdi oracle hazard is real but cheap. With the oracle present and INSTAR_REQUIRE_LIBVHDI=1: Ran: 1273, Passed 1257, Skipped 16, Failed 0, and zero differencing skips. Only 7 of ~100 differencing tests touch the oracle, and primary assurance is the recorded *-composed.raw goldens, which are oracle-independent. CI sets the variable on the right job.
    • Three deliberate mutations were all caught, including one to a parent-owned payload sector inside vhd-diff-parent.vhd, which proves instar genuinely sources those bytes from the parent -- the direct inverse of issue #547.
    • No dead code. All 84 public items the plan added were checked for uses outside their defining file; the 21 with none are measured byte-offset constants used by their own layout tests.
    • The production unsafe surface of this entire plan is seven function signatures. Of the 171 added lines containing unsafe, none is under src/vmm/**, 51 are #[cfg(test)] mock call tables, 20 are fuzz harness, and 19 of the apparent qcow2 total are a diff-alignment artifact blame-verified to pre-plan commits.
