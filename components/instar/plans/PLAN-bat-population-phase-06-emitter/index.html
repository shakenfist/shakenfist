    Phase 6: the streaming BAT filler, the fixed plan_vhdx, and qemu's VHDX structure¶

    Phase 6 of PLAN-bat-population.md. Read its Situation ("What qemu-img actually emits" and "What instar does today"), open questions 4, 7 and 8, and the phase 6 paragraph of "Sequencing rationale" first. This file assumes them, and corrects that paragraph where the survey found it incomplete.

    Planning effort: high, as the master plan's guidance sets for phases 6 and 7: they emit structures whose only external check is a structural comparison. The survey also found that instar's shared VHDX builders differ from qemu's in more fields than the master plan knew, and that fixing them changes the bytes of every VHDX instar writes (decision 1).

    Decisions already taken by the operator¶

    Every open question in the master plan was resolved with its recommendation adopted (Michael Still, 2026-10-21). The ones this phase carries out:

    • Open question 4: never materialise a fixed BAT. Each entry is a pure function of its index, so a filler writes one caller-supplied buffer of entries at a time.
    • Open question 7: dynamic VHDX does not honour block_state_zero. Its BAT stays NOT_PRESENT.
    • Open question 8: a fixed image's default block_state_zero is qemu's, on, so every payload entry is PAYLOAD_BLOCK_ZERO.

    Neither is revisited here.

    Scope¶

    In:

    • qemu's structure in the shared VHDX builders, for every writer (decision 1). The region table's Required bit, the metadata items' placement and flags, and the physical sector size. These are vhdx::build_region_table and vhdx::build_metadata, which create, convert and resize all call.
    • The fixed layout rule: qemu's data start and file length for a fixed image, on VhdxLayout (decision 3).
    • The streaming BAT filler in the vhdx crate (decision 4).
    • A fixed subformat in plan_vhdx, which returns the structure writes plus everything the guest needs to stream the BAT and extend the file (decision 5).
    • Crate tests against qemu's pinned structure, and mutation cases kept in tools/mutate-differencing.sh (decisions 6 and 7).

    Out:

    • Any guest or host change for fixed output. The create op keeps asking for a dynamic image, and the host keeps refusing subformat=fixed. Streaming the BAT through the guest, extending the file, the output device's capacity and the CLI are phase 7. Convert's fixed path is phase 8, and measure's is phase 9.
    • Dynamic VHDX's file length and BAT state (decision 2). qemu extends a dynamic image to its data start and writes ZERO entries by default. instar stops at the end of the metadata region and leaves the BAT as a hole. After this phase those are the only two fields in which instar's dynamic create differs from qemu's.
    • A dynamic writer's payload start. VhdxLayout::data_start keeps its meaning, the end of the metadata region, where convert's dynamic writer packs blocks and measure predicts it does.
    • Fuzzing the filler and the fixed planner. Phase 11. This phase only keeps fuzz_create_emitters compiling.
    • Documentation. No user-facing page describes the fields this phase changes, and fixed output is not reachable from the CLI until phase 7 (survey). Phase 12 owns docs/format-internals.md's VHDX section. The changed output itself gets a CHANGELOG.md entry here, added at review (see Execution notes), because the change ships with this pull request rather than with phase 12.
    • Any call-table struct layout change. Nothing here needs one.

    What the survey found¶

    All references are to origin/develop at f224e881, built with make instar in this worktree. qemu claims are cited to instar-testdata/qemu-sources/7.0.0/block/vhdx.c or measured with the pins in tests/golden/qemu-create-pins.json, which every one of the 80 static builds agrees on.

    instar's dynamic output differs from qemu's in five fields, not two¶

    The master plan names two structural divergences for this phase: the Required bit and the physical sector size. Running every dynamic pin case through instar's create and helpers.vhdx_structure.structural_diff gives five, on vhdx-dynamic-64M-bsz-off, vhdx-dynamic-64M and vhdx-dynamic-131041M-block-1M alike:

    Field instar qemu Where instar writes it
    Region table Required, BAT and metadata, both tables 1 0 build_region_table, src/crates/vhdx/src/lib.rs:3343, :3350
    Metadata item flags, Virtual Disk Size, Page 83, Logical and Physical Sector Size 4 (IsRequired) 6 (IsRequired, IsVirtualDisk) build_metadata, :3390-3423
    Metadata item offsets FP 65536, VDS 65544, LSS 65552, PSS 65556, Page 83 65560 FP 65536, VDS 65544, Page 83 65552, LSS 65568, PSS 65572 build_metadata, :3438-3468
    Physical sector size 4096 512 PHYSICAL_SECTOR_SIZE, :3914
    File length 4 MiB (end of metadata) 8 MiB (qemu's data start) plan_vhdx, src/crates/create/src/lib.rs:1435

    plus the BAT state at the default block_state_zero (instar NOT_PRESENT, qemu ZERO), which open question 7 keeps.

    qemu's values come from vhdx_create_new_region_table, which never sets a region entry's data_bits (so Required is 0), and vhdx_create_new_metadata (:1568-1680). The latter places File Parameters, Virtual Disk Size, Page 83, Logical and Physical Sector Size in that order from 64 KiB, flags File Parameters IS_REQUIRED and the other four IS_REQUIRED | IS_VIRTUAL_DISK (:1626-1661), and writes the logical sector size as the physical one (:1611). build_metadata's own comment says it writes "IsRequired | IsVirtualDisk" and writes 0x04, which is IsRequired alone.

    The comparator compares every one of these fields, so phase 7's "structurally identical to qemu" criterion cannot hold for a fixed image while the builders write instar's values.

    Other writers agree with qemu on two of the fields, not all¶

    Two fixtures in tests/manifest.json were not written by qemu: vhdx-disk2vhd (Microsoft Sysinternals Disk2VHD) and qemu-vhdx (iotest-dynamic-1G.vhdx, a sample image from qemu's iotests whose metadata region sits before its BAT in the file, which qemu's region table builder never does). Parsed with the comparator:

    Field Disk2VHD iotest image qemu instar today
    Required 1 1 0 1
    Virtual-disk item flags 6 6 6 4
    Page 83 item placement after VDS last after VDS last
    Physical sector size 512 4096 512 4096

    So instar's metadata flags are wrong against every writer. instar's Required bit matches both other writers and not qemu, and its physical sector size matches the iotest image and not qemu or Disk2VHD. Decision 1 chooses qemu's values, because qemu is this plan's oracle, and says why.

    The builders have three callers, and resize is one¶

    build_region_table and build_metadata are called by plan_vhdx (src/crates/create/src/lib.rs:1461, :1470) and convert_to_vhdx (src/operations/convert/src/main.rs:4546, :4616). resize calls build_region_table (src/crates/resize/src/vhdx.rs:304, :311) when it moves the metadata region of an existing image, so after this phase a resize writes Required 0 into a table that had 1. Nothing reads the bit for the two regions every reader must know, and qemu-img cannot resize a VHDX at all, so there is no oracle to match. The qcow2 crate's VHDX test fixture builder calls both (src/crates/qcow2/src/lib.rs:11405, :11412) and is test-only.

    qemu's fixed layout, at the byte¶

    From vhdx_create_bat (:1690-1767):

    • The data region starts at bat_offset + bat_region_length + 5 MiB (:1708): 4 MiB past the end of the metadata region, "a 4 MB buffer for future expansion". At 64 MiB with 8 MiB blocks that is 8 MiB. With a 17 MiB BAT (2 TiB at 1 MiB blocks) it is 24 MiB, and at 64 TiB with 1 MiB blocks (a 513 MiB BAT) it is 520 MiB. VhdxLayout::data_start is the end of the metadata region, 4 MiB earlier.
    • A fixed file is truncated to data_start + image_size (:1720), where image_size is the size already rounded to 512. A dynamic file is truncated to data_start (:1714), which is the 8 MiB in the table above.
    • Every payload block gets an entry by emulating one write per block (:1745-1756). The BAT index is i + i >> chunk_ratio_bits (vhdx_block_translate, :1130), so sector-bitmap slots are never written and stay zero. A FULLY_PRESENT entry's offset is ROUND_UP(data_start + i * block_size, MiB) (:1749), which is already MiB-aligned because both terms are. A ZERO entry's offset is forced to 0 (vhdx_update_bat_table_entry, :1295: Hyper-V refuses a non-zero FileOffsetMB on one).
    • The state is FULLY_PRESENT for fixed, overridden to ZERO when block_state_zero is on (:1741-1743).
    • The whole BAT region is written in one blk_pwrite, padding included. Entries past the last needed one are zero, which a hole reads as.

    The pins agree: vhdx-fixed-17M-bsz-off is three FULLY_PRESENT entries from 8388608 with stride 8388608, file length 26214400. vhdx-fixed-131041M-block-1M-bsz-off is 31 repeats of 4096 FULLY_PRESENT entries plus one sector-bitmap slot, then 4065 more entries from index 127007 at offset 133152374784, file length 137414836224. vhdx-fixed-64M and vhdx-fixed-17M are all ZERO at offset 0. All four set LeaveBlocksAllocated. vhdx-fixed-backing fails on every build ("Backing file not supported for file format 'vhdx'"): qemu cannot create any differencing VHDX.

    The filler belongs in the vhdx crate¶

    convert links the vhdx crate but not the create crate (src/operations/convert/Cargo.toml), and phase 8's fixed path must use the same filler. qcow2's metadata preallocation is the precedent for the split. The qcow2 crate computes a layout and fills one L2 table per call (qcow2::create::compute_layout, build_l2_table). The guest loops over them, writes each through one reusable slot and extends the file with a zero sector (emit_qcow2_l2_and_extend, src/operations/create/src/main.rs:1147-1224).

    Decisions¶

    1. The shared builders write qemu's structure, for every writer. build_region_table writes Required 0 for both regions. build_metadata places the five items in qemu's order from 64 KiB (File Parameters 8 bytes, Virtual Disk Size 8, Page 83 16, Logical Sector Size 4, Physical Sector Size 4), lists them in the table in the same order, flags File Parameters IsRequired (0x4) and the other four IsRequired | IsVirtualDisk (0x6), and gains a leave_blocks_allocated: bool that sets File Parameters bit 0 (vhdx::FILE_PARAMETERS_LEAVE_BLOCKS_ALLOCATED, added by phase 4). PHYSICAL_SECTOR_SIZE becomes 512, as qemu writes the logical size in both items. The parent locator item still goes where build_metadata says its items end.

    This is the decision a reviewer is most likely to dispute, on two counts:

    • It changes the bytes of every VHDX instar writes, dynamic included, in a phase the master plan calls crate-only. The builders are shared, and the alternative is a builder that writes Required 1 for a dynamic image and 0 for a fixed one, from the same tool. That is two structures with no reason between them. No reader instar or qemu ships behaves differently on any of these fields: Required only matters for a region the reader does not recognise, and BAT and metadata are the two every reader must. The flags fix is a correction in its own right: instar's 4 matches no writer, and its comment says it writes 6.

    • On Required and the physical sector size, qemu and the other writers disagree, and this picks qemu. Both non-qemu fixtures write Required 1, and the iotest image a 4096-byte physical sector. This plan's success criteria define "correct" as structurally identical to qemu-img create, and instar's product is qemu-img parity. Keeping the other writers' values would mean every fixed-output test masks two fields for good, as TestCreateVhdxPinLayout does today. The cost is that a hypervisor that reports the image's physical sector size to its guest reports 512 bytes for an instar VHDX, as it does for a qemu-written one. The back brief puts this choice to the operator before 6a starts.

    • Dynamic output keeps its file length and its NOT_PRESENT BAT. After 6a, structural_diff between instar's dynamic create and each dynamic pin must name file_length and nothing else for a block_state_zero=off pin. For a default pin, it may also name only the BAT runs that differ in state, NOT_PRESENT against ZERO. The tests assert exactly that, so a later divergence cannot hide behind the masks they carry today.

    • qemu's fixed layout goes on VhdxLayout, beside data_start. Add fixed_data_start: u64, which is `bat_offset + bat_region_len

    • 5 MiB, andfixed_file_length: u64, which isfixed_data_start

    • virtual_size(the rounded size). Both use checked arithmetic and are computed for every layout. Their doc comments cite:1708and:1720, and say that qemu's dynamic file also ends atfixed_data_start, while instar's dynamic writers place payload fromdata_start.data_startkeeps its meaning, so no phase 5 consumer moves. Two fields with similar names invite the wrong one, so the doc comment on each names the other, and 6b adds a test that the two differ by exactly 4 MiB at every pin geometry. That test fails if either is ever redefined in terms of the other. At 64 TiB with 1 MiB blocks the fixed data start is 520 MiB and the file length is 64 TiB + 520 MiB, both well insideu64, andFileOffsetMB`'s 44 bits.

    • The filler. In src/crates/vhdx/src/lib.rs:

    pub enum FixedBlockState { Zero, FullyPresent }
pub enum BatFillError { UnalignedBuffer, PastRegion, Overflow }
pub fn fill_fixed_bat(
    layout: &VhdxLayout,
    state: FixedBlockState,
    first_entry: u64,
    out: &mut [u8],
) -> Result<(), BatFillError>

    out holds out.len() / 8 entries starting at BAT index first_entry. A length that is not a multiple of 8 is UnalignedBuffer. An entry at or past bat_region_len / 8, the region's capacity, is PastRegion. The function writes nothing in either case, so a caller cannot write a half-filled buffer. For each index j:

    • j >= bat_entries is padding: 0.
    • (j + 1) % (chunk_ratio + 1) == 0 is a sector-bitmap slot: 0.
    • Otherwise it is payload block p = j - j / (chunk_ratio + 1). Zero gives 2, with offset 0. FullyPresent gives (fixed_data_start + p * block_size) | 6, an offset in bytes whose low 20 bits are zero, which is FileOffsetMB in bits 20-63.

    That is qemu's forward map j = p + p / chunk_ratio inverted, which a test checks for every p at a small chunk ratio. It is the rule the reader's BAT lookup applies (block_index + block_index / chunk_ratio, src/crates/vhdx/src/lib.rs:2614) and the comparator's sector-bitmap test, and 6c's round trip reads every filled entry back through that reader. The filler is for an image with no parent. The planner refuses fixed with a backing file, and the doc comment says so. Entries are written little-endian. The function is no_std, panic-free and allocation-free, and uses checked arithmetic throughout, as the crate requires. It does not compute the layout. The caller passes the one layout returned, so the BAT and the region table come from the same values.

    1. plan_vhdx gains the subformat, and returns what the guest streams. VhdxCreateOpts gains subformat: VhdxSubformat (Dynamic or Fixed, a new enum beside VhdSubformat) and block_state_zero: bool. block_state_zero is read only for Fixed, and its doc comment says that dynamic output ignores it. plan_vhdx returns Result<VhdxPlan<'a>, CreateError>:
    pub struct VhdxPlan<'a> {
    pub metadata: MetadataPlan<'a>,
    pub fixed: Option<FixedVhdxPlan>,
}
pub struct FixedVhdxPlan {
    pub layout: vhdx::VhdxLayout,
    pub state: vhdx::FixedBlockState,
    /// Bytes of BAT that hold entries: bat_entries * 8. The rest of
    /// the region is padding, zero, and may stay a hole.

    Fixed sets LeaveBlocksAllocated through build_metadata, and Dynamic never does. The metadata writes are the same for both subformats apart from that bit, so metadata.minimum_file_size stays the end of the metadata region. The round-trip harness enforces that invariant.

The BAT the guest streams and the region table the plan writes must come from one call, which is the reasoning plan_vhdx's own comments give for sizing the BAT by the same fact as HasParent. The cost is that every caller reads .metadata. That is the create op, the tests and the fuzz target, none of which changes behaviour.

    1. The oracle is the pin, copied into the tests and checked by the management session. Crate tests encode, per pin case, every field the comparator compares.     The cases are:

    • materialised in memory (the largest is 73 MiB) and parsed back through the vhdx crate's reader: vhdx-fixed-16M, -17M, -64M, -65M, -64M-block-1M, each with and without -bsz-off;
    • checked through the filler alone, never materialised: vhdx-fixed-131041M-block-1M-bsz-off, 2 TiB at 1 MiB blocks (fixed data start 24 MiB, from the Situation's measurement), and 64 TiB at 1 MiB blocks (520 MiB, computed).

    1. The mutants are kept, not run from scratch. Each one below goes into tools/mutate-differencing.sh as a rust_case or integration_case, and the step that adds the code it breaks also adds the case:

    2. Required back to 1, and a virtual-disk item's flags back to 4 (6a).

    4. The 5 MiB dropped from fixed_data_start (6b).

    Phase 13's audit can then re-run every one. docs/testing.md's case list and the script's enforced count move with them, as in phase 5's step 5e.
