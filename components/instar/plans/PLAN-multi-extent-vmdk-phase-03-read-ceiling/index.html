    Phase 3: read side, lift the extent ceiling¶

    Status: In progress¶

    Part of PLAN-multi-extent-vmdk.md. Planned at high effort, as that plan's Planning effort section requires for the rotation and ABI phases.

    Scope¶

    In scope:

    • Remove the device-slot ceiling for a VMDK descriptor's extents, so a descriptor with any extent count up to the new documented bound is readable.
    • Add twoGbMaxExtentSparse as a readable input.
    • Read each extent's declared sector count rather than inferring 2 GiB from the create type.
    • Retire the four over-deep-chain guards for the extent case, and make DeviceSet::add_device's assert unreachable by construction for extents rather than by a caller remembering to check.
    • Make the virtqueue-region compile-time assert derive from MAX_CHAIN_DEVICES instead of a hard-coded 16 (#934).
    • Fix the chain printer's allocation figure (#927), which is the last unfixed member of #922's class and lands in this phase because this is the phase that touches the chain walk's extent handling.
    • Un-flag the five instar_unsupported fixtures and give them live baseline comparisons.

    Out of scope, and why:

    • The whole write path. Phases 4 to 11 own it. Nothing here emits a descriptor or an extent.
    • twoGbMaxExtent* as a backing file or inside a backing chain. Excluded by the master plan's scope. A split image is readable as the top image here; a split image with a parent stays refused.
    • instar map on flat sources, refused today for every flat source and wider than this plan. Recorded in the master plan's Future work.
    • The oracle hardening in #928. Items 1 and 2 there are latent until a chain baseline exists; this phase creates none. Item 3 is consumed by step 3f, which is a different change from the one #928 proposes, so #928 stays open for items 1 and 2.

    What the survey found¶

    The master plan's phase 3 intent was written before phases 1 and 2 ran. Six of its claims needed correcting, and the corrections are made at source in the master plan and index.md as part of this phase's registration commit, so a later reader does not trip over them.

    1. The line reference is stale. The intent cites "the guard at src/vmm/src/main.rs:15088 and its siblings". That line now holds sector-size validation. There are four guards, not one and some unspecified siblings:

    Operation Line What it bounds
    bench src/vmm/src/main.rs:6719 the chain's own device count
    check :13573 the chain's own device count
    compare :14405 both inputs' chains combined
    convert :15462 input chain plus the output device

    2. The real ceiling is a guest memory map, not MAX_CHAIN_DEPTH. The binding constraint is in src/shared/src/lib.rs: VQ_BASE_START is 0x00100000 (line 637), DMA_POOL_BASE is 0x00200000 (641), and a device's virtqueue takes 64 KiB (636). One mebibyte at 64 KiB each is exactly sixteen devices, and a seventeenth would land on the DMA pool. Four constants encode that 16 independently:

    Constant Location
    MAX_CHAIN_DEPTH src/vmm/src/main.rs:412
    max_chain_depth default src/vmm/src/config.rs:251
    MAX_INPUT_DEVICES src/core/src/main.rs:49
    MAX_CHAIN_DEVICES src/shared/src/lib.rs:5186

    MAX_INPUT_DEVICES covers input and output slots together (src/core/src/main.rs:210-213), which is where the intent's "15-extent limit" comes from: an operation holding an output device has fifteen slots left.

    3. The compile-time guard hard-codes its own 16. src/shared/src/lib.rs:664 asserts VQ_BASE_START + 16 * 0x10000 <= DMA_POOL_BASE with a literal rather than with MAX_CHAIN_DEVICES, so raising the constant does not trip it and the two silently disagree. Filed as #934 and fixed in step 3a.

    4. One extent already costs one device slot, by design. The intent reads as though extents were unsupported past a limit. In fact the host attaches the descriptor as device 0 and each extent as its own marked data device, and the guest's reader walks them as the descriptor's content -- src/crates/qcow2/src/lib.rs:15841, with vmdk_descriptor_reads_each_of_its_extents and vmdk_descriptor_extent_walk_stops_at_its_last_extent. This phase replaces a working, tested mechanism rather than filling a void, which raises what the definition of done has to prove.

    5. A second refusal the intent does not mention. Alongside the non-FLAT refusal at src/vmm/src/chain.rs:960, a non-zero offset_sectors is refused at :967. qemu's split subformats give each extent its own file at offset 0, so lifting that one is not required here; it stays refused and is noted in the master plan's Future work.

    6. "Inherits a VMM that already sums extent allocations" is half true. Phase 2 fixed the non-chain info paths. The chain walk still reports the descriptor's own apparent length at src/vmm/src/main.rs:3809. Measured against qemu-img 10.2.0 on vmdk-flat-with-parent.vmdk: qemu reports 1052672 for both chain members, instar reports 368. Filed as #927 during phase 2's review and pulled into this phase's scope.

    One further fact the intent could not have known, because phase 2 created it: all five instar_unsupported images in tests/manifest.json are the split-sparse fixtures this phase makes readable. Phase 2 added TestInstarUnsupportedIsStillUnsupported, which asserts the field is set on at least one image. When this phase succeeds, that assertion fails. That is the test working as designed, and step 3f owns the consequence.

    Decisions¶

    1. Host-side concatenation with a guest-visible extent table, not device-slot rotation. BackingStore (src/vmm/src/backing.rs:15) holds exactly one File today. It gains an ordered list of extent files and routes a device offset to the file that owns it, so a descriptor and all its extents occupy one device slot whatever the extent count. ChainConfig goes to version 5 carrying the extent table, so the guest can still find and parse each sparse extent's own header at a computed device offset.

    The master plan's open question 1 resolved to rotation, and this departs from it for the read path with the operator's agreement (2026-11-19). The reasoning the resolution did not have: there is no guest-to-host request channel in this architecture at all. The host writes CHAIN_CONFIG_ADDR before the guest starts and the guest does I/O through virtio; rotation would require inventing a channel for the guest to say "bind extent k" and block until it was done, which is ABI work the master plan scoped to phase 6. Concatenation needs no new channel, because a virtio request already carries the offset the guest wants.

    This is the decision most likely to be argued with, on the ground that the read side was meant to rehearse the mechanism the write side would reuse. It no longer does. The honest position is that the rehearsal argument assumed the mechanism had to live at the device-slot level, and for reads it does not; whether the write path can also route host-side is a real question, but it is phases 6 to 8's to answer, and this phase does not prejudge it. Recorded in the master plan's open question 1 so the change of mechanism is visible there rather than only here.

    1. Concatenation alone is not enough, and the plan says so plainly. For FLAT extents the extents are a plain concatenation and the guest needs nothing new. For twoGbMaxExtentSparse each extent carries its own header, grain directory and grain tables covering only its own span, so concatenated sparse bytes are not a valid image. The extent table is what makes sparse work: the guest resolves a virtual offset to an extent, then to that extent's own metadata at its own base. Any design that concatenates without telling the guest the boundaries reads sparse images wrongly, and would do it silently.

    2. The extent table carries three u64s and a kind per extent: the device offset where the extent's bytes begin, the extent file's length, the extent's virtual span in bytes, and whether that file is flat or sparse. The span cannot be derived from the length, because a sparse extent's file is shorter than its span and phase 2 measured a real image declaring 3.96 GiB extents under twoGbMaxExtentSparse. Reading the declared sector count rather than assuming 2 GiB is therefore not a refinement, it is the only thing that works.

    Amended 2026-11-19 by step 3c. Three u64s cannot say whether an extent is flat or sparse, and a guest left to work it out has to guess from the bytes. Looking for a sparse header would read a flat extent whose first sector happens to hold one as sparse; comparing the file's length with its span would read a sparse extent padded out to its span as flat. Either way one file means different bytes to instar than to qemu, which believes the type on the descriptor's extent line -- a line only the host has read. So the host states it: ChainExtent::kind is KIND_FLAT or KIND_SPARSE, and zero, the value a writer that never set it leaves behind, is refused rather than read as either.

    1. MAX_CHAIN_EXTENTS = 64, and the refusal above it is documented. ChainConfig lives at CHAIN_CONFIG_ADDR (0x000F2000) and the next region, VMM_PARAMS_ADDR, begins at 0x000F3000, so the whole structure must fit in 4096 bytes. At 32 bytes per entry -- 24 as first planned, plus the kind decision 3 now carries -- 64 extents costs 2048 bytes, which the page has room for; step 3a proves it with a free-standing const _: () = assert!(..) on size_of::<ChainConfig>() rather than by arithmetic in this plan. Sixty-four extents is 128 GiB at qemu's 2 GiB default and covers both corpus images (17 and 26 extents). qemu has no such limit, so this is a divergence: it is refused with a message naming the bound, recorded in the master plan's Future work, and lifting it means moving the config region rather than changing a constant.

    2. The guest's per-device extent walk is removed, not left alongside. Keeping both paths would mean two ways to read the same image and a silent dependence on which one the host chose. The two tests at src/crates/qcow2/src/lib.rs:15941 and :15982 are rewritten against the extent table rather than deleted, because what they assert -- that a read past the last extent stops and returns zeros instead of taking the next device -- is still the contract.

    3. This phase does not raise any of the four 16s. The ceiling stops applying to extents because extents stop consuming slots. Backing chain depth stays bounded at 16 and the four guards keep bounding it; what changes is that a descriptor's extents no longer count toward it. Raising the slot count is a separate change with a guest memory-map cost, and #934 records what it would involve.

    4. One live sparse-extent parser state at a time, not one per extent. The guest keeps a format state per device: chain_states.vmdk_states[dev_idx], and each device's grain directory and grain table caches come from shared::l1_cache_addr/l2_cache_addr, which hand out 2 * MAX_SECTOR_SIZE -- 128 KiB -- per device slot from a region sized 2 * MAX_SECTOR_SIZE * MAX_CHAIN_DEVICES, or 2 MiB in total. After step 3b a descriptor and all its extents are one device, so a state per extent would want 64 slots and 8 MiB of cache, which does not exist and cannot be made to exist inside the guest's memory map.

    So the descriptor device holds one VmdkState at a time, re-read when a read moves into a different extent, reusing that device's single pair of cache buffers. Sequential access pays for this once per extent boundary; a seeking workload pays per crossing, which is the honest cost and is bounded by a header read plus a grain directory read.

    Two consequences the implementer must not have to discover. VmdkState::init assumes its image begins at device offset 0, so it needs the extent's base offset -- everything it reads, header, grain directory and grain tables, is relative to that base. And the rotation this plan removed from the device slots reappears here, in the parser state. That is worth saying plainly: the master plan's instinct that this phase would rehearse a rotation was not wrong, only wrong about which layer rotates.

    1. Each extent file's place in the device is the running total of the lengths before it, rounded up to 512 (added 2026-11-19 by step 3d). The plan said the extent table's device_offset is where the extent's bytes begin and left the placement to the implementer, and those two things turned out to conflict: the reader requires a sparse extent's base to be a multiple of 512, because sparse VMDK counts 512-byte sectors from the start of its own file, while a real extent file's length is whatever it is. Rounding every extent's contribution up to 512, unconditionally, satisfies that for every extent without the placement depending on what the next entry is -- the alternative, padding only before a sparse extent, makes one extent's address depend on its neighbour's kind, which is the kind of rule that is correct when written and wrong after an edit.

    The table still carries the file's own length, not the rounded one, so up to 511 bytes between two extents belong to neither. Nothing addresses them: a flat read stops at file_length and zero-fills the rest of the span, a sparse read stays inside its own file, and the backing store returns zeros for a member's declared length past the end of its file. The host test that pins this gives the first extent a 1000-byte file and asserts that reading at offset 1000 returns zeros rather than the second file's first bytes.

    1. vmdk::MAX_EXTENTS is the extent table's size, not a number of its own (added 2026-11-19 in review of step 3d). The descriptor parser had its own cap of 32, justified in a comment that said twoGbMaxExtentFlat "caps at ~1TB/2GB extents per file so this limit comfortably covers any legitimate descriptor". That arithmetic is wrong -- 32 extents of 2 GiB is 64 GiB -- and it did not matter before this phase, because the 16-device ceiling refused such an image first. Lifting that ceiling promoted the parser's cap from dead to live, and would have shipped a phase that documents 64 and refuses at 33.

    So MAX_EXTENTS is now defined as shared::MAX_CHAIN_EXTENTS. The two bound the same thing, the smaller is what a user meets, and a constant defined in terms of the other cannot drift from it. It costs nothing measurable: the guest binaries are byte-identical, because the descriptor parser's array is transient rather than static. The corpus image that forced the question is 100 GiB in 26 extents of 3.96 GiB; written with qemu's 2 GiB default the same image needs 50.

    What step 3c hands step 3d¶

    The reader is in place and the host does not yet feed it. These are the constraints the reader now imposes, found while writing it, and they are step 3d's to satisfy rather than to rediscover:

    • every entry must state kind, KIND_FLAT or KIND_SPARSE, from the type on the descriptor's extent line. An entry left at zero is refused;
    • a sparse extent's device_offset must be a multiple of 512. Sparse VMDK counts in 512-byte sectors from the start of its own file, so only then does each header and table entry sit whole inside one device sector;
    • step 3b's declared_len for an extent must be the file's own length. A fully allocated sparse file is longer than its span, and a span would truncate it;
    • vmdk::MAX_EXTENTS is 32, below MAX_CHAIN_EXTENTS, so the descriptor parser is the tighter bound today. Whichever bound refuses an image, the message must name the one that actually applied;
    • ChainConfig::data_devices_are_owned still permits a descriptor to own a run of marked data devices. Nothing reads a descriptor that way any more, so that clause and the VMM test pinning it are vestigial and 3d should remove them with the attachment code they describe;
    • a descriptor's virtual_size must still be the sum of its extents' spans, and the device's capacity the sum of their file lengths: the reader bounds a flat read with the device capacity, not the extent's.

    Two refusals the reader makes that qemu would not, both deliberate and both needing a message that names the bound rather than a bare failure: a compressed sparse extent (nothing can hold a compressed grain to its extent's file, and qemu only compresses the single-file stream-optimised subformat), and a sparse extent whose header capacity is not the span the descriptor line declares (qemu takes the span from the header and the host has only the line, so where they differ every later extent sits at a different virtual offset for each reader).
