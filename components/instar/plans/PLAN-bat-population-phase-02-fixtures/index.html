    Phase 2: qemu-written fixed VHDX fixtures¶

    Phase 2 of PLAN-bat-population.md. Read its Situation and the phase 2 paragraph of "Sequencing rationale" first; this file assumes them, and corrects that paragraph where the survey found it wrong.

    Planning effort: medium. The phase follows an established fixture pattern, but its survey overturned three of the master plan's premises (fixture size, generator location, and the create baselines), so the decisions below are worth reading before the steps.

    Decisions already taken by the operator¶

    Every open question in the master plan was resolved with its recommendation adopted (Michael Still, 2026-10-21); phase 1's plan lists them. None is revisited here.

    Scope¶

    In:

    • Five small qemu-written VHDX fixtures, committed to instar-testdata through git-LFS and registered in tests/manifest.json: fixed at a block multiple and at a partial final block, each in both block_state_zero modes (the off pair carrying data), and the dynamic image at the #626 geometry.
    • Four new pin cases, so every committed fixed fixture has a pinned qemu structure across all 80 builds.
    • The generator, in instar's scripts/create-vhd-testdata.sh.
    • A test module that proves each fixture is what qemu writes and pins what instar's readers do with it today, including the three failures #626 and #797 cause, in a form that fails when phase 4 fixes them. The same module also generates, at test time, the two fixed images that are too large or too awkward to commit.
    • docs/testing.md, for the fixtures and the known-failure table.

    Out:

    • Any change under src/. The read-side defects are phase 4's.
    • generate-baselines.py's CREATE_CASES and per-image cross-version baselines for the new fixtures. Both move to phase 10 (decision 5).
    • A committed fixed VHDX at the #626 geometry (decision 2).
    • Issues #807 (compare reports a read failure as a content mismatch) and the unmeasured convert leftover below. They are recorded, not fixed.

    What the survey found¶

    Two sub-agents surveyed, one each for instar-testdata's fixture pattern and for instar's reads of qemu's fixed VHDX. The management session re-measured every claim below that a decision rests on; the re-measurements are marked.

    The 128 GiB fixture is not cheap in bytes¶

    The master plan's phase 2 paragraph calls the #626 region-crossing fixture "sparse and so cheap in bytes". It is not, once it goes through git-LFS:

    • git-LFS does not preserve holes. A 1 GiB sparse fixed VHDX committed to a scratch LFS repository was stored fully allocated in .git/lfs/objects (1,082,134,528 bytes) and checked out fully allocated by the smudge filter. Nothing in the tree compresses LFS objects.
    • CI resparsifies only downloaded/, never custom/ (tools/ci/resparsify-testdata.sh:24-27,112; docs/testing.md:1156-1162).
    • The manifest's sha256 check reads the whole file (tests/base.py:355-411).

    So a committed 131041 MiB fixed VHDX is a 128 GiB LFS object, upload and checkout on every CI leg. The largest fixture today is 1 GiB (custom/external-data/qcow2-external-data-raw.raw); the whole LFS set is 324 objects, about 10.2 GB.

    The fixed file is also unnecessary for #626. The miscount is in the BAT entry count, which a dynamic image at the same geometry reproduces in 8 MiB. Re-measured with the instar binary built from da9f043f: qemu-img create -f vhdx -o block_size=1M d.vhdx 131041M gives an 8,388,608-byte file on which instar check exits 2 and instar map exits 1 ("source format unrecognised"), while the same command at 131040M checks clean. Phase 1 already pins that dynamic case (vhdx-dynamic-131041M-block-1M).

    The house generator lives in instar, not instar-testdata¶

    The master plan says the generator goes in instar-testdata "following the house pattern from PLAN-differencing phase 2". That phase's pattern was the reverse: the generator is instar's scripts/create-vhd-testdata.sh and the binaries are committed to instar-testdata (PLAN-differencing-phase-02-fixtures.md:68-84). The script already owns every VHDX fixture, including the differencing ones. Because qemu-written VHDX is not byte-reproducible (a fresh DataWriteGuid each run), its VHDX outputs are opt-in under REGEN_VHDX=1 and skipped when present (scripts/create-vhd-testdata.sh:109-127). Generators inside instar-testdata exist too (generate-{vdi,parallels,dmg,qcow1}-fixtures.py), but not for VHDX.

    Adding the create baselines now would break develop for no signal¶

    Adding vhdx fixed cases to instar-testdata's scripts/generate-baselines.py CREATE_CASES (:404; the vhdx target has five dynamic cases at :454-461) has two problems:

    • test_create_cases_match_baselines (tests/test_create.py:1793-1826, read by the management session) fails whenever the host's profile holds baselines that instar's mirror at :1618 lacks. Testdata lands on main before instar's pull request, so develop would be red in between. And each mirrored case runs instar create and asserts exit 0 (:1868-1872), which fixed VHDX cannot pass until phase 7, so every case would need a KNOWN_WRITER_DIVERGENCES entry on arrival.
    • The baselines are qemu-img info --output=json, which for vhdx has no format-specific block, and tests/helpers/info_json.py:23-35 strips actual-size and the nested virtual-size. They compare virtual size and cluster size only, and cannot tell fixed from dynamic or one block_state_zero mode from the other.

    The structural comparator and the pin are the oracle for fixed output; the create-info baselines are a cross-version smoke check. They belong with the matrix in phase 10, where instar can already create the images they describe.

    The #626 count is written out three times: VhdxState::init (src/crates/vhdx/src/lib.rs:2331-2345), check_vhdx (src/operations/check/src/main.rs:1677-1688) and calculate_bat_layout (src/crates/vhdx/src/lib.rs:3773). The #797 test is src/operations/check/src/main.rs:1783-1791. info passes on the #626 geometry because it does not walk the BAT.

    Also measured, and what each means for this phase:

    • qemu does not keep a block_state_zero=on fixed image fixed when it writes to it. Writing 64 KiB into a 64M on image grew the file from 75,497,472 to 83,886,080 bytes (re-measured †): qemu appends a new block at end of file instead of using the preallocated slot. Writing into an off image changes nothing structural (re-measured: structural_diff is empty). So the data-bearing fixtures are off images, and the on fixtures stay empty.
    • qemu's default convert to fixed does the same. The pinned vhdx-convert-fixed case is a 100,663,296-byte file against 75,497,472 for vhdx-convert-fixed-bsz-off: the data blocks are appended past the preallocated area. That mixed layout is the most interesting read case in the phase, and the cheapest to produce at test time from qemu_pins.write_convert_source, so it is generated rather than committed.
    • instar measure agrees with qemu-img on fixed 16M and 17M sources for -O qcow2 and -O raw (re-measured †).
    • instar info cannot tell fixed from dynamic, and neither can qemu-img info: the only differences are file length and the child node's sizes.
    • instar create -f vhdx -o subformat=fixed refuses with create: -O vhdx -o subformat=fixed is not yet supported (only the dynamic vhdx subformat is implemented). The refusal now sits at src/vmm/src/main.rs:15435-15441, not the :15166-15181 the master plan cited. Every src/vmm/src/main.rs citation in the master plan's Situation had drifted by about 270 lines since it was written; all seven were re-located by reading the code and corrected there (the -o parser's block_state_zero accept-ignore, preallocation refusal and fixed refusal; validate_create_args's --subformat, monolithicFlat and preallocation checks; and the convert host's 32 MiB block assumption, now :13893).

    • 798 and #799 reproduce as filed. resize of a fixed 64M image to¶

      128M leaves LeaveBlocksAllocated set with the eight new BAT entries NOT_PRESENT, which qemu-img check accepts; instar create -f vhdx at 65T exits 0 where qemu-img refuses.
    • Two smaller defects, recorded where the phases that own them will find them:
    • instar convert leaves a zero-byte output file when it fails (seen on the #626 geometry). Whether qemu-img does the same was not measured; it is in the master plan's Future work, which asks for that measurement before calling it a defect.
    • instar check reports an image end offset of 75,497,472 on the 65M off image, whose file is 76,546,048 bytes; on block-multiple images the two agree. It is the partial final block again, so it is recorded on #797 (issuecomment-6334705401), which phase 4 fixes. qemu-img reports no end offset for VHDX at all.

    Manifest and the tests that read it¶

    tests/manifest.json entries require id, path, format, safety, run_in_ci and description (tests/helpers/types.py:68-85), and the VHDX fixtures carry sha256, generated_by and tags. No manifest image is fixed today: leave_blocks_allocated is false on all six parseable VHDX entries.

    Registering a safe vhdx image has these effects, which the steps rely on:

    • TestVhdxStructureManifest parses every safe vhdx entry (tests/test_vhdx_structure.py:368-380), so the new fixtures are parsed with no further work.
    • test_info_safe, test_map and test_measure build their per-image scenarios from cross-version baselines, and skip an image that has none (tests/test_info_safe.py:75-82; tests/test_map.py's "no baseline meta" skip). Until phase 10 generates baselines, those modules skip the new fixtures, and the new test module carries their coverage.

    Master plan corrections made in this commit¶

    The planning commit corrects, at source: the phase 2 paragraph of "Sequencing rationale" (fixture size, generator location, and the create baselines moving to phase 10); the phase 10 paragraph, which gains the create baselines and the per-image fixture baselines; and the phase 2 row of the Execution table, which drops "and baselines"; and the seven drifted src/vmm/src/main.rs citations in the Situation. Later steps do not need to redo them.

    Decisions¶

    1. The fixtures are small, and match pin cases. Five fixtures, about 106 MiB stored in total:
    Manifest id qemu-img command File Purpose
    vhdx-fixed-16M create -f vhdx -o subformat=fixed X 16M 24 MiB Block multiple (two 8 MiB blocks), ZERO entries
    vhdx-fixed-16M-bsz-off-data create -f vhdx -o subformat=fixed,block_state_zero=off X 16M, then data at 0 and 12M 24 MiB Block multiple, FULLY_PRESENT at sequential offsets, with data to read back
    vhdx-fixed-17M create -f vhdx -o subformat=fixed X 17M 25 MiB Partial final block (three blocks, the last holding 1 MiB), ZERO entries
    vhdx-fixed-17M-bsz-off-data create -f vhdx -o subformat=fixed,block_state_zero=off X 17M, then data at 0 and in the last 64 KiB 25 MiB Partial final block with data in it: the #797 reproducer
    vhdx-dynamic-131041M-block-1M create -f vhdx -o block_size=1M X 131041M 8 MiB The #626 reproducer

    The data writes are qemu-io -c 'write -P 0x11 0 64k' -c 'write -P 0x22 12M 64k' for the 16M image and qemu-io -c 'write -P 0x33 0 64k' -c 'write -P 0x44 17344k 64k' for the 17M image (17344 KiB is 17 MiB less 64 KiB). The phase 1 pin already holds 64M and 65M cases, but at 72 and 73 MiB each, four of them would triple the bytes every CI leg checks out. The four fixed fixtures get pin cases of their own instead (vhdx-fixed-16M, vhdx-fixed-16M-bsz-off, vhdx-fixed-17M, vhdx-fixed-17M-bsz-off), and the dynamic one already has vhdx-dynamic-131041M-block-1M. Each fixture's structural summary must then equal its pin case's, which proves the committed file is what every one of the 80 qemu builds writes, not only the build that happened to generate it. The data writes do not change the summary (re-measured).

    1. The fixed #626 geometry is generated at test time, not committed. Committing it costs 128 GiB per CI checkout (survey), and the committed dynamic fixture already reproduces the miscount. The test module creates the two fixed 131041M images (on and off) with the host qemu-img in a temporary directory, as tests/test_qemu_create_pins.py already does for vhdx-fixed-131041M-block-1M-bsz-off, and runs only the operations that do not read the data region: info, check and map. A convert or compare of 128 GiB would be the first test in the suite to read that much, and the BAT walk that #626 breaks is already exercised by check and map. The same holds for the committed dynamic 131041M fixture, which is 128 GiB virtual too, so it also gets only info, check and map (corrected during step 2c; see the execution notes).

    2. The generator goes in scripts/create-vhd-testdata.sh, as a new section behind the existing REGEN_VHDX=1 switch, writing to the script's default output directory (../instar-testdata/custom/format-coverage/). That is the house pattern the master plan meant to follow, and the script already owns every VHDX fixture and the non-reproducibility switch. It uses the host qemu-img; decision 1's structural check is what makes the version that generated it irrelevant.

    3. Today's failures are pinned as known failures that fail once fixed. The new module carries a KNOWN_READ_FAILURES table keyed by (image, operation), each with the issue number and the guest message. A listed pair must still fail with that message; when it starts passing, the test fails and says to remove the entry. That is the TestMapDivergenceRegression pattern in tests/test_map.py, and it makes phase 4's job visible from the test output rather than from a plan: fixing #626 and #797 turns seven known failures into test failures that point at the table. The expected entries, from the survey, are check on vhdx-fixed-17M-bsz-off-data (#797), and check and map on vhdx-dynamic-131041M-block-1M and on both runtime 131041M fixed images (#626). Any other failure the step finds is reported to the management session before it is tabled, because it may be a defect nobody has filed.

    4. CREATE_CASES and per-image baselines move to phase 10. Adding create baselines now breaks test_create_cases_match_baselines on develop between the testdata push and the instar merge, needs a divergence entry per case on arrival, and measures nothing the pin does not (survey). Per-image cross-version baselines for the new fixtures (info, map, measure, check) are the same kind of work: regenerating every image for a command across 80 builds, then regenerating and validating profiles/, which has been silently wrong twice before. Phase 10 is the phase the master plan built for that procedure. This is the decision a reviewer is most likely to question, because it leaves test_info_safe, test_map and test_measure skipping the new fixtures until then. The new module's live comparison with the host qemu-img is what covers them meanwhile, and the skips are by-name (the modules print "no baseline"), not silent.

    5. Landing order: instar-testdata first, then instar. The fixtures go to instar-testdata main as a direct commit (that repository takes no merge requests), and the instar pull request follows. Until the instar pull request merges, develop's manifest does not name the new files, so nothing on develop can see them. The reverse order would make develop's sha256 checks fail on missing files. The Merged cell records both: instar-testdata <sha> (direct to main); instar <merge> (#<pr>).

    6. The runtime convert-to-fixed images join the read matrix. The test module also builds vhdx-convert-fixed and vhdx-convert-fixed-bsz-off at test time from qemu_pins.write_convert_source with the host qemu-img, and runs the full read matrix on them. qemu's default convert appends data blocks past the preallocated area (survey), a layout no committed fixture has and the one phase 8's in-place writer will deliberately not produce. Reading it correctly is instar's job either way.

    Risks and mitigations¶

    • The pin and the fixtures disagree because the host qemu-img differs from the swept builds. Decision 1's structural test is what detects that; if it fires, the management session compares the fixture's summary with the pin's group for 10.0.x and treats any difference as a new version boundary, which phase 1 says needs a human decision.
    • A new failure in the read matrix is tabled without being understood. Step 2c must stop and report any failure beyond decision 4's list. The management session reproduces each with the CLI before agreeing to table it, and files an issue for anything that is not #626, #797 or #807.
    • The testdata push and the instar merge are separated by a long queue. Harmless in this order (decision 6). If the instar pull request is abandoned, the five files sit unreferenced in instar-testdata; the management session says so in the plan rather than deleting them, since LFS history keeps them anyway.
    • The 131041M runtime images run out of space on a CI filesystem that does not support sparse files. test_qemu_create_pins already creates the same geometry on every CI leg, so a failure would already be visible there. Do not weaken the assertion; report it.
    • Host load makes a qemu command fail during the re-pin. Step 2a replays any changed existing case and never commits one.
