    Phase 11: coverage and differential fuzzing¶

    Phase 11 of PLAN-bat-population.md. Read its phase 11 paragraph of "Sequencing rationale" and the "Constraints that apply throughout" section, in particular the no_std panic-free rule and the requirement that every qemu-img behaviour claim is cited or measured. This phase consumes what phases 6, 7 and 8 built: the streaming BAT filler (vhdx::fill_fixed_bat), create -f vhdx -o subformat=fixed and convert -O vhdx --subformat fixed.

    Planning effort: high. The master plan's paragraph reads as four picker edits; the survey found that two of the four are blocked on preconditions it does not mention, and the convert half needs a new comparison strategy rather than a new picker entry. Deciding what to fuzz and what the oracle is, is the whole of this phase's judgement.

    Review effort: high. A differential fuzzer that reports a known bug on every iteration is worse than no coverage, because the next person triages it; and a fuzz target whose invariants are too weak passes forever while proving nothing. The review that matters is of the oracles and the exclusions, not of the harness code.

    What the survey found¶

    The master plan's phase 11 paragraph was written before phases 6 to 10 executed. Four of its claims are stale or incomplete, and two of them are load-bearing. File and line references are against e0b0fe13.

    fuzz_create_emitters says fixed output reaches no caller¶

    src/fuzz/fuzz_targets/fuzz_create_emitters.rs:194-201 pins the VHDX arm to VhdxSubformat::Dynamic and block_state_zero: true, with this comment:

    // The dynamic image the create op writes. Fixed
// output reaches no caller yet, and its BAT filler
// is not among the emitters this target checks.

    The first sentence was true when phase 6 wrote it and is false now: phase 7 shipped create -f vhdx -o subformat=fixed and phase 8 shipped convert -O vhdx --subformat fixed. The second sentence is still true and is this phase's work. Step 11a replaces the comment along with the code it describes.

    The target asserts five numbered invariants over the returned MetadataPlan (assert_invariants, :~230-290): bookkeeping consistency, every write inside minimum_file_size, no overflow, a write-count bound, and no two writes overlapping. None of them says anything about BAT contents, because no emitter it drives produces a BAT.

    fill_fixed_bat is already reachable from the fuzz crate¶

    vhdx::fill_fixed_bat is pub (src/crates/vhdx/src/lib.rs:4374) and src/fuzz/Cargo.toml already depends on the vhdx crate, so a new target needs no plumbing. Phase 6 left six unit tests beside it (:5598-5784) covering qemu pins, buffer-size independence, the forward map, a mid-chunk start, a partial last block and the error paths. They pin specific layouts; what a fuzz target adds is arbitrary layouts crossed with arbitrary index ranges.

    The differential fuzzer excludes the vhd create target entirely¶

    scripts/differential-fuzz.py:1574-1592, _create_option_picker:

    Excludes:
    vhd target entirely        (CHS-geometry rounding divergence)

    and target = rng.choice(['qcow2', 'vmdk', 'vhdx', 'raw']). The divergence is live, not historical: tests/test_create.py:2658-2665 still carries five KNOWN_WRITER_DIVERGENCES entries reading "qemu rounds VHD virtual_size to CHS geometry", and the comment below them records that the preallocation cases inherit it (qemu-img reports 1079296 for a 1M VHD where instar reports 1048576).

    So "teach the pickers ... the non-qcow2 preallocation modes" cannot include vpc's by adding an option: vpc is not a create target in this fuzzer, and adding it would diverge on virtual-size on every iteration for a reason that has nothing to do with preallocation. Decision 2 settles what to do.

    Also measured in the same function: preallocation is offered only inside the qcow2 arm (:1616-1631), the vmdk arm offers only monolithicSparse and streamOptimized (:1637), and the vhdx arm offers only block_size (:1641-1647) — no subformat, no block_state_zero. The master plan is right that all three are missing.

    The fuzzer hand-mirrors tests/helpers/info_json.py, and the mirror has drifted¶

    scripts/differential-fuzz.py:1504-1505:

    # Mirrors tests/helpers/info_json.py — keep in sync by hand. A divergence
# whitelist change in either copy should also land in the other.

    The field sets are equivalent today: the mirror's _CREATE_UNIVERSAL_STRIP merges the canonical UNIVERSAL_DIVERGENCE and CACHE_HINT_FIELDS, which info_json.py:208-210 also unions, and the per-target sets match (the mirror omits a vpc key, but it looks up with .get(target, set()) and the canonical vpc set is empty, so the behaviour is the same).

    The filename handling has not kept up. The mirror's _create_substitute_filename (:1533-1542) substitutes only a value exactly equal to tmp_path. Phase 10 taught the canonical copy to recognise the sibling file a create subformat writes beside its output — SIBLING_NAME_SUFFIXES, _decompose_name and the $FILENAME<suffix> rule at tests/helpers/info_json.py:72-160 — and the mirror has none of it.

    That is harmless today, because no caller's picker selects monolithicFlat. (This paragraph first said the mirror's only caller was op_create. It has ten call sites across five ops -- create, resize, amend, rebase and commit -- which step 11c measured and which widened its own scope; see the execution notes.) It stops being harmless the moment this phase adds that pick, and the failure is not subtle: op_create writes the two sides to different names, create-instar.vmdk and create-qemu.vmdk (scripts/differential-fuzz.py:1668-1669). A monolithicFlat descriptor names its extent, so the two info outputs carry create-instar-flat.vmdk and create-qemu-flat.vmdk — different strings, neither equal to its side's tmp_path, so neither is substituted and every monolithicFlat iteration reports a divergence that is purely the temp name. Phase 10's rule handles exactly this shape: it derives the sibling from the primary's own name, so both sides normalise to $FILENAME-flat.

    Convert has no VHDX target, and its oracle is blind to layout¶

    op_convert picks target_fmt = rng.choice(['raw', 'qcow2']) (scripts/differential-fuzz.py:1017). VHDX is not a convert target at all, so there is no picker to teach.

    The deeper finding is the oracle. For any non-raw target, op_convert flattens both outputs to raw with qemu-img convert -O raw and compares the bytes (:1066-1090, "neutral ground — neither tool is favoured"). That is a content comparison, and it is deliberately blind to the container's layout. Every property the fixed subformat exists to get right — LeaveBlocksAllocated, a BAT entry for every payload block, PAYLOAD_BLOCK_ZERO against FULLY_PRESENT, strictly increasing 1 MiB-aligned offsets, nothing written past the payload region — survives a raw flatten identically whether instar got it right or wrong. Adding vhdx to that rng.choice list would buy no coverage of this plan's subject.

    This is why the master plan says "comparing through the structural comparator for VHDX", and the survey's correction is about size rather than direction: it is a new comparison arm in op_convert, not a picker entry. The comparator itself is ready — tests/helpers/vhdx_structure.py exists and is used by five test modules — and the import mechanism is already proven in this very file, which does sys.path.insert on tests/ and imports helpers.snapshot_readback (:41-47).

    Corrected at source¶

    The master plan's phase 11 paragraph and docs/plans/index.md's phase 11 entry are rewritten by this plan's registration commit to say what the survey found, so the next reader does not re-derive it.

    Decisions¶

    1. Delete the hand-mirror; import the canonical normaliser. Step 11c removes _CREATE_UNIVERSAL_STRIP, _CREATE_TARGET_STRIP, _CREATE_NESTED_INFO_STRIP, _create_strip_keys, _create_substitute_filename and _normalise_create_info from scripts/differential-fuzz.py and calls helpers.info_json.normalise_info_json instead, by the sys.path/helpers. pattern the file already uses for snapshot_readback. The alternative — port phase 10's sibling rule into the mirror — keeps a comment that asks a human to notice a change in another file, which is the mechanism that just failed. Importing is the root-cause fix, and it is what makes the monolithicFlat pick in 11d safe rather than merely tested.

    2. vpc stays out of the differential create picker; its preallocation no-op is covered by the host tests instead. The CHS virtual-size divergence is a real, documented, unfixed difference, and nothing in this plan proposes to change instar's rounding. The options were to add a vpc arm restricted to CHS-exact sizes, to mask virtual-size for vpc in the normaliser, or to leave vpc out. This phase leaves it out. Masking the field would blind the comparison to the one thing most worth catching in a VHD writer, and restricting sizes would mean the fuzzer only ever generates the shapes where the bug cannot appear — coverage theatre. The non-qcow2 preallocation no-op is already asserted directly against the pinned qemu builds by test_vpc_noop_preallocation and test_vpc_fixed_noop_preallocation, and phase 10 added 1M-prealloc-falloc / 1M-prealloc-full create baselines for vhd across all 80 versions. So this phase's preallocation fuzzing covers vmdk and vhdx only, and says so in the picker's docstring. This is the decision most likely to be argued with: it means the master plan's "the non-qcow2 preallocation modes" lands two-thirds complete. The counter-argument is that a fuzzer which cannot reach vpc create at all is a gap worth closing on its own merits; it is, and it is recorded in Future work rather than bolted onto a phase about fixed VHDX.

    3. Convert gets a structural comparison arm, not a picker entry. Step 11e adds a vhdx branch to op_convert that compares the two outputs through helpers.vhdx_structure, and keeps the existing raw-flatten path for raw and qcow2. Both comparisons run for the vhdx branch: content equality through the flatten (which proves the payload survived) and structural equality through the comparator (which proves the layout matches). Reporting which of the two diverged is what makes a finding triageable.

    4. No preallocation=metadata for non-qcow2 targets. instar refuses it there and so does qemu-img, so a picker that generated it would be fuzzing two error paths against each other.     Risks and mitigations¶

    • The refactor in 11c silently widens the comparison. Replacing a normaliser with a different one can make the fuzzer stop reporting real divergences, and a clean run looks like success. Mitigation: 11c's brief requires byte-identical normaliser output across all four existing targets before and after, and a fixed-seed run with the same divergence count. The management session re-runs one of those comparisons itself.

    • A new picker shape reports a real instar bug and the round gets spent debugging it. This is the fuzzer working, but it can consume a phase. Mitigation: 11d and 11e are forbidden from adding whitelist entries to quieten a divergence; they report it. The management session decides whether it is a finding for a follow-up issue or a fix inside this phase, and records the decision in the execution notes.

    • An option is drawn so rarely that the run never hits it, and the phase reports coverage it does not have. Mitigation: 11d and 11e both report per-shape hit counts, and an unreachable shape is a reportable failure of the step rather than a footnote.

    • The fixed convert arm's oracle needed settling. (This risk first said qemu-img cannot write VHDX, which is wrong; see the execution notes for what the oracle actually compares and why.) qemu-img cannot write VHDX, so a symmetric differential comparison may not exist for this target. Mitigation: 11e's brief makes naming the oracle a required output and explicitly permits the answer "there is no qemu side", with the pinned expectations used instead. The management session checks that whatever the step built is what its report claims.

    • A fixed VHDX iteration writes its full length to disk. Fixed output is dense by definition and the fuzzer runs many iterations. Mitigation: decision for small sizes in the picker, stated in 11d and 11e's briefs, and the plan-wide constraint that no test allocates a test image's data region.

    • A fuzz target hangs rather than crashing. A mutated loop guard hangs by design. Mitigation: every fuzz run and every mutant runs under timeout, one per run, and a timed-out mutant counts as killed.

    The integration suite is flaky on this host at 16 workers, and round 1's single 0-fail run was a lucky sample. Round 2 was verified against three full runs of the same tree: 0 failed, then 32, then 4. Every failure was Content mismatch at offset 0! from a convert content comparison, every one was in tests/test_convert.py, and the sets were unstable in both directions -- only 2 of the 32 reappeared among the 4, and 2 of the 4 were new. All 36 distinct tests pass when replayed away from a loaded run (32 at concurrency 2, 4 at concurrency 4), and load average was 6 to 10 during the failing runs. A deterministic regression cannot produce different failure sets from one tree, and nothing in these rounds touches convert or the two vhdx_structure functions test_convert uses, so the attribution is host contention between 16 concurrent qemu conversions.

    Two things follow for anyone verifying work here. A single 0-fail run is weak evidence on this host, and the right response to a cluster of Content mismatch at offset 0 failures is to replay the named tests at low concurrency before believing them -- not to bisect.

    Review round 3 (2026-11-08 AEDT). 1 fix, 6 consider, 3 none. The fix item was an off-by-one in 11b, not in either review round: MAX_BUFFER_ENTRIES was 4096 and its comment claimed that cleared the largest legal chunk_ratio so a call from index 0 could reach the sector-bitmap slot after a whole group. It cannot. The BAT repeats every chunk_ratio + 1 entries with the slot last, so at ratio 4096 the slot is index 4096 and a 4096-entry call stops exactly one short. No single call in the target could ever span a group and its slot. The constant is now 4097, and the reason is a const _: () = assert!(MAX_BUFFER_ENTRIES > MAX_CHUNK_RATIO) rather than a comment, so lowering it is a build failure -- verified by lowering it and reading the error.

    Five of the six consider items were taken. Two were the last wide dimensions of guards these rounds built:

    • truncated_inside_region accepted any region whose extent ran past the end of the file. The filed defect is the metadata region specifically, so a corrupt region table plus an unallocated BAT was being suppressed as #883 -- the exact class of finding the arm exists to catch. Now metadata-only. Making that falsifiable needed a test with a third region, since with only bat and metadata the BAT is the only other candidate and an overrunning BAT cannot be read at all; the test crafts the third region-table entry.
    • The field-classification scan read an interpolated type by its literal tail and silently dropped any record whose type it could not read -- the one way that guard fails unsafely. An unreadable type is now a hard failure. The first version of that test was vacuous, which the mutation run caught: it asserted the real file has none, so it passed against a detector that found nothing. The detector is now a function over source text, tested against fixtures.

    The third worth naming: a structural comparison that found no pinned case, or whose source size could not be probed, returned None with no record, which reads exactly like a clean comparison. STRUCTURAL_OUTCOMES now counts every comparison by outcome and reports it in the run summary, on the same reasoning as the #883 skip counting -- a comparison nobody can see did not happen is not coverage. The hand-measured coverage figures in docs/testing.md are now reported numbers.

    Declined and recorded in the master plan's Future work: biasing the convert source size toward pinned geometries so the fixed arm is drawn more than ~8% of the time. It is a real coverage gap, but it shifts the fuzzer's draw sequence and wants measuring rather than a review round.

    The outcome counter found something on its first run. The 60 iterations at seed 2024 that rounds 1 and 2 used as their fuzz evidence report convert:skipped_issue_883 x4 and convert:no_pin_for_geometry x3 -- and no compared at all. That run exercises the rest of the fuzzer, but the structural arm compared nothing in it, so quoting its "0 divergences" as evidence that the comparison still behaved was quoting a comparison that never ran. This is exactly the blindness the review item described, found by the counter added to answer it. A convert-only run of 150 iterations at seed 7 gives compared x34, no_pin_for_geometry x44, skipped_issue_883 x56, which is the arm working end to end and the same shape as the hand measurement quoted in docs/testing.md.
