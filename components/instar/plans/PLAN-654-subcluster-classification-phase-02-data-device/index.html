    PLAN-654 phase 2: the data device is not a chain layer¶

    Master plan: PLAN-654-subcluster-classification.md. Read its Situation, Decisions D3 and D4, and phase 1's plan (PLAN-654-subcluster-classification-phase-01-classifier.md) first, in particular "Step 1a measurements". This file assumes them.

    Planning effort: high. The phase changes the chain config ABI shared by the VMM and every guest operation, and the read path every chained input goes through.

    Scope¶

    In:

    • external data file devices stop being read as backing layers: an unallocated cluster in a data-file image reads its backing chain, or zeros, never the data file (#792);
    • the VMM marks data devices in the chain config, and the guest validates the marking before it walks the chain;
    • the two other places that treat a data device as a layer: the VmdkDescriptor extent walk and check --chain's backing validation;
    • qemu's two data-file host-offset refusals: a compressed entry in a data-file image, and a host offset that differs from the guest offset (#803);
    • tests built the way phase 1's were, and documentation.

    Out:

    • moving data devices out of the chain segments (see D1);
    • fuzz-target changes: fuzz_chain_compose keeps data_device_idx at 0 (the master plan's Future work);
    • map and measure composing a qcow2 chain (#641, #642): neither touches the device chain today (map refuses input_device_count != 1, src/operations/map/src/main.rs:174);

    • 804 (check counts L2 tables) and #805 (subclusters under 512 bytes).¶

    Closes #792 and #803.

    What the survey found¶

    Surveyed on 2026-10-21 against develop d08841e3 (phase 1 merged).

    1. #792 still reproduces after phase 1. Six fixtures, under convert and compare, are EXPECTED_FAILURES citing #792 in tests/test_qcow2_subclusters.py:51-62. Phase 1's CI passed with them as expected failures, and testtools reports an unexpected success as a failure, so they still fail. Phase 1's step 1c table lists them.
    2. Every layer advance in the reader steps into the data device. read_chain_virtual_cluster (src/crates/qcow2/src/lib.rs:15162) moves to the next layer in two ways: the device loop's continue (the qcow2 Unallocated arm at :15225, and the VMDK, VHD and VHDX arms), and a recursive descent sized by devices_behind (:14963), for qcow2 subcluster runs (:15394) and the VHD and VHDX sector bitmaps. Both land on the next device in the segment, and the VMM puts the data device there. The raw arm (:16881) then reads the data file at the virtual offset and returns.
    3. The ABI documents the fall-through as intended. ChainSegment's doc comment (src/shared/src/lib.rs:4860-4866) says a data device "counts as a device behind the image above it, which is what the reader's own arithmetic already assumes". docs/chain-config.md:63-65 says the same thing.
    4. The VMM gives the guest no way to tell a data device from a layer. write_chain_device_entries (src/vmm/src/main.rs:3584-3640) writes a data device as format Raw, flags 0 and data_device_idx 0, immediately after its owner, and sets the owner's data_device_idx to its own index plus one. open_chain_devices (:3648) and open_chain_devices_rw (:3740) open devices in the same order.
    5. The crate tests never used the VMM's layout. Phase 1's harness puts the data device at index 2 with chain_len 1 or 2, outside the chain (lib.rs:6749-6752, sc_read at :6884-6932). That is why #792 has no crate test: the harness could not reproduce it.
    6. VmdkDescriptor walks past its own extents. Its arm (lib.rs:16839-16878) treats every device from data_device_idx onward as an extent until it meets a virtual_size of 0 or the end of the array. If a layer follows the extents, that layer counts as another extent. Step 2a measured that qemu-written images reach this: under compare, the device after a flat descriptor's extent is the other input's top image, so a qcow2 overlay larger than the descriptor it sits on compares as different in one argument order and identical in the other.
    7. check --chain validates a data device as a backing image. validate_chain (src/operations/check/src/main.rs:3398-3400) iterates 1..device_count and runs format and size cross-checks meant for backing images on each device. The VMM sets the flag for instar check --chain (src/vmm/src/main.rs:12377). Step 2a measured that a data device reports an error only when its contents look like another format, or when it is empty. The chain error that every data-file fixture with a raw backing file shows comes from the raw backing file. Discovery records a raw file as Unknown, so every raw backing file gets that error, with or without a data file (#808, filed from step 2a).
    8. The chain config version is defined twice. The guest uses ChainConfig::VERSION (src/shared/src/lib.rs:5049) and the VMM has its own CHAIN_CONFIG_VERSION (src/vmm/src/main.rs:336), both 3.
    9. Nothing else reads data_device_idx. The reader, check's data file size lookup (check/src/main.rs:294-310, which reads only device 0's data device and is unaffected), and fuzz_chain_compose, which leaves it 0 on purpose. compare packs two chains with each data device inside its own segment (src/vmm/src/main.rs:13071-13256). D1 keeps that layout valid.
    10. #803 is ready to take. Its fixtures are built by HOST_OFFSET_REFUSAL_BUILDERS (tests/helpers/qcow2_subclusters.py:641) and are kept out of the test module (tests/test_qcow2_subclusters.py:28-32). docs/quirks.md:4904-4912 records both shapes as open divergences.

    The master plan's section was accurate except on one point: its Future work asked phase 2 to decide whether qemu's data-file offset check belongs here, and D5 decides it does. The planning commit updates that entry and the master plan's "Bugs fixed" paragraph to match, so a later step does not need to.

    Decisions¶

    D1. Data devices are marked by role, not moved out of the chain. The VMM sets a new bit, ChainDeviceInfo::FLAG_DATA_DEVICE (bit 31), on every data device it writes. The info operation never sets it. The chain config version goes to 4. Moving data devices out of the segments was considered and rejected: the segments would no longer tile the device array, so ChainSegment::covers, every operation's chain_len (each passes the host's device count today), compare's packing and the VMM's slot numbering would all change, while the reader already reaches data devices only through data_device_idx. Marking the devices fixes the defect and leaves the array's shape as it is. This is the decision a reviewer is most likely to dispute.

    D2. The reader skips a data device at the top of its device loop, and nowhere else. Every layer advance passes through that loop: a continue reaches the next iteration, and a descent re-enters the reader at the next device. One check there covers every format arm. devices_behind still counts data devices. That is harmless, because a descent into a run of nothing but data devices skips them all and reaches the zero fill at the bottom of the reader, which is the right answer at the bottom of a chain. The bit says what a device is, so this check is about the device's role, not an ad hoc value test of the kind the master plan criticises.

    D3. init_chain_states validates the marking before any read. A segment's first device is never a data device. Every non-zero data_device_idx names the marked device in the slot immediately after its owner, which is where the VMM always puts it. Every marked device has exactly one owner: a qcow2 owns one, and a VmdkDescriptor owns the contiguous run of marked devices that starts at its data_device_idx, which is also how its extent walk now ends (survey item 6). A config that breaks these rules is refused with a plain failure, as a bad segmentation is. It means the host and the guest disagree about the config, not that the image is corrupt.

    D4. check --chain skips data devices in validate_chain. A data file has no header to cross-check, and it is not a backing image. This removes only the two errors a data device can raise itself (survey item 7). The raw-backing error is #808, so tests of D4 use a qcow2 backing file.

    D5. #803 joins this phase. The master plan's Future work left the decision to phase 2. Both refusals sit at the read site this phase is already changing (data_read_device and the Normal reads). The offset-mismatch shape is a read of the wrong bytes that exits 0, and its fixtures already exist. The refusal follows the InvalidL2EntryRefusal pattern (src/shared/src/lib.rs:3190-3226, VMM renderer at src/vmm/src/main.rs:810-860). Its text uses qemu's own wording for each shape, taken from the v10.0.0 source rather than from memory. map, check and measure follow qemu on the two fixtures as the test module requires. Where one cannot in this phase, it gets an EXPECTED_FAILURES entry that names a filed issue.

    D6. The crate harness uses the VMM's layout. It places the data device at the owner's index plus one, inside the segment and marked, with any backing device after it. The layout with the data device outside the chain is not one the VMM writes, so tests that use it prove nothing about real reads. That is how #792 escaped.

    D7. One version constant. The VMM uses shared::ChainConfig::VERSION instead of its own copy, so a future bump cannot reach only one side.

    Steps¶

    Step Effort Model Isolation Brief for sub-agent
    2a high opus none Measure and build the fixtures; no Rust changes. Build instar from this branch with make instar (Docker only; rm -rf src/target/release first if make test-rust ran in this tree, because the two share that directory and a GLIBC mismatch follows). Use host qemu-img/qemu-io 10.0.13. Extend tests/helpers/qcow2_subclusters.py with builders for: (1) #792's two measured cases from the issue body (data file plus raw backing file, cluster size 64K, classic and extended L2; data file with data_file_raw=off, no backing, and bytes written straight into the data file at an offset the qcow2 does not map); (2) a three-layer chain whose middle layer is a qcow2 with its own data file, so a data device sits between two layers; (3) one compare case whose two inputs are both data-file images, so the device array holds two segments that each contain a data device.     Risks and mitigations¶

    • A layer advance that does not pass through the loop head. If a path reaches the next device without re-entering the loop, it reads the data device. Mitigation: step 2b's report audits every advance, and the management session re-checks it with grep -n "devices_behind\|dev_offset + 1\|continue;" src/crates/qcow2/src/lib.rs over the reader before committing.
    • Version skew between the VMM and an operation binary. Mitigation: the bump to 4 makes is_valid refuse a mismatched pair, and D7 removes the second constant. The shared version tests pin it.
    • check --chain output changes on existing images. Skipping data devices can only remove reports. Mitigation: step 2d runs test_check_chain and test_check_formats, and any expectation that changes is justified against qemu-img check in the commit.
    • D3's validation refuses a layout the VMM really writes, such as a VMDK descriptor with several extents, or compare with two data-file inputs. Mitigation: step 2a's compare fixture and the existing VMDK extent tests run through the real VMM in step 2d, and step 2b has a crate test for each accepted shape as well as each refused one.
    • qemu's wording quoted from memory. Mitigation: step 2c fetches the source, and the management session checks the quoted lines against it.

    (b) The VmdkDescriptor extent walk¶

    qemu-img create -o subformat=monolithicFlat -b … refuses with "Flat image can't have backing file". A hand-edited flat descriptor with parentFileNameHint naming a monolithicSparse VMDK opens in qemu, which forces the parent's format to vmdk (qemu-img info shows "backing file format: vmdk", and a raw parent fails with "invalid VMDK image descriptor"); in every row below qemu's output contains none of the parent's bytes. instar's VMM follows the hint (src/vmm/src/main.rs:3245-3248), so the parent becomes the next device after the extent.

    Image qemu-img convert instar convert instar compare vs qemu's raw
    flat descriptor, no parent 0 0, equal 0
    flat descriptor with a parent hint 0 0, equal (reads never pass the extents) 0
    1M qcow2 over a 512K flat descriptor 0, 00 past 512K 0, equal 1, mismatch at 524288
    1M qcow2 over a 512K flat descriptor with a 1M sparse parent 0, 00 past 512K 0, differ: 4b at 524288 (the parent's KDMV magic), then the parent file's raw bytes 1, mismatch at 524288
    1M data-file qcow2 over a 512K flat descriptor 0, VMDK bytes 33 0, differ: 00 from 65536 (#792: the data device is read instead of the descriptor) 1

    So the walk does read the following device as an extent, exit 0, once a read lands past the descriptor's extents, which happens when the overlay is larger than the descriptor. It needs no hand-editing: under compare the following device is the other input's first device. instar compare overlay.qcow2 qemu.raw reports a mismatch at 524288 although instar convert of the overlay equals qemu's output, and with the inputs swapped it says identical. qemu-img compare says identical both ways.
