    Phase 4: read side -- BAT entry count, partial last block, fixed VHDX resize¶

    Phase 4 of PLAN-bat-population.md. Read its Situation (especially "Reading fixed VHDX: mostly right, with three defects") and the phase 4 paragraph of "Sequencing rationale" first. This file assumes them, and corrects that paragraph where the survey found it incomplete.

    Planning effort: high, as the master plan sets for this phase. Every change here alters what instar accepts from an untrusted image, and the survey found that qemu's own partial-last-block rule is wrong in a way instar must deliberately not copy (decision 3).

    Decisions already taken by the operator¶

    Every open question in the master plan was resolved with its recommendation adopted (Michael Still, 2026-10-21). The two this phase carries out:

    • Open question 5: close #626 now, and #797 and #798 (filed during master planning) with it.
    • Open question 6: resize refuses a fixed VHDX with a typed error naming the subformat, until a fixed-preserving grow exists. SPEC(VHDX) 2.6.2.1 (revision 8.0) bears it out: with LeaveBlockAllocated set "the implementation SHOULD NOT change the state of any blocks to a BLOCK_NOT_PRESENT state".

    Neither is revisited here.

    Scope¶

    In:

    • #626. One non-differencing BAT entry count, qemu's and SPEC(VHDX) 2.5's, defined once in the vhdx crate and used by every reader and writer that counts today.
    • #797. check accepts a final FULLY_PRESENT payload block that ends at the end of the virtual disk, short of a whole block.
    • #798. The vhdx crate parses LeaveBlocksAllocated, and resize refuses a fixed VHDX by name instead of growing it into a hybrid.
    • Tests that turn phase 2's KNOWN_READ_FAILURES entries into passing reads, and the per-phase documentation: docs/check.md, docs/resize.md, docs/quirks.md and docs/testing.md.

    Out:

    • One shared VHDX layout, the chunk-ratio formula, #645 and the 64 TiB ceiling. Phase 5. This phase only folds the entry count. The chunk ratio is computed in three places as well, but phase 5 replaces all of it with one layout function, so unifying it here would be work phase 5 redoes.
    • The region table's Required bit. instar writes 1 for both regions and qemu writes 0 (survey). It is a writer-structure question, for phase 6.
    • The measure quirk that states the VHDX-source divergence the wrong way round (survey). Phase 9 owns measure.
    • #582 (VhdxState::init discards the active header). The master plan made folding it in optional. Nothing here reads the active header, so it stays separate.
    • check policing LeaveBlocksAllocated (for example flagging a fixed image with NOT_PRESENT entries). qemu does not, and the spec's wording is SHOULD NOT, not MUST NOT.
    • Any call-table struct layout change. The new resize error code is appended to ResizeResult's code list, which is not a layout change (decision 5).

    What the survey found¶

    Line numbers are against develop at a8d2f4ca. Measurements used the host's qemu-img 10.0.13, the 80 static builds under instar-testdata/qemu-img-binaries/x86_64/, and an instar built on 2026-10-19 from the primary clone. No commit since then touches the VHDX read code, the check op or the measure crate's VHDX code (git log --since=2026-10-19 over those paths shows only 3943c781, which is qcow2 data-file documentation).

    #626 is as the master plan says, and has a fourth copy¶

    The non-differencing count total_blocks + ceil(total_blocks / chunk_ratio) is written out in:

    • calculate_bat_layout (src/crates/vhdx/src/lib.rs:3758-3780), which create (src/crates/create/src/lib.rs:1416), convert (src/operations/convert/src/main.rs:4415), measure (src/crates/measure/src/lib.rs:1033) and resize (src/crates/resize/src/vhdx.rs:91) all call;
    • VhdxState::init (src/crates/vhdx/src/lib.rs:2325-2348);
    • the check op (src/operations/check/src/main.rs:1677-1688);
    • and, as a deliberately independent oracle, the qcow2 crate's VHDX test fixture builder (src/crates/qcow2/src/lib.rs:11371-11376), whose comment at :13552-13562 also describes VhdxState::init's count as total_blocks + sb_entries.

    qemu's rule is data_blocks_cnt + ((data_blocks_cnt - 1) >> chunk_ratio_bits) (block/vhdx.c:868-882 in instar-testdata/qemu-sources/7.0.0/). The Python comparator already uses it (tests/helpers/vhdx_structure.py:301-309).

    Re-measured at a8d2f4ca on the committed vhdx-dynamic-131041M-block-1M fixture: instar info exits 0, and check (2), map (1), measure -O qcow2 (1, "source image is unsupported format") and convert -O qcow2 (1) all fail. qemu-img check is clean.

    The writer side is measured too. instar create -f vhdx -o block_size=1M d.vhdx 131041M declares a 2 MiB BAT region at 2 MiB and metadata at 4 MiB. qemu's pin case vhdx-dynamic-131041M-block-1M declares a 1 MiB BAT at 2 MiB and metadata at 3 MiB. After the fix the offsets and lengths should agree.

    Resize is less affected than the master plan implied. It takes the current entry count from the region's capacity (bat_len / 8, src/operations/resize/src/main.rs:822), not from the rule, so only its target count moves. A grow to a boundary geometry that relocates the BAT today will fit in place after the fix.

    Shrinking the count also shrinks sb_bat_entry_bound for an image with no parent. That changes nothing, because block_lookup already refuses PARTIALLY_PRESENT when there is no parent (src/crates/vhdx/src/lib.rs:2583-2600), so sector_bitmap_lookup is never reached for such an image.

    qemu's partial-last-block allowance is wrong past the first chunk¶

    vhdx_check_bat_entries (block/vhdx.c:884-960) computes the length of block i as MIN(block_size, virtual_size - i * block_size). i is the BAT index, which counts sector-bitmap slots, and not the payload index. The two are equal only inside the first chunk. Past it, i * block_size exceeds the virtual size, so the unsigned subtraction wraps, MIN picks block_size, and qemu requires the whole block to be in the file. The check runs on every open (:1082-1087), so qemu then refuses to open the image.

    Measured: qemu-img create -f vhdx -o subformat=fixed,block_size=1M,block_state_zero=off f.vhdx 4608.5M succeeds on all 80 static builds (6.0.0 to 10.2.0). On every one of them, qemu-img info f.vhdx then exits 1 and qemu-img check exits 2: "VHDX BAT entry 4609 end offset 4841275391 points after end of file (4840751104)". Entry 4609 is payload block 4608 plus one sector-bitmap slot. At 2048.5M, inside the first 4096-block chunk, and at 4097M and 4609M, which have no partial block, both tools are clean. With block_state_zero on, every entry is ZERO, the check never fires, and qemu opens the image.

    So qemu writes, by default and with no error, fixed images that it cannot open again. Decision 3 settles what instar does with them. The same images are what phase 7's create and phase 8's in-place convert will write for parity, so the master plan's phase 7 and 8 paragraphs now carry a warning that qemu-img cannot be the oracle for them.

    check's whole-block assumption is in three places, not one¶

    The FULLY_PRESENT arm (src/operations/check/src/main.rs:1771-1903) uses file_offset + block_size for the bounds test (:1784-1793), the declared-region overlap test (:1847-1863), and max_block_offset (:1866-1868), which becomes image_end_offset (:1931-1933). On the 17M fixture today, image-end-offset is 25165824 (24 MiB). That is only because the partial block takes the continue at :1792 and is left out. If only the bounds test were relaxed, the field would report 32 MiB, past the 25 MiB end of file. qemu-img check --output=json reports no image-end-offset for VHDX at all. That is an existing divergence and stays as it is.

    LeaveBlocksAllocated is unparsed, and resize is its only writer¶

    FILE_PARAMETERS_HAS_PARENT (src/crates/vhdx/src/lib.rs:1145) is the only File Parameters bit the crate reads. It reads it in two parsers: parse_metadata_region (:1262-1264, building VhdxMetadataItems at :1276) and parse_metadata (:1352-1353, building VhdxMetadata at :1443). Bit 0 is LeaveBlocksAllocated (qemu block/vhdx.h:275).

    Of the operations that handle VHDX, only convert, create, resize, rebase and bench write. convert and create write new files. rebase reads VHDX only as a chain member (src/operations/rebase/src/main.rs:1846-1902), and bench writes to its own scratch. resize is the only operation that modifies an existing VHDX, so it is the only consumer of the bit this phase needs.

    resize refuses a differencing VHDX with UnsupportedSubformat (src/crates/resize/src/vhdx.rs:52-54). The host renders that as the generic "subformat does not support resize" (src/vmm/src/main.rs:8548), which does not name the subformat. BitmapsPresent is the precedent for a refusal with its own code: ResizeError::BitmapsPresent (src/crates/resize/src/lib.rs:91), then ResizeResult::ERROR_BITMAPS_UNSUPPORTED = 14 (src/shared/src/lib.rs:3937, pinned at :5639), then the host constant (src/vmm/src/main.rs:309), message (:8567) and a code-range test (:20740).     Decisions¶

    1. One count function, in the vhdx crate, replacing every non-differencing copy. Add pub fn bat_entry_count( total_payload_blocks: u64, chunk_ratio: u32, has_parent: bool) -> Option<u64> beside differencing_bat_entry_count (src/crates/vhdx/src/lib.rs:1912), which it calls when has_parent is set. With no parent it returns:
    2. 0 for zero payload blocks;
    3. the payload count for a zero chunk_ratio, as calculate_bat_layout does today. Every reader refuses a zero chunk ratio before counting, so this only keeps a total function total;
    4. otherwise n + (n - 1) / chunk_ratio.

    It uses checked arithmetic throughout. Its doc comment quotes SPEC(VHDX) 2.5 ("Total BAT Entries = Payload Blocks Count + Fl((Payload Blocks Count - 1) / Chunk Ratio)") and cites block/vhdx.c:868-882. It also states the identity that made #626 easy to misread: ceil(n / c) == floor((n - 1) / c) + 1, so the old rule was one entry over at every geometry, and the excess only showed when it crossed a 1 MiB region boundary.

    calculate_bat_layout, VhdxState::init and the check op call it. The qcow2 crate's fixture builder keeps its own arithmetic, because its comment says it is an independent oracle, but switches to qemu's rule, and its stale comment at :13552-13562 is corrected.

    1. The writers change at boundary geometries, and the tests say so. calculate_bat_layout sizes the BAT region for create, convert, measure and resize, so at a geometry like 131041 MiB with 1 MiB blocks each now writes or predicts a region 1 MiB shorter. That is the point of the fix: qemu's layout. The reader bound only loosens, so every VHDX instar wrote before still opens, including one with the old, longer region. Unit tests pin the boundary in the vhdx crate (131041 blocks at a chunk ratio of 4096 gives 131072 entries, exactly 1 MiB), in plan_vhdx, in measure_vhdx, and in resize's decide_action: a grow from 131040M to 131041M at 1 MiB blocks no longer relocates. One integration test creates -o block_size=1M at 131041M and compares the region table's offsets and lengths with the pin case's, but not the Required bit, which is phase 6's.

    2. A partial last block is judged by its payload index, which is what qemu means, not by its BAT index, which is what qemu does. The check op computes each FULLY_PRESENT block's length as min(block_size, virtual_disk_size - payload_block_idx * block_size), with checked arithmetic, and uses that length for the bounds test, the declared-region overlap test and max_block_offset. A block whose start is at or past end of file is still a corruption. So is a block that falls short of its own length, and only the last block can be short.

    This is the decision a reviewer is most likely to dispute, because it makes instar check accept images that qemu-img check calls truncated: fixed block_state_zero=off images whose partial last block lies past the first chunk. Copying qemu would mean calling qemu's own default output corrupt, although no reader has trouble with it: the bytes the virtual disk needs are all in the file. It would also mean phase 7 writing images that instar's own check then fails. qemu's comment ("Allow that the last block exists only partially") says what it intends, and only the arithmetic falls short. docs/quirks.md records the divergence, with the measurement, so that the next reader of a qemu-img check failure on such an image finds it.

    Reporting the qemu defect upstream is outside this repository and is the operator's call. This phase does not do it.

    1. LeaveBlocksAllocated is parsed in both metadata parsers, and used only by resize. Add FILE_PARAMETERS_LEAVE_BLOCKS_ALLOCATED: u32 = 1 << 0, documented from SPEC(VHDX) 2.6.2.1 and block/vhdx.h:275. Add leave_blocks_allocated: bool to VhdxMetadata and VhdxMetadataItems, set by parse_metadata and parse_metadata_region alike, so the two parsers cannot disagree. It does not go on VhdxState, which nothing here needs. info does not surface it, because qemu-img info does not, and check does not police it (Scope).

    2. resize refuses a fixed VHDX with its own error code.

    3. Add ResizeError::FixedVhdx.
    4. Add VhdxResizeOpts::leave_blocks_allocated, set from the parsed metadata.
    5. In plan_grow, refuse right after the has_parent refusal, so that a same-size request and a shrink get this refusal too. Both are refused by qemu-img resize for any VHDX.
    6. Append ResizeResult::ERROR_FIXED_VHDX = 15, mapped in the op.
    7. On the host, add the constant and a message such as "refusing to resize a fixed VHDX: a fixed image keeps every block allocated, and growing one would add blocks that are not; convert it to a dynamic VHDX to resize it". Extend the code-range test to 15.

    Reusing UnsupportedSubformat would be smaller, but its message is exactly what open question 6 asked to improve on. Appending a code is the pattern ERROR_BITMAPS_UNSUPPORTED set, and it changes no struct layout. The fuzz target sets the new field from a free flag bit, so the refusal is fuzzed rather than always off.

    1. The phase 2 read matrix is the integration oracle, and grows.
    2. Each fix removes its KNOWN_READ_FAILURES entries. The table and its "remove this entry" mechanism stay, empty, for the next regression.
    3. measure joins METADATA_OPS, as _op_measure: instar measure -O qcow2 --output json must exit 0, and its fully-allocated must equal qemu-img measure -f vhdx -O qcow2 --output=json's. required is not compared, because of the divergence the survey found.
    4. The dynamic #626 fixture gains a convert test: instar convert -O qcow2 exits 0, and qemu-img info of the output reports the same virtual size. Every entry is ZERO, so this walks the BAT without reading 128 GiB. compare at the #626 geometry is not added, because both tools would read the whole virtual disk. compare goes through the same VhdxState::init that convert does, and it is covered on the partial-block fixtures.
    5. A runtime image vhdx-fixed-4608.5M-block-1M-bsz-off joins RUNTIME_CREATE_IMAGES with the metadata operations. instar's info, check, map and measure must all pass on it. A separate test pins that the host qemu-img check exits 2 on it, so that a qemu fix shows up as a test failure that points at the quirk text.
    6. Negative cases, on copies of vhdx-fixed-17M-bsz-off-data: truncate it 512 KiB into the partial block, and truncate it to the partial block's start. instar check must exit 2 on both.

    Risks and mitigations¶

    • The count change moves a pinned output. It changes writer bytes only where the old count crossed a 1 MiB boundary. The management session greps tests/, scripts/ and src/ for golden VHDX sizes and BAT lengths, and runs test_create, test_measure, test_convert and test_differencing in full after 4a, not only the modules 4a touched. That follows the standing rule that a crate-only change can alter its consumers.
    • Loosening check hides a truncated image. Only the last block may be short, and only by the virtual disk's own arithmetic. The two truncation cases in decision 6 must fail. The management session's mutation run replaces the clamp with block_size (the partial fixture must then fail), uses bat_idx in place of payload_block_idx (the 4608.5M image must then fail), and drops the start-past-end test (the truncation case must then fail). Each mutant must be killed.
    • A walk skips a slot it used to read. The count now stops before the trailing sector-bitmap slot. Every walk classifies that slot as a bitmap slot and skips it, and the survey shows no no-parent read consults it. The existing VHDX map, check and convert suites on every committed VHDX fixture are the check. The management session confirms that they run, not skip, by looking for "Ran: N".
    • Guest and host disagree on the new resize code. The shared pin test, the host's code-range test and an integration test that matches the message text cover all three sides. The mutation run maps FixedVhdx to ERROR_UNSUPPORTED_SUBFORMAT and expects the message test to fail.
    • The refusal is never exercised by the fuzzer. Decision 5 has the fuzz target draw the bit from its input. The management session reads the target diff to confirm it is not a constant.
