    Proxmox source phase 5: the CI lane¶

    This is the detailed plan for phase 5 of PLAN-proxmox-source.md. Read the master plan first. Its What the measurements settled and Three protocol details that cost an afternoon are assumed knowledge here. So is the phase 4 plan, whose driver this lane is the first to run against a real node. Its decision 7 asks this lane to prove the least-privilege account, and its Future work lists what the driver knowingly does not handle.

    Prompt¶

    All work for this phase lands in shakenfist/kerbside. It adds a CI lane that builds a real Proxmox VE node with shakenfist/actions' deploy-proxmox-on-shakenfist action. The lane deploys the pull request's kerbside on the runner, registers a type: proxmox source against the node, and relays a real SPICE session through kerbside's proxy and PVE's spiceproxy. It adds .github/workflows/proxmox-functional.yml and tools/proxmox-e2e/, and documents the lane. It changes the driver only where the lane proves it wrong. Consult ARCHITECTURE.md, docs/testing.md (CI tiers and The oVirt end-to-end kerbside lane), tools/ovirt-e2e/README.md and docs/console-sources.md's Proxmox VE section. Run tox -eflake8, tox -epy3 and pre-commit run --all-files before every commit.

    Planning effort: high. The lane handles live credentials in public CI logs: two PVE API tokens, a SPICE password and a signed CONNECT host. Its oracles have to tell a harness timing fault from a real defect when a ticket lasts 30 seconds. And it is the first contact between phase 4's driver and PVE, so it may find defects in that driver.

    Scope¶

    In scope:

    • A workflow that deploys a PVE node, deploys kerbside on the runner, and drives one proxied console end to end.
    • Creating the source's token with the documentation's own pveum commands, and proving that the two privileges are both enough and both needed.
    • Fixture VMs on the node that discovery must skip.
    • Oracles read from PVE's own access log, for the property that matters most here: discovery and the direct refusal never mint, and a session mints once.
    • Fixing any driver defect the lane proves, each with a unit test that reproduces it.
    • Documenting the lane, its tier, and its place in the pre-release check.

    Out of scope:

    • The Proxmox use-case page, which is phase 6.
    • PVE clustering and live migration. The action builds one node, so phase 4's live-migration gap stays in its Future work.
    • Changing deploy-proxmox-on-shakenfist itself. See Future work.
    • Generalising tools/ovirt-e2e/ into a shared lane library. See decision 6.

    What the survey found¶

    1. The action does most of the node's setup. deploy-proxmox-on-shakenfist (shakenfist/actions main, deploy-proxmox-on-shakenfist/action.yml) boots PVE 9 in the runner's own Shaken Fist namespace, at 10.0.2.2 by default. It starts a running SPICE guest (vmid 100, --vga qxl, cirros) and maps the node's FQDN in the runner's /etc/hosts. It adds the FQDN and the address to no_proxy and NO_PROXY through GITHUB_ENV. Its outputs include api_url (https://<fqdn>:8006), node_name, node_fqdn, vmid, token_id, token_file (0600, masked) and ca_file. The weekly proxmox-substrate.yml run of 2026-10-25 took nine minutes for the whole job.

    2. The action's token is not the documented one. Its ansible/tasks/proxmox/api.yml and ansible/vars/proxmox.yml create kerbside@pve!console with --privsep 0. They grant the user PVEVMUser on /vms and PVEAuditor on /. Their own comment says this least privilege is "asserted, not proven", although action.yml's description calls it "a least-privilege API token". docs/console-sources.md documents a different account: a KerbsideConsole role holding VM.Audit and VM.Console, and a privilege-separated token. The doc's commands also create the user kerbside@pve, which the action has already created, so they cannot run unchanged on this node.

    3. The runner can reach the node as root. The action's tools/proxmox-deploy.sh drives the playbook from the runner with the inventory in /home/debian/ansible-hosts. So the runner can SSH to the node and run pveum and qm there with sudo.

    4. The smoke guest has an SMBIOS UUID. It is made with qm create, which writes one (phase 4, survey finding 6). So its console uuid is 100-<smbios uuid>. This is the first time that is checked on real PVE rather than read from source.

    5. The oVirt lane is the model, and it runs nightly only. functional-tests.yml's ovirt_matrix builds the proxy wheel and ryll on the runner. It deploys kerbside there as plain processes with tools/ovirt-e2e/deploy-kerbside.sh, which reuses tools/direct-qemu/start-kerbside.sh. Then tools/ovirt-e2e/drive-console.py drives the session with ryll and tools/direct-qemu/smoke-client.py. That script holds the session past the token's expiry, terminates it over REST, and scans the artifacts for the engine password. It runs on [self-hosted, vm, debian-13, l], nightly and on dispatch (docs/testing.md, CI tiers). deploy-kerbside.sh and gen-sources.py are oVirt-specific throughout.

    6. Ryll's Proxmox lane is advisory and path-filtered. shakenfist/ryll's .github/workflows/proxmox-functional.yml runs on pull requests touching the tunnel code, and on dispatch. It is deliberately not a required check, because a path-filtered required check never reports, which blocks a pull request forever. It also skips pull requests from forks, because its runner holds the CI mesh's SSH key. Upstream drift in PVE is left to the actions repository's weekly lane.

    7. Nightly failures already have a home. The scheduled jobs in direct-qemu-functional.yml and sf-e2e-functional.yml call tools/file-nightly-failure-issue.sh <lane> <run-url>, which files or updates a Nightly <lane> lane failing issue. docs/development.md's Releasing asks the tagger to check for open oVirt and OpenStack nightly issues before tagging.

    8. PVE's access log can count mints. Every API request, POST .../spiceproxy included, is written to /var/log/pveproxy/access.log on the node. That is the only place a mint can be counted without trusting kerbside's own account of it. The log's field layout, and whether it names the token, must be checked in pve-http-server's source before an oracle depends on it.

    9. PLAN-two-tier-ci.md placed this lane in the merge tier. Its Future work says the Proxmox lane lands "directly in the merge tier". The cloud lanes have since left the merge queue for the nightly tier (docs/testing.md, CI tiers). That plan is complete and is not edited. The master plan's Relationship to other plans now notes that the tier is decided here.

    Nothing in the master plan's phase 5 row is false, but it is one line. It is expanded in the planning commit from decisions 1 and 2, and the index.md row describes this phase from the survey.

    Decisions¶

    1. The lane is nightly, on dispatch, and advisory on pull requests that touch the Proxmox path. This is the decision most likely to be argued with. Its own workflow, proxmox-functional.yml, runs:
    2. on schedule, filing Nightly proxmox lane failing through tools/file-nightly-failure-issue.sh when it fails;
    3. on workflow_dispatch;
    4. on pull_request, path-filtered to:
      • kerbside/sources/proxmox.py, kerbside/sources/base.py and kerbside/sources/minting.py;
      • kerbside/rpc/**;
      • rust/kerbside-proxy/src/backend.rs and the proxy's Cargo.lock;
      • the workflow and tools/proxmox-e2e/**.

    It has no merge_group trigger and is not a required check. The alternative is the smoke tier, which would book a nested PVE node, about nine minutes and an l runner, on every push of every pull request. PVE's churn, like the cloud lanes', is upstream (the no-subscription repository, and the action itself), and that churn is what pushed those lanes out of the gate. Path filtering gives signal on the pull requests that can break this source, as it does in ryll (finding 6). The price is that such a pull request can merge red. The nightly issue and the release check (step 5.3) are what stop that from reaching a release.

    1. The source's token is created by running the documentation. A script extracts the shell block under Proxmox VE account in docs/console-sources.md. It renames kerbside@pve to kerbside-lane@pve, because the action already owns that user (finding 2), and runs the block on the node over SSH. If the documented commands are wrong, the lane fails, and a doc edit that breaks them is tested by the lane. The script refuses a block containing any command other than pveum role add, pveum user add, pveum acl modify and pveum user token add. That matters because CI runs this text as root. The token is created with --output-format json, and its secret goes over SSH straight into a 0600 file on the runner. It is masked with ::add-mask:: before anything reads it, and is never echoed. Kerbside is given only this token. The action's token is used only for the lane's own setup reads.

    2. Both privileges are proven necessary, not only sufficient. The same script also makes two more privilege-separated tokens, one with a role holding only VM.Audit and one holding only VM.Console. The lane checks them directly against the API, before any session is opened:

    3. the token without VM.Audit gets 403 on the smoke VM's config;
    4. the token without VM.Console gets 403 on spiceproxy;
    5. the documented token gets 403 on status/stop, which needs VM.PowerMgmt.

    With the session passing on the documented token, that settles the master plan's open question 4. Neither of the refused spiceproxy calls mints, so none of them changes the smoke VM's password.

    1. Discovery is tested against VMs it must skip. Over SSH, with qm, the lane creates diskless 64 MB guests that never boot an OS:
    2. 101, running with the default std display;
    3. 102, running with qxl and its smbios1 deleted;
    4. 103, stopped with qxl;
    5. 104, a qxl template, if qm template accepts a diskless VM (if it does not, the step says so and drops 104).

    The lane asserts that the console list for the source is exactly the smoke VM. That console's uuid must be 100-<smbios uuid>, with the UUID read from the VM's config through the action's token. Its hypervisor must be the node name, and its host subject OU=PVE Cluster Node,O=Proxmox Virtual Environment,CN=<fqdn>. The daemon log must name vmid 102 at info level. This is the oVirt lane's no-spice-test lesson applied to every skip rule phase 4 wrote.

    1. Mints are counted by PVE, not by kerbside. The lane records the size of /var/log/pveproxy/access.log before it starts kerbside. It then counts spiceproxy POSTs after that point, at each checkpoint below, and expects:
    Checkpoint Expected mints
    After the first scrapes 0
    After a refused direct .vv request (409, audited) 0
    After the first proxied session's channels have all connected 1
    After holding the first session 1
    After a second session opens while the first is held 2
    After the lane's own mint, while the second is held 3
    At the end, after terminating the second 3

    The second session displaces the first. qemu's SPICE server serves one client at a time, and disconnects the client it has when a new client's main channel links, as it does for any SPICE client. So once the second session's channels have connected, the first session's ryll must have exited and the proxy must have logged each of its relays ending, while the second passes frames. The first still running is a defect, "the first session was not displaced". That a password change keeps a connected client is shown instead by the lane minting once itself, with the documented token and kerbside's own request, while the second session is held: the second must still pass frames afterwards. That is measured on real PVE rather than in the direct-qemu lane. Before relying on the log, step 5.2 confirms its layout from pve-http-server's source, and whether it names the token. If it names the token, the count is filtered to kerbside-lane@pve.

    The oracle keeps two faults apart. A count that is wrong is a defect. A session whose channels did not all connect within REUSE_MARGIN of the first channel's mint is a harness timing fault, because a later channel legitimately mints again. That fault is reported as such, from the proxy's log timestamps. This is the same split docs/testing.md's Log-derived oracles asks for.

    1. The session checks follow the oVirt lane. The first session is driven by ryll and smoke-client.py. The proxy log must show the backend leg as tunnelled, over TLS, with a non-empty subject pin. The lane then:
    2. holds the session past the ticket's 30 seconds and past CONSOLE_TOKEN_DURATION, and checks that it still passes frames;
    3. opens the second session from decision 5, which displaces the first, and mints once itself while the second is held;
    4. terminates the second session over REST, and checks that the proxy dropped it.

    New scripts go in tools/proxmox-e2e/, built on tools/direct-qemu/start-kerbside.sh, setup-mariadb.sh, generate-tls.sh and smoke-client.py. The oVirt scripts are copied where it helps, not refactored. Refactoring them would change a lane that runs only nightly, so a mistake there gets no signal on the pull request that makes it. A shared library is Future work.

    1. No live credential reaches an artifact or the log. Every token secret is masked as soon as the runner holds it. The lane mints once itself (decision 5), and never prints, logs or writes that response: its SPICE password and connect host are held in memory for the scan and the redactor, and every other SPICE password and connect host exists only inside kerbside. Before upload, the lane scans every artifact for each token secret and the literal pvespiceproxy:, and fails if it finds any of them. It never uploads:
    2. sources.yaml;
    3. any .vv file;
    4. a token file;
    5. ryll's unredacted /tmp/ryll.log, which ryll's lane already excludes.

    The scan's matcher is a pure function with a unit test, so that it can be mutation-checked.

    1. The lane builds before it books a node. The proxy wheel and ryll are built before the deploy step, as ryll's lane does, so a compile error never spends a PVE node. The runner is [self-hosted, vm, debian-13, l], like the oVirt lane's. The workflow carries ryll's fork guard, for the same reason (finding 6). It has a concurrency group that cancels a superseded run on the same ref.

    2. A defect the lane finds in the driver is fixed here. Each fix gets a unit test that fails without it, and an entry in Bugs fixed during this work. A defect that needs a design change, rather than a fix, is recorded and filed as an issue, and the lane's expectation is narrowed to match, with the issue cited.

    Risks and mitigations¶

    • A live credential reaches the public log. The lane holds three API token secrets, and kerbside holds minted SPICE passwords and connect hosts. Mitigation: decision 2's file-only path for secrets, ::add-mask:: before first use, and decision 7's pre-upload scan, which fails the lane. The management session reads every echo, print and run: line in the diff for a value that could carry a secret, and searches the first green run's step log for pvespiceproxy: before recording it.
    • CI runs repository text as root. Decision 2 executes a documentation block on the node. Mitigation: the allowlist, unit-tested and mutation-checked, and a node that is discarded with the runner's namespace.
    • The timing oracle flakes. Under TCG emulation, or on a busy sfcbr, a session's later channels can connect after the reuse window. Then a second mint is correct behaviour, not a regression. Mitigation: decision 5's split reports that case as a timing fault, distinct from a wrong count, and the README says what each means.
    • First contact finds a lot. The driver was written from PVE's source, and the lane may find several defects in it. Mitigation: decision 9. Fixes stay in this phase only when they are fixes, each with a reproducing unit test. Anything larger is filed.
    • The lane goes red for reasons that are not kerbside's. A PVE release, the no-subscription repository or the action can break it. Mitigation: the actions repository's weekly substrate lane breaks on the same causes and tells them apart. The nightly issue names the run, and decision 1 keeps such breakage out of the merge queue.
    • An advisory lane lets a regression merge. Mitigation: the nightly issue the next morning, and step 5.3's pre-release check, which makes an open Proxmox nightly issue a release blocker, as the oVirt and OpenStack ones are.
