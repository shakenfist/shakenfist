    SPICE performance phase 6: push audit of phases 1-5¶

    Master plan: PLAN-spice-performance.md.

    Planning effort¶

    This plan was written in a high-effort session. The master plan gives the phase no effort level, only the push-audit shared block. Review effort: medium. The judgment is in the range, in which repository's rules apply to which landing, and in how the review is split. The steps themselves follow the runbooks.

    Scope¶

    In scope:

    • Running kerbside's PUSH-AUDIT.md, waves 1 and 2, over everything phases 1-5 landed in this repository: seven merges carrying content outside docs/plans/, listed under Audit range.
    • Running ryll's PUSH-AUDIT.md over ryll #406, which phase 3 landed and nothing has audited (survey finding 3).
    • Applying the shared block's floor checklist, plus questions of its own, to the two kerbside-patches landings. That repository has no PUSH-AUDIT.md (survey finding 2).
    • Reviewing the carried qemu v2 series, the only code in the plan that no upstream reviewer will read (decision 4).
    • The floor checklist's items 2 to 5 for kerbside too, as the Proxmox audit did.
    • Triaging every finding as blocking or advisory, with the reason, in this plan's Outcome.
    • Filing problems that predate the plan as issues.

    Out of scope:

    • Fixing findings. They land in follow-up pull requests after this one merges, one per repository that has any (decision 7).
    • andris #56 (phase 4), whose push audit is recorded in its pull request body (survey finding 4).
    • Phase 2's dri-devel submission of the kernel fix. It is not yet sent, and its audit is the upstream review (decision 6).
    • The spice-server and Linux series' code. Their disposition is submit, so the upstream review is their audit (decision 4).
    • The open audit-tooling defects #488, #491 and #638. This plan works around them (decision 1) and does not fix them.

    What the survey found¶

    1. Phase 3's Merged cell recorded a SHA that does not resolve. 9d1b64d6 is not a prefix of #505's merge commit, which is 9d1b64deae. git rev-parse 9d1b64d6 fails, so an audit reading the cell would have skipped #505's 140 lines of session.rs. The planning commit corrects the cell.

    2. kerbside-patches has no PUSH-AUDIT.md, and the audit the master plan says to cite does not exist. The master plan's phase 2 and phase 6 sections both say this phase cites kerbside-patches' own audit. kerbside-patches' docs/plans/upstream-series.md does carry a push-audit phase (its phase 5), but its status table reads Not started. Its phase 1, the import, still reads In progress though it merged as #1748. #2024 landed under no kerbside-patches plan at all. The template's shared block, now at v4, says what a repository without a runbook does instead: the floor checklist, plus the questions its own blast radius raises, and not another repository's runbook. The master plan still carries v3 of the block, which predates the checklist. The planning commit syncs the block verbatim from PLAN-TEMPLATE.md, and corrects both sections. The stale status table in kerbside-patches is left for that repository's follow-up (6j).

    3. ryll #406 was never audited. Phase 3 recorded it in its Merged cell. Neither its pull request body nor its comments carry an audit, and no plan in ryll's docs/ mentions it. ryll's push-audit merges since then (#411, #630, #633, #657) each audit a different plan. Phase 3's re-survey decision 1 says andris and ryll audit the work that step 3a found already delivered. That covers other pull requests, not #406. kerbside's proxy consumes #406 through caps.rs to parse a client's link message, which is untrusted input, so this one is worth the opus agent.

    4. andris #56 was audited, and the record is in its pull request body. Style passed and nothing was blocking. The one medium finding was fixed in the pull request's second commit, and two items were declined with reasons. This phase cites it.

    5. The plan changed Rust in five merges, and PUSH-AUDIT.md has no Rust gate. Wave 1 is tox only. rust.yml runs cargo fmt --check, clippy with -D warnings, cargo test and a release build on every push to develop that touches rust/**. Since #630 it also runs clippy and the tests with --features transcode. #616 added the transcoder before those two steps existed, so its own push run never built the feature.

    Declined, and why¶

    • The transcoder's size and comment proportion: transcode/mod.rs is 1,120 lines, and geometry.rs and tests.rs are past 800 (6c, advisory). The transcoder is an experiment the phase 3 verdict declined, behind a feature no wheel enables; splitting it is work on code nobody is changing. The same holds for 6c's low-confidence note that the backend task is detached rather than aborted if the outer future is dropped.
    • relay.rs, backend.rs and session.rs past 800 lines (6c, advisory). Each crossed the mark by a little, in a merge that added coherent code. A split is its own change, along seams the next change to those files will show.
    • Type hints on config.py's validator (6c). No function in the file has them; adding them is a whole-file change.
    • tools/shaped-link/test_quality.py is run by nothing, and summarise.py has no tests (6d, survey finding 7). The rig is not shipped, the measurement phases are over, and each verdict's raw results and summary tables are published, so a wrong exclusion is recoverable from the data. Wiring numpy into CI for a finished rig costs more than it protects.
    • BUFFER_BDP is undocumented outside the plans (6c). It is a rig knob, described in run-matrix.sh where it is read.
    • The client's capability words are logged before authentication (6b, 6f). ryll caps them at 16 words of integers, so the volume is bounded and nothing is injectable.
    • The rig's ticket is visible in the process list (6f). It is a constant dummy value for a throwaway guest.
    • "scratchpad" in kerbside-patches prose, and build-spice.sh's forgeable output marker (6h). The first names no path. The second guards a directory the operator chose.
    • switch.rs has no refuse-to-switch code (6d). That is the design: the client leg never carries GLZ, and the first transcoded frame clears streams. The mutant removing that guard was killed.
