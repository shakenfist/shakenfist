    SPICE performance phase 9: push audit of phases 6 and 7¶

    Master plan: PLAN-spice-performance.md.

    Planning effort¶

    This plan was written in a high-effort session. The master plan gives the phase no effort level, only the push-audit shared block. Review effort: medium. The judgment is almost entirely in the range -- the survey found landed, unaudited work the master plan's phase 9 section does not mention -- and in weighting the review by blast radius rather than by line count. The steps themselves follow the runbook.

    Scope¶

    In scope:

    • Running kerbside's PUSH-AUDIT.md, waves 1 and 2, over the two landings under Audit range: phase 6's follow-up (#701) and phase 7 (#716).
    • The shared block's floor checklist, items 1 to 5, for kerbside.
    • Deciding, for each Future work entry in this plan's phase files and the master plan, whether it has a live home; and listing those that do not (decision 5).
    • Triaging every finding as blocking or advisory, with the reason, in this plan's Outcome.
    • Filing problems that predate the plan as issues.

    Out of scope:

    • Fixing findings. They land in a follow-up pull request after this one merges (decision 4), which also marks the plan Complete if phase 2 has landed by then.
    • Phases 1 to 5, and the kerbside-patches landings #1748 and #2024: audited by phase 6, which this phase cites rather than repeats (decision 1).
    • ryll #406, audited by phase 6 step 6g under ryll's own runbook. Phase 7 landed nothing in ryll (survey finding 5), so no second repository is in range.
    • Phase 8, which was abandoned and landed nothing.
    • Wiring tools/quic-bench/ into CI. Whether that should happen is a finding for triage; an audit phase does not change code (decision 2).
    • Phase 2's dri-devel submission, which is still unsent and whose audit is the upstream review.

    What the survey found¶

    1. Phase 6's follow-up landed unaudited, and it is shipped code. This is the finding that reshapes the phase. The master plan's phase 9 section says the phase "audits phase 7's accumulated diff ... and cites phase 6 for phases 1-5". But phase 6's audit merged on 2026-10-31 as #668, and the follow-up pull request it called for merged seven days later, on 2026-11-07, as 17a31ebf75 (#701). Nothing audited that follow-up: a grep for 17a31eb and #701 across docs/plans/ finds them only in the master plan's Merged cell for phase 6. It is 736 insertions over 26 files and, unlike phase 7's, most of it ships -- rust/kerbside-proxy/src/caps.rs (+135), main.rs (+95), ackwindow.rs (+61), relay.rs (+60), backend.rs (+20), kerbside/config.py (+30) and tools/build-proxy-wheel.sh (+49). The shared block is explicit that the final phase audits the accumulated diff of every phase rather than the last phase alone, precisely so that work landing between audits is not missed. Corrected at source in the master plan's phase 9 section and the index.md row as part of this planning commit.

    2. Nothing automated compiles or tests the phase's Rust. tools/quic-bench/ is 1,162 lines of Rust outside Cargo.lock, and no repository gate touches it. .github/workflows/rust.yml triggers on rust/** plus four named tools/ scripts, none of them this one, and runs with working-directory: rust/kerbside-proxy; nothing anywhere in .github/ mentions quic-bench; there is no Rust hook in .pre-commit-config.yaml; and wave 1's own gates are tox, meaning flake8 and py3. The crate is a standalone cargo project -- there is no root Cargo.toml and it is not a workspace member -- whose only Rust gate is a hand-run make lint, make test and make mutants in Docker. Its shell and Python are gated: shellcheck matches ^(tools|demo)/ and flake8 matches ^tools/, so run-bench.sh, mutation-check.sh and summarise.py are covered. Wave 1 would therefore pass vacuously on the Rust, which is why decision 2 names a substitute gate. - Corrected 2026-11-12 during execution: "no repository gate touches it" was too strong. CodeQL does. codeql-analysis.yml pins languages: actions, javascript-typescript, python, rust with no path configuration, and its run on the phase 7 merge found both Cargo manifests and extracted 30 Rust files without error -- exactly the 24 under rust/kerbside-proxy/src/, plus build.rs, plus the crate's 5. Its Python extractor took tools/quic-bench/summarise.py as well. The narrower claim is the one that matters and still holds: nothing builds, tests or lints the crate. CodeQL neither compiles it -- it logged "unable to determine project Rust toolchain" -- nor runs its tests, so a broken build or a failing test still lands unseen.

    3. A phase-1 page states one thing phase 7 disproved, and the finding as first written overstated which. This entry was rewritten on 2026-11-12 after step 9d refuted most of it; the corrected version is below, and what it replaced is recorded in Execution notes.

    What is wrong is one sentence. docs/performance/proxy-backpressure.md:253 says BBR "was not measured" because "This host's kernel has only reno and cubic loaded". That is false in the present tense -- the host now reports reno cubic bbr, which docs/performance/quic-transport-bench.md records -- and, more to the point, it reads as the reason BBR cannot be measured here, where phase 7 found the module shipped with the kernel and simply not loaded. The rest of the bullet survives: loading it needs root, and an unprivileged namespace cannot autoload it, which the master plan's correction already says.

    What is not wrong is the prediction. "On these profiles BBR could only trim the bottleneck queue (about 20 ms at 20 ms RTT, one BDP)" is a statement about queue depth, and phase 7's 171 to 104 ms no-loss cut on 80 ms / 10 Mbit is roughly one BDP at that RTT, so it illustrates the mechanism rather than refuting it. Phase 7's throughput result is a loss effect: at 0% loss the two controllers tie, and phase 1's rig had no loss term at all, since phase 7 added it. Nor can phase 7 touch "small next to the ACK-window backlog", because its bench has no spice-server and no ACK window.

    The first draft of this finding also said phase 7's numbers were "not phase 1's profiles". That is wrong: PROFILES='20:50 80:10 80:50' at docs/performance/proxy-backpressure.md:87 includes 80 ms / 10 Mbit. Only 150 ms / 2 Mbit is new.

    4. A discoverability gap, not a stale page. Also rewritten on 2026-11-12 after step 9d refuted half of it. The loss-term half was wrong: docs/testing.md says in terms that "The header of run-matrix.sh documents every variable", and phase 7 documented the :loss_pct field in that header at length, so the page delegates by design and is not stale. Its one PROFILES=0:0 is an incidental example of an unshaped case, not a field reference. What survives is advisory: tools/quic-bench/ appears nowhere outside docs/plans/ and the two measurement pages, and docs/testing.md's shaped-link material is a subsection of its Ryll section -- which the bench does not belong in, having no Ryll, no guest and no SPICE. The measurement page owns the bench's invocation; a one-line cross-reference would help discovery, and that is the whole of the finding.

    5. The premise that holds. Phase 7 landed nothing in ryll: its diff touches neither tools/shaped-link/ryll-surface-drawn-rect.patch nor build-ryll.sh's RYLL_REF pin, both of which its execution notes record as deliberately untouched once steps 5a, 5b and 6 became void. Phase 8 landed nothing at all. So the master plan's "all of it in Kerbside" is correct, even though its scope is not.

    6. Two Future work entries phase 7 asked to have tracked have no home. As first written this said "two entries have no home", which step 9d showed is false: about fifteen have none, nearly all of them the master plan's own long tail. The defensible version is narrower. Two entries are ones phase 7 itself flagged as deserving a home -- the kernel-BBR finding, "worth its own plan", and the missing ticket-valid-until in the .vv template, "worth an issue" -- and gh issue list --state all --search finds no issue for either. Phase 9 is the plan's last phase, so an entry with no home dies with the plan when it retires.

    7. Floor item 3 looks clean mechanically. The addresses in the files phase 7 added are RFC1918 rig addresses inside unprivileged namespaces -- 10.77.0.x for shaped-link, 10.78.0.x for quic-bench, deliberately distinct -- plus 0.0.0.0 and loopback. No home or scratchpad paths, no hostnames. The audit confirms rather than discovers this, and extends it to #701.

    Decisions¶

    Findings¶

    All advisory or informational; none blocks the landing. Each goes to the follow-up pull request unless marked otherwise.

    1. tools/quic-bench/summarise.py: a lost repeat narrows the gate's own threshold, silently. collect appends a repeat only when read_run returns a value, and read_run returns None when a repeat's {arm}.json is missing, so such a repeat never enters runs -- while aggregate's unmeasured = len(runs) - len(measured) can only see repeats that are present with a null percentile. A repeat lost to a crash, a kill or a full disk therefore shrinks p95_spread_ms, which is the figure decision 2 of phase 7 gates its verdict against, and nothing warns. This is the same class as the null-percentile path that #716's own review round fixed, one layer further up: the fix generalised to the wrong boundary. It cannot have moved a published number -- the independent recomputation covered those, and phase 7's margin was about seventy times its spread -- but the next run of this bench is unprotected. Fix: count repeats attempted against repeats read, and warn on the difference.
    2. detect_headline_cc falls back to ccs[0]. bbr sorts before cubic, so the fallback would label every row's scope backwards, making the sensitivity arm read as the gate.
    3. The throughput medians were never independently recomputed. Phase 7's recomputation covered the interactive percentiles and bytes per queue slot, not the megabit tables, which pass through the same aggregate.
    4. tools/quic-bench/run-bench.sh: a pre-created TLS directory. The script does mkdir -p "${WORKDIR}/tls" and then chmod 700, and its comment correctly reasons that narrowing must precede writing. The residual case is a WORKDIR under a world-writable directory, where another local user can pre-create tls as a symlink: mkdir -p succeeds on it, chmod follows it, and the unencrypted keys land somewhere readable. Not reachable with the default WORKDIR. Fix: port the ownership refusal already in tools/shaped-link/quality.sh, which rejects a path this user does not own.
