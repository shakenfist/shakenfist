    Deployment options phase 6: installation hand-off¶

    Master plan: PLAN-deployment-options.md.

    Planning effort¶

    The master plan asks for medium effort. This plan was written in a low-effort session, below that. The survey read every page this phase touches, and checked for links into them here and in the sibling Shaken Fist clones, so it was not cut short. The review should still be done at medium. Review effort: medium. The edits are small, and the risk is in what they leave behind: a sentence on another page that still sends readers to a guide by cloud.

    Scope¶

    In scope:

    • docs/installation.md: the "Deploying for real" section becomes a pointer to docs/deployment/, and the page's opening paragraph stops promising "the guide for the cloud you actually run".
    • docs/index.md: delete the Deployment Options table's stale "not a link" sentence, reword the Use Cases introduction, and reword the Installation bullet under Operator Documentation.
    • README.md: one new curated link, to the Deployment Options table, and the two link descriptions that frame deployment by cloud.
    • AGENTS.md's question table and ARCHITECTURE.md's directory trees and Related Documentation list, which do not mention docs/deployment/ at all (findings 4 and 5).

    Out of scope:

    • The Use Cases table's Proxmox row, which is stale but belongs to another plan (finding 6).
    • The README's pitch paragraph about Kolla-Ansible (decision 4).
    • The Deployment Options table's rows. Phases 2 to 5 wrote them, and phase 7's audit checks them.
    • The push audit, which is phase 7.

    What the survey found¶

    The master plan's phase 6 paragraph is right about installation.md. It is wrong that README.md might need nothing and that ARCHITECTURE.md and AGENTS.md probably need nothing: findings 3 to 5 correct it. The planning commit corrected that paragraph at source.

    1. "Deploying for real" is still keyed by cloud. docs/installation.md:360-377 opens "Kerbside is deployed as a component of the cloud it serves", the opposite of the front-door default this plan argues for. Its table has rows for oVirt, OpenStack, Shaken Fist and static targets. The OpenStack row links kerbside-patches, not deployment/kolla-ansible.md. It has no Proxmox row, though #618 merged the Proxmox source. The closing paragraph (the pieces are the same; configuration.md and console-sources.md apply throughout) is still true. The page's opening paragraph (installation.md:3-4) promises "the guide for the cloud you actually run".

    2. Nothing links the section's anchor. #deploying-for-real has no inbound link in this repository outside docs/plans/. The local clones of shakenfist, kerbside-patches and client-python have no link to installation.md at all. Keeping the heading is free anyway (decision 1).

    3. Four more places frame deployment by cloud.

    4. docs/index.md:110, the Use Cases introduction, says "One page per deployment permutation".
    5. docs/index.md:156-158, the Installation bullet, says the page tells you "where to go for your cloud".
    6. README.md:44-45 says the same two things.
    7. ARCHITECTURE.md:470 and :504 call the use cases "Per-deployment and topology guides".

    The README has no link to the Deployment Options table, so its curated links do change. The master plan says to touch README.md only in that case.

    1. AGENTS.md does not know docs/deployment/ exists. Its question table (AGENTS.md:23-25) sends "How do I install and deploy it?" to installation.md and "How is it deployed against a specific cloud?" to docs/use-cases/. This is an index entry gone stale, not a convention change, so it does not cost a new line of convention.

    2. ARCHITECTURE.md's tree has no ansible/ and no docs/deployment/. The repository tree near ARCHITECTURE.md:412 lists etc/, demo/ and tools/, but not ansible/, where the role has lived since #580. The docs tree (:468-471) lists spice/, use-cases/ and plans/, but not deployment/. Its Related Documentation list (:497-504) has no deployment entry.

    3. The Use Cases table's Proxmox row is stale. docs/index.md says "Deferred until a Proxmox source driver exists" and "No source yet", but #618 merged the driver. PLAN-proxmox-source.md's phase 6 owns that row and a use-case page, and its phase 5 is in progress in another worktree. This phase leaves the row alone.

    4. The rest of the Deployment Options section is current. Every mechanism row is now a link. That leaves the sentence "Mechanisms whose name is not a link are planned rather than written" with no case; phase 5's execution notes left it for this phase.

    5. Editing installation.md starts the advisory demo-compose lane. .github/workflows/demo-compose.yml includes it in the path filter on purpose, because the page walks through the demo. That is expected and does not gate the merge.

    Decisions¶

    1. Keep the heading and rewrite the body as a short pointer. ## Deploying for real stays, so that any link from outside these clones still lands. Under it, about three short paragraphs:
    2. The default: a Kerbside deployed in front of the clouds rather than by one of them, as the index's Deployment Options introduction puts it.
    3. Where to go: link the four mechanism pages by name in one sentence, then send the reader to Deployment Options for which sources each configures and what CI proves.
    4. What each cloud needs from Kerbside, and Kerbside from it, is in its use case, linked through Use Cases.

    Then keep the existing closing paragraph about the pieces, configuration.md and console-sources.md as it is.

    1. No table on installation.md. The index table is the plan's one matrix (phase 1, decision 1). A second table keyed by mechanism would drift from it, as this one did from the clouds. Naming the four pages in a sentence is a pointer, not a matrix: it carries no sources or CI column.

    2. Fix the cloud-keyed wording everywhere it appears, in the same change. Every phrase in finding 3, and installation.md:3-4, is rewritten. The use cases become "one page per cloud or topology", which is what they are. The Installation bullets in the index and the README say the page ends by pointing at the deployment mechanisms. The definition of done greps for the old phrases.

    3. The README gains one link and keeps its pitch. A "Deployment Options" bullet goes between Use Cases and Installation, linking docs/index.md#deployment-options with an absolute GitHub URL like its neighbours. The pitch paragraph at README.md:17-20, which calls OpenStack "probably the best documented integration" because of the Kolla-Ansible patches, stays. This is the decision a reviewer is most likely to argue with. That sentence is the README framing Kerbside by cloud, the framing this plan exists to change. But it is the pitch, the master plan limits README changes to the curated links, and the claim is still defensible: OpenStack is the only cloud with a deployer outside this repository. Rewriting the pitch is a separate change, if Mikal wants it.

    4. AGENTS.md and ARCHITECTURE.md get index fixes only.

    5. AGENTS.md: one new row, "How do I run it for real: by hand, Ansible, Kolla-Ansible or containers?", pointing at docs/deployment/. The use-case row becomes "How is it set up in front of a specific cloud?". No convention text changes.

    6. ARCHITECTURE.md: ansible/ in the repository tree, as the shakenfist.kerbside collection and its kerbside role; deployment/ in the docs tree, as one page per deployment mechanism; a Deployment Options entry in Related Documentation; and the two "Per-deployment" descriptions become "Per-cloud". No prose about components changes, because no component changed.

    7. Leave the Proxmox use-case row to its plan. Finding 6 is real, but PLAN-proxmox-source.md phase 6 owns that row and is the phase that writes the page it will link. Changing the cell here would collide with that plan's worktree for a one-line gain. The execution notes record that it was seen.

    The two steps write to the same tree, so they run one after the other.
