    Deployment options phase 7: push audit¶

    Master plan: PLAN-deployment-options.md.

    Planning effort¶

    The master plan gives this phase no effort level; it only carries the push-audit shared block. This plan was written in a low-effort session. The survey derived the audit range by hand, merge by merge, and checked it against the merge history and against the audit tooling's known defects, so it was not cut short. Review effort: medium. The judgment here is in the range, not in the steps, which follow PUSH-AUDIT.md.

    Scope¶

    In scope:

    • Running PUSH-AUDIT.md, waves 1 and 2, over everything the plan landed. That is seven merges, listed under Audit range.
    • Triaging every finding as blocking or advisory, and recording it, with the reason, in this plan's Outcome.
    • Filing problems that predate the plan as issues.
    • One issue for tools/audit/plan-range.sh (finding 3), if Mikal approves the wording.

    Out of scope:

    • Fixing findings. They land in a follow-up pull request after this one merges (decision 4).
    • Work other plans own: the index's Proxmox use-case row (PLAN-proxmox-source.md phase 6), #602 and #629 (the role), and #553 (a first-party image).

    • 491 itself. This plan works around it (decision 1) and does not fix¶

      it.

    Audit range¶

    Every merge below is a merge commit on develop's first-parent chain. Its diff against its first parent is the whole of what that pull request landed.

    What the survey found¶

    1. #589 is the plan's, and the Execution table does not record it. deployment-options-role-move-landed changed only the master plan. It recorded that the role move had landed, which unblocked phase 5. It is not a phase, so it has no row. It belongs in the audit range all the same, because it changed the plan's own text. The planning commit records it in the master plan's new phase 7 paragraph.

    2. The master plan had no phase 7 paragraph. It had only the shared block and a table row. The planning commit adds one, which names the range and #589.

    3. tools/audit/plan-range.sh refuses this range from a phase worktree. It resolves the base branch by trying develop before origin/develop (plan-range.sh:41-47). The main clone has develop checked out at 7e8b8ea, behind origin/develop, and a worktree cannot fast-forward a branch another worktree has checked out. So the script reports "'eebb1b2' is not an ancestor of develop". That is loud, which is right, but it blames the SHA, not the stale ref. This predates the plan, so it is an issue, not a finding (step 7h).

    4. #491 is still open, so a single range would audit other plans' work. plan-range.sh unions the files the merges touched, then diffs one contiguous range, 200d6b3^1..eebb1b2, over them. Those 18 days include the Proxmox source (#618 and #632) and other work on docs/index.md, README.md, ARCHITECTURE.md, AGENTS.md, ansible/README.md, functional-tests.yml and installation.md. The use-case-docs plan's audit met exactly this, reviewing 188 unrelated lines of test_db.py.

    5. The plan's executable surface is small but real.

    6. Phase 1 extended the TLS claim guard's DOC_PATHS and its mutation tool, with a test.
    7. Phase 2 shipped two systemd units and a 120-line test that holds them to the role's templates.
    8. Phase 5 changed one workflow comment.

    The units are what an operator copies into /etc, so 2d has material, as do the operator instructions for secrets and TLS on the deployment pages.

    1. Review items no pull request took. The automated reviews left consider items untaken. #635's two are worth 2c's attention as candidates, not findings:
    2. item 2: the front-door default reads as contradicting the Kolla-Ansible option, which deploys Kerbside as part of OpenStack;

    3. item 4: phase 6's title said "and closeout", which the phase did not do. The planning commit corrected that title at source.

    4. The master plan's Dependencies on other plans looks stale. It still says shakenfist#4479 is open "on 2026-10-10". #589 updated part of that section. 2c checks the rest against Shaken Fist's state on the day.

    Decisions¶

    1. Audit merge by merge, not as one range. For each merge M, the range is M^1..M, with no path restriction. That is exactly one pull request's diff, which the shared block calls the whole of what landed. It sidesteps both #491 (finding 4) and the stale develop (finding 3) without changing the main clone. The mechanical scripts run seven times, once per merge, with AUDIT_RANGE exported and AUDIT_PATHS unset. The judgment agents read the seven diffs. The cost is seven tox runs of about 15 seconds each.

    2. Run all of wave 2, including 2d. This is a documentation plan, but it shipped units an operator installs as root, a test that claims to hold them to the role, and instructions for handling the signing seed, database credentials, a Keystone password and TLS material. The use-case-docs audit ran 2d on a documentation plan, and it produced that phase's one substantive finding.

    3. 2c runs on opus at medium, above the runbook's sonnet. The documentation review is this plan's whole substance: six pages written over three weeks, and four shared blocks. The failure the shared block warns about is one phase's page made wrong by a later phase. Examples are a page written before #618 that lists source types without Proxmox, or a claim about client libraries stated differently on manual.md, ansible.md and installation.md. Finding those means holding all six pages at once. This is the decision a reviewer is most likely to argue with: the runbook names sonnet, and departing from it makes this audit harder to compare with others. I think the material justifies it. The other agents keep the runbook's settings.

    4. Findings are fixed in a follow-up pull request. This phase's pull request is the record: the range, every wave's result, and every finding with its triage. Once it merges, a follow-up pull request fixes the blocking findings and the advisory ones worth taking. It also records this phase's merge commit in the Merged cell and marks phase 7 and the plan Complete. If the audit finds nothing to fix, this pull request marks both Complete itself, and no follow-up is needed.

    5. Keep the record public-safe. The Outcome holds verdicts, paths, commands and counts. It quotes no configuration values, hostnames, addresses or credentials, even from examples. The definition of done runs a probe over the text this phase adds.

    Step plan¶

    7a runs first and alone, because wave 2 is only worth spending on if wave 1 passes. Steps 7b to 7f only read, so they spawn in parallel once 7a is green. They write nothing to the worktree, only to their own scratch directories. 7g depends on all of them. 7h is independent.

    Every agent works from the Audit range table. "The seven diffs" means git diff M^1 M for each merge M in it, in that order. Unless a brief says otherwise, an agent reads every non-plan file, and reads docs/plans/ only for what the brief asks about.

    Step Effort Model Isolation Brief for sub-agent
    7a low sonnet none Wave 1. For each merge M in the Audit range table, oldest first, run AUDIT_RANGE="$M^1..$M" tools/audit/wave1.sh, with AUDIT_PATHS unset. Report each run's exit code, and its advisory output verbatim, not only the fatal checks. Exit codes are at PUSH-AUDIT.md:55-64. Do not use plan-range.sh (decision 1), and do not change a range to make a run pass. If any run exits 6, stop and report. Expect fatal checks to find nothing in five merges that add no Python; say so per merge rather than omitting them. Report in under 300 words.
