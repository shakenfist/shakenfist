    Proxmox source phase 7: push audit¶

    Master plan: PLAN-proxmox-source.md.

    Planning effort¶

    This plan was written in a high-effort session. The master plan gives the phase no effort level, only the push-audit shared block. Review effort: medium. The judgment is in the range and in how the review is split, not in the steps, which follow PUSH-AUDIT.md.

    Scope¶

    In scope:

    • Running PUSH-AUDIT.md, waves 1 and 2, over everything the plan landed in this repository. That is five merges carrying code, listed under Audit range.
    • The shared block's floor checklist, items 2 to 5, which this plan's blast radius makes concrete. It added:
    • a scheduled workflow;
    • live console passwords and a credential-bearing CONNECT host held in the shared database;
    • a Target proto change that feeds the proxy wheel's published dev releases;
    • an oVirt ticket column that stopped being written.
    • Triaging every finding as blocking or advisory, with the reason, in this plan's Outcome.
    • Filing problems that predate the plan as issues.

    Out of scope:

    • Fixing findings. They land in a follow-up pull request after this one merges (decision 5).
    • Phases 1b and 2, which landed in shakenfist/actions and ryll and were audited there (survey finding 2).
    • The open audit-tooling defects #488, #491 and #638. This plan works around them (decision 1) and does not fix them.
    • Deployment options' follow-up pull request, which is not yet open. It also touches the TLS claims checker (survey finding 6).

    What the survey found¶

    1. The master plan's phase 7 row prescribes plan-range.sh, which would audit the wrong content. The row says to derive the range from the Merged cells with tools/audit/plan-range.sh. Three open issues stand against that:

    2. 491: the script unions the touched files and diffs one¶

      contiguous range, here 696f5aa^1..746c7ef, which spans five days of other plans' work on docs/index.md, README.md, docs/installation.md, docs/testing.md and more.

    3. 638: from a phase worktree, the script prefers the main clone's¶

      stale develop, which is 13 commits behind today.

    4. 488: wave 1's flake8 gate ignores AUDIT_RANGE.¶

    Deployment options' push audit met all three on 2026-10-30 and audited merge by merge instead. The planning commit corrects the row at its source.

    1. Phases 1b and 2 were audited in their own repositories, as the shared block requires. Phase 1b's actions half was audited by its step 1b.6, recorded in that plan's Outcome. Its ryll half, and phase 2, were audited by ryll's PUSH-AUDIT.md in phase 2's step 2g, and the findings landed as ryll #411. Phase 1 changed no code. This audit cites those and does not repeat them.

    2. The plan changed Rust, and PUSH-AUDIT.md has no Rust gate. Wave 1 is tox only. Phase 3b rewrote the backend dial in backend.rs and added session.rs (about 400 lines), and phase 5 touched backend.rs and relay.rs. rust.yml runs cargo fmt --check, cargo clippy --all-targets -- -D warnings and cargo test on every push to develop that touches rust/**, so it has a run on each merge's exact tree. 7a cites those runs (decision 2).

    3. This plan's security surface is large, so 2d is split in two. What the plan put into production:

    4. 3a put live SPICE passwords on the session token row in the shared database, for about a minute and a half, under a row lock. The master plan meant to keep them out of it.
    5. 3b put the signed CONNECT host, which 3b's own survey calls a credential, beside the ticket.
    6. 4 added a driver that writes the cluster CA to a temporary file, authenticates with an API token, and mints. Every mint replaces the VM's SPICE password.
    7. 5 added a scheduled workflow that deploys a node, creates tokens with real secrets, and drives sessions on a self-hosted runner. Its round-3 review found raw log tails reaching the public job log before the secret scan ran.

    The deployment-options audit's one 2d agent covered about 1,700 lines of documentation. This plan's 2d material is about 9,000 lines of code and a workflow.

    1. Phase 6 left a known gap in the TLS claims checker. A sentence is a claim only if it names the backend: BACKEND in tools/check-backend-tls-claims.py lists backend, hypervisor, node and target. The page's own heading, "The SPICE session to qemu is TLS and pinned", names none of them, so the checker no longer reads it as a claim. The bullet states its conditions, so the page is right today. A later edit that removed them would pass. This is recorded in #647's last commit message and the index, and nowhere else. It is a candidate finding for 7e, introduced by 746c7ef. The phase 6 decision to leave the rules unchanged was taken before the gap was known.

    2. Deployment options' follow-up overlaps this audit's likely fixes. That audit's item 8 changes tools/check-backend-tls-claims.py and its test. Phase 6 already refreshed the docstring's backend.rs line references, which is half of that item. #641 (the checker passes when it reads no files) is open against the same file. Whichever follow-up opens second rebases onto the first; 7g notes the overlap.

    3. Deferred work across the plan should be checked, not assumed. Phase 3a recorded serialising mints across daemons as future work. Phase 5 recorded that the action's own token is not least-privilege. Phase 6 recorded the worked example's follow-up. 7e checks that each Future work entry in the phase plans has an issue, or is still tracked somewhere live. The shared block counts silent disappearance as a failure.

    4. The master plan's Status stated the overclaim phase 6 corrected. It said the proxy "dials a minted tunnel over TLS only". The close-out commit before this plan corrects it at source. Line 163's account, a transport step beneath TLS, was already right.

    Decisions¶

    1. Audit merge by merge. For each code merge M, the range is M^1..M with AUDIT_PATHS unset. That is exactly one pull request's diff, it sidesteps #491 and #638, and it has precedent: the deployment-options audit used it. The cost is five tox runs. The shared block's real point is what the phases did to each other, so the judgment agents read all five diffs together, and each brief names a cross-phase question (decision 4). The three plan-only merges are not run through the wave scripts. They would pass vacuously, and 7e reads the master plan's final text.

    2. Rust is gated by CI's own runs, not by a new local gate. 7a finds rust.yml's push run on c435ea3 and c4b4011 with the read-only ci-status helper and records each conclusion and run ID.     Risks and mitigations¶

    Risk Mitigation
    An agent audits the wrong content: a contiguous range, develop...HEAD (empty here), or a stale develop. Decision 1, and every brief names the per-merge diffs. 7g checks that each 7a run's output names its range, and that there are five runs.
    The split 2d misses a defect that crosses its boundary. Decision 3's handoff. 7f1 lists the sensitive fields, 7f2 checks the paths that read them, and 7g checks one against the other.
    An agent copies a credential-shaped fixture into its report, and from there into the plan. Every brief forbids printing values, and decision 6's probe runs over the text this phase adds before the commit.
    A mutation run damages the worktree, or runs forever. Mutations run on copies, one per run under timeout 300. 7g checks git status --short is empty before committing.
    The parallel agents trip over each other's tox runs. Only 7a, running alone, and 7c run tox, through the wave scripts. 7d runs single test files in a copy.
    A finding is real but predates the plan, and gets fixed here, widening the follow-up. The push-audit rules: file it as an issue. 7g decides which with git log -S or blame against the five merges.
    The follow-up collides with deployment options' follow-up in the TLS checker. Survey finding 6. 7g names the overlap in the Outcome, and the second follow-up to open rebases.
